# openLab — Agent Instructions

openLab is an open-source (GPLv3-or-later) show-playback system for theatre, a QLab 5 alternative. It runs live shows: **a crash or wrong behaviour can stop a performance.** Correctness and robustness beat speed of delivery every time.

## Read before any work
1. [`REQUIREMENTS.md`](REQUIREMENTS.md) — what we build (IDs like `AUD-07`, release tags like `v0.0.1`, scope limits in §21).
2. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — how we build it. Do not deviate; if it seems wrong, stop and report back instead of improvising.
3. [`PROGRESS.md`](PROGRESS.md) — what is done and what is next.

## Layout
- `engine/` — Rust workspace: `crates/core` (pure logic, no I/O), `crates/audio` (devices, decode, real-time mixer, offline render), `crates/engine` (binary: control thread, WebSocket, OSC, persistence).
- `mac/` — Swift + AppKit app, Xcode project generated by XcodeGen from `mac/project.yml` (never commit `.xcodeproj`).
- `docs/` — architecture, file format, protocol, OSC.

## Commands
```
make lint        # cargo fmt --check, cargo clippy -D warnings, swift format lint
make test        # all Rust tests + mac unit/UI tests
make test-rust   # Rust only
make mac         # generate project + build app (includes universal engine)
make verify-bundle  # check the Release app is universal, minos 12.0, validly signed
make prepush     # pre-push gate: runs the checks the diff needs, prints PREPUSH PASS or PREPUSH FAIL: <step>
```

## Non-negotiable rules
**Real-time audio thread** (anything called from the audio callback):
- No allocation/deallocation, locks, syscalls, logging, formatting, or disk I/O. Preallocate; return objects to the control thread for freeing.
- Communicate only via `rtrb` SPSC queues and atomics. `assert_no_alloc` must stay enabled in debug/test.

**Engine Rust code:**
- No `unwrap`, `expect`, `panic!`, or unchecked indexing in non-test code (lints enforce it). Return `Result`; surface failures as broken-cue state, warnings or log entries.
- `openlab-core` stays pure: no threads, clocks, files, sockets. Time is passed in.
- `unsafe` only outside core, with a `// SAFETY:` comment and a test.
- Validate every external input (show files, media, OSC, protocol messages). Bad input → warning, never crash or hang.

**Tests:**
- Every change ships with tests. Every bug fix ships with a regression test that failed before the fix.
- No real-time sleeps or wall-clock dependence in tests — use the virtual clock / offline render driver.
- Integration-test support modules (`tests/common/mod.rs`) start with `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::panic)]`: clippy's in-test allowances only cover `#[test]` fns and `#[cfg(test)]` items.
- All tests, `fmt` and `clippy -D warnings` must pass before you report a task done.
- Also run `cargo clippy --target x86_64-pc-windows-gnu --workspace --all-targets -- -D warnings` (Windows-only unused imports break CI). Tests that compare paths as strings must expect Windows `\` separators or convert with `to_portable`; macOS (APFS) refuses non-UTF-8 file names.

**Contracts:**
- Protocol change → update Rust types in core, regenerate fixtures in `engine/fixtures/protocol/`, update Swift `Codable` types, update `docs/protocol.md`. Same commit.
- Show-file change → bump `format_version`, add a migration step + fixture of the old version, update `docs/file-format.md`. Same commit.
- New dependency → must be GPLv3-compatible, justified, and added to the table in ARCHITECTURE §12. Prefer stdlib or an existing dependency.

**macOS app:**
- Swift 6, AppKit only, deployment target macOS 12.0. No SwiftUI, no Observation framework, no APIs newer than 12 without `#available` fallback. No third-party Swift packages without approval.
- View controllers talk to `WorkspaceStore`, never to the socket.
- Layout and workflow follow QLab 5 closely; all assets are original or SF Symbols. Never copy QLab icons, artwork, names or documentation text.
- All user-facing strings go through `Localizable.strings`.

**Every source file** starts with `SPDX-License-Identifier: GPL-3.0-or-later` (in a comment).

## Behaviour decisions
- Functional behaviour is grounded in QLab 5. When the brief doesn't settle a behaviour question, follow QLab 5 and say so in your report. If QLab's behaviour is unclear, **research QLab's documentation first**: search the local QLab 5 manual index first: `~/qlab-ref/qlab-ref search "<words>"` (then `show <page>` / `section "<title>"`; QLab 5.6 reference manual, local to this Mac, never copied into the repo: paraphrase and cite pages), then the online docs (https://qlab.app/docs/v5/) and follow what it says, citing the page in your report. Only if the documentation does not settle it, as a last resort, implement the most likely behaviour and add a row to [`docs/todo/open-qlab-questions.md`](docs/todo/open-qlab-questions.md) with the assumption you implemented and what you searched. Never block on the user for these; the user answers that file in batches.

## Style
- Match surrounding code. Small focused modules. Boring over clever. No speculative abstractions, no scaffolding for future features.
- Comments explain *why*, not *what*.

## Progress tracking
- Open tasks are GitHub issues (`gh issue view N`). Work only on the issue(s) you were assigned.
- Each issue has a **Checklist** of its requirement IDs (plus tests and docs). Tick each box as soon as that part is implemented **and tested** (`gh issue edit N --body-file …`, or the issue page), so the issue always shows what is left. Don't tick a box for a part that is only partly done; say what is missing in your report.
- Do not edit `PROGRESS.md` or tick `REQUIREMENTS.md` in a task branch (every open PR would conflict). After merge the orchestrator ticks the `PROGRESS.md` line, and a requirement once no open issue lists it and every part of it within the current release scope (§21) is implemented and tested.
- If you discover missing work, report it (the orchestrator files an issue) — don't silently expand scope.
- Review findings rated Low or low-Medium are not fixed in the batch: file each as a GitHub issue labelled `low` (title, file:line, scenario) and move on. Only Highs and show-safety Mediums get a fix round. One regression test per bug, not a matrix of variants.
- Do not fix states that only a property generator, fuzzer or contrived input can reach (e.g. invalid workspaces load refuses): fix the test oracle or file an issue.
- Niche QLab-parity features not needed for v0.0.1 go to the `v0.0.2` milestone (label `v0.0.2`), not into the current batch.
- Notes and decisions go in the issue, the PR, the docs, or `docs/handoff/`, never appended to `PROGRESS.md` lines.

## Git
- Commit with plain terminal commands: `git add …` then `git commit -m "…"`.
- **Never add `Co-authored-by` or any AI-attribution trailer.**
- Message style: short imperative subject with area prefix, e.g. `core: add continue-mode state transitions`, `audio: equal-power fade curve`, `mac: cue list outline view`.
- Don't push, rebase shared history, or force anything unless the orchestrator asks. Changes reach `main` only through a PR that the orchestrator merges after CI is green; nobody pushes to `main` directly.

## Workflow
- The orchestrator follows `.claude/skills/orchestrate/SKILL.md`: brief → `implementer` agent → verify → `pr-reviewer` agent (adversarial, High/Medium/Low) → fix → push task branch → PR into `main` → CI green → orchestrator merges.
- Agent definitions: `.claude/agents/implementer.md`, `.claude/agents/pr-reviewer.md`. High and Medium review findings block merge.

## Known environment facts
- Test targets deploy at macOS 14.0 (XCTest requires it); the app itself stays at 12.0.
- XCUITest needs macOS Automation Mode; on a dev machine the first run may prompt the user for authorisation.
- The engine build phase (`mac/scripts/build-engine.sh`) ad-hoc signs the engine; Xcode doesn't sign nested binaries in `Contents/MacOS`.
- CI's mac job runs on the `xcode-27` runner image (preview) with Xcode 27.1 pinned; fallback is `macos-26` + Xcode 26.x.
- Agents act on GitHub as `openlab-dev`, never the owner's account: commits use `openlab-dev <349245076+openlab-dev@users.noreply.github.com>` (repo-local git config; set it in any fresh clone), and `gh` must be logged in as `openlab-dev` before pushing, opening PRs/issues or merging.
- Agents share this machine and sccache (`~/.cargo/config.toml` wraps rustc; incremental compilation is off). Never wait on machine-wide process checks (`pgrep cargo`, "is anything building?"): wait on your own command only.
