# OSC API (NET-01, NET-02, NET-05, TRG-03, DOC-02)

Status: implemented, matched to what QLab 5.5.3 was measured to do (M4.5b). The socket-free layer is `engine/crates/engine/src/osc/` (decoding, address dispatch, patterns, passcode and updates state, replies); the UDP and TCP listeners and the update messages are `engine/crates/engine/src/net/osc.rs` and `osc_mirror.rs` (see "Listeners" below and [network.md](network.md)). `host::run` starts them; if port 53000 is taken the engine logs a warning and runs without OSC. This file lists exactly what is done; anything not listed is not implemented.

The address space follows QLab 5's OSC dictionary, so existing remotes keep working where openLab has the feature. Where openLab does something else on purpose, it is listed under "Differences from QLab".

## Transport

- UDP and TCP on port **53000**, IPv4, on every interface (as QLab does: set a passcode on a network you do not control). Replies and updates to a UDP peer go to its IP address on port **53001**, whatever port it sent from, unless the peer has set another with `/udpReplyPort` (below).
- TCP carries OSC 1.1 SLIP frames (END `0xC0` at both ends; `0xDB 0xDC` is a literal END, `0xDB 0xDD` a literal ESC). The length-prefixed framing of OSC 1.0 is not supported.
- A UDP peer is identified by its IP address, a TCP peer by its connection.

## Sending: Network cues (CT-30, M4.6)

The listener above is for incoming OSC. A **Network cue** sends one OSC message out, to a network patch (host, port, UDP or TCP). It reuses the listener's encoder (`osc::encode_message`, `rosc`) and framing: UDP is one datagram with the message as its payload, TCP is one SLIP frame (END `0xC0` at both ends) on a connection opened for the message and closed after it. The same OSC 1.1 SLIP framing QLab 5's own TCP listener reads, which is our reading of what a QLab TCP patch sends; the length-prefixed OSC 1.0 framing is not offered. Arguments are `int` (32 bit), `float` (32 bit), `string` and `bool` (`T`/`F`, no data). Limits (a cue that exceeds one is broken before GO, with the reason): the address starts with `/`, is printable ASCII without spaces, at most 512 bytes (`* ? [ ] { }` are allowed, it is sent as written); at most 32 arguments; a string argument at most 4096 bytes and with no NUL; floats finite; the whole message at most 8192 bytes (under macOS's 9216-byte default datagram limit). Sending never runs on the control thread: [control.md](control.md), Network output. The global switch that stops all of it is the OSC/network output override (`set_output_overrides`, docs/protocol.md). Raw UDP/TCP string messages and OSC parameter fades are not implemented.

## Listeners

Both sockets run on the network runtime (the one that serves the UI over WebSocket; no extra threads). One task owns all OSC state: the sessions, a copy of each open workspace and the TCP connection table. The sockets' tasks only pass bytes to it through bounded queues, so one slow or hostile peer never delays another, and the control thread is never waited for or blocked. UDP datagrams have a queue of their own (256) and the task takes **datagrams first** (at most 32 in a row, then the queues at random), so a TCP peer that streams requests cannot make a console's datagrams find the queue full or wait behind a whole read of the flood. The UDP socket asks the kernel for 1 MiB send and receive buffers (macOS refuses a datagram larger than its send buffer, 9216 by default, which would lose large replies). The kernel's receive buffer in front of the socket is still finite; a burst of a few hundred datagrams faster than the server reads them can overflow it and those datagrams are lost without being counted. Operators' remotes send single messages, far below that.

- **Input.** Each accepted message becomes the same `command` or `transport` message a WebSocket client sends, for the doc it is for (as a connection bound to that doc sends it, `Inbox::Conn`; an un-prefixed `/go` is one per open doc), on a reply channel of its own. Request ids start at 2^63 and never reach `u64::MAX` (the WebSocket server's own id); the control loop answers each request on the channel it came from, so they cannot clash with a UI client's anyway. At most `max_inflight` (default 2048, above the 1024 inputs one datagram can make) requests may be unanswered at once; beyond that new inputs are dropped and counted (`inputs_dropped`), so a UDP flood cannot pile up in the control inbox. A request the control loop answers with an error is counted (`control_refused`); it gets no reply to the OSC peer.
- **The workspace copy.** Answering `/cue/1/name`, resolving `/cue/{number}` and `/cue_id/{id}`, a cue's OSC trigger, the queries below and the passcode all read a copy the OSC task keeps from the engine's own messages: the `snapshot` it asks for at start, then `model_changed` (applied with `Workspace::apply_changes`), `runtime` (playheads, cue states), `document`, and a broadcast `snapshot` of the doc (installed unless it is at or below the revision and seq the copy holds; sessions end if the workspace changed, or its passcode table lost or changed a row or the No Passcode rights). There is **one copy per open doc** (M4.15h; ARCHITECTURE section 7): the hub forwards every doc's broadcasts with their doc, and the `workspaces` list. At start the task asks for the list of open docs as an app connection does, then each doc's snapshot. A doc the tap's list names that the task does not know opened: its snapshot is asked for. A doc's `closed` drops its copy and its sessions at once; the list the task asked for itself (at start, and after a lag) also drops any doc it does not name. A list read from the tap never drops a doc: the answer to the task's own request can overtake a list made before it. With no doc open there is no copy: nothing is answered from a closed doc's. Nothing asks the control thread a question per message. A gap in the revision or seq, an edit that does not apply, a `document` message with another file path, or a broadcast queue that overflowed makes it ask for a new snapshot. **The gate is per doc** (#178). A doc's copy is not ready while it has none yet or a snapshot of it that the task asked for is out; while the list is out (at start, and after a lag) no copy is ready. A doc's broadcasts wait while its copy is not ready (as in the WebSocket server), so no copy goes back in time; the other docs' broadcasts are applied. **OSC input that may reach a doc whose copy is not ready waits too**, so no `/cue/5` or trigger address is resolved against a copy known to be wrong; input that reaches only ready docs goes at once (a console working show A is not held up while show B opens, is saved as, or is rebuilt). Which docs a datagram or TCP read may reach is read from its addresses before it is handled: an un-prefixed message, `/version`, `/workspaces` and a packet that does not decode reach every doc (so they wait while any copy is not ready); `/workspace/{id}` reaches every doc whose copy or list entry goes by that id or name, and when none does, every doc whose copy is not ready (its name may not be known yet). A bundle or a TCP read waits whole if any message in it must. Order is kept: input never overtakes earlier waiting input from the same peer (its session, its stream and its replies depend on that), nor earlier waiting input that reaches a doc it reaches; a TCP connection's close waits behind its input. A TCP read from a peer that may ask in no ready doc, or that already has input waiting, waits undecoded, so its frame limit is decided once the copies it may depend on are in. Held input is bounded (`MAX_HELD_INPUTS`, 512 pieces, and 16 MiB); past that, input waits in the queues as before (datagrams beyond the UDP queue are dropped, counted in `udp_dropped`). Held broadcasts are bounded by the tap's size; more mark the copies lagged and they are rebuilt once the answers are in. The listener's `held_inputs` counts what waits. Input that waited longer than `max_input_age` (2 s) is dropped and counted (`inputs_dropped`), so a console mashing GO while the engine starts does not have every press replayed at once. A lost `model_changed` is only noticed at the next broadcast (PROGRESS M4.4a): until then the copy can be stale.
- **Active cue list.** `/go` and `/playhead/next|previous` act on each doc's **active** cue list: the list whose playhead moved last (QLab: the list on display, which selecting a cue or setting the playhead in another list switches). It starts as the first list. The copy updates it from every playhead move it hears of (a cross-list GoTo cue also moves the target list's playhead and so makes that list active: open question 7), a replacement of the copy (Save As, a resync, a snapshot broadcast) keeps it while the list still exists in the same workspace, and the OSC task sets it at once, ahead of that broadcast, when it forwards a message that moves a list's playhead, so a `/go` right after `/playhead/20` acts on the list that holds cue 20. Cue numbers are looked up in **all** lists (QLab numbers are unique across the workspace), whichever list is active. The engine has no selection of its own: "selected" is the playhead (QLab's default "lock playhead to selection"), so `/select/...` and `/playhead/...` are the same and `/cue/selected/...` is `/cue/playhead/...`.
- **Sessions end** (`/connect`, `/updates` and `/udpReplyPort` forgotten; each doc's sessions on their own) when the doc closes (its known addresses go too; the wrong-passcode counts are shared by all docs and stay), when the workspace id differs in a new snapshot of the doc, or its passcode table lost or changed a row or the No Passcode rights (a row added keeps them), for a TCP peer when its connection closes, and for a UDP peer after 60 s of silence (below). A table edit reaches the OSC task as a `model_changed` settings upsert (sessions end when a row was removed or has other rights, or the No Passcode rights changed, once it is applied; only adding a row keeps them, so adding a passcode mid-show does not make every console connect again) or in a snapshot. `AddOscPasscode`, `RemoveOscPasscode` and `SetOscRights` (docs/commands.md) are the commands that edit the table. A table edit ends the sessions but keeps the known addresses, so consoles can connect again at once even while the global budget is used up.
- **Replies.** UDP: to the sender's IP on port 53001, or on the port it set with `/udpReplyPort` while its session lives (a datagram is never answered on its source port). TCP: SLIP-framed on the same connection, all the replies to one read in one queue entry. Sending never waits: a full socket buffer or write queue loses the message (`send_failed`). A TCP peer that does not read for 10 s (one write that makes no progress) is disconnected. Each connection may have 4 MiB of replies queued and not yet written, and all connections 64 MiB together; past either, further replies are dropped and counted (`send_failed`), so a peer that asks for large replies and does not read cannot make the server hold them.
- **TCP connections.** At most **256** at once (QLab took 1000 in the capture; each costs a task, a decoder and a write queue). The worst case of memory is 256 half-sent frames: 4 KiB each for a peer that may not ask yet, up to 1 MiB each for one that may (no passcode, or connected), 256 MiB. The next connection is closed at accept, counted (`tcp_refused`) and logged as a warning at most once per 10 s with a count (`Inbox::Log`, like the WebSocket server). Accepted connections have **TCP keepalive** on (`socket2`, already a dependency): after 30 s of silence the system probes the peer every 10 s, and a peer that vanished without closing (a laptop that dropped off Wi-Fi) is noticed after its probes go unanswered (8 to 10, by platform; about 2 minutes) and its connection closed, which frees its slot. Keepalive is best effort (a failure to set it is ignored). Also, when the table is full the task closes the connection that has been silent longest, if it has sent nothing for `tcp_idle_evict` (60 s) and is not subscribed to updates, and logs it (warning). The new connection waits up to 0.5 s for that slot, then is refused if none was freed. Connections subscribed to updates are never closed this way (a console that only listens must stay), and **with a passcode set neither is one that has completed `/connect`**: a stranger's idle connections must not be able to push a console out, so with the table full of consoles the newcomer is refused. The cost is that a console that vanished without closing holds its slot until a write to it fails or keepalive notices it. **One host (IP address, an IPv4-mapped IPv6 address counted as its IPv4 one) may hold at most 16** (`max_tcp_connections_per_host`). At its cap, its next connection asks the task to close **that host's own** connection that has been silent longest, by the same rules as above (silent for `tcp_idle_evict`, not subscribed, not let in with a passcode; never another host's), and waits up to 0.5 s for the slot, so a console that reconnected many times over a flaky network is not locked out by the dead connections it left behind. That wait runs in a task of its own, one per host at a time (a second connection from the host meanwhile is refused at once), so a host cannot slow the accept loop for others. If none of the host's connections may be closed (all of them active, subscribed or let in), the new one is refused, counted (`tcp_refused`) and logged with the limit and the host (`per-host connection limit (16) reached by 10.0.0.5`, in the same rate-limited warning). So a host whose connections stay subscribed or keep sending holds at most 16 slots and other consoles can still connect; it takes 16 hosts to fill the table.
- **Counters.** `WsServer::osc_stats()` returns the `OscStats` plus `udp_dropped` (the task's queue was full), `tcp_refused`, `inputs_dropped`, `send_failed`, `control_refused` and `tcp_connections`. Malformed, oversize, bad-address, throttled, capped and dropped input is also logged, as one warning with counts, every 10 s while it happens.

## Limits

| Limit | Value | When exceeded |
|---|---|---|
| Datagram | 64 KiB (UDP carries 65507 bytes at most) | dropped, counted as malformed |
| SLIP frame (one message or bundle over TCP) | **1 MiB** from a peer that may ask; **4 KiB** from one that may not yet (a passcode is set and it has not connected) | the frame is skipped to its next END without being buffered, counted as `oversize_frames` |
| Bundle nesting | 4 levels (the outermost counts as 1) | whole packet dropped, malformed |
| Messages in one packet | 128 | whole packet dropped, malformed |
| Array nesting in type tags | 4 levels | message dropped, malformed |
| Address | 256 bytes, 8 `/`-separated parts, no empty part (one trailing `/` is allowed) | dropped, counted as `bad_address` |
| Peers with a session (connected or subscribed) | 1024 | a full table refuses newcomers (their `/connect` or `/updates` gets an error reply) until idle UDP peers expire or TCP connections close; existing peers are never evicted, so a flood of forged sources cannot push out a real console |
| Sessions without rights (a bare `/updates` or `/udpReplyPort`), when a peer that has not connected may not view | 64 | past it the one silent longest among them is evicted, so forged subscribers cannot fill the table; a session with rights is never evicted, and a console's `/connect` still gets a slot. Where No Passcode has View such peers are ordinary subscribers and not capped |
| Replies per datagram or stream read, **for every doc together** | 1024 | the rest are dropped, counted as `replies_dropped` |
| Reply bytes per datagram or stream read, every doc together | 2 MiB | the rest are dropped, counted as `replies_dropped` |
| Inputs per datagram or stream read, every doc together | 1024 | the rest are not produced, counted as `inputs_capped` |
| Cues one pattern, or `/cue/active`, may act on or answer for, in one doc | 1024 (and the per-read caps above for all docs) | the cues found are used, the rest are not; counted as `matches_capped` |
| Pattern alternatives (the product of its `{..}` groups) | 64 | the message gets an `error` reply |
| Matching work of one datagram or stream read, **all its messages and every doc together** (an un-prefixed pattern fanned out to 8 docs costs no more than the budget) | 1,000,000 steps (a step is one character against one token or one token placed in one alternative while the pattern is compiled, about 5 to 10 ns, so about 5 to 10 ms; a `[..]` class costs one step per range plus one; each cue's number costs its length); a cue number longer than 256 characters is not matched by a pattern | matching stops, the rest of the read's pattern messages get an `error` reply (each alternative is charged for its tokens even against an empty number, and runs of `*` count as one); counted as `matches_capped`. A hostile bundle of patterns therefore cannot hold the OSC task much past ten milliseconds (measured on a fast machine in a release build; several times that on old hardware), and a GO that arrives behind it is not held up |
| Reply body to a peer that may ask | what fits a UDP datagram (65507 bytes in all) over UDP; 1 MiB over TCP | replaced by an `error` reply with no data (QLab sends nothing over UDP when a reply cannot fit) |
| Reply body to a peer that may not ask yet | 1400 bytes (about one unfragmented datagram) | replaced by an `error` reply with no data |
| Reply and update bytes to one UDP source IP that has not completed `/connect`, **a passcode is set** (it is only sent small refusals) | 16 KiB burst, refilling 8 KiB/s (headers counted) | further replies dropped, counted as `replies_throttled`; updates as `updates_dropped` |
| The same, **no passcode set** (it may ask, but has not shown the source address is its own) | 256 KiB burst (four full 65507-byte datagrams), refilling 64 KiB/s (about one more full datagram a second, or a few hundred updates) | the same counters. A 60 KB notes read works; sustained reflection at a forged victim is held to 64 KiB/s per IP. With no passcode, `/connect` proves nothing about where a datagram came from, so **every** UDP source stays on this budget whether it has sent `/connect` or not. Only a UDP peer that connected with a real passcode has no budget; neither has a TCP peer |
| Open TCP connections | 256 | an idle unsubscribed one (silent 60 s) is closed for the newcomer; otherwise the next is closed at accept, counted as `tcp_refused`, logged (at most every 10 s) |
| Bytes queued to write, per TCP connection / all connections | 4 MiB / 64 MiB | the reply is dropped, counted as `send_failed` |
| Datagrams waiting for the server | 256 | further datagrams dropped, counted as `udp_dropped` |
| Age of input when it is handled | 2 s | dropped, counted in `inputs_dropped` |
| Requests to the engine not yet answered | 2048 | further inputs dropped, counted as `inputs_dropped` |
| Cues reported one by one after one change | 32 | one `/update/workspace/{ws}/cue_id/__root__` (and the dashboard) instead |
| Group nesting written by `/cueLists` and the cue objects | 16 levels | deeper groups are written with no children |

**Budget table.** The byte budgets are **per source IP, whatever doc** a reply or update is about (several open docs must not multiply what a forged source can draw). The kind of budget for a doc's reply follows that doc's table; an application reply (`/version`, `/workspaces`, an unknown workspace's error, `/updates` and `/udpReplyPort` errors) is unbudgeted only for a peer that connected to some doc with a passcode, and held to the open budget when some open doc has no passcode, else the strict one. At most 1024 source addresses have a budget at once. A bucket is only dropped once it has refilled; a depleted one is never evicted (that would hand its address a fresh burst, and cycling forged addresses would remove the budget). When the table is full of depleted buckets, a source with no bucket yet is sent nothing (counted as `replies_throttled` or `updates_dropped`) until one refills: 2 s at the strict budget, 4 s at the open one. A console that is already tracked keeps its bucket.

**Why 1024 replies per read.** A wildcard answers once per matched cue (QLab does), so a show of several hundred cues must be able to answer `/cue/*/name` in full from one datagram; 1024 matches the per-message match cap. A reply is about 250 bytes unless a note or `/cueLists` is in it, so the byte cap (2 MiB) is what bounds the work in the odd case of large notes. Large UDP replies go to any peer that may ask. A UDP source that has not connected with a passcode is held to a per-IP byte budget for replies **and updates**, because its source address may be forged and we must not become an amplifier: 16 KiB burst and 8 KiB/s when a passcode is set (such a peer is only sent small refusals), 256 KiB burst and 64 KiB/s when none is, so that a 60 KB read still works. 256 KiB is four full datagrams; 64 KiB/s is about one more a second, which is generous for one console's queries and far below what a forged-source flood could otherwise reflect (without it one 40-byte datagram could draw 2 MiB). A UDP peer that has `/connect`ed **with a passcode** is not budgeted (with none set a `/connect` can be forged along with the source address, so it exempts nobody): a UDP peer is only an IP address, so forged traffic from a console's own address can make us send it replies up to the caps above, which is the accepted cost of answering large UDP replies as QLab does. On macOS a datagram over 9216 bytes needs a raised `net.inet.udp.maxdgram` on the sender's side (and ours); a reply that cannot be sent is counted as `send_failed`.

Bundle time tags are ignored: every message runs when it arrives, in bundle order. Bundles are flattened, so a bundle holding `/cue/1/start` and `/cue/2/start` starts both (QLab-confirmed).

Malformed or oversize input never reaches the engine. It is dropped and counted (`OscStats`: `packets`, `messages`, `malformed`, `oversize_frames`, `bad_address`, `unknown_address`, `wrong_workspace`, `denied`, `rejected`, `replies_dropped`, `replies_throttled`, `updates_dropped`, `duplicates_dropped`, `matches_capped`, `inputs_capped`).

## Addresses

Every workspace address may be prefixed with `/workspace/{id}`, where `{id}` is an open workspace's id **in upper case, as replies write it**, or its name exactly as written (QLab 5: "{id} may be either the display name ... or the unique ID"; an id is matched first, then the one doc with that name; a name with a `/` in it cannot be addressed). **A name several open docs share is refused**, not guessed (a Finder copy of a show keeps its name, and a GO must not fire the backup instead of the running show): the same `error` as an unknown workspace, and one warning in the show log per peer and name (rename one, or use the id). A message for no open workspace (another id, a non-id, the right id in lower case, a name in another case) gets one `error` reply that holds only `address` and `status` (counted as `wrong_workspace`).

**Several workspaces** (M4.15h; ARCHITECTURE section 7, QLab 5: "the message will be sent to all open workspaces listening on the port"). A workspace message **without the prefix goes to every open doc**, whichever window is in front: an un-prefixed `/go` fires every doc's GO, `/cue/*/start` acts in each. Each doc judges it on its own: its passcode table and the peer's session with it, its cues; a query gets **one reply per doc**, in open order, each with that doc's `workspace_id` and its address rewritten to `/workspace/{that ID}/...`, and a doc where it fails (no such cue, denied) answers with that status. With the prefix only the named doc acts and answers. **With no doc open** a workspace message (`/go`, `/cue/1/name`, `/connect`, ...) gets the same one `error` as an unknown id; `/workspaces` answers `[]` and `/version` its version. The caps on replies, inputs and matching work of one datagram or read (Limits) hold for every doc together, so the fan-out never multiplies them. Application-level addresses (`/version`, `/workspaces`, `/updates`) are not available under the prefix (`error`). Address matching is exact and case-sensitive: `/GO`, `/Cue/1/start`, `/cue/1/NAME`, `/cue/1/prewait` and `/cue_id/` with a lower-case UUID are all unknown addresses (`error`).

Each accepted message becomes the same input the UI sends (`docs/protocol.md`); OSC adds no engine behaviour. "The list" below is the active cue list. **A message that succeeds gets no reply** (QLab sends none for actions, writes and `/updates`); one that fails gets an `error` reply, and an address nothing answers to (that is no cue's trigger) gets one too.

A cue number is looked up in **all** cue lists, at any depth, as written in the address (the words `selected`, `playhead` and `active` are the exceptions above). A number or id that matches no cue gets an error reply. Arguments of the wrong type or count get an error reply; nothing is sent to the engine.

Not implemented: level and time properties beyond pre-wait and post-wait, `/new`, `/save`, the other QLab application and workspace queries.

### Patterns

The cue-number part of `/cue/{number}/{verb}` is an OSC address pattern when it has `*`, `?`, `[...]` or `{a,b}` in it: `*` any run of characters (also none), `?` one character, `[abc]` and `[a-c]` one of those, `[!a-c]` none of those, `{a,b}` one of the alternatives (not nested). A pattern is matched against every cue number, in **every list and inside groups**, in workspace order (each list, then its cues, a group before its children). It acts on, or answers for, **every match**:

- A read (`/cue/*/name`) answers **once per match**, each with the matched cue's own address in the JSON (`/workspace/{ID}/cue/3/name`, or `/cue_id/{ID}/name` for a cue without a number) while the OSC address of the reply is the one asked (`/reply/cue/*/name`). `*` also matches the cue lists (their number is empty, so does a cue without a number): a list answers `name` with its name and `number` with `""`, at its `cue_id` address, and is skipped by every other property and by actions. A match that has no such property gets an `error` of its own.
- An action (`/cue/{1,2}/start`, `/cue/*/stop`) is sent for each cue matched, in order. A write reaches every match. An argument that is wrong for the verb is an `error` reply for each match.
- No match, or a pattern that is not valid (unclosed `[` or `{`, `{` in `{`, a stray `]` or `}`, more than 64 alternatives): one `error` reply.
- Pattern characters elsewhere in the address are not expanded. The address may still be exactly a cue's OSC trigger (looked up first), which can therefore contain such characters.
- The work is bounded: at most 1024 matches (the first 1024 are used, counted as `matches_capped`), 64 alternatives, 1 million matching steps for the whole read (all its messages together), and a number longer than 256 characters is not matched by a pattern (use its exact address).

## Connecting and the passcode (NET-02)

- **The table.** The workspace keeps a passcode table (`settings.osc_access`, show file v4): rows of passcode + View / Edit / Control (Edit and Control need View), and a **No Passcode** row. A peer that has not connected has the No Passcode rights; `/connect` with a passcode of the table gives it that row's rights. A new workspace: No Passcode has none and there is one random 4-digit passcode with all rights. A show migrated from a single passcode: that passcode with all rights, No Passcode none; from none: No Passcode with all rights (open, as before). With no rows in the table any `/connect` argument is accepted and gives the No Passcode rights.
- **`/connect` replies** are QLab's: `{"status":"ok","data":"ok:view|edit"}` when accepted: `ok:` and the rights of the passcode given, joined by `|` in the order view, edit, control (`ok:` alone for none). A wrong passcode is `{"status":"ok","data":"badpass"}` (status `ok`, not an error). **Send the passcode as a string**, as QLab does: a number (int32 or int64) never matches, because a passcode with a leading zero cannot be told from a shorter one, and it counts as a wrong passcode. A new workspace's generated passcode is 1000 to 9999 (no leading zero). **`/connect` with no argument** connects with the No Passcode rights (`ok:` plus them); it stores nothing (the peer had those already), costs no table slot, counts no failure and does not make the address a known one. Another type or several arguments are a wrong passcode where the table has rows. A lockout is `denied`; a full peer table is `error`.
- **Rights.** Every message except `/connect`, `/version`, `/workspaces` and `/updates` needs a right in the doc it reaches, judged on its address and argument count before any cue is looked up, so a refusal reveals nothing; a peer without it gets a **`denied` reply over UDP and TCP** (QLab answers both). The reply holds `address`, `status` and `workspace_id` (an application-level message such as `/udpReplyPort` is `{"address":"/udpReplyPort","status":"denied"}`). A UDP reply to a peer that may not read (no View) is held to the per-source-IP byte budget (16 KiB burst, 8 KiB/s) and to 1400 bytes; both are counted.
  - **View**: every read (`/cue/{n}/{property}` without an argument, `/cue/selected|playhead|active/...`, `/cueLists`, `/runningCues`, `/runningOrPausedCues`, `/selectedCues`, `/playheadID`), writing a cue's **`notes`** and `/udpReplyPort`. A peer without View has the strict reply budget and the small frame limit.
  - **Edit**: writing any other cue property (`name`, `number`, `preWait`, `postWait`, `armed`, `flagged`; a read-only property is refused as an error once allowed) and `/select/...`.
  - **Control**: transport (`/go`, `/stop`, `/hardStop`, `/panic`, `/pause`, `/resume`), `/playhead/...`, the cue verbs (`start`, `stop`, `hardStop`, `panic`, `pause`, `resume`, `load`, `reset`, `preview`, by number, id or pattern) and a cue's own OSC trigger address. An address nothing answers to counts as a possible trigger, so it needs Control too. **Firing a cue through its trigger needs Control whatever the trigger looks like**: a trigger shaped like a read (`/cue/zz*/name`) is checked after it is found, and a peer without Control gets the same `error` as for an address nothing answers to (so it cannot tell a trigger from a missing cue) and nothing starts.
  - **`/updates`** works at any access level, as in QLab (no right, no reply). What an update carries is cue data, so it is sent only to subscribers that have View **at the moment it goes out**: a subscriber without View keeps its subscription but receives nothing, and starts receiving when it connects with a passcode that has View (or the table gives No Passcode View).
  - Measured in QLab: name, notes and pre-wait only (open question 5); the rest follows QLab's documented table by analogy and is recorded in `docs/handoff/decisions/m4-5c.md`.
  - A TCP peer's `/udpReplyPort` is ignored without a reply, whatever its rights.
- `/connect` forms: `/connect` and `/workspace/{ID}/connect`. **Per doc** (M4.15h): the session, its rights and the known addresses are kept per peer and doc, so connecting to one doc leaves another locked. The wrong-passcode counts below (per IP, and all IPs together) are **not** per doc: they are shared by every open doc, so trying the docs in turn is no fresh budget (eight docs do not give eight times the guesses), and a lockout of an address holds at every doc. An un-prefixed `/connect` is answered by **every** open doc, each checking its own table (`ok:<rights>` or `badpass`, or `denied` while locked out there); `/workspace/{ID}/connect` reaches that doc only. An un-prefixed `/connect` whose passcode some open doc accepts is **not a guess** in the others (they answer `badpass` without counting it), so a console sending each doc's passcode un-prefixed cannot lock itself out; a passcode no open doc accepts is **one** failure, however many docs answer it.
- A wrong `/connect` from a peer that is already connected is answered `badpass` and changes nothing: it never disconnects the peer or lowers its rights (a UDP peer is only an IP address, so anyone sharing or forging it could otherwise cut a console off mid-show). **It does count toward the lockouts below**, and while its IP is locked out its `/connect` is `denied`, the right passcode too (the known-address exemption is for peers that are not connected): otherwise a view-only peer could try passcodes without limit until it found a row with Control. It keeps the rights it has.
- Failures are counted per remote IP address across all docs, for TCP too (reconnecting does not reset them). After 5 wrong passcodes from one IP (a peer that is connected counts too; a correct passcode does not reset the count, it ages out), that IP is locked out for 30 s: `/connect` during the lockout is answered `denied` without checking the passcode. Across all IPs together, 50 wrong passcodes in 60 s make every new `/connect` get `denied` until the window ends (so rotating forged source addresses does not give unlimited guesses). Peers already connected keep their session and rights, but their `/connect` is refused while either lockout lasts. **This differs from QLab's, on purpose** (see "Differences from QLab").
- **Known addresses.** Each doc remembers up to 64 IP addresses that completed a `/connect` to it (until it closes or its copy holds another workspace; a table edit keeps them). A **correct** passcode from a known address passes the **global** budget, so an attacker's forged wrong guesses from rotating sources cannot keep the operator's console from reconnecting after its session expired or a TCP link dropped. It never passes the address's **own** lockout: during that, no `/connect` from the IP succeeds (the right passcode included) and wrong guesses keep counting (5 more extend the lockout by 30 s from then), whether or not the IP is known, so a peer sharing a known address cannot guess for free. A wrong passcode from a known address is still refused. Remaining trade-off: a device that has never connected can be blocked by an attacker's wrong guesses (first-time devices during an attack). To recover from a lockout, wait 30 s without a wrong guess from that IP (a wrong guess during the lockout extends it), use another IP, or stay connected: a connected peer keeps its rights during a lockout. Against the global budget, wait for the 60 s window or connect from a known address. A table edit ends sessions but keeps the known addresses; the doc closing or its copy holding another workspace id forgets them, and opening a doc forgets none. **Worst case:** the per-IP lockout counts each address separately, and an IPv6 host can take many addresses from its /64, so a multi-address attacker is bounded only by the global 50 wrong passcodes per minute: the default 4-digit passcode (9000 values) falls in about 3 hours at most. Use a longer passcode on an open network; QLab has no lockout at all.
- Limits of the guards: an attacker rotating 1024 forged addresses can evict the oldest reply budget (bounded: still at most 16 KiB per forged address), and forged traffic from the console's own address can make us send it replies (a peer that has connected is not budgeted: see "Limits"). Without a passcode a forged `/connect` takes a session slot just as `/updates 1` does; slots free as UDP peers go idle (60 s).
- Because a connected UDP peer is only an IP address, any packet from that address (including a forged one) can switch its `/updates` subscription on or off (`/updates 0`). It cannot disconnect the peer.
- **A UDP peer is forgotten after 60 s of UDP silence**: its `/connect` and its update subscription end (in every doc: anything it sends, to whichever doc, renews them all), as QLab's do (measured: still there at 58 s, gone at 62 s). Any message from it within the window renews it. A TCP peer's session ends when the connection closes. The runtime ends a doc's `/connect`s and subscriptions when that doc's passcode table changes (it keeps the known addresses), and forgets everything about the doc when it closes or its copy now holds another workspace (another workspace id after a snapshot); the other docs' sessions are untouched, and opening a doc ends none. **Operator note:** a UDP console that has `/connect`ed but stays silent for over 60 s is forgotten and must `/connect` again (its next message is `denied`); this is how QLab behaves too. A display that only listens must therefore send something at least once a minute over UDP (QLab's remotes do), or use TCP. Unlike QLab, a bare `/updates 1` after the session was forgotten subscribes again by itself.
- The passcode comparison does not stop at the first differing byte (its time depends on the longer string, not on where they differ; it does not hide whether the lengths are equal). It travels in clear text: this is access control for a trusted show network, not security against an attacker on the wire.
- **Without a passcode, OSC is for trusted networks only.** Any host can then get replies and subscribe to updates, and a forged UDP source address can direct our replies and updates at someone else (up to the caps above, with no byte budget). Set a passcode on any network you do not control.

### Identical messages

A message that is identical (same address and arguments) to the previous one from the same peer, received less than **100 ms** earlier, is dropped: no action, no reply, `/go` included (QLab does; measured with two `/go` 50 ms apart starting one cue). A message's time is when it **arrived**, not when the task got to it (two GOs 250 ms apart are both GOs even if handled back to back). Frames from one TCP read share that read's arrival time, so two GOs 250 ms apart that land in one read (only when the OSC task was stalled) count as a repeat. Only the last message handled for each peer is remembered, and a dropped repeat does not renew the time, so a message sent every 50 ms is handled every other time. A peer is one UDP IP address or one TCP connection. Memory is bounded: one fingerprint for each of at most 1024 peers; with more peers than that, the peers past it are not deduplicated until entries leave the window (at most 100 ms later). A client that polls the same query faster than every 100 ms gets answers to some of the polls only.

## Updates (NET-05)

### `/udpReplyPort`

`/udpReplyPort {port}` (one int, 1 to 65535) from a UDP peer makes replies **and updates** to that peer go to its IP address on `port` instead of 53001. QLab-confirmed (2026-10-27, over UDP): after `/udpReplyPort 54329` reads were answered on 54329 and nothing came on 53001, and updates after `/updates 1` followed; after 75 s of silence a read was answered on 53001 again, so the port lives in the UDP session and is forgotten with it. Ours:

- **No reply** when it is accepted (QLab sends none). The port applies to the sender's IP only, never another address; the peer's source port is still irrelevant.
- The port lasts as long as the session: 60 s of silence from the peer forgets it (the "A UDP peer is forgotten" rule above; any message renews it), as do a passcode change and a different workspace opening. `/updates 0` keeps it. Another `/udpReplyPort` replaces it.
- **Bad argument** (none, more than one, not an int, 0, negative, over 65535): an `error` reply without `workspace_id`, counted as `rejected`, like `/updates` with a bad argument; the port the peer had is kept.
- It takes a session slot like `/updates`: with the table full (1024) a newcomer's message gets an `error` reply and sets nothing; a peer that already has a slot can still set it.
- **Rights:** needs View (see Rights) in some open doc: a peer without it anywhere (or with no doc open) gets one `denied` (no `workspace_id`). It is an application message, the peer's and not a workspace's (QLab manual, Workspace Settings, Network, pp. 111-113: "individual clients can request a custom UDP reply port"): it is kept in the session of every doc where the peer has View (a doc where it has none does not hold it) and is given to a doc that opens later, where the peer has View, while the peer's own entry lives (60 s of UDP silence); closing the doc it was sent to does not lose it. Replies and updates to the peer use it. Letting a peer that may not read change where we send would be no use, and `/updates` itself works at any level but sends nothing to a peer without View.
- Not available under `/workspace/{id}` (`error`), like `/updates`.
- **TCP:** ignored, with no reply and no state (replies go on the connection); a UDP peer at the same IP is unaffected.
- The reply byte budgets are per source IP and are not touched: changing the port does not refill a budget.
- `/workspaces` still reports the server's default (53001) in `udpReplyPort`: the entry is not per peer in our reply, and QLab's was not measured to differ.

`/updates 1` (int or boolean true) subscribes the peer, `/updates 0` unsubscribes; it works at any access level, connected or not (QLab: "at any access level"); the updates themselves go only to a subscriber with View (see Rights). It is an application message and goes to **every open doc** (M4.15h), and to every doc opened later while the peer's entry lives (QLab, OSC Dictionary, "Getting status updates from QLab" and `/updates`, pp. 383, 396-397: a client requests updates, not a workspace): the peer is subscribed in each, and each doc sends its own updates only to its subscribers that have View **in it**. **No reply when it is allowed**; a bad argument, a full peer table in some doc, or no doc open is one `error` reply, without `workspace_id`. `/workspace/{ID}/updates` is an `error` (not available under the prefix, as measured).

A subscribed peer is sent these messages exactly as QLab sends them (to its IP on port 53001 for UDP, whatever port it sent `/updates` from; SLIP-framed on its own connection for TCP, and on no other). `{WS}`, `{ID}` and `{LIST}` are upper-case UUIDs; `__root__` is lower case. One message per datagram. QLab sends each burst twice about 100 ms apart; **we send each once**.

| Address | Argument | Sent when |
|---|---|---|
| `/update/workspace/{WS}/cue_id/{ID}` | none | the cue changed. For a **property edit** of a cue that stays where it is: that cue only. For a **state change** (start, pause, resume, stop, finish, break): the cue, then each group around it (nearest first), then its cue list (`{ID}` is the list's id), then `__root__`. For a cue **added, removed or moved**: the cue, the groups and the list it was in and is in, then `__root__` |
| `/update/workspace/{WS}/cue_id/__root__` | none | with state changes and changes of shape (above); alone for a change to the cue lists themselves, and instead of the cue-by-cue messages when one change touched more than 32 cues ("ask again for everything") |
| `/update/workspace/{WS}/cueList/{LIST}/playbackPosition` | the id of the cue the playhead is on, as a string; **no argument** when it is past the end (or the list is empty) | a playhead moved |
| `/update/workspace/{WS}/dashboard` | none | last in the change, when a playhead moved, a cue **started** (went from idle or loaded to running, pre-waiting or paused), or the cue tree changed shape. Not for a pause, resume or finish |

There is no workspace-level update message: patches and settings edits send nothing (QLab has no message for them). A doc's copy rebuilt from a snapshot that differs (a resync) sends `__root__` and the dashboard, with a `playbackPosition` for each list whose playhead moved; a doc that opens or closes sends nothing (a client sees it in `/workspaces`). Order within one change: the cue messages, `__root__`, the playhead messages, the dashboard; a message is built once and sent to every subscriber. Update messages carry no data beyond this: the peer asks (`/cue/{number}/name` and the other reads) for what it wants to know. Switching the displayed list in QLab sends nothing and so does moving our active list without moving a playhead.

Updates to a UDP peer share its reply byte budget (see Limits) unless it connected with a passcode (with one set a subscriber always has). A subscription also lapses after 60 s of silence. A TCP peer is paced by its connection (see Listeners). A peer that fell behind loses updates and should ask again for what it displays when it sees `__root__`; there is no catch-up.

## Replies

A reply is an OSC message to the sender whose address is `/reply` followed by the address that was sent (prefix included), with one string argument holding JSON, with exactly the keys QLab's have:

```json
{"status": "ok", "address": "/workspace/<ID>/cue/1/name", "workspace_id": "<ID>", "data": "Opening"}
```

- `status` is `ok`, `error` or `denied`. `address` is always the full `/workspace/{ID}/...` form of what was asked, even when it was sent without the prefix (the exception: a wildcard, `selected`, `playhead` or `active` answers with the matched cue's own address); `workspace_id` is on every workspace-level reply; `data` is there only when there is a value: errors and refusals have none.
- Application-level replies (`/version`, `/workspaces`, and the `error` of `/updates`, the `denied` of `/udpReplyPort`) have `address` as sent and no `workspace_id`. The reply to a message for another workspace has only `address` and `status`.
- Replies are sent for: `/connect` (above); reads; the queries below; and anything that failed or was refused. Successful actions (`/go`, `/cue/1/start`, `/stop`, property writes, `/updates`) get none.
- Key order is not fixed (QLab's varies too).

### Queries

| Address | Reply `data` |
|---|---|
| `/version` | our version (`CARGO_PKG_VERSION`, the engine's), as the string; QLab answers its own (`5.5.3`) |
| `/workspaces` | `[{"version", "displayName" (the workspace name), "udpReplyPort", "uniqueID" (the workspace id), "port"}]`; one entry per open doc, in **open order** (not front order); `[]` with none; the ports are the ones the server is bound to. One reply, without `workspace_id`. A peer that may not view anywhere gets at most 1400 bytes of it (Limits): with eight docs with long names the list does not fit, and it gets an `error` instead |
| `/cue/selected/{property}`, `/cue/playhead/{property}` | the property of the cue at the active list's playhead; `error` when there is none |
| `/cue/active/{property}` | **one reply per running cue**; one `error` when none runs |
| `/runningCues` | an array of cue objects: the running cues (waiting, playing, fading or stopping; not paused, loaded or broken); `[]` when none |
| `/runningOrPausedCues` | the running cues and the paused ones |
| `/selectedCues` | the cue at the active list's playhead, in an array; `[]` when none |
| `/cueLists` | an array of cue-list objects (`"type": "Cue List"`, `"number": ""`) each with its cues under `cues`, groups nested (to 16 levels) |
| `/playheadID` | the id of the cue at the active list's playhead, or `"none"` |
| `/playheadId` | the same, at the address `/playheadID`, with `"deprecated": true` and a `warning` (the spelling is deprecated) |

A cue object has QLab's fields: `number`, `uniqueID`, `cues` (the children of a group), `colorName/live`, `flagged`, `listName`, `type`, `colorName`, `name`, `armed`. `listName` is the cue's name and `colorName/live` its colour (QLab's is the colour it is showing live). `type` is `Audio`, `Group` or `Cue List` as QLab writes them; the names for the other kinds (`Fade`, `Start`, `Stop`, `Pause`, `Load`, `Reset`, `Devamp`, `GoTo`, `Arm`, `Disarm`, `Wait`, `Memo`, `Network`) are ours (QLab's were not measured). `/cue/{number}/isRunning` and the other state properties follow the same states as the queries.

## Differences from QLab

- **Lockout.** QLab backs off per TCP connection for a fraction of a second, doubling with each wrong passcode, and does not share the back-off between connections or with UDP (measured). openLab keeps its own, stricter guard (above): 5 wrong passcodes from one IP lock it out for 30 s, with a global budget of 50 per minute and a set of known addresses whose right passcode gets through the global budget (never the address's own lockout). A show's network is small and a guessed passcode gives control of the show, so we prefer the slower, shared guard; the replies are QLab's (`denied`).
- **No-argument `/connect`** matches QLab (connects with the No Passcode rights). Rights per property beyond name, notes and pre-wait are our reading of QLab's documented table (open question 5).
- **Resubscribing after the session lapsed.** QLab also needs a workspace-level message; a bare `/updates 1` resubscribes with us.
- **Updates are sent once**, not twice.
- **Update details beyond the capture.** QLab sends a few more message sets for particular edits (for example a move sends the list and the dashboard only); ours follow the three rules above for every edit. Property edits do not send the list or the root, as in the capture.
- **A reply too large for a datagram** is an `error` reply; QLab sends nothing.
- **`/version`** is openLab's version, and the cue `type` names for kinds other than Audio, Group and Cue List are ours.
- **Cue lists** answer to patterns only for `name`, `number` and `uniqueID`; QLab's answer every property.
- **No `/new`, `/save`**, or the other application and workspace queries.
