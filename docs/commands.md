# Editing commands

Every change to a workspace is a `Command` (`openlab-core`, `command.rs` with `command/` (structure, properties, numbers), and `command_model.rs` for everything but the cue tree): cues, workspace settings, output and network patches, cue lists (ED-07). The UI sends them, OSC edits become them, and mirroring (RED-01) will replay them. Commands are serialisable (`serde`, internally tagged by `type`) and travel inside the UI protocol's `command` message ([protocol.md](protocol.md)).

```rust
let inverse = workspace.apply(command)?;   // Result<Inverse, CommandError>
```

`Inverse` is a `Command`: applying it undoes the original, and applying *that* result redoes it. `History` keeps the undo and redo stacks of inverses and is the only thing that should change a workspace in the engine (`History::execute`, `execute_coalescing`, `undo`, `redo`). Undo is unlimited (ED-07). Call `History::clear` when the workspace is changed behind its back (a save-as that re-spells media references).

`History::execute` returns `Ok(true)` if the command changed the workspace and was recorded, `Ok(false)` if it changed nothing.

### Undo and redo while cues play

An undo or redo is performed whatever is playing, as QLab 5 does (checked in QLab 5.5.3: its undo of a playing cue's add goes through). A step that removes an active cue (pre-waiting, running, paused, fading, post-waiting, stopping; a group's run too), alone or inside a removed group, or turns it into a cue of the other sort (group or not), stops it exactly as a deliberate `RemoveCue` does: the engine follows the edit and hard-stops the cue with a `CueRemoved` warning (docs/cue-engine.md "Model edits"); a previewed cue the step removes stops its preview. A step that leaves every active cue in place (an edit to an idle cue, a move, a property of the playing cue) stops nothing.

## Guarantees

- **Atomic.** A refused command leaves the workspace exactly as it was (the one exception, `RollbackFailed`, means an inverse is wrong: see `Transaction`).
- **Exact.** Undo then redo restores ids, order and parent/child structure.
- **Valid.** A command never produces something `repair` would have to fix, so `save_show` accepts the result and the saved file loads back identical (NFR-03):
  - cue ids unique across the workspace; numbers unique and not empty;
  - nesting at most `MAX_GROUP_DEPTH`; checked before recursing, so a hostile tree cannot overflow the stack;
  - every time and level finite and in range (the same checks as load).
- **References between cues are not checked.** A missing target, a wrong-kind target, a self-target, a missing patch and trigger cycles are the *broken-cue state* of ARCHITECTURE §10: `validate` warns, the cue shows as broken. Removing a cue legitimately leaves them behind, and undo must be able to put back states that contain them. The exception is removing a patch or cue list that something still uses: see "Settings, patches and cue lists".
- **A change to what is already there is not an edit.** `SetCueProperty` to the value the cue has, a `MoveCue` in place, `SetCueNumbers` that changes no number, a setting or patch property set to its current value and the like return an empty `Transaction` as their inverse, which `History` does not record: no undo step, no redo cleared, and the engine sends no `model_changed`, makes no revision and leaves the document clean. (Values are validated first: an invalid value is refused even if the field "already has" something equal-looking.)

## Network cue properties (M4.6a)

`destination`, `address` and `args` of `CueProperty` apply to Network cues only (`PropertyNotApplicable` on any other kind); they undo, redo, coalesce (one gesture key, one slot per property) and batch like the other properties. As in QLab 5 (manual pp. 371-372), the editor **accepts a malformed message and a destination that names no network patch** (or none): the cue shows broken, with `network_message_invalid` / `network_patch_missing` (docs/protocol.md), until it is fixed, and a broken cue never sends.

Only memory bounds are refused (`InvalidMessage(reason)`, nothing changes): an address over 64 KiB, more than 1024 arguments, a string argument over 64 KiB, or a non-finite float (JSON cannot hold one). They sit far above the send limits (512 bytes, 32 arguments, 4096 bytes per string, 8192 per message; `network::check_message`), so normal typing is never refused; they only stop a hostile client filling the document through one command. The same bounds hold on every path that creates or replaces a Network cue: `AddCue`, `Paste` and `PasteClipboard` (each new cue, at any depth in a pasted group) and `SetCueProperty { Kind }`; there they come from `subtree_issues` and are refused as `InvalidCue` (`TooLarge`). Every refusal reaches the client as `command_refused`. Load keeps an over-limit message and warns (`TooLarge`); the cue shows broken (`network_message_invalid`) as before.

## Commands

| Command | Notes |
|---|---|
| `AddCue { at, cue, auto_number }` | A Group brings its children. `auto_number` replaces the cue's number with `next_auto_number`. |
| `Paste { at, cues }` | One undo step. Ids must be fresh: build `cues` with `prepare_paste`. What the engine applies for a client's paste; a client sends `PasteClipboard`. |
| `PasteClipboard { at, cues, source_dir? }` | The raw clipboard (cues copied in any workspace). `source_dir` is the absolute folder of the show they were copied from (absent for a show never saved): relative media paths are read against it, then stored for this show by the media-path rule below, so the file still plays from another folder. A missing, relative or equal-to-this-show's `source_dir` leaves the paths as written. The engine runs `prepare_paste` (fresh ids it makes itself) and applies the result as a `Paste`, one undo step. Core's `apply` refuses it (`NotPrepared`): it needs `Command::prepare`. A clipboard nested deeper than the limit is refused. |
| `RemoveCue { id }` | Removes the subtree. Its inverse re-adds it at the same place. |
| `MoveCue { id, index }` | Reorder among current siblings. |
| `ReparentCue { id, to }` | Into another group or cue list, children with it. Not into itself or its descendants. |
| `SetCueProperty { id, property }` | `CueProperty`: name, notes, colour, flagged, armed, pre/post wait, continue mode, triggers, second trigger, second trigger on release, target, group mode, or the whole kind (never to or from Group), or `KindFields`: named fields of the kind merged into the kind the cue has when the command arrives (same rules; `type`, `children` and `media` cannot be named; not in `BatchSet`); for Audio cues only `media`, the file alone (`value` a path or `null`; levels, routing, fades and slices untouched); for Network cues only (M4.6a, CT-30) `destination`, `address` and `args`, each `value` the whole new setting; for Wait and Fade cues only `duration`, and for Load cues only `load_to_time` (M5.6b, CUE-02, CT-14, CT-20): seconds, finite, 0 to `MAX_TIME` (24 h), anything else refused (`InvalidCue`, an `InvalidTime` issue naming the field), the rest of the kind untouched. A running Wait or Fade takes the new duration (a Fade keeping its rate); a Load cue reads its time when its action starts (cue-engine.md, Model edits). |
| `BatchSet { ids, property }` | One property on several cues, all or none. Not `Kind`. Applied in place with each cue's old value kept; a refusal writes the old values back, so the cost follows the cues named, not the show. |
| `SetCueNumbers { numbers }` | Set, clear or swap numbers; uniqueness is judged on the result. |
| `Renumber { ids, start, increment }` | Numbers `ids` in cue-list order (a group before its children), whatever order `ids` is in. |
| `Transaction { commands }` | One undo step; if any command is refused, none applies and the error names its index. No nesting; the inverse is flat. Commands that changed nothing add nothing to the inverse. A refusal is rolled back by applying the inverses of the commands already applied, newest first, as an undo would (restoring); the workspace is not copied, so the cost follows the commands, not the show (tests in `tests/transaction_rollback.rs` hold every inverse to restoring exactly; no build checks it at run time). A rollback step can only be refused if an inverse is wrong; then the error is `RollbackFailed`, the workspace is valid but partly changed, and `History` drops its undo and redo steps, which no longer fit it. |
| `SetWorkspaceSetting { setting }` | `WorkspaceSetting`: `min_go_interval`, `panic_duration`, `autosave_interval`, `master_db`, `hotkey { key, value }` (`key`: `go`, `stop_all`, `pause_all`, `resume_all`, `load_selected`, `pause_resume_selected`, `start_selected`, `stop_selected`, `reset_selected`; `value` null = no key), `hotkeys { value }` (the whole key map, `settings.hotkeys`: for swapping two keys or a Reset, which one key at a time would refuse halfway; **every key must be present**, `null` for none, and an unknown field is refused: `bad_request`, so a client bug cannot silently clear the keys it left out), `auto_number_start`, `auto_number_increment`. Each is the whole new value. **Key-map rules** (TRG-01, M5.11c): every key the edit changes to a value must not be reserved (Esc with any modifiers: always panic; Up / Down with any modifiers: QLab 5 refuses the arrows whatever is held), must not equal another key of the new map, and must not be the hotkey of any cue (the first in workspace order is named); a refusal is `HotkeyRefused { field, reason }` (`command_refused`, message e.g. `settings.hotkeys.pause_all: the same key is already settings.hotkeys.go`, or `... is the hotkey of cue 12.5`, the cue's id when it has no number). Keys the edit does not change are not judged, so a clash a hand-edited show was loaded with blocks nothing else; clearing a key (null) is always allowed. The other direction stays allowed: a cue hotkey may be set to a key of the map (QLab check K1b), and then the workspace key wins and the cue warns. QLab 5 itself refuses nothing but Esc and the Up / Down arrows; the duplicate and cue rules are openLab's, so the map never silently takes a key from a cue or another action. Only issues the edit itself introduces are refused: a warning the show was loaded with (a bad hotkey name) does not block other settings, and any new invalid hotkey name is refused (judged on the new value alone). An undo or redo (`Workspace::apply_restoring`, crate-internal: only `History` calls it, never with client input) puts back a state that existed and is never refused for a value problem, so it cannot get stuck on a load warning; the same holds for cue properties (`triggers.hotkey`) and for a cue an undo adds back (the inverse of `RemoveCue`): its values are not judged, only its id, number, place and nesting. |
| `AddOscPasscode { index, passcode, rights }` | Adds a row to the OSC passcode table (`settings.osc_access`) at `index` (0 to the row count). `passcode`: 1 to 32 ASCII digits, not already in the table; `rights`: `{view, edit, control}`, Edit and Control need View. At most 16 rows. Undo removes it. |
| `RemoveOscPasscode { passcode }` | Removes the row. Any row may go, the last too (nobody can then connect with a passcode; undo brings it back at its place, with its rights, even if it is a legacy non-digit passcode). |
| `SetOscRights { target, rights }` | `target`: `{type:"no_passcode"}` or `{type:"passcode", passcode}`. Replaces that row's rights; the same rights are not an edit. Errors never repeat a passcode. |
| `AddPatch { index, patch }` | Output patch at `index` (0 to the current count). Id unique, values valid (1 to 64 outputs, levels). |
| `RemovePatch { id, even_if_used? }` | Refused (the error names a cue) while an Audio cue routes to it. `even_if_used` (default false) is only for the inverse of an add; see below. |
| `MovePatch { id, index }` | `index` counts the patches after taking this one out. |
| `SetPatchProperty { id, property }` | `PatchProperty`: `name`, `master_db`, `output_level`, `output_mute`, `output_polarity` (each `{ output, value }`), `channel_count { value }` (1 to 64; new outputs 0 dB, unmuted, polarity normal), `outputs { value }` (replaces all). Shrinking keeps cue routing to the dropped outputs (silent, a warning), and its inverse is `outputs`, so undo brings the dropped outputs back with their settings. |
| `AddNetworkPatch { index, patch }`, `RemoveNetworkPatch { id, even_if_used? }`, `MoveNetworkPatch { id, index }`, `SetNetworkPatchProperty { id, property }` | As for patches. `property`: `name`, `host`, `port`, `protocol`. Ports are 1 to 65535 for a new or changed value; load accepts port 0, so an undo, redo or rollback may put a patch on port 0 back. Removal is refused while a Network cue uses the patch. |
| `AddCueList { index, id, name }`, `RemoveCueList { id }`, `MoveCueList { id, index }`, `RenameCueList { id, name }`, `RenameWorkspace { name }` | A new list is empty. `RenameWorkspace` sets the show title (the `name` of the `settings` upsert), not the file: Save As names that. Undoable and coalescing, like a list rename. Removing is refused for a list that has cues (move or remove them first, in one `Transaction` if it should be one step) and for the only list. |

`Position { list, parent, index }`: `parent` is `None` for the top level of the list. `index` counts the cues already there (after taking out the moved cue, when moving).

**A new Group from the selected cues** (the app's new Group with two or more cues selected, as QLab 5 does) is no command of its own: the app sends one `Transaction` of `AddCue` (the empty group, auto-numbered, where the first selected cue is) and a `ReparentCue` per selected cue into it at index 0, 1, … in list order (a selected cue inside a selected group goes with its group). So it is one undo step, all or none (a cue that would nest too deep refuses the whole thing), and undo puts every cue back exactly. A cue that is playing, paused or waiting is moved, never stopped or started, and the new group does not count it as its run: it stays idle, and the cue's end neither plays the group on nor fires its continue (docs/cue-engine.md, Modes: a run moved into a group). Where the group goes and what it takes in are assumed from QLab 5 (`docs/todo/open-qlab-questions.md` #47). Tests: `tests/commands.rs` (`a_new_group_…`), `tests/cue_engine/group_playhead_follow.rs` (`wrapping_a_playing_cue_in_a_new_group_…`), mac `CueEditingTests` (`testNewGroup…`).

## Settings, patches and cue lists

- **Names.** A new name of the workspace, a cue list, a patch or a network patch (the add commands and the renames) is at most 1024 Unicode scalar values (`MAX_NAME_SCALARS`; characters, not bytes, so a name in any script gets the same room) with no control character except a newline (NUL, tab, carriage return, escape codes are refused; a newline is allowed, as in QLab 5). Empty is allowed. A network patch `host` is at most 253 bytes (the DNS limit) with no control character; whether it can be addressed is not checked here (a bad host makes a Network cue broken). A name or host that breaks the rule is refused with `command_refused` (`InvalidValue`). The rule is for the value being set only: load keeps an odd name or host with one `InvalidName` warning per field kind (`name`, `cue_lists.name`, `patches.name`, `network_patches.name`, `network_patches.host`), and undo, redo and a transaction's rollback put such a value back. QLab 5's documentation sets no limit; it took 300 characters and newlines, and 1024 is our choice.
- **Cue name and notes** (memory bounds, not a naming rule): a cue name is at most 1024 bytes (`MAX_CUE_NAME_BYTES`: 256 characters of any script at 4 bytes each at most; not raised with the names above) and notes at most 64 KiB (`MAX_CUE_NOTES_BYTES`, the bound on a Network string argument). Otherwise both are free text (newlines allowed). A new value over the bound is refused with `command_refused` (`InvalidCue`, `TooLarge { field: "name" | "notes" }`) on `AddCue`, `Paste`, `PasteClipboard`, `SetCueProperty` and `BatchSet`; a value already in the cue is not re-judged by other edits. Load keeps an over-limit value with a `TooLarge` warning, and undo, redo and rollback put it back; an edit may replace such a value with one no longer than it (a longer one is refused), and the same holds for a loaded over-limit Network message replaced through a Kind change.
- **Valid.** A new or changed value must pass what load checks (`validate`/`repair`), including values `repair` would silently normalise (a level below silence): it is refused with the issues listed. An OSC passcode added by a command is 1 to 32 digits (NET-02); a show file may hold other text (a migrated v3 passcode), which load keeps with a warning.
- **In use.** Removing a patch, network patch or cue list that something uses is refused, so a UI cannot orphan cues by accident. A cue that already points at a patch the workspace lacks is the usual broken-cue state. Two things follow: `RemovePatch` / `RemoveNetworkPatch` take `even_if_used`, which `AddPatch` / `AddNetworkPatch` put on their inverse (the patch may have been added to mend a cue that already pointed at it, and undo must restore exactly, not be blocked by that cue); and a client may send it too, to remove a patch on purpose and break its cues.
- **Playing.** Patch edits of any kind (insert, remove, move, resize) and their undo and redo are allowed while audio plays: mixer slots are keyed by patch id, so a playing voice keeps its routing (docs/control.md, "Patch slots", M4.15b).
- **Footprints.** `Footprint` also names the cue lists, patches and network patches an edit touched (`Touched`: changed, removed, reordered) and whether settings changed; `model_changes` turns them into `cue_list`, `patch`, `network_patch` and `settings` upserts and deletes. A move, or an edit touching two or more items of one collection (a merged undo step), sends every member of the collection, each at its final index, in index order, which sorts the client's copy whatever the old order. An edit that is `is_model_wide()` makes the control loop call `CueEngine::model_changed` (patches decide which cues are broken, lists have playheads) instead of the cue-scoped `model_changed_cues`.

## Coalescing (fader drags)

`History::execute_coalescing(workspace, command, key)`; on the wire, `coalesce` on the `command` message ([protocol.md](protocol.md)). An edit with a key joins the previous edit's undo step if that edit had the same key and nothing but such edits happened since: no other command without or with another key, no undo or redo, no `History::clear`. A client sends a fresh key for each gesture (for example `fader:<cue>:<n>`) and none for a one-off edit. A no-op edit and a refused one leave the gesture open.

Every edit is still applied and sent to clients at once; only the undo step is shared. Undoing a gesture restores the state before its first edit, redo the state after its last. When the new step and the gesture's step each set the same single value (the same cue property, setting, patch property, name, or the same item's position), the merged step is the older one alone, so a thousand-event drag is one small command. A step of the newer edit is left out only where that is provably safe: both steps are one command setting the same value (or moving the same item), or the newer step only sets values (cue properties, settings, patch and list names), no two of them the same value, with no add, remove or move and not both a `Kind` and a field inside that kind (`target`, `group_mode`, `media`, `destination`, `address`, `args`) of one cue, and the older step holds a command for that exact value (a multi-cue level drag stays one command per cue; a `Kind` is kept when the older chain sets one of those fields on that cue). Anything else is chained flat, newest undone first. Core has no clock, so a gesture ends only by the events above; a client that sends the same key forever merges forever.

## Preparing a command (M5.10e, WS-03, ED-05)

Before applying a client's command the engine calls `Command::prepare(&Workspace, &MediaPaths, new_id)`. Core stays pure: the engine passes the show file's folder (`None` for a show never saved) and makes the ids.

- **Media paths** in `AddCue`, `Paste`, `PasteClipboard`, `SetCueProperty` and `BatchSet` (a `Kind` that is Audio, or `Media`) are stored as docs/file-format.md section 4.3 says: forward slashes (a Windows path with backslashes is converted), NFC, relative to the show folder only when the path as sent is literally under it (same components after NFC, no case folding, no `.` or `..`), absolute exactly as sent otherwise. A path that is already relative is kept as written. A client sends the absolute path it was given. An empty path is left alone. A show never saved has no folder, so paths stay absolute; the first Save As (and any Save As to another folder) then stores an absolute path that lies literally inside the new folder relative, by the same rule, and never touches one outside it (the live workspace, the saved file and every client's snapshot agree, the show is not left dirty, and history is kept only for the first save of a never-saved show, where every path was absolute and an undo restores a spelling that still names its file; a Save As from one folder to another clears history, as before).
- **`PasteClipboard`** becomes a `Paste` of `prepare_paste(workspace, clipboard, ids)`. Inside a `Transaction` every command is prepared against the workspace as it is before the transaction.
- `Paste` still arrives on the wire (cues must carry fresh ids; its media is converted too), so a client that prepares its own cues keeps working; the macOS app now sends `PasteClipboard`.

## Helpers

- `next_auto_number(&Workspace)`: one `auto_number_increment` above the highest numeric cue number in the workspace, never below `auto_number_start`; plain decimal text (`0.3`, not `0.30000000000000004`).
- `prepare_paste(&Workspace, &[Cue], new_id)`: copies a clipboard for pasting into any workspace. Fresh ids from `new_id` (core cannot make ids); targets inside the copied set follow to the copies, others are kept if they exist in the destination and cleared otherwise; numbers already in use are cleared; a missing patch or network destination becomes the destination's first.
- Cut is copy + `RemoveCue`; duplicate is `prepare_paste` + `Paste` — both in a `Transaction` when they must be one step.

## Editing levels, routing and Fade settings from the UI (M5.9)

There is no finer command for an Audio cue's levels, routing and gangs or for a Fade cue's curve, stop-target flag and levels (its duration has its own property, `duration`, M5.6b): the macOS inspector edits them (and an Audio cue's trims, slices and fades) with `SetCueProperty { KindFields }`, naming only the fields it changed (`levels`, `curve`, `stop_target_when_done`, `slices`, ...). The engine merges them into the kind it has when the command arrives, so a change another client made to the other fields meanwhile is kept; two clients changing the same field is last write wins. Undo of such an edit restores the whole old kind, as undo of `Kind` does. A fader or matrix drag sends every move with one `coalesce` key (`levels:<cue>:<n>`, a fresh `n` per mouse gesture), so the drag is one undo step; typed values are one-off edits.
