# M4.7b decisions (crash capture beyond panics, DX-04)

Decided by the implementer from the orchestrator's brief (2026-10-27). Code: `engine/crates/engine/src/diag/run_marker.rs`, wired in `host::run_show`. Behaviour: [logging.md](../../logging.md), "Unclean exits".

## What we do: a clean-shutdown marker

- At start, after the show log and the panic hook are up, the engine writes `<app-support>/openLab/Running/running-<pid>.json` (`{"pid", "started_ms", "version"}`) and holds an exclusive lock on it (`File::try_lock`, std, no new dependency) for as long as the process lives. It is written, locked and synced under a temporary name (`running-<pid>.json.<pid>-<n>.tmp`, not a marker name; since #364 by the shared `persist::write_engine_file`) and then renamed into place, so an engine starting at the same moment never finds it empty or unlocked (the lock belongs to the open file and survives the rename).
- A graceful end of `run_show` (stdin closed, `goodbye { shutdown }`, or a start that failed with an error) closes and removes the marker.
- **A panic on the control thread is an unclean exit** (orchestrator's decision, review of M4.7a/b/c). The show has stopped, so from the operator's point of view it crashed. `run_show` returns `HostError::ControlPanicked` (the process exits non-zero) and drops the marker without removing it, so the next start reports the run like any other crash, naming the report the panic hook wrote.
- Before writing its own marker, the next start looks at the folder. A marker it can lock belongs to a run that is over (the OS drops a lock when its process ends, however it ends), so it was not a clean shutdown: one `warn` record, kind `engine`, goes into the show log ("previous run ended without a clean shutdown (crash, kill or power loss): openLab engine <version>, pid <pid>, started <UTC>"), naming the crash reports that run's panic hook wrote (`crash-<UTC>-<pid>*.txt` not older than its start; at most 3 named), and the same line goes to stderr. The marker is then removed, so each unclean exit is reported once.
- A marker some other process still holds (a second engine running at the same time) is left alone; it is not a dead run.
- The record lives in the show log, which belongs to the engine and not to a workspace: it is in the log file, in `log_tail`, and so in the log window whichever workspace the UI opens. No client is connected yet at start, so there is no `log` broadcast; a live `log_entry` push (M4.7c) only carries later records.
- Covered: aborts (double panic, `std::process::abort`, an out-of-memory abort), SIGSEGV/SIGBUS/SIGILL, SIGKILL (Activity Monitor's force quit, the OOM killer, `kill -9`), a hang that the user or the UI kills, a power cut or kernel panic. A panic that unwinds out of the main thread or the control thread is covered too; a panic on another thread is the panic hook's (its report is named in the record if the run then dies).
- Edge cases, decided: only regular files are read (a FIFO or device named like a marker is left alone, so it cannot hang a start); an extreme `started_ms` in a marker saturates instead of overflowing; an empty or unreadable marker (a power cut while it was written, or a foreign file) is still reported, "its details were not readable"; markers over 4 KiB are not read; at most 32 leftovers are handled per start (oldest first) and at most 10 000 folder entries looked at, so a junk-filled folder cannot slow a start. A filesystem without locks: every marker is treated as over, because missing a crash is worse than a false notice when two engines run at once (not a supported setup: M4.9's `engine.json` makes the engine single-instance). With no app-support folder, or an unwritable `Running` folder, the engine runs without a marker.

## What we do not do, and why

- **No signal handler.** Only async-signal-safe functions may run in a handler for SIGSEGV/SIGBUS/SIGABRT: no allocation, no locks, no formatting, no `std` I/O beyond a raw `write(2)` to a pre-opened fd. A useful report (version, workspace, last log lines, a backtrace) needs all of those, and getting it wrong turns a crash into a deadlock (a hung engine holding the audio device is worse than a dead one: the UI cannot tell it apart from a busy one and cannot relaunch it). Rust's std has no signal API, so it would also mean `unsafe` FFI to `sigaction`/`sigaltstack` and, on Windows, `SetUnhandledExceptionFilter`, each with its own rules. SIGKILL and power loss cannot be caught at all. The marker covers every one of these the same way, with no code running at crash time. macOS's own crash reporter still writes `~/Library/Logs/DiagnosticReports/openlab-engine-*.ips` with a native backtrace for signals and aborts; the UI (M5) can point the user there.
- **Nothing is sent.** v0.0.1 has no network code for reports. Orchestrator's decision: for v0.0.1, "never sends" satisfies DX-04's "sending is opt-in"; the opt-in send path (M6.6) stays later. The opt-in path (a setting, off by default, plus an explicit "send report" action per report, showing what would be sent) is UI work for M6; until then a user attaches the file from the crash folder to an issue by hand. M5 shows the crash folder (`AppDirs::crash_dir`) in the UI.
- **The UI's view of an engine exit** stays M4.9's: the engine relaunch should log the exit status (signal or code) of the engine it relaunches; the marker is the engine-side half that works even when the UI was not running.
