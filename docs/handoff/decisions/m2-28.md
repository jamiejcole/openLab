# M2.28 decisions (second batch of QLab checks)

The user measured these in QLab 5 (checks page answers of 2026-10-27, with chat follow-ups). Where QLab's answer left a case open, the implementer decided as below (unconfirmed against QLab; to check on a later rental day). Rules: docs/cue-engine.md.

| Point | QLab (measured) | openLab now | Decided here (unconfirmed) |
|---|---|---|---|
| D7 Devamp modes | "Devamp currently looping slice" on a cue that loops as a whole with slice 1 looping: slice 2 plays, then the cue plays again and slice 1 loops again. "Devamp looping cue" fired while slice 1 loops: nothing happens | `devamp_mode` `current_slice` / `looping_cue` on Devamp cues (show file v3) | openLab has no whole-cue play count, only slice play counts (a cue without markers loops as a whole through `last_slice_play_count`). So `looping_cue` leaves the loop of a cue without markers and does nothing (warns `DevampIgnored`) on a cue with markers; `current_slice` keeps the old behaviour (leaves whatever loop plays, including the whole-file loop of a cue without markers). The "first slice loops again on the next pass" part needs a whole-cue play count: filed as M2.30. |
| D7 default | - | `current_slice` | Existing (v2) shows migrate to `current_slice`: it is exactly what their Devamp cues did, so no show changes behaviour. New cues also default to `current_slice` (QLab's default for a new Devamp cue was not checked). The second trigger `devamp` acts as `current_slice`; a looping playlist target is devamped the same in both modes. |
| F2 Fade of a group | each child moves by the fade's 10 dB ("definitely relative") | relative: each level of each audio cue in the group moves by the fade's dB | Relative to the level on the ramp's first sample, including where an earlier fade put or is moving it (QLab's stacking of concurrent relative fades is not modelled). Capped at +12 dB (`MAX_DB`). A silent level (an unlisted crosspoint) stays silent and gets no ramp. A Fade straight at an audio cue stays absolute. |
| S1 trigger on a paused cue | resumes it (second trigger Hard stop) | every trigger (GO, Start, Start cue, continue, hotkey) resumes a paused cue, whatever its option | A **release** (`TriggerReleased`) still applies the option to a paused cue (S5 only measured press-resume then release-stop on a running cue); a release never resumes. |
| S4 play previous on the first child | stops the playlist entirely (on child 2 it goes back to child 1) | stops the group (as `stop`: its continue is cancelled) | With loop, "play previous" on the first child still wraps to the last child (QLab's check used a playlist without loop). |
| S5 hotkey on a paused cue | press resumes; release with "stop" on release stops | follows from S1 and the release rule | - |
| V1 group preview | a group can be previewed (and video) | a group previews every armed audio cue inside it at once, each as its own preview; the group is previewing while any of them is | QLab's behaviour per group mode was not measured: all audio cues play together whatever the mode (open question for playlist/random/start-first groups). Audio cues inside a disarmed child group are left out; broken ones are skipped with `CueBroken`; one already previewed on its own stays its own. New reason `nothing_to_preview` when none can play. |
| V2 disarmed | does not play | refused: `PreviewIgnored { reason: disarmed }` (a group too) | - |
| V4 Pause All | pauses the preview | Pause All pauses previews (`PauseVoice` with the preview's run), Resume All resumes them (`ResumeVoice`, fresh preview id) | Pause/Resume of the single cue still concern the show only. |
| V4/V6 Panic | a playing preview fades out; a second Panic stops it at once; a paused preview stops at once | as measured | A fading preview is reported ended at the Panic (not at the fade's end), so it can be previewed again during the fade; its voice is still cut by a second Panic or Stop All until its end report or the panic window's end. |
| K1b cue hotkey = workspace key | "Warning: Hotkey used by workspace", yellow icon; the workspace hotkey wins, the cue is not started by it | validation warning `HotkeyUsedByWorkspace { action }` (like the other hotkey check); `cues_with_hotkey` returns nothing for a transport key; edits to such a key are allowed | A validation warning, not a static problem (the cue is not broken and can still be started any other way), so no protocol change; the app shows it from the model (M5). |

No engine (binary) change was needed: group previews are per audio cue on the wire to the mixer, and preview pause/resume use the existing run-keyed `PauseVoice`/`ResumeVoice` handling.
