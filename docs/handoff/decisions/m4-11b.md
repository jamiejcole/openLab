# M4.11b decision: `Load` with `at` past the cue's length

Decided 2026-10-27 (implementer, from the PROGRESS note: "QLab loads to the end"; unconfirmed against QLab's docs).

**Decision.** Loading to a time past a cue's length (pre-wait + action) loads it to its end. It sits `loaded`; it does not complete, fire its continue, or warn. Starting it ends the action on its start sample and its continue runs on schedule (no `late_start`).

**Why.** The soak found that a cue loaded past its end finished the moment it started and its chained successor logged `late_start` (8 ms): the empty-plan start was reported by a deferred `ActionEnded`, which reaches the core after the sample it names. QLab's "Load to time" documentation (qlab.app/docs/v5/other-cues/transport-cues, tools/tools-menu) describes loading to a time but is silent on a time past the end (checked 2026-10-27); the PROGRESS note records QLab loading to the end, so that is followed. Refusing the load was rejected: a Load cue with a fixed time must keep working when the target is later trimmed shorter.

**Where.**
- Core `load`: clamps `t` to `P + D` for cues with a known action length (Wait, Fade, Memo, controls, disarmed). Tests: `cue_engine.rs` (`load_past_the_end_*`), property `a_load_past_the_end_is_a_load_to_the_end`.
- Binary `voices.rs`: an empty plan on start reports `ActionLength { frames: offset }`. Test: `control_timing.rs` `load_past_the_end_starts_the_successor_on_time`; the soak operator now loads any cue 0.5 s in.
- Audio length is not known to core, so core does not clamp audio.

**Infinite loops.** An infinite loop has no end; loading past "length" wraps within the loop (`plan::skip` works modulo the loop), so the cue is loaded into the loop, never at an end. Defensible because the loop is the cue's steady state, and a stop or devamp is what ends it.

**Open.** M4.11c: an audio cue's post-wait is counted from the unclamped offset (core cannot clamp it), so it can be shorter than for a load exactly at the end.
