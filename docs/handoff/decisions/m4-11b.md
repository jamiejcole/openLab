# M4.11b decision: `Load` with `at` past the cue's length

Decided 2026-10-27 (implementer, from the archived progress note: "QLab loads to the end"; unconfirmed against QLab's docs).

**Decision.** Loading to a time past a cue's length (pre-wait + action) loads it to its end. It sits `loaded`; it does not complete, fire its continue, or warn. Starting it ends the action on its start sample and its continue runs on schedule (no `late_start`).

**Why.** The soak found that a cue loaded past its end finished the moment it started and its chained successor logged `late_start` (8 ms): the empty-plan start was reported by a deferred `ActionEnded`, which reaches the core after the sample it names. QLab's "Load to time" documentation (qlab.app/docs/v5/other-cues/transport-cues, tools/tools-menu) describes loading to a time but is silent on a time past the end (checked 2026-10-27); the archived progress note records QLab loading to the end, so that is followed. Refusing the load was rejected: a Load cue with a fixed time must keep working when the target is later trimmed shorter.

**Uniform timeline rule (orchestrator decision, unconfirmed against QLab).** The load time `t` is a position on the cue's own timeline. Only the action is clamped to its length; the post-wait is not clamped and counts from the unclamped `t` (`W - (t - P)` left; none left means the continue fires at the start). Same for every kind (audio, groups, Memo/control, Wait, Fade). No kind-specific clamp in `load()`: core's `begin_action` already ends a known-length action at `start + (D - a)` saturating at 0, so the first implementation's load-time clamp (which also read armedness at load and so lost the offset of a cue armed between load and GO) was removed.

**Playlist and random groups (orchestrator decision).** They follow the same rule rather than being an exception: the group's nominal span is the sum of its children's spans (playlist, not looping) or the chosen child's span (random). A load offset at or past it ends the group's action at once on GO, the post-wait follows `W - (t - P)`. Unknown spans and looping playlists clamp nothing. Implemented in `start_children` (`group.rs`) with `nominal_span`; tests in `cue_engine_groups.rs`.

**Where.**
- Core: no change to `load()`. Tests pin the rule: `cue_engine.rs` (`load_past_the_end_*`, `started_after_a_load_past_the_end_*`, `a_cue_disarmed_at_load_and_armed_before_the_start_keeps_its_load_time`), property `a_load_past_the_end_ends_the_action_and_counts_the_post_wait_from_the_time`.
- Binary `voices.rs`: an empty plan on start reports `ActionLength { frames: offset + hold delay }`. Test: `control_timing.rs` `load_past_the_end_starts_the_successor_on_time`; the soak operator now loads any cue 0.5 s in.

**Infinite loops.** An infinite loop has no end; loading past "length" wraps within the loop (`plan::skip` works modulo the loop), so the cue is loaded into the loop, never at an end. Defensible because the loop is the cue's steady state, and a stop or devamp is what ends it.
