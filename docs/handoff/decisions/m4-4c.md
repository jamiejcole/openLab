# M4.4c decisions (default patch mapping)

Orchestrator decision (2026-10-27, unconfirmed against QLab 5 beyond "QLab maps a new workspace's audio patch to the current output device automatically"):

- A workspace with **no patch mapping at all** in this machine's `settings.json` (a new workspace, or a show opened from another Mac) has each patch with N outputs mapped to the playable device's outputs 1..N. Any existing mapping for the workspace stops this entirely; nothing is ever overwritten.
- The mapping is written to the machine settings (keyed by workspace id), off the control thread, and an `info` show-log line says `mapped patch 'Main Outputs' to <device> outputs 1–2`.
- No playable device (none, or an outage): nothing is mapped or written; the patch is `Unmapped`. The next patch sync with a device (device back) maps it. Simplest safe rule: map at the moment a device is known and the workspace has no mapping.
- A device with fewer outputs than the patch: the outputs that exist are mapped (a shorter channel list) with a `warn` log. A mapping cannot name an unmapped output, so it resolves `OutputCountMismatch` (silent, cues broken). That mapping is kept (it is an existing mapping); the operator fixes it with the mapping request (M4.4g).
- Granularity is the workspace, not the patch: a patch the operator cleared stays unmapped while its siblings are mapped.
- No protocol change.
