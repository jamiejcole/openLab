# M4.2g device watchdog: stall limits and where it lives

Decision (orchestrator, 2026-10-27; two-stage revision after review the same day).

- **What:** a running stream whose callback counter does not advance, with its device still listed and no host error, is handled in two stages.
  1. **Warning** after `max(500 ms, 20 buffer periods)` of silence: `warn` log and the `device_stalled` workspace warning. Nothing stops. Cleared (with an `info` log) when callbacks resume.
  2. **Loss** after `max(3 s, 50 buffer periods)` of silence: a device loss with reason `stalled` (M4.2g policy: cues on it stop at once, no automatic resume, close then the existing reopen path, cues un-break on return).
- **Why two stages (review H1):** a one-stage 500 ms loss turned a recoverable 600 ms dropout (paging stall, starved HAL thread) into a stopped show with every cue broken. A true hang ends the same way at 500 ms or at 3 s (it is silent already, the same cues stop), so the later loss costs 2.5 s of an already silent show, while a false positive costs the whole show. Sample-rate changes, `IsAlive=false` and `DEVICE_INVALIDATED` already reach `needs_reopen()`; the watchdog only adds the ambiguous no-error cases.
- **Numbers:** a healthy callback comes every 1-50 ms (buffers of 64 to 2048 frames). 500 ms is ten times a large normal period; 3 s outlasts any recoverable pause seen on slow disks and USB wakes. Big buffers scale: 4096 frames at 44.1 kHz warn at 1.86 s and are lost at 4.64 s.
- **Where:** the device supervisor on the control thread (`devices::Device::poll`, every tick), not the audio thread. The audio callback already increments `DeviceShared::callbacks` (relaxed); nothing is added to it, so real-time rules are untouched.
- **Clocks (injected):** `WallClock` for all timing; `SleepClock` (a clock that counts sleep) only to detect a wake.
- **Only watched silence counts (review H2):** a gap between two supervisor samples above `max(100 ms, warning limit / 8)` starts the window over, and each stage needs 10 samples in the window. A frozen process (both threads stopped, the control thread waking first with an unchanged count) is therefore never a stall. This replaces the 5 s `CLOCK_JUMP` guard.
- **Sleep (review M1):** on macOS `Instant` does not advance during sleep, so a sleep makes no gap. The system clock does advance: if it moves more than 1 s further than the monotonic clock between two samples, the Mac woke, and the stream gets a grace of one loss limit (3 s or 50 periods) to call back.
- **First callback (review M3):** a stream gets one loss limit (at least 3 s) for its first callback after open, so an interface that re-locks its clock does not reopen forever. No warning is raised during the grace.
- **List vs watchdog (review M2):** when the device has left the list, the reason says "no longer listed". The list check itself (two reads, or one read with no callbacks since the previous one) usually acts first, since the watchdog needs 3 s.
- **Not up:** only `Stream::Up` is watched (closing, down, opening are not). openLab never pauses a stream and a silent mixer still calls back, so "paused by us" reduces to "not up".
- **Flapping (round-2 review M1):** a device that calls back every 0.5-3 s is never silent for 3 s but plays almost nothing. (a) The warning clears only after callbacks ran one warning limit (500 ms) with no silence of that length. (b) The warn log is written at most once per 10 s with the count of stalls since (the clearing is logged only if the raise was). (c) Over a sliding 10 s window of watched time (at least 8 s watched, first-callback grace excluded), silence of 50% or more is a loss, reason `stalled (intermittent)`. A single 600 ms stall is 6% of the window and recovers. The watchdog no longer words a loss as "no longer listed": the list check owns that reason.
- **Status:** `status.device.state` stays `ok` while `device_stalled` is up; the stall shows as a workspace warning only (docs/logging.md). No protocol change.
