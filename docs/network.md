# openLab network layer (`openlab-engine::net`)

The WebSocket server for the UI protocol ([protocol.md](protocol.md)); ARCHITECTURE §3.1 and §6. Code: `engine/crates/engine/src/net/` (`ws.rs` server and connections, `hub.rs` fan-out, `token.rs`). The OSC listeners (UDP and TCP 53000, [osc.md](osc.md)) run on the same runtime: `osc.rs` (sockets and the actor task), `osc_mirror.rs` (the OSC side's workspace copy), `refusals.rs` (shared refusal logging).

## Shape

- **Threads**: a tokio runtime with 2 worker threads (`openlab-net`) and nothing else (ARCHITECTURE §3.1). On it run the accept loop, one task per connection and the **fan-out task**. The control loop's reply channel (`control::reply_channel`, tokio unbounded) and outbound channel (`control::outbound_channel`, tokio bounded) wake those tasks directly; the control thread only ever sends on them without blocking (`send` / `try_send`), so nothing here can hold up the control or audio thread.
- **Listening**: `127.0.0.1` only, an OS-chosen port. `WsServer::port()` and `token()` are what M4.9 writes to `engine.json` (this task does not write the file). `host::run_show` starts the server; nothing publishes the port yet, so no client can connect until M4.9.
- **Token**: 32 bytes from the OS CSPRNG (`getrandom`, already in the dependency tree through `tempfile`/`uuid`; ARCHITECTURE §12), 64 hex characters, fresh per start, compared in constant time (`constant_time_eq`, no early exit, walks the longer input). Never in `Debug` output.
- **Limits**: 16 authenticated connections, 8 still upgrading or waiting for `hello` (more are closed at accept). Refusals are logged (`warn`, through the control inbox as `Inbox::Log`) at most once per `refusal_log_interval` (10 s) with a count: the first at once, the ones inside the interval once it has passed (by a timer, even if no connection follows), so a UI that cannot connect because something holds every slot can be diagnosed without one entry per attempt and every refusal is counted. Up to 64 requests in flight per connection (until their `result` is written): beyond that the server stops reading the socket, so TCP holds a flood back instead of the inbox growing.

## Connection

1. **Upgrade and `hello` within `hello_timeout` (5 s) in total.** Before `hello` is accepted the socket delivers at most 16 KiB (the upgrade request plus the 4 KiB hello); the WebSocket library would otherwise buffer a whole 1 MiB message before anyone looks at it. The first frame is decoded with `decode_hello` (4 KiB).
2. Refusals are an `error` message, then close: wrong token or any other message first -> `bad_token`; version differs -> `protocol_version_mismatch` (token is checked first); unreadable or oversize hello -> `bad_request`. A hello over 16 KiB, a timeout or a closed socket just closes.
3. On success the connection is registered with the fan-out, then the server asks the control loop for a snapshot with a request of its own (id `u64::MAX`, **reserved**: a client using it gets `bad_request`; its `result` is swallowed) and answers `welcome { snapshot }`. Broadcasts made in between are queued and filtered: a `model_changed` at or below the snapshot's revision and a `runtime` at or below its `runtime_seq` are not sent. `document`/`warnings` queued from before the snapshot may arrive after it; the last one before the snapshot equals the snapshot's own state, so the client ends up right.
4. After `welcome`: client frames are decoded with `decode_client` (1 MiB; the WebSocket layer enforces the same limit while reading) and `command`/`transport`/`undo`/`redo`/`request` go to the control inbox with the connection's reply channel. An unreadable frame gets `error` (`bad_request`, or `unknown_message` for an unknown `type`) and the connection stays up; 32 in a row (any good frame resets the count), a frame over the limit, or a socket error close it. Binary frames are `bad_request`. A second `hello` is `bad_request`.
5. `goodbye`: the connection closes. With `shutdown: true` the message is also forwarded to the control inbox, which stops the show and ends the loop (docs/control.md). The server does not exit the process: `host::run_show` returns when the control loop ends (the process exit policy, relaunch and `engine.json` cleanup are M4.9).

## Ordering and gaps

- The server keeps a **per-connection** order: broadcasts are written before replies, and a `result` carrying `ok.revision = N` is **held** until the `model_changed` for N (or a snapshot at N or later) has been written; it is in the connection's queue or about to be, as the control loop puts it on the outbound channel first. The connection keeps reading client frames and serving other replies meanwhile (a GO is not delayed by a held result); results may therefore leave in a different order than they arrived, which the protocol allows (clients match them by `id`). If the `model_changed` never arrives (the control loop's outbound channel was full and dropped it, docs/control.md "Outbound") the result goes out after `revision_wait` (2 s); the client sees `result.revision` ahead of its own model and requests a `snapshot`.
- **Snapshots never go back in time.** While a request that answers with a `snapshot` is out (the server's own, or the client's `snapshot`/`open`/`new`/`revert`, until its `result` arrives) the connection forwards no broadcasts: they wait in its queue, and are filtered against the snapshot's revision and seq once it has been written. So a `model_changed` made after the control loop took the snapshot can never reach the client before it. Held results wait for the snapshot too (it covers them: the control loop answered them before taking it). As a second line, a snapshot behind what the client was already sent (revision or seq below the connection's: stale, or the numbering restarted) is followed at once by a fresh one (the connection marks itself lagged). It is not dropped: after a restart of the numbering the fresh one would be behind too and never get through.
- **A new workspace reaches every client (M4.4a).** After `new`, `open`, `open_recovery` or `revert` the control loop sends the new `snapshot` to the requester (its reply, before its `result`) and on the outbound channel, which the hub delivers to every connection as `Kind::Snapshot { revision, seq }`. A connection takes it unless it already holds that revision and seq (the requester does), resets its filter to it and writes it, so no client is left on the old workspace. `revision` and `runtime_seq` keep rising across these requests (they are never reset), so nothing queued from before the replacement is mistaken for newer: a `model_changed` or `runtime` at or below the snapshot's numbers is dropped by the filter, later ones pass. A request that may answer with a snapshot (`open`, `open_recovery`, `new`, `revert`) holds the requester's broadcasts until its `result`, even when the answer is a refusal or a `recovery_offer` with no snapshot. The hold is bounded: after `snapshot_wait` (60 s, `ServerConfig`) without the `result` the connection drops the hold and takes a fresh snapshot, so a lost or very late answer cannot leave a client without updates for the rest of the show (the engine also bounds its own document reads, docs/control.md).
- A `snapshot` message resets the connection's filter to its revision and seq. Revision/seq gaps in broadcasts are **forwarded as they are**; clients recover with `request: snapshot` (protocol section 2).

## Slow clients

Each client has its own bounded queue (`CLIENT_QUEUE`, 1024 messages). The fan-out task encodes a message once (outside the lock on the client list) and `try_send`s it to every queue; it never waits for a client.

- `meters` and `progress`: dropped for a client whose queue is more than half full.
- A state message (`model_changed`, `runtime`, `document`, `warnings`, `log`) that does not fit marks the client **lagged**; the same happens when a message cannot be encoded or exceeds `MAX_SERVER_FRAME_BYTES` (32 MiB). A lagged client is **not closed**: its queue is thrown away, broadcasts for it are skipped, and the server sends it a fresh `snapshot` (asked from the control loop like the first one, with broadcasts held back as above) as soon as its connection task runs and no other snapshot is out; later broadcasts are queued again before the snapshot is requested and filtered against its revision. A client whose snapshot itself exceeds the cap gets `error internal` and is closed. A `result` without a revision may overtake the snapshot during such a resync.
- A client that stops reading entirely stalls its TCP write; a single write that makes no progress for `write_timeout` (10 s) closes the connection. Meanwhile it costs the control loop and the other clients nothing (tested with 1500 x 16 KiB messages).
- Dead peers: a `ping` every `ping_interval` (10 s); a connection that has sent nothing (a `pong` counts) for `dead_after` (30 s) is closed.

## OSC on this runtime

`ServerConfig::osc: Option<OscConfig>` (default `None`; `host::run_show` sets `Some(OscConfig::default())`) starts the OSC sockets on the same two-thread runtime. They are bound before the tasks start; a bind failure (port in use) sends a warning through `Inbox::Log` and leaves OSC off while the WebSocket server starts normally (`WsServer::osc_ports()` is `None`). Tests set `port: 0`, `bind: 127.0.0.1` and `reply_port`. Other `OscConfig` fields: `max_tcp_connections` (256), `max_inflight` (unanswered requests to the control loop, 2048), `duplicate_window` (identical messages from one peer closer than this are dropped, 100 ms like QLab; the tests set zero), `write_timeout`, `tcp_idle_evict`, `max_input_age` and the log intervals.

The fan-out task also offers every `model_changed`, `runtime` and `document` broadcast to the OSC task through a bounded **tap** (`hub::Tap`): a full tap marks the OSC task lagged, which then rebuilds its workspace copy from a snapshot, exactly as a lagged WebSocket client does. The OSC task asks the control loop for snapshots with its own reply channel and ids from 2^63 up. Everything else (queues, caps, counters, TCP limit and idle eviction) is in [osc.md](osc.md) "Listeners". `net/hub.rs` has unit tests for the tap; `osc_mirror.rs` for the workspace copy.

## Tests

`tests/net_ws.rs`: real sockets against a stand-in control thread (auth success, wrong token, wrong version, other message first, hello timeout, 4 KiB and pre-auth caps, handshake limit, connection limit and its single log entry, refusals after the first log flushed once the interval passes, result ordering over 200 commands, lost `model_changed`, frames read while a result is held, two clients, welcome filtering, gap and snapshot recovery, a requested snapshot never after a newer `model_changed` (the stand-in holds the snapshot answer until the newer `model_changed` is in the connection's queue), a stale snapshot replaced, a 2,000-cue group upsert, over-cap message resync, queue overflow -> snapshot -> filtered broadcasts, stalled client, malformed and abusive frames, goodbye, keepalive, dead client, stop). `net/hub.rs` unit tests: meters/progress dropped at half full, overflow marks only that client lagged. `tests/net_docs.rs`: two clients over real sockets in front of the real control loop: `open` by one gives both the snapshot (the requester only once), `new` over unsaved edits likewise, and an edit after each reaches both at the next revision. `tests/net_control.rs`: the same server in front of the real `runner::run` loop. `tests/net_osc.rs`: the OSC listeners over real UDP/TCP sockets (GO over each, replies at the reply port, SLIP framing across reads, passcode (`denied` over both), QLab's update messages over UDP and TCP, repeats within the window, large UDP and TCP replies, a 900 KB TCP message, the pending-write cap, `/version` and `/workspaces`, gaps and passcode changes, TCP cap, malformed input, in-flight cap, bind failure, and a GO in front of the real control loop). Timeouts in the tests are hang guards; the server's own timers are shortened through `ServerConfig`.
