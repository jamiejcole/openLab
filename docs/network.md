# openLab network layer (`openlab-engine::net`)

The WebSocket server for the UI protocol ([protocol.md](protocol.md)); ARCHITECTURE §3.1 and §6. Code: `engine/crates/engine/src/net/` (`ws.rs` server and connections, `hub.rs` fan-out, `token.rs`). The OSC listeners (UDP and TCP 53000, [osc.md](osc.md)) run on the same runtime: `osc.rs` (sockets and the actor task), `osc_mirror.rs` (the OSC side's workspace copy), `refusals.rs` (shared refusal logging).

## Shape

- **Threads**: a tokio runtime with 2 worker threads (`openlab-net`) and nothing else (ARCHITECTURE §3.1). On it run the accept loop, one task per connection and the **fan-out task**. The control loop's reply channel (`control::reply_channel`, tokio unbounded) and outbound channel (`control::outbound_channel`, tokio bounded) wake those tasks directly; the control thread only ever sends on them without blocking (`send` / `try_send`), so nothing here can hold up the control or audio thread.
- **Listening**: `127.0.0.1` only, an OS-chosen port. `host::run` starts the server and writes `WsServer::port()` and `token()` to `engine.json` (M4.9; docs/control.md "Process lifecycle").
- **Token**: 32 bytes from the OS CSPRNG (`getrandom`, already in the dependency tree through `tempfile`/`uuid`; ARCHITECTURE §12), 64 hex characters, fresh per start, compared in constant time (`constant_time_eq`, no early exit, walks the longer input). Never in `Debug` output.
- **Limits**: 32 authenticated connections (M4.15f: a window and a spare per open workspace, at most 8, plus the app connections), 8 still upgrading or waiting for `hello` (more are closed at accept). Refusals are logged (`warn`, through the control inbox as `Inbox::Log`) at most once per `refusal_log_interval` (10 s) with a count: the first at once, the ones inside the interval once it has passed (by a timer, even if no connection follows), so a UI that cannot connect because something holds every slot can be diagnosed without one entry per attempt and every refusal is counted. Up to 64 requests in flight per connection (until their `result` is written): beyond that the server stops reading the socket, so TCP holds a flood back instead of the inbox growing.

## Connection

1. **Upgrade and `hello` within `hello_timeout` (5 s) in total.** Before `hello` is accepted the socket delivers at most 16 KiB (the upgrade request plus the 4 KiB hello); the WebSocket library would otherwise buffer a whole 1 MiB message before anyone looks at it. The first frame is decoded with `decode_hello` (4 KiB).
2. Refusals are an `error` message, then close: wrong token or any other message first -> `bad_token`; version differs -> `protocol_version_mismatch` (token is checked first); unreadable or oversize hello -> `bad_request`. A hello over 16 KiB, a timeout or a closed socket just closes.
3. On success the connection is registered with the fan-out, bound to the doc its `hello` names (`workspace`) or as an app connection, then the server asks the control loop for a snapshot with a request of its own (id `u64::MAX`, **reserved**: a client using it gets `bad_request`; its `result` is swallowed) and answers `welcome { doc, snapshot }`. On an app connection the same request answers the `workspaces` list and the server answers `welcome { workspaces }`. A doc that is not open answers the request with `no_workspace`, which the server sends as an `error` before closing. Broadcasts made in between are queued and filtered: a `model_changed` at or below the snapshot's revision and a `runtime` at or below its `runtime_seq` are not sent. `document`/`warnings` queued from before the snapshot may arrive after it; the last one before the snapshot equals the snapshot's own state, so the client ends up right.
4. After `welcome`: client frames are decoded with `decode_client` (1 MiB; the WebSocket layer enforces the same limit while reading) and `command`/`transport`/`undo`/`redo`/`request`/`close`/`panic`/`hotkey` go to the control inbox as `Inbox::Conn { doc, .. }` (the connection's doc, `None` for an app connection) with the connection's reply channel; a `transport`, `panic` or `hotkey` is announced first as an `Inbox::Trigger` (`ui`) for the show log. An unreadable frame gets `error` (`bad_request`, or `unknown_message` for an unknown `type`) and the connection stays up; 32 in a row (any good frame resets the count), a frame over the limit, or a socket error close it. Binary frames are `bad_request`. A second `hello` is `bad_request`.
5. `goodbye`: the connection closes. With `shutdown: true` the message is also forwarded to the control inbox, which stops the show and ends the loop (docs/control.md). The server does not exit the process: `host::run` returns when the control loop ends (after the final recovery writes), removes `engine.json` and the process exits (docs/control.md "Process lifecycle").

6. **An app connection that ends without `goodbye`** (M4.9; ARCHITECTURE §8: the UI crashed, or its connection died) is logged (`warn`, "the app's connection closed without goodbye ..."); playback goes on. With `ServerConfig::relaunch` (the host sets it for `--relaunch-app BUNDLE_ID`) a task waits `Relaunch::delay` (1 s) and then, unless an app connection is registered again (`Hub::app_connections`) or the server is stopping, runs the relaunch action on a blocking thread (`open -b <id>` on macOS, `platform::relaunch`; it brings the app to the front, which an app relaunched after a crash needs on macOS 14+ for keyboard GO to reach it), at most 3 times in any 60 s (`net::relaunch::Budget`; beyond that an `error` log record and no relaunch) and one waiting at a time. **An app that still runs is not relaunched** (#168): an app connection's `hello` `pid` is noted with that process's name (`platform::relaunch::process_name`, libproc `proc_name`; the latest app connection's wins, and no `pid`, or no process with it, notes nothing). While a process with that pid and name lives (the app is reconnecting slowly, or hung), the check finds the app alive and waits another `Relaunch::delay`, again and again (logged once, `warn`, "the app (pid N) is still running ..."), until an app connection is back or the server stops (nothing to do) or the process is gone (relaunch, through the budget). `open -b` on a running app would only pull it to the front mid-show. The name check keeps a pid reused by another program from counting as the app; another openLab process at the same pid would itself be an app, so waiting for it is right. Off macOS no name is known and the app counts as gone (relaunching is not available there yet). A connection bound to a doc (a window) never relaunches anything; a `goodbye` (with or without `shutdown`) is not a crash. Tests: `tests/net/ws.rs` (goodbye and a window's drop: nothing; the app connection's drop: logged and relaunched; an app whose process runs: waited for, relaunched once it is gone), `relaunch.rs` (`next`, the pid-and-name identity), `platform/relaunch.rs` and `hub.rs` unit tests.

## Ordering and gaps

- The server keeps a **per-connection** order: broadcasts are written before replies, and a `result` carrying `ok.revision = N` is **held** until the `model_changed` for N (or a snapshot at N or later) has been written; it is in the connection's queue or about to be, as the control loop puts it on the outbound channel first. The connection keeps reading client frames and serving other replies meanwhile (a GO is not delayed by a held result); results may therefore leave in a different order than they arrived, which the protocol allows (clients match them by `id`). If the `model_changed` never arrives (the control loop's outbound channel was full and dropped it, docs/control.md "Outbound") the result goes out after `revision_wait` (2 s); the client sees `result.revision` ahead of its own model and requests a `snapshot`.
- **Snapshots never go back in time.** While a request that answers with a `snapshot` is out (the server's own, or the client's `snapshot`, until its `result` arrives) the connection forwards no broadcasts: they wait in its queue, and are filtered against the snapshot's revision and seq once it has been written. So a `model_changed` made after the control loop took the snapshot can never reach the client before it. Held results wait for the snapshot too (it covers them: the control loop answered them before taking it). As a second line, a snapshot behind what the client was already sent (revision or seq below the connection's: stale, or the numbering restarted) is followed at once by a fresh one (the connection marks itself lagged). It is not dropped: after a restart of the numbering the fresh one would be behind too and never get through.
- **Each connection gets its own doc's broadcasts (M4.15f).** The control loop tags every broadcast with its doc (`Outgoing { doc, message }`); the hub offers a doc's to the connections bound to it, the engine's own (`log`, `log_entry`, `status`) to every connection and `workspaces` to the app connections only. `revision` and `runtime_seq` are per doc, so a connection's filter only ever sees one numbering. Opening a doc sends no snapshot to anyone (M4.4a's broadcast snapshot of a replaced workspace is gone with replacing): a connection bound to the new doc takes its snapshot in `welcome`. A doc's `snapshot` broadcast is sent only when its model changed in a way no `model_changed` says (a save-as to another folder re-spelled media references); a connection takes it unless it already holds that revision and seq. The hold for an outstanding snapshot request is bounded: after `snapshot_wait` (60 s, `ServerConfig`) without the `result` the connection drops the hold and takes a fresh snapshot.
- **Closing a doc closes its connections.** `closed { doc }` reaches each connection bound to it (`Kind::Closed`): the connection writes its held results and the replies already in its reply channel (the control loop answers the `close` before it broadcasts `closed`, so the requester has its `result`), then `closed`, and ends. A connection that lagged meanwhile (its queue, and the `closed` in it, thrown away) learns it from its resync: the snapshot request of a closed doc answers `no_workspace`, and the connection writes `closed` and ends then.
- A `snapshot` message resets the connection's filter to its revision and seq. Revision/seq gaps in broadcasts are **forwarded as they are**; clients recover with `request: snapshot` (protocol section 2).

## Slow clients

Each client has its own bounded queue (`CLIENT_QUEUE`, 1024 messages). The fan-out task encodes a message once (outside the lock on the client list) and `try_send`s it to every queue; it never waits for a client.

- `meters`, `progress`, `status`, `log_entry` and `log`: dropped for a client whose queue is half full or more, never marking it lagged (a `log` notice is also a show-log record, which `log_tail` still has).
- A state message (`model_changed`, `runtime`, `document`, `warnings`) that does not fit marks the client **lagged**; the same happens when a message cannot be encoded or exceeds `MAX_SERVER_FRAME_BYTES` (32 MiB). A lagged client is **not closed**: its queue is thrown away, broadcasts for it are skipped, and the server sends it a fresh `snapshot` (asked from the control loop like the first one, with broadcasts held back as above) as soon as its connection task runs and no other snapshot is out; later broadcasts are queued again before the snapshot is requested and filtered against its revision. A client whose snapshot itself exceeds the cap gets `error internal` and is closed. A `result` without a revision may overtake the snapshot during such a resync.
- A client that stops reading entirely stalls its TCP write; a single write that makes no progress for `write_timeout` (10 s) closes the connection. Meanwhile it costs the control loop and the other clients nothing (tested with 1500 x 16 KiB messages).
- Dead peers: a `ping` every `ping_interval` (10 s); a connection that has sent nothing (a `pong` counts) for `dead_after` (30 s) is closed.

## OSC on this runtime

`ServerConfig::osc: Option<OscConfig>` (default `None`; `host::run` sets `Some(OscConfig::default())`) starts the OSC sockets on the same two-thread runtime. They are bound before the tasks start; a bind failure (port in use) sends a warning through `Inbox::Log` and leaves OSC off while the WebSocket server starts normally (`WsServer::osc_ports()` is `None`). Tests set `port: 0`, `bind: 127.0.0.1` and `reply_port`. Other `OscConfig` fields: `max_tcp_connections` (256), `max_tcp_connections_per_host` (16), `max_inflight` (unanswered requests to the control loop, 2048), `duplicate_window` (identical messages from one peer closer than this are dropped, 100 ms like QLab; the tests set zero), `write_timeout`, `tcp_idle_evict`, `max_input_age` and the log intervals.

The fan-out task also offers every doc's `model_changed`, `runtime`, `document`, `snapshot` and `closed` broadcasts, tagged with their doc, and the `workspaces` list to the OSC task through a bounded **tap** (`hub::Tap`): the OSC side keeps a copy of each open doc (M4.15h, [osc.md](osc.md) "Listeners"). A full tap marks the OSC task lagged, which then rebuilds every copy (the list of open docs, then each doc's snapshot), exactly as a lagged WebSocket client does. The OSC task asks the control loop as an app connection (`Inbox::Conn { doc: None }`) for the list and as a bound one (`doc: Some`) for each snapshot and every input, with its own reply channel and ids from 2^63 up. Everything else (queues, caps, counters, TCP limit and idle eviction) is in [osc.md](osc.md) "Listeners". `net/hub.rs` has unit tests for the tap; `osc_mirror.rs` for the workspace copy.

## Tests

`tests/net/ws.rs`: real sockets against a stand-in control thread (auth success, wrong token, wrong version, other message first, hello timeout, 4 KiB and pre-auth caps, handshake limit, connection limit and its single log entry, refusals after the first log flushed once the interval passes, result ordering over 200 commands, lost `model_changed`, frames read while a result is held, two clients, welcome filtering, gap and snapshot recovery, a requested snapshot never after a newer `model_changed` (the stand-in holds the snapshot answer until the newer `model_changed` is in the connection's queue), a stale snapshot replaced, a 2,000-cue group upsert, over-cap message resync, queue overflow -> snapshot -> filtered broadcasts, stalled client, malformed and abusive frames, goodbye, keepalive, dead client, stop). `net/hub.rs` unit tests: meters/progress dropped at half full, overflow marks only that client lagged. `tests/net/docs.rs` (M4.15f): the real control loop over real sockets: two docs isolated (each bound connection sees its doc's changes only, per-doc revisions; the app connection follows the list and its dirty flags; workspace messages on it answer `no_workspace`; the app-scope panic on any connection), closing a doc sends `closed` after the requester's result and closes its connections (a bound `hello` to it is refused `no_workspace`), `already_open` and a copy's fresh id. `net/hub.rs` unit tests also cover the routing by doc and the tap following the first doc. The multi-doc OSC rules are in `tests/osc/docs.rs`; the server in front of the real `runner::run` loop is `tests/net/session.rs`. `tests/net/osc.rs`: the OSC listeners over real UDP/TCP sockets (GO over each, replies at the reply port, SLIP framing across reads, passcode (`denied` over both), QLab's update messages over UDP and TCP, repeats within the window, large UDP and TCP replies, a 900 KB TCP message, the pending-write cap, `/version` and `/workspaces`, gaps and passcode changes, TCP cap, malformed input, in-flight cap, bind failure, and a GO in front of the real control loop). Timeouts in the tests are hang guards; the server's own timers are shortened through `ServerConfig`.
