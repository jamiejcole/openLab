# openLab control loop (`openlab-engine::control`)

The engine's control thread (ARCHITECTURE §3.1, §3.2): it owns the workspace, its undo history, the cue engine and the mixer controller, and wires them to the disk streams. Contracts it follows: [cue-engine.md](cue-engine.md) "Actions for the binary (M4.2 contract)", [audio.md](audio.md) "Threads and queues", [protocol.md](protocol.md). Status: M4.2a and M4.2b (devices: [Devices](#devices-m42b-nfr-08)), M4.4 (documents: [Documents](#documents-m44)).

## Shape

- `Control` holds the state and logic and has **no thread or clock of its own**. Time is the mixer's sample counter (`MixerController::samples_rendered`), whoever advances it. Two drivers call the same `Control::handle(inbox message)` and `Control::tick()`:
  - `runner::run(control, &inbox)` — the control thread against a running device (`host::run` opens the default device and starts the loop with no doc open; `openlab-engine --open SHOW_FILE` opens a show through the same `open` request a client sends);
  - `offline::OfflineShow` — the offline render driver (ARCHITECTURE §3.6): render one block into memory, then tick. Tests drive it step by step; no sleeps, no wall clock.
- **Engine and docs (M4.15d, M4.15e).** `Control` is an `Engine` shared by every open workspace plus its `Doc`s, in open order, at most `MAX_DOCS` (8, REQUIREMENTS §21; ARCHITECTURE §3.1). `Engine`: the mixer controller and its clock (`block`, `now_floor`, stall tracking), the `Backend` and playable devices, the disk streamer, the voice-id allocator and owner map (`VoiceIds`), the patch-slot allocator (`Patches`, keyed `(DocId, PatchId)`), machine settings and their writer, the document worker and `SaveWriter` (`Docs`: one read at a time, autosave removals and closed docs' saves in flight), the probe pool (`ProbePool`: the workers, their watchdog and the volume gate), the one media watch (`WatchShare` over `MediaWatch`), the PB-10 override flag and the look-up thread bound (`LookupThreads`), the outbound channel, mixer meter reads and health counters, the show log and status (`Observe`, its logged cue states keyed by doc). `Doc`: its `DocId`, the workspace, `History`, `CueEngine`, `Voices` (the voice table), `MediaCatalog` (entries, budget, cue index; jobs to the pool through a `PoolHandle`), `PlanChecks`, `NetOut` (its send threads), the show path and file state (`DocFile`), revision, saved revision, `runtime_seq`, deferred feedback, the mixer events routed to it this wake, warnings and resend flags. Per-doc logic runs on a `DocCx` (one doc with the engine). **`DocId`** (`u64`) is handed out in open order from 0 (the first doc, the one `Control::new` builds) and never reused, so a late answer or event of a closed doc cannot be taken for another's. **One wake** (`Control::tick`) runs the engine-wide steps once whatever the number of docs, zero included: the device (a loss or return acts on every doc), the mixer's events drained and handed to the doc that owns each voice (`VoiceIds::owner`; an event of a voice no open doc owns is dropped), the catalogs' key changes and the watch's batches (each event to every doc watching its file), the watchdog and notices of the watch, one meter read when a report is due (`MeterRound`); then each doc's tick (its routed events, streams, deadlines, priming, progress and its share of the meter read, warnings, saves); then the probe watchdog (a stuck probe reported unplayable in the doc that asked), slots freed since handed to docs waiting for one, the document worker's watchdog, autosave removals, closed docs' saves, settings, health and status, `pump`. `Control::wait_hint` is the shortest wait any doc asks for (each doc's next deadline or deferred report, at most `MAX_WAIT`; `MAX_WAIT` with no doc), floored after a stalled tick as before. Worker answers are tagged with their doc (`Inbox::Probe(doc, _)`, `Inbox::Net(doc, _)`) and dropped for a doc closed since; a document worker answer names its request (one read at a time), and the request its doc. **Client messages** (M4.15f) come as `Inbox::Conn { doc, .. }` from a WebSocket connection or the OSC side (M4.15h: it sends each doc's inputs and snapshot requests bound to that doc, and asks for the list of open docs as an app connection): bound to `doc`, or the app connection (`None`); `Inbox::Client` (tests, the offline driver) addresses the first open doc. `Control::app_scope` takes the app-scope messages first, whoever sends them (`new`, `open`, `open_recovery`, `scan_recovery`, `list_devices`, `log_tail`, `set_output_overrides`, `close`, `panic`, `hotkey`); the rest go to the sender's doc (`no_workspace` with none: an app connection, a closed doc). Every broadcast goes out as an `Outgoing { doc, message }`: a doc's reports tagged with it, the engine's own (`log`, `log_entry`, `status`, `workspaces`) with `None`. The test API (`Control::open_doc`, `close_doc`, `handle_doc`, `panic_all`, `hotkey`, `hotkey_released`, `doc`, `doc_ids`, `workspace_list`; `OfflineShow` wraps them, `send_app` and `send_doc` send as an app or a bound connection) addresses any doc. See [Several docs](#several-docs-m415e) below.
- `Backend` is what only a device has (`Device(devices::Device)` or `Offline`): the device list, loss and reopen, and the allocation-violation counter.
- The loop logic never reads the wall clock, except the device policy (reopen backoff, list polling, the device watchdog: [Devices](#devices-m42b-nfr-08)) through an injected `WallClock`, and the probe watchdog. Otherwise the only wall-clock value is how long `runner::run` waits on the inbox (`wait_hint`).

## Threads

| Thread | Owns | Talks via |
|---|---|---|
| control (`openlab-control`) | `Control` | crossbeam-channel inbox in; bounded outbound channel (`OUTBOUND_CAPACITY` 4096, a tokio `mpsc` channel: `outbound_channel`) out; `MixerController` (SPSC) to the audio thread |
| probe workers (`openlab-probe-N`, `PROBE_WORKERS` = 2 for the engine, every doc's jobs) | `probe`, `preload_within` | two job channels from control (high priority first), each job tagged with its doc; answers through the control inbox (`Inbox::Probe(doc, _)`) |
| document worker (`openlab-docs`) | reading shows, `check_recovery`, `scan_recovery`, clearing recovery files, writing `settings.json` | job channel from control; answers through the control inbox (`Inbox::Doc`) |
| writer (`openlab-writer`, `persist::SaveWriter`) | serialising and writing saves and autosaves | `save` / `autosave` from control (a cloned workspace); the control loop polls the answer channel each tick |
| device (`openlab-device`) | the device layer (cpal) and the open stream | job channel from control (open, close); answers through the control inbox (`Inbox::Device`) |
| device list (`openlab-device-list`) | the device lister | list requests from control; answers through the control inbox (`Inbox::Device`) |
| disk workers (`DiskStreamer`, 2) and openers (4) | decoders, resamplers, rings; openers only open stream files | `prepare` from control (no I/O); `StreamHandle` atomics back |
| audio (device) / caller (offline) | `Mixer` | SPSC queues, atomics |

**The control thread never touches the disk.** Reading and saving shows run on the document worker and the writer thread ([Documents](#documents-m44)). Probing a file decodes it whole (seconds for a long compressed file) and preloading decodes it into memory, so both run on the probe workers; `DiskStreamer::prepare` does no I/O (an opener thread opens the file, never a disk worker, so a hung open stalls only its own stream; docs/audio.md). Tested with a probe held on a stalled volume (gated): the loop keeps ticking and a GO meanwhile does not block (`control/media.rs::the_control_loop_never_waits_for_the_disk`). A named pipe or device chosen as media cannot stall a worker: media opens refuse anything but a regular file at once (`MediaError::NotAFile`, docs/audio.md; the cue shows `media_unsupported`, `a_fifo_as_media_breaks_its_cue_at_once`). Tests stall a stream's open through `StreamerConfig::before_open` instead (feature `test-support` only, never in a shipped build: `scripts/rust-checks.sh clippy` fails if a test-only feature reaches the shipped engine's dependency graph). Only the offline driver waits for the disk, outside `tick` (below).

## Inbox and replies

`Inbox::Client { message, reply }` carries a `ClientMessage` already decoded and authenticated by the network layer (docs/network.md). Every `command`, `transport`, `undo`, `redo` and `request` gets exactly one `result` on `reply`; broadcasts go to the outbound channel. Both are tokio channels (`reply_channel`: unbounded; `outbound_channel`: bounded, `try_send`), so the network layer's tasks wait on them without threads of their own while the control thread only ever sends without blocking. `Inbox::Log { level, message }` is a log entry from the network layer (refused connections), sent out like the loop's own `log`. `Inbox::Probe` is internal feedback; `Inbox::Shutdown` (or `goodbye { shutdown: true }`) ends the loop, which then hard-stops the show (two Panics).

- **Transport** → the cue-engine input of docs/protocol.md's table (`hard_stop` = `Stop { fade_out: None }`; `stop_all` and `hard_stop_all` = `StopAll`, `panic_cue` = `PanicCue`), handled at once; `result` ok means "handed to the cue engine".
- **Command / undo / redo** → `History` on the workspace through its write guard, which tells the cue engine `model_changed_cues(footprint)` (`model_changed()` when the edit also touched settings, patches or cue lists: `Footprint::is_model_wide`; see [Model changes](#model-changes-m41a)), then `MediaCatalog::sync_cues(footprint)` before the engine's next call (M4.2 contract; M4.12a), one `model_changed { revision, upserts, deletes }` broadcast (below), a `document` broadcast, then the `result` with that revision, then one `Tick` so the edit takes effect now (a deleted running cue stops on the next block). A refused command changes nothing: `command_refused`. An undo or redo goes through `History::undo` / `redo` like a command; a step that removes an active cue is performed and the engine stops the cue as for a delete ([commands.md](commands.md) "Undo and redo while cues play"). `unsignalled_model_changes()` is checked after every engine call; a rise is logged as an error. A `RollbackFailed` refusal (a wrong inverse left the workspace partly changed; core cleared history) is treated as an edit nobody can undo: error log record, `revision += 1` (the write guard told the engine `model_changed()`: a failed rollback may have changed anything), `MediaCatalog::sync` (probe results kept), `sync_workspace`, `document` and a whole `snapshot` to every client, then the `command_refused` reply (`DocCx::partly_changed`).
- **Requests**: `snapshot` answers `snapshot` then `result`; `list_devices` answers at once from the last device list read (no device call on the control thread; offline: `ControlConfig::devices`); `relink` walks the folder on a thread of its own ([Relink](#relink-m117)); the document requests are [Documents](#documents-m44).
- **Ordering across channels**: a command's `model_changed` goes to the outbound channel before its `result` goes to `reply`. The network layer keeps that order per connection (docs/network.md: a `result` with `ok.revision = N` waits for the `model_changed` for N).

### Model changes (M4.1a)

**The cue engine is told of every edit by construction.** A doc's workspace and its cue engine live together in `DocModel` (`control/model.rs`), whose fields are private to that module: the rest of the loop reads them (`ws()`, `engine()`, `handle`) and writes the workspace only through `DocModel::edit()`, a guard that derefs to `&mut Workspace`. Dropping the guard calls `engine.model_changed()`; `touched(footprint)` (or `ended(footprint, result)`, which keeps the full signal for a `RollbackFailed`) ends it with `model_changed_cues(footprint)` instead, so an edit costs what it touched. A refused command, and one `History` reports as changing nothing (`Ok(false)`: a value set to what it was, an empty transaction, nothing to undo), ends with an empty footprint (core property-tests that `Ok(false)` leaves the workspace as it was), so a no-op a client repeats costs no rebuild, model-wide or not. `DocModel::new` tells a new engine of the whole workspace. Code that holds a `Doc` cannot reach a `&mut Workspace` any other way, so a forgotten signal does not compile; the check is O(1) per engine call (a flag). The paths through the guard: a command (paste included), undo, redo, a relink, the re-spelling of references after a save-as to another folder, an Arm/Disarm `SetArmed`, a copy's fresh workspace id at open; opening builds the `DocModel`. A footprint that misses a cue is not caught by the types: debug builds' edit cross-check counts it (docs/cue-engine.md, Model edits).

Every model edit (command, undo, redo, a relink command, an Arm/Disarm `SetArmed`) broadcasts exactly one `model_changed`; the revision rises by one per message, so a client that sees a gap requests a `snapshot`. A newly opened doc is a `snapshot` (in a bound connection's `welcome`), not a diff. A command refused by `History`, or an undo/redo with nothing to do, sends nothing.

The contents are derived from the edit, not by diffing workspaces. Commands touch cues by id and nothing else (`core::changes`): `Command::footprint()` lists the cue ids a command added, removed, moved or edited (a transaction: the union). For an undo or redo the footprint is that of the step about to be applied (`History::peek_undo`/`peek_redo`; the inverse is itself a command). `SetArmed` names the cues whose flag changed. After the edit, `model_changes(&workspace, &footprint)` reads those cues from the new workspace: one pass over the tree with ordered-set (`BTreeSet`) lookups, no per-cue allocation unless the cue is sent. A command whose footprint is empty (an empty transaction) changed nothing: no revision, no `model_changed`, no `document`, not dirty; the `result` reports the current revision. What is sent is O(cues named), not O(show): renaming one cue in a 2,000-cue show is one upsert.

- `deletes`: every removed or moved cue. Deleting movers first means a client never reasons about where a cue used to be, so several moves in one step (a transaction) land correctly applying `deletes` then `upserts` in order.
- `upserts`: every named cue that exists after the edit, at its final `(list, parent, index)`, in tree order (ascending within a container, parents first). A named cue inside another named group is not sent separately: the group's upsert carries its subtree. So the one case that costs more than the footprint is editing a group itself (rename, mode): its subtree travels with it, as the protocol defines a group upsert.
- A move is therefore a delete plus an upsert in one message.

Commands for settings, patches, network patches and cue lists (M1.12) add `Footprint::{lists, patches, network_patches, settings}`; `model_changes` sends `settings`, `cue_list`, `patch` and `network_patch` upserts (every item of a collection that was reordered, at its final index) and deletes, before the cue upserts. Such an edit is `Footprint::is_model_wide`: the control loop tells the cue engine with `model_changed()` (patches decide which cues are broken, lists own playheads), not `model_changed_cues`, and `sync_patches` brings the mixer matrices (with the workspace master in them) and delays up to date.

A command with `coalesce` goes through `History::execute_coalescing`; a key over 128 bytes is `bad_request`. `History::execute` says whether anything changed: if not (a value set to what it was, an empty transaction) there is no revision, no `model_changed`, no `document`, and the document is not dirty.

**Patch slots (M4.2f, M4.15b, M4.15e).** A patch's mixer matrix (slot) is allocated by `(DocId, PatchId)` (`Patches`, `control/patches.rs`; one free list for every doc, the least recently freed first; a slot belongs to one doc's patch at a time, so only that doc's voices can hold it back; a closed doc's slots are zeroed and freed at once, and a doc whose patches waited for one syncs again on the next wake), not by its index in `Workspace::patches`, so inserting, removing or moving a patch, and the undo or redo of it, is allowed while voices play and never re-routes or silences one. A voice keeps the slot its `VoiceStart` named until it ends, except that **a playing cue edited to name another patch follows it** (#293, `Voices::follow_patches`, run after every `sync_patches`, so after every edit, undo and redo): its voice (started, paused or stopping; not a preview, which keeps its patch as it keeps its levels) gets `MoveVoice` to the new patch's slot, dated no earlier than its own start or resume, and crossfades there over the de-zipper (docs/audio.md). Cue outputs beyond the outputs of the patch the voice started on were silenced at its start; those the new patch has get their levels first (`Ramp`, de-zippered): the model's, with their crosspoints, except a level a Fade cue has set, which the voice already has. A new patch with no slot (none free) leaves the voice where it is until a later sync gives it one. The slot it left stays in use (`VoiceRec::former`), since its crossfade may still play through it, until the mixer reports the voice settled after every move sent for it (`MoveEnded` with `moves` equal to the `MoveVoice`s sent; a move still on its way makes the counts differ) or the voice ends; a lost report only keeps the slot until then. The next wake's reclaim hands the slot on (`a_slot_a_move_left_is_handed_on_once_the_crossfade_ends`). A resize of the cue's own patch is not a patch change: the resize rule below applies. Tests: `control/live_levels.rs` (`a_playing_cue_follows_its_patch_change_without_a_click`, `outputs_the_new_patch_adds_…`, `a_faded_output_keeps_…`). `Voices::slots_in_use` lists the slots of every voice the mixer may still hold (started, paused, stopping; previews and orphans included). The rules, applied on every `sync_patches`:
- A patch keeps its slot while it exists. A new patch takes the least recently freed slot (at open, patch `i` gets slot `i`); with none free it is `unmapped` and listed as a `mixer_patches_exhausted` warning until one frees (a mixer has `ControlConfig::mixer_patches` slots, 64 in the engine). A slot just handed to a patch (every slot of a newly opened doc, or one another patch freed) takes its gains at once (`SnapPatch`) instead of ramping from what it held before, so a cue started or moved onto it on that sample is heard on its own patch's outputs only (`tests/control/live_levels.rs::a_slot_handed_to_another_patch_takes_its_routing_at_once`).
- A removed patch's slot is **retired** while a voice uses it: it keeps the routing it had (still scaled by the workspace master, which applies to everything the workspace plays) and follows no other edit. When no voice uses it any more it is zeroed and freed; the loop checks on every tick (`reclaim_slots`, only while a slot is retired) and syncs again, so a patch waiting for a slot gets it then. A patch that comes back with the same id and output count while its slot is still retired (an undo) takes that slot again. A slot is never handed out while a voice may play through it.
- **Resize** (channel count or outputs) while a voice plays through the patch's slot: the voice keeps the layout it started with (the old slot is retired as above) and the patch moves to a fresh slot, so the next start uses the new layout. The edit therefore never silences or re-routes audio already sounding; it applies from the next start. Only the layout is frozen: while the patch exists, every sync rebuilds the retired slot's first `min(old, new)` outputs from the patch's current master, levels, mutes and polarity, and from its current device mapping when that resolves (`mapped`; otherwise the channels it had when the slot was retired), so muting an output or pulling the patch master down still reaches the playing cue (`Patches::retired_base`). Outputs the patch no longer has keep their last gains (nothing controls them any more, and cutting them would change what is playing); the workspace master still applies to them. With no voice on the slot the resize is made in place. (With no slot free the resized patch waits as above. QLab 5's behaviour for a patch resized under a playing cue is not known; this is openLab's rule.)
- Level, mute, polarity, master and device-mapping edits apply to the slot in place, so to the voices already playing through it, as before. Output delays are per device output and follow only the patches in the workspace (a retired slot's delay goes with its patch).

`Workspace::apply_changes` is the reference client: deletes (an unknown id is ignored), then upserts (a cue already present is replaced wherever it is). Tests (`core/tests/commands_prop.rs`, `engine/tests/control/model.rs`) assert mirror == engine workspace after every step of random command/undo/redo sequences.

## Time and wake rules (ARCHITECTURE §3.2)

- `block` = frames per device callback (the device's buffer, else the mixer's `max_block_frames`); offline: the step size.
- `now = samples_rendered + block`: the earliest sample a command can still hit. `EngineConfig::lookahead = block`, so a call commits the deadlines in `now .. now + block` (end excluded) — exactly the next block — and no voice start is ever scheduled beyond it.
- `tick` runs `Input::Tick` only when `engine.is_due(now)`.
- `runner::run` waits on the inbox until a message comes, the next deadline enters the window, a deferred report becomes due, or `MAX_WAIT` (5 ms), then ticks. Wake jitter never shifts audio: every transition is computed from sample time.
- **No spin on a stalled clock (M4.2j).** `wait_hint` is the distance, in frames, to the sample where the deadline enters the window; it assumes sample time moves continuously. It moves in whole blocks, and a device that stalls without an error (up to the watchdog limit, 3 s) does not move it at all, so a deadline one frame outside the window gave a one-frame hint (125 us at 8 kHz, 21 us at 48 kHz) over and over: a full tick per wake, a spin. Never zero: a due deadline is consumed by the tick that sees it. Now, when the last tick saw `samples_rendered` unchanged since the tick before, the hint is at least `stall_floor`: 1 ms (`MIN_STALL_WAIT`), or a quarter of the device block if that is shorter (a 64-frame block at 48 kHz: 0.33 ms). This applies whenever the last tick saw no progress, so also to the wake between two ordinary callbacks. The first wake after a tick that saw progress is not floored, a message ends any wait at once (GO is never delayed), and a device outage (`is_down`) keeps its `MAX_WAIT` hint. Test: `control/timing.rs::a_frozen_sample_clock_does_not_spin_the_loop`.
- `EngineConfig::seed` comes from `entropy_seed()` (std's OS-seeded `RandomState` over the time and process id), so random groups differ between runs; tests pass a fixed seed.

Each `tick`: probe answers to the engine (one `Availability`), voices that waited for them; mixer events; stream failures; deferred feedback that is due; `Tick` if due; priming; progress and meters (≤ 30 Hz); the workspace warnings list if it changed; health counters; `MixerController::pump()` (every tick, docs/audio.md).

## Voices

Each run segment gets its own mixer `VoiceId`, allocated by the loop from one engine-wide counter (`VoiceIds`, outside the voice table, shared by every doc, M4.15e) and **never reused**; each id is recorded with the doc it was taken for (`owner`), so the mixer's events, which name only voices, are handed to that doc (an event of a voice no open doc owns is dropped), and an id is forgotten once its doc's table no longer knows it (checked after each meter read) or the doc closes (a later workspace's engine starts its `RunId`s again; its voices can never be taken for an old one's). `RunId ↔ VoiceId` are kept in both directions.

| Action | Carried out |
|---|---|
| `LoadVoice { run, offset }` | slice table, `prepare` (or wait for the probe); kept as the run's stream |
| `UnloadVoice` | the stream is dropped (cancelled) |
| `StartVoice { run, at, offset }` | the loaded stream, else the cue's primed one (offset 0), else a fresh `prepare`; `VoiceStart` with the model's levels; `StartVoice` at `at`; for a finite table, `Input::ActionLength { frames: offset + table frames (+ delay if held) }` back to the engine, which then owns the end as a deadline (auto-follow and playlist moves on the exact end sample; docs/cue-engine.md); an offset at or past the end of the table is an empty plan: nothing plays and `ActionLength { frames: offset (+ delay if held) }` ends the action on its start sample (M4.11b) |
| `StopVoice { at, fade }` | mixer `StopVoice` (fade with the curve); the record goes with the `VoiceFinished` |
| `PauseVoice { at }` | mixer `PauseVoice` (native pause, M3.18: position and ring kept) |
| `ResumeVoice { run, paused, at }` | mixer `ResumeVoice { voice: old, new_id }` re-keys the voice to a fresh id for the fresh run |
| `Ramp` | mixer `Ramp` (`Master` / `CueOutput` / `Crosspoint`), no gangs (a Fade's values, and a level edit's, are already per output). Ramps come from Fade cues and from level edits on a playing cue (docs/cue-engine.md, "Level edits on a playing cue"): the loop carries them out alike, one fixed-size mixer command each, through the queue every command takes |
| `DevampVoice { stop }` | mixer `Devamp` |
| `PreviewStart` / `PreviewStop` | as `StartVoice` (offset 0, never a primed stream) / `StopVoice`, on the cue's own patch until PB-09's audition output (M2.21) |
| `SetArmed` | applied to the model through its write guard (the engine is told of that cue) before the engine's next call, then a `model_changed` broadcast with an upsert of each cue whose flag changed |

- **Routing** (`VoiceStart`): master `master_db`; cue output `o` at its level (muted or beyond the patch's outputs: silent); listed crosspoints (muted: silent); the patch's mixer matrix; the integrated fade-in (none when starting part way in) and fade-out. dB → gain with core's `db_to_gain` (the mixer's conversion). Levels are read once, at the start; an edit while the voice plays reaches it as `Ramp`s from the engine (M5.9b), never as a restart.
- **Slice table**: `plan::cue_slices` turns trims, markers and play counts into `plan_at_rate`'s table (markers outside the trims are dropped; the slice the out point falls in plays as the marker that ends it says), then skips `offset` frames of the action with loops unrolled. An offset at or past a finite action's end plays nothing: the action ends on its start sample. A table that cannot be built (`LoopTooShort`, M3.17, or bad markers) fails the run (`StartFailed { stream_failed }` when the cue was started, so it is skipped; `ActionFailed { stream_failed }` when it was only loaded; a `bad_plan` notice) and is listed in the workspace warnings as soon as the file is probed (the pre-show view; a `CueProblem` for it would need core and protocol changes, #410).
- **Waiting for a probe**: a start (or load) whose file has not been probed yet waits; commands for it (ramps, devamps) are queued and replayed after the start, a pause holds it, a stop drops it. A held start sends a `probe_wait` notice at once. When the probe answers it starts at `max(start, now)` from its head with a `cold_start` notice (and its delay counted into its `ActionLength`); a failed probe fails the run. A start still held after `PROBE_HOLD_LIMIT` (5 s of sample time) fails (`StartFailed { stream_failed }`: it never played, so the cue is skipped and its auto-follow fires; a `probe_timeout` notice): the cue goes broken instead of showing as running with no sound. It stays broken (a run-time break) until it is reset or started again; a late probe answer clears the file's static problem but does not restart it.
- **A stream that never opens** (its volume hangs after the probe: a dead network share, a stalled USB disk): the voice starts cold and plays silence while the open waits, holding one opener, never a disk worker, so every other stream keeps refilling (docs/audio.md, Disk streaming). A started voice whose stream is still not primed `STREAM_START_LIMIT` (5 s of sample time, paused time not counted) after its start is stopped at once with a `stream_timeout` notice, and its run fails when the mixer reports the end (`StartFailed { stream_failed }` when nothing was written: the cue is skipped and its auto-follow fires), so it never plays late if the volume answers. A cue shorter than the limit has already completed on its planned end by then (as any underrunning cue does); its silent voice is stopped with the same notice. Tested in `control/media.rs::a_start_whose_open_hangs_fails_after_five_seconds`; an open that answers within the limit plays late as before (`stalled_tail`).
- **Probe order and stuck workers**: probes go out in workspace order on a low-priority queue; every priming pass (playhead move, edit, probe answer) puts the files of the cues it wants primed on the high-priority queue, which the workers always empty first, so after a restart mid-show the cue at the playhead is not behind a hundred others. A worker busy on one file longer than `probe_timeout` (`PROBE_TIMEOUT`, 30 s, wall clock: the only wall-clock rule in the loop) is abandoned and replaced, at most `MAX_ABANDONED_WORKERS` (16) times (reaching the limit is logged once as an error; further stuck probes then just wait, and their starts fail after the hold limit); a replacement that cannot be started (out of threads) is logged as an error once (`could not start a media probe worker (...); N of 2 running, retrying`) and tried again every tick until the pool has its workers again (logged at `info`); its file is reported `unsupported` ("could not be read in time") meanwhile, and a late answer still counts. The abandoned thread is leaked, not joined: it ends when its read returns, if it ever does. A re-probe (after a stream failure) keeps the last answer, and so the cues' primes, until the new answer comes. **Stalled volumes (M2.25b)**: probes are scheduled per volume, a volume being the mount a path is on (`bucket_of`, as the media watch names them: `/Volumes/<name>`, `/mnt/<name>`, `/media/...`, a drive or share; everything else, the system disk included, is `/`, so all local files in the user's folders share one volume). **The system volume and the show file's volume are never gated**: `/` (it mixes the local disk with automounts and cloud folders), on Windows the system drive (`%SystemDrive%`, read once, `C:` if unset; compared without regard to case), and the volume holding an open show file (each open doc's; found from the show file's own path, so a show at the root of a volume counts; updated when another show is opened). Probes there run exactly as before (a stuck worker is replaced, a GO waits the usual 5 s). Only other volumes (removable drives, network shares, other mounts) can be stalled for probe scheduling. One slow probe is not a verdict on a mount (a 90-minute MP3 decodes end to end), so a volume counts as stalled for probe scheduling only when corroborated: the media watch reports it stalled (its state, `MediaWatch::stalled_volumes`, fed to the catalog every tick, and its `media_volume_not_responding` notice is the only notice), or two different files' probes are stuck on it (preloads never count; the engine log notes this at `info` only, in different words from the watch's notice, and when it answers). While stalled, the volume gets at most one trial job in flight; its other jobs wait in a deferred list (no worker taken, one job per file and kind, an urgent request stays urgent) and the files stay pending with any last answer: nothing is failed early, so a GO on such a file is held and fails by the usual 5 s hold limit. Jobs on healthy volumes always run. A trial that gets stuck stops blocking the next one: its worker is abandoned as above and the next trial waits 30 s, doubling to 5 min; a trial that fails with an I/O error waits the same way. Waiting files are never stranded: a stalled volume always gets its next trial after the backoff, and the first trial that answers clears the stall (stuck probes that never return are forgotten then), releasing every waiting job; a volume the watch sees healthy again stops being stalled at once. Any answer from the volume (even "file missing") ends the probe-side stall and releases every waiting job at once. `reset()` (a new workspace in the only open doc) forgets all volume state, and jobs still running from before cannot touch the new state (epoch); with other docs open the volume state is theirs too and stays, and only the resetting doc's claims and waiting jobs go (M4.15e), so a job that never returns (a FIFO, a hard-mounted share) cannot stall a volume for ever. A copy of a job a worker already took (the urgent copy priming sends) is dropped, keyed by (doc, probe or preload, file), so a probe and a preload of one file never shadow each other. Tests: `media.rs` unit tests (corroboration, trials and backoff, reset, watch-driven stall, the system drive and the show file's volume never gated, `/` never gated, a share that recovers while two reads never return, one slow file on `/`, a hung volume with many files) and `control/media.rs`: `a_dead_volume_does_not_starve_a_healthy_one_with_priming_on`, `slow_probes_on_the_system_disk_never_delay_a_short_file`, and a GO on a deferred file (held with `probe_wait`; plays if the share answers within the hold, else `probe_timeout` at 5 s). Decisions: docs/handoff/decisions/m2-25b.md.
- **Patches** (`Patches`): each workspace patch uses the mixer matrix (slot) allocated to its id ("Patch slots" above; no slot free: `unmapped`). Each patch is resolved with `resolve_patch` against the machine settings and the **playable** devices (the device the mixer plays on, with the mixer outputs that reach it; none during an outage; offline: `ControlConfig::devices`) and sent to the engine (`Availability` on open, `PatchStatus`-equivalent `Availability` on every change: edits, device list changes, loss, reopen). The engine plays on one device (REQUIREMENTS §21, AUD-03): a patch mapped to another device resolves `device_missing`. A mapped patch's matrix routes cue output `o` to its device channel at workspace master × (patch master × output level) (muted: 0; polarity: negative gain); everything else 0. Only changed matrix entries are sent. The workspace master is folded into the matrices, so the mixer's own master (`SetMaster`) is never sent and stays at unity: with several workspaces sharing the mixer (M4.15) each has its own master. At 0 dB the workspace master is exactly 1.0, so the gains, and the output, are bit for bit what they were when the master was the mixer's (tested); a master change ramps with the matrices' de-zipper, as `SetMaster` did.
- **Default patch mapping** (M4.4c, WS-07; QLab maps a new workspace's patches to the current output device): before each patch resolution (`sync_patches`: start, a doc opened, edits such as AddPatch, device back), every patch with **no mapping entry** on this machine gets, when a device is playable (the first of the playable list), a mapping to the device's outputs 1..N (`PatchMapping { device, channels: [0..N) }`) in `config.machine`. The machine settings are written (`SettingsWriter` thread, not the control thread; a failed write is a `warn` log) and an `info` log says `mapped patch 'Main Outputs' to <device> outputs 1–2`. A patch with an entry is never touched, so an operator's mapping is never overwritten. A device with fewer outputs than the patch needs (N) leaves the patch **unmapped** (silent, cues broken) with one `warn` log per patch and device (`device X has M outputs, patch 'P' needs N: left unmapped`); the next sync with another device or a bigger one (device back) maps it. No playable device (an outage, none listed): nothing is written and the patches stay `Unmapped` until the next sync with a device. A patch the operator cleared has an explicit empty entry (below), so it counts as having an entry and is not mapped. Tests: `tests/control/default_mapping.rs`, `tests/control/devices.rs`.
- **Setting a patch's mapping** (M4.4g, WS-07; `Request::SetPatchMapping { patch, mapping? }`, workspace-bound, handled by `Control::set_patch_mapping`): the operator remaps a show once on a new machine, or fixes a patch the default mapping left `unmapped` / `output_count_mismatch`. Validated first against `list_devices` (the device exists; one channel per output of the patch; each channel below the device's output count) and the doc's patches; a refusal (`not_found`, `bad_request`) changes and writes nothing. The machine settings are engine-wide, so the entry is keyed by the doc's **workspace id and patch id**, exactly as the default mapping stores it (two open docs with the same workspace id share it). It is written like the default mapping (settings thread; `info` log `patch 'P' mapped to <device> channels 1, 2`). `mapping` null clears: the entry becomes `{"device": "", "channels": []}` (stored, and the patch `Unmapped`), so the default mapping never re-applies to it; setting a mapping replaces it. A **clear** first pauses every Audio cue playing (running or fading) through that patch in each open doc with that workspace id (`DocCx::pause_cues_on`, an ordinary `Pause`), as QLab 5.5.3 does when a cue's device is set to none; mapping a device again does not resume them (the operator resumes). Then every open doc resolves its patches again (`sync_patches`), as for a device change: the mixer slot follows the mapping in place, so a cue already playing through the patch moves to the new outputs (a cleared or broken mapping is reported as `Availability`, same as a device edit today); idle and loaded cues show broken or playable from the new resolution, and `preshow_check` reports `unmapped` / `output_count_mismatch` for the app to offer a fix. A mapped device that later disappears is the usual device-loss handling. A mapping to a device `list_devices` names but the mixer is not playing on is refused (`bad_request`, naming the device in use): the engine plays on one device, so the patch would be silent with nothing to say why. While no device is playing (an outage) nothing can be compared and the mapping is accepted; it resolves `device_missing` until that device is back. A change that cannot be kept (a settings folder is configured but `settings.json` could not be read at start, so the engine leaves the file alone, or the settings writer is not running) is refused with `io` and changes nothing, instead of working until the app quits; a write that fails later on disk is still only a `warn` log. Tests: `tests/control/patch_mapping.rs`.
- **Output delays**: a patch output's `delay_ms` is a device-output setting (`SetOutput { delay_frames }`, rounded at the device rate; level, mute and polarity stay in the matrix). Each device output gets the delay of the mapped patch outputs routed to it, over every open doc's patches (one value per physical output; an openLab extra, QLab 5 has no output delay); patches that disagree, in one doc or across docs, get the longest and an `output_delay_conflict` warning in each doc that maps to that output (a doc's change makes every doc look at its notices again). Only changes are sent; an unmapped patch's outputs go back to 0.

## Priming (ARCHITECTURE §3.5)

After every playhead change, model change, probe answer and preload that lands the loop keeps primed (a stream prepared and filling, ready to start): from each list's playhead the next `prime_cues` (16) cues, the targets of those cues (a group target primes its audio cues), and every cue with a hotkey or OSC trigger — armed audio cues with media and no run, at most `max_primes` (64). A prime is used by a start from the top of that cue if the cue's file, probe, trims/slices and source (the file, or its preloaded samples) still match (a preload that lands re-primes the cue from memory); otherwise it is released. A start without one is cold: it is heard once its ring fills, with a `cold_start` notice, never a failure.

**Preload** (AUD-05): a file whose cue asks for it, or whose probe advises it (`preload_advised`: damaged files that seek slowly), is decoded into memory on a probe worker within the `preload_budget` (default 512 MiB; one budget for every open workspace together, M4.15e1); a file that does not fit streams and is listed as `preload_over_budget`, one whose preload fails (a decode error, memory) streams and is listed as `preload_failed`. Memory goes back when no cue uses the file. The catalog counts, per file, the cues that use it and the cues that ask for a preload, kept up to date from each edit's footprint (`sync_cues`; `sync` is the full pass for an opened workspace and the reference): a file that gains its first preload-asking cue is preloaded at once if it is already probed (otherwise when its probe answers), and one that loses its last (and whose probe does not advise it) gives back its budget and its samples; a voice already playing from the samples keeps them, and a preload job that answers after its release is ignored (M4.12b). Only a change of mind acts: a file that stays wanted keeps whatever its last attempt came to (an over-budget file is not retried when budget frees up elsewhere).

## Feedback

Mixer events, stream state and probe answers become cue-engine inputs:

| From | Input |
|---|---|
| `VoiceFinished` (current id) | `ActionEnded { cue, run, at }`; a failure instead if its stream failed (`StartFailed` if the stream wrote no frame, else `ActionFailed`, as below) |
| `VoiceFinished { Faulted }` (the mixer dropped the voice after repeated render panics, or a panic while applying a command to it) | a failure with `stream_failed`, as for a failed stream, also after a pending pause, plus an `audio_fault` notice for the cue; `health` logs the engine's `faulted_voices` count (`error`) |
| `VoiceFinished` dated after a pending pause (the voice ended as the pause applied; one dated on the pause sample left nothing to pause and is handled as an end, as the engine does, M2.34) | forwarded (the engine ignores it while paused); the record is kept, and the resume that follows reports `ActionEnded` with the **fresh** run on the resume sample (M2-E (a): the mixer ignores the resume of a voice it no longer has) |
| `VoiceFinished` under an old id after a resume was sent | the voice ended before the resume applied: `ActionEnded` with the fresh run, dated no earlier than the resume |
| `VoiceRejected` | `StartFailed { voice_rejected }` when the refused id is the one the start was sent with (the voice never played, also when a pause and resume were sent meanwhile), `ActionFailed { voice_rejected }` for a refused resume, which also stops the voice still paused under its old id |
| `StreamHandle::error` (polled every tick) | once per run, and the file is probed again (it may have gone or changed): `StartFailed { stream_failed }` if the voice never played (a started voice not yet in the mixer, or a stream that wrote no frame), else `ActionFailed { stream_failed }`; a loaded, unstarted voice reports `ActionFailed` |
| a start whose stream cannot be prepared (file gone or changed after its probe, a failed probe, a plan that cannot be built), or that the mixer cannot take at once | `StartFailed` (M4.14, QLab P5/G2): the cue is skipped, its auto-follow fires and a playlist moves on instead of halting (tested in `control/media.rs`) |
| `DevampScheduled` / `DevampIgnored` | `Input::DevampScheduled { at }` / `DevampIgnored` for the run the id stands for (an old id's run is stale and ignored by the engine); after `DevampScheduled` for the current id, the action's new `ActionLength` (position on `at` plus the table after the loop; `at` alone for a devamp stop; none while the rest loops for ever) |
| `MoveEnded { moves }` | no feedback; when `moves` equals the `MoveVoice`s sent for the voice, the slots it moved off (`VoiceRec::former`) are no longer in use (Patch slots, above) |
| `Underrun` | an `underrun` notice for the cue. A starved voice does not skip what it missed (docs/audio.md, Voices), so it ends later than its planned end; the engine keeps the planned end (the next cue starts on time, the late tail overlaps it) |
| probe answer | `MediaStatus` in one `Availability` per tick: `available` (damaged-but-playable included; its damage is listed in the warnings), `missing` (`NotFound`), else `unsupported { reason }` |

- **No feedback before its sample**: a report dated `at` (a re-reported end on a resume sample, the end of an empty action) is held until `now > at` (answers progress archive M2-E (c) for this binary: a voice event is never handed over at a `now` at or before the sample it reports; mixer events always report rendered samples, so they qualify at once).
- The id a voice had before its latest resume stays an **alias** until the voice is gone (an end before the resume applied comes under it); older ids are named for one more meter read only (one more entry after a re-key, docs/audio.md), so a cue paused and resumed many times keeps one alias.
- **Orphaned tails**: after an underrun a voice can sound past the end the engine completed its cue on (the cue no longer owns it). Panic, Stop All (`stop_all`, `hard_stop_all`), a hard stop (`hard_stop`, `stop` without fade) and Reset also stop every such voice in their scope (the whole show, or the cue and its descendants): Panic with a fade ending on the panic's end, the others at once. A cue's own panic (`panic_cue`) leaves such a tail to the cue's own end (rare; a later Stop All or Panic cuts it). Tested with a voice starved by a stalled disk worker (`control/media.rs`).
- The resume of a voice that had ended (re-reported with the fresh run) is now only reachable for an action whose length the engine was not told (a loop): with a known length the engine completes the action on its end sample before a pause dated there.

## Documents (M4.4, M4.15f)

New, open, open-recovery, close, save, save-as and autosave (`control/docs.rs`; contract: [protocol.md](protocol.md) "Opening and closing workspaces", file work: [persistence.md](persistence.md)). `new`, `open` and `open_recovery` open another doc beside the ones open ([Several docs](#several-docs-m415e)); nothing is replaced and there is no `revert` (QLab 5 has none).

- **Nothing blocks the control thread.** A save or autosave is a clone of the workspace handed to `SaveWriter` (tagged with the revision); the loop polls the answer channel on every tick (`docs_tick`) and answers the request when the file is written (`save`/`save_as` results come after the data is durable; a `document` broadcast with the new path and dirty flag goes first). Several saves of one file in flight collapse in the writer (the older answer is `Superseded`); the loop collects every answer first and then answers the older request with the outcome of the newest save of that file whose revision is at least its own (a save that finished meanwhile counts if it holds the same edits). A failed write is `io`; nothing about the workspace changes (still dirty, same path). A save of a doc closed meanwhile is answered when it finishes and changes nothing.
- **Reading runs on the document worker** (`open`, `open_recovery`, `scan_recovery`: read, parse, `check_recovery` / `scan_recovery`). Only regular files are read (a FIFO or device is `io` at once): the file is opened non-blocking (`O_NONBLOCK` on Unix; opening never waits on Windows) and its type checked on the opened handle, so a FIFO swapped in after any check of the path is refused too, never waited on. Its answer (`Inbox::Doc(DocAnswer)`) is applied by the control thread. One such request at a time (`command_refused` for a second). **A read that stalls** (a network volume that stopped answering) is bounded like a stuck probe: after `ControlConfig::doc_timeout` (20 s, on the injected `EpochClock`) the request answers `io`, the worker is abandoned (its late answer carries an old ticket and is ignored; it exits when its read returns) and a fresh worker takes over the shared job queue; after 4 abandoned workers are still stuck, requests that read are refused with `io` until one returns (try again when the volume answers). A timeout that fires while the worker is idle (its answer is already in the inbox, not yet applied) leaves the request to that answer instead of failing it. An edit made while a file is read stays in its doc: the file opens beside it.
- **One show file, one doc** (review H1): the claimed files are every doc's show path, every save in flight (a save-as takes its path only when written), the file an `open` in flight reads (`PendingDoc::path`) and closed docs' saves still running (`Control::claimed_paths`). `open` and `save_as` of a claimed file answer `already_open`: first on the control thread by the spelling (no disk access there), then off it by the file itself (`persist::file_key`: canonical path of the file or its folder): the document worker before it reads, the writer before it writes (`SaveWriter::save_unless`, `PersistError::OpenElsewhere`), so a symlink or `/var` for `/private/var` is caught too. Tests: `control/docs.rs` (save-as onto another doc's file, also via a symlink; an open via a symlink; an open of a file a save-as is writing).
- **Opening** (`Control::open_doc`, [Several docs](#several-docs-m415e)): `open` of a claimed show file answers `already_open` (above; again at install, in case another doc was saved there meanwhile); a workspace whose id an open doc has (a copy of a show) is installed with a fresh id and dirty, and an `info` log says so. The requester gets `opened { doc }`; the doc's snapshot goes to the connections bound to it, and the `workspaces` list to the app connections (below).
- **The `workspaces` list** (M4.15f): after each wake (and at once after an open or a close) the loop compares each doc's id, workspace id, name, path and dirty flag with what it last listed (no allocation when nothing changed) and sends `workspaces` (`doc: None`; the hub gives it to app connections only) when they differ; a list that did not fit the outbound channel is sent again at the next wake. `Control::new` lists its first doc before any of that doc's reports, so the hub knows the first doc (the OSC side's) from the start.
- **Closing** (`close`, `close { doc }`; `Control::close_doc`): the doc is removed ([Several docs](#several-docs-m415e), Close), the requester gets its `result`, and then `closed { doc }` goes on the outbound channel tagged with the doc (again at the next wake if it did not fit), so the network layer writes it to the doc's connections and closes them, after the result.
- **Revision and seq are per doc** (M4.15f): a doc's `revision` starts at 1 and its `runtime_seq` at 0; each connection sees one doc's, so they never mix. (Before M4.15f they kept rising across replacements and a replacement was broadcast as a `snapshot`, M4.4a; both are gone with replacing.)
- **Documents state**: `document` (`path`, `dirty`, `can_undo`, `can_redo`) is derived from `revision != saved_revision`. Opening an autosave (`recovery: restore`, `open_recovery`) installs it dirty (`saved_revision = revision - 1`).
- **Autosave** (NFR-05): every tick, if the workspace is dirty, no autosave is in flight, the revision was not already autosaved, and `autosave_due(dirty_since, last_autosave, now, interval)` says so (`interval` = the workspace's `autosave_interval`, at least 1 s; `now` is `ControlConfig::clock`, wall-clock milliseconds, `EpochClock`; tests inject `ManualClock`, so autosave is tested on virtual time), the loop clones the workspace and hands it to the writer, bound to the show path (or to the workspace id before the first save). So the first autosave is one interval after the workspace became dirty (first tick that saw it), later ones one interval after the previous autosave, and a workspace dirty for longer than an interval since its last autosave is written at the next tick after an edit. A failed autosave is logged once per run of failures and retried at the next due time. The writer drops an autosave whose revision a manual save has already made durable.
- **Save As to another folder** rebases relative media references so they name the same files (`Request::SaveAs` into a folder other than the current show folder): the copy being written is rebased first (`relink_command` on the clone), and when the write succeeds the live workspace gets the same relinks without an undo step: history is cleared, `revision` rises, the doc's clients get a `snapshot` (the hub's `Kind::Snapshot`), the media catalog resets to the new folder (`MediaCatalog::reset`: cue index rebuilt, every file probed again from the new place), and the workspace is clean unless it was edited meanwhile. Absolute references are left alone; relative references of a never-saved workspace have no folder to resolve against and are left as they are.
- **Recent files are the app's (WS-08)**: the engine keeps no list (M5 decision; the macOS app uses its document controller and records paths from the broadcast `document`). Old `settings.json` files that still have a `recent_files` key load fine (unknown keys are ignored).
- **Final recovery write at shutdown** (M4.15g, M4.4d; ARCHITECTURE §8): `Control::shutdown` (after the hard stop) hands every doc with unsaved changes whose last edit no autosave holds yet to the writer as an autosave, and waits for those and for an autosave of the last edit already under way, in all at most `ControlConfig::shutdown_wait` (`SHUTDOWN_WAIT`, 10 s, on the wall clock: shutdown is the one place the loop waits on it). A write that fails (an error, not a timeout or a writer that is gone: a transient disk error) is handed to the writer once more while the wait has time left, with a `warn` log record, since the previous autosave lacks the last edits; a second failure is final. It returns `FinalWrites { written, failed, unfinished }`; each failure and each write still running when the wait ran out is an `error` log record naming the workspace, and a clean run an `info` one. This must come before the docs are dropped: dropping `SaveWriter` discards the autosaves still queued. The drop itself waits at most `persist::DROP_WAIT` (5 s) for the running jobs and pending manual saves, then leaves the threads to finish on their own, so a hung volume cannot keep the process alive. Tests: `tests/control/shutdown.rs` (two dirty docs, two recovery files, the next launch scans and opens both; a hung disk; a write that fails once is retried, one that fails twice is given up and logged; a doc already autosaved is not written again), `tests/persist/writer.rs` (the bounded drop).
- **A save that stalls** (the writer thread stuck on a volume that stopped answering; `persist/writer.rs`): each tick the loop runs the writer's watchdog (`SaveWriter::check_stalled`, on `ControlConfig::stall_clock`, a monotonic clock, so a wall-clock step neither fails a save nor postpones the watchdog). A save, autosave or recovery-file removal first seen running `ControlConfig::doc_timeout` (20 s) ago is answered `PersistError::Stalled` (a save's requester gets `io`, an autosave logs its usual `autosave failed` warning, an `error` log names the file), its thread is abandoned (it leaves once the write returns, if ever) and a fresh thread takes over the queue, at most `MAX_WRITERS` (17) threads in all, so every open show can have its show file and its recovery file stuck and one thread still serves the others; with all of them stuck, saves and autosaves are answered `io` at once until one returns. Two threads never write the same files at once: a job waits while another thread runs one that writes the same show file or the same recovery file (by its name's stem; a save also removes two recovery files when it is done), so a stale write that returns late cannot land over a newer one. While a stalled write is out, saves and autosaves of the files it holds are refused at once (`io`) and recovery-file removals wait for it; everything else saves as usual. A stalled save holds only its show file: given up on, it no longer removes the recovery files when it returns (an autosave since may hold newer edits), so the same workspace can still be saved to another file (Save As) and autosaved, its final recovery write at shutdown included. Once the stalled write returns, its file saves again. Its late answer is not reported (the request was answered). At shutdown, `final_recovery_writes` adds a spare writer thread when every one is busy (`SaveWriter::add_spare`), so one show's slow write does not keep the others' final recovery writes waiting. Tests: `tests/persist/writer.rs` (a stalled save, another show's autosave, the refusal, the save after the stall clears; Save As elsewhere and an autosave of the stuck workspace, the recovery file kept by the late save; every open show stuck on its show and recovery files while another still saves, then the bound), `tests/control/docs.rs` (the save answered `io` at the timeout of the stall clock, not the wall clock), `tests/control/shutdown.rs` (a slow save of one show and another show's final write; the final recovery write of a show whose save is stuck).

## Several docs (M4.15e)

The engine holds up to `MAX_DOCS` (8) docs (ARCHITECTURE §1, §3.1, §3.5; REQUIREMENTS WS-02). The protocol reaches each through the connections bound to it (M4.15f, [protocol.md](protocol.md) section 2).

- **Open** (`Control::open_doc(DocSource, id, reply)`: `New`, `Open { path, recovery }` or an in-memory `Workspace`). Refused with `command_refused` while another document request is being handled (one read at a time, engine-wide) or when 8 docs are open, and with `io` while reads are stuck, as the other document requests. The document worker reads the file (recovery offer and choice as for `open`) and builds the doc's parts there (`DocParts`): the workspace, a cue engine that has followed it once (its static problems and playheads; the actions it gave are carried out at install), the media catalog's reading of it (`index_workspace`: cue index, the file each audio cue plays, workspace order, each file's path resolved against the show folder) and the slice-plan checks walked once (no file probed yet). Installing on the control thread is an insert, the probe jobs, the slot commands (its slots take their gains at once, `SnapPatch`, so a cue started as it opens is not faded in), the first reports and the reply (`result { opened { doc } }` to the requester; the `workspaces` list to the app connections); gated at one audio block over the headroom in `perf.rs` (M4.15i, [Performance budgets](#performance-budgets-nfr-24-nfr-25-m412)). Its cue engine's seed is the configured seed plus its `DocId` (the first doc's is the configured seed). `Control::take_opened` gives the request and the new `DocId`.
- **Close** (`Control::close_doc(doc, discard_changes)`): `no_workspace` for a doc not open; `unsaved_changes` while it has unsaved edits unless `discard_changes`, and then its autosave is removed through the writer, after any write of it in flight (as for a replaced workspace). Its cues stop as Panic pressed twice stops them, orphans and every voice it has in the mixer are stopped (hard), its voice table is forgotten; then its mixer slots are zeroed and freed on the same sample (`Patches::release_doc`; a doc waiting for a slot gets it on the next wake), its voice ids' owners, logged cue states, mapping warnings, watched files and waiting probe jobs are dropped, saves still being written are answered when they finish, and the doc itself is handed to the document worker to be dropped there (its preloaded media can be hundreds of megabytes). The other docs' voices, slots and commands are not touched: a doc playing beside it plays on sample for sample (tested with a ramp).
- **App-scope actions** (ARCHITECTURE §6, QLab 5 checks): `Control::panic_all` (Esc; the `panic` message, or `transport: panic` on an app connection) panics every doc as a `panic` transport in each would (twice within the fade is a hard stop in each); `Control::hotkey(&Hotkey)` (the `hotkey` message, `phase: down`) starts every cue of every doc with that hotkey (`Workspace::cues_with_hotkey`: none in a doc whose transport keys use it, M2.28), and `Control::hotkey_released` (`phase: up`) sends each of those cues `TriggerReleased` (a cue whose second trigger is not on release ignores it). Pause All, Stop All, GO and the rest act on the doc they are sent to.
- **Device loss** stops every doc's cues on the device (the one device; [Devices](#devices-m42b-nfr-08)); it is logged once with the total, and each doc's clients get the `device_lost` notice with its own count. A reopen with another block size sets the new lookahead in every doc's cue engine before the engine's block changes (if one cannot, all keep the old one and a warning says commands may land late).
- **Shared, counted once**: the probe pool (2 workers whatever the number of docs; the volume gate's knowledge stays while another doc is open, and a doc's reset forgets only its own claims and waiting jobs; a closed doc's jobs still in the queues are dropped when a worker takes them; the show file's volume is exempt from holding back only while one doc is open: with several, a doc whose show volume hangs would take every worker one 30 s abandonment after another, so it is held back once two of its probes are stuck past the probe watchdog, never on the media watch's word alone (one slow stat, a disk spinning up, must not slow a show's own probes because another workspace is open); held-back jobs are released urgent ones first, so a stalled volume's one trial is the file near a playhead), the preload budget (`preload_budget` for every doc's preloads together, given back when a doc closes; M4.15e1), the primes (a pool of at most `max_primes`, and never more than half the streamer's `max_streams`, so primes never take a permit a start needs: a start finding no permit fails with `stream_failed`; shared by demand: each doc keeps all it wants while every doc's wants fit the pool, so an idle workspace opening beside a busy show takes nothing and nothing re-primes; when they do not fit, max-min fair shares, a doc over its share lets go of its least urgent primes at its next pass and a doc under it fills at most 4 new rings per pass, so a hand-over is no disk burst; with one doc and the defaults, 64 as before), the media watch (one thread; [Media watch](#media-watch-m225-m229-architecture-31)), the look-up bound (8 slots engine-wide: a look-up holds its slot until its doc takes the answer; a closed doc's until its thread ends) and the PB-10 override ([Network output](#network-output-m46-ct-30-pb-10-nfr-07)), the meter read (once per report period; each doc takes its voices' peaks and its patches' outputs, and reconciles its voices against the voices listed), health counters and status (one each). Per doc: `seen` unsignalled model changes (from zero again when a replace gives the doc a new cue engine), progress and `meters_live`, resend flags.
- **Zero docs** (the last one closed): every engine-wide step runs with none open; a workspace message then answers `no_workspace` (a shutdown still shuts down; the app-scope messages are still carried out, `new` and `open` among them), and the first-doc accessors show an empty workspace. The engine starts with no doc (M4.15g): `Control::empty`, which `host` uses; `Control::new(ws, ..)` (tests, the offline driver's `OfflineShow::new`) is `empty` plus `ws` installed as doc 0, and `OfflineShow::empty` starts with none.

Tests: `tests/control/multi_docs.rs` (two docs sample-exact, per-doc Panic/Stop All/Pause All, app-scope panic and hotkey down and up (through the protocol messages), device loss, unique voice ids and their owners forgotten, a closed doc's late mixer events and probe answers, closing with no gap, the cap, ids never reused, close freeing slots and clearing an autosave, the shared pool, watch and override, a delay conflict across docs, a 2,000-cue open during an auto-follow chain, a seeded random operator over several docs); unit tests in `patches.rs`, `media.rs` (gate), `netout.rs` (shared look-up bound), `watch_share.rs`, `voice_ids.rs`.

## Media watch (M2.25, M2.29; ARCHITECTURE §3.1)

One watch serves every doc (`control/watch_share.rs`, `WatchShare`, M4.15e): each catalog's key changes name files by that doc's keys (media references, relative to its show folder) and watch ids; the watch thread is told each file once, by its path, under an id of the engine's, with a count of the doc keys that name it. One doc letting go of a file (an edit, a reset, a close) leaves the watch running for the others; an event goes to every doc key that names its file, under that doc's key and id (an event of an earlier watch id of the file is dropped). A doc's reset is the watch's own `Reset` (below) when no other doc watches anything, so a one-doc engine behaves as before; otherwise only that doc's files are let go. The watch's notices and logs are the engine's: every doc lists the stalled-volume notices.

`control/watch.rs` (`MediaWatch`) sends the watch thread `Watch`/`Unwatch` jobs for the keys the media catalog gains and loses (`MediaCatalog::take_key_changes`, drained each tick) and a `Reset` when the catalog resets (the show saved into another folder; a doc that opens or closes adds or drops its own files instead): a generation number, so a batch of an older generation is dropped. Each `Watch` carries a watch id (the catalog entry's first probe ticket); every event carries it back and the catalog ignores an event whose id is not its entry's current one (a file unwatched and watched again by an undo while a pass was under way). A reference with no place on disk (relative, in a show never saved) is not watched; its probe has already failed.

The worker answers with `Inbox::Watch(WatchAnswer::Batch(WatchBatch { generation, events }))`, one per pass and only when non-empty, so an unchanged show costs control nothing (`watch_batches()` stays 0 over 2,000 files; tested). Batches are kept until the next tick and handled at its start, before the probe answers go to the engine:

| Event | Control does |
|---|---|
| `Gone { key, trashed }` | `MediaCatalog::mark_missing` (as a NotFound probe: probe failed, preload dropped, budget returned, the ticket moves on so an in-flight probe answer is ignored); `Missing` in the tick's single `Availability`, so the cue is broken within the tick |
| `Back` / `Changed` / `Unreadable` | `MediaCatalog::recheck`: a fresh probe even if one is under way (it may have read the old file); it goes to the high-priority queue when the cue is near a playhead (the re-prime calls `prioritize`); the answer becomes `Availability` as for any probe; an unreadable file probes as `media_unsupported` |
| `Moved { key, new_path }` | (M2.29b, not yet: a moved file is `Gone`) follow ([persistence.md](persistence.md) "Media watch and follow"): relink as a model edit outside undo, `History::rewrite_media`, `MediaCatalog::rekey`, `model_changed`, document dirty |

Pass rules (`WatchCore::record`, pure, tested with `FakeFs`): a file that is not there (or not a regular file) is `Gone` on the first pass that sees it; a different file (identity, size or modified time) at the path, or a file back, is reported only when two passes in a row see it the same (a half-copied file is never probed); an unreadable path is reported once per change; the first pass after a file is watched takes a file it finds silently (its probe is under way; if that probe finds no file, see Failed probes). A pass covers every file once in `max(period, n ms)` (`period` 3 s), in chunks of 64 with a pause between them; jobs are taken between chunks and before each stat. Playing cues are unaffected: the voice holds an open file, and a static problem shows once the run ends.

**Watchdog** (every tick, `MediaWatch::supervise`, on `WatchConfig::clock`, monotonic in the engine): the watcher publishes each stat under way (a number of its own, and the volume: the path's mount prefix, `/Volumes/<name>`, `/media/<user>/<name>`, `/mnt/<name>`, a Windows drive or share, else `/`, found from the text because a stat could hang on exactly that volume). A stat is stalled once the watchdog has seen the watcher in that same stat for `WATCH_STALL` (10 s), timed from when it first saw it, so a clock jump does not stall a stat that was under way. The watch state (files, pass position, events found so far) lives in one `WatchCore` shared by the watchers, locked only between stats, and the job queue is shared too, so a replacement carries on where the stuck one stopped and loses nothing. Jobs are taken and the volume's skip checked before every stat.

- **Abandon**: decided under the watcher's busy lock as a compare-and-set on the stat judged stalled; the watcher clears its stat and reads the flag under the same lock, so a stat that returns as the watchdog fires is either answered (not abandoned) or reports its volume (abandoned), never neither. Control queues `Skip { volume }` and starts a fresh watcher (`openlab-watch-<n>`); the volume's files keep their last status and the notice `media_volume_not_responding` names it (a `warn` log too).
- **Return**: the abandoned thread's stat returns, it sends `WatchAnswer::BucketAnswered { healthy }` and ends; it is counted back (`abandoned_watchers()` counts threads still stuck). `healthy` (a file, or no file): `Unskip`, the notice goes. An error (a dead share's ETIMEDOUT): the volume stays skipped and is retried after `retry_first` (30 s), doubling up to `retry_max` (5 min); a retry is an `Unskip { trial }` whose next stat is reported in the batch's `volumes`; a failing trial waits again. The notice stands from the first stall until the volume answers, through every retry (no flapping).
- **Cap**: at most `MAX_ABANDONED_WATCHERS` (4) threads stuck at once. A stall beyond that abandons nothing: `media_watch_stopped` (naming the volume) and an `error` log stand until that stat returns; the volume is then skipped and retried like a failing one, so it cannot hold the only watcher again.
- A watcher thread that ends on its own (a bug) is logged (`error`) and restarted once; if it ends again, `media_watch_stopped` stays.

**Failed probes**: a probe answer that fails tells the watch (`KeyChange::ProbeFailed`). No file: the watch takes the file as gone, so a file that appears later is reported `Back` (after two passes) even if it appeared before the watch first looked (a show opened before its drive is mounted). Another error while the path is unreadable: the file's return is reported even if unchanged. Otherwise a file that is unreadable for a while and comes back unchanged is not reported again (its re-probe on `Unreadable` already read it), and a failed probe of a readable file changes nothing (no re-probe loop on a file that stats but cannot be decoded).

Tests use an injected `WatchFs` (`FakeFs`: files with an identity, the Trash, denied and hung paths; feature `test-support`, which the engine's own dev-dependency turns on, so it is not in the shipping binary) and `ControlConfig::watch.mode = Manual`, where `OfflineShow::watch_pass()` runs one pass on the test thread and handles its batch in a tick (`tests/control/watch.rs`); the watchdog tests run the thread on `FakeFs` with a `ManualClock` and wait for its messages, never sleeping. `tests/show` sets manual mode, so other tests never see a pass.

## Mixer faults (NFR-01)

A mixer panic outside any voice's render is blamed on its stage and reported as `Event::StageFaulted { stage, at, disabled }` (docs/audio.md "Faults"). The unit is already reset (a patch to silence, an output or the master to unity); `Control::stage_faulted` (`control/faults.rs`) logs it (`error`, with the `faulted_stages` count) and sends it its settings again from the control thread's copy (`Patches`), at `now`:

| Stage | Reset (`disabled: false`) | Disabled |
|---|---|---|
| `Patch(slot)` | the slot's non-zero gains as last sent (`Patches::resend`); an `audio_fault` notice in the doc that owns the slot, naming the patch | the slot is quarantined (`Patches::quarantine`: taken from its patch, never freed or handed out); every voice on it stops (no fade, dated no earlier than its start or resume) and its cue breaks as a faulted voice does (`Voices::fail_slot`); the doc syncs, so the patch takes another free slot or, with none free, is `mixer_patches_exhausted` and its cues cannot start; an `audio_fault` notice |
| `Output(o)` | (the mixer reset it to unity, its delay kept) `SetOutput` with the output's delay (`Patches::resend_output`); a notice in every doc | an `audio_fault` warning in force in every doc (the output is silent) |
| `Master` | `SetMaster { 1.0 }` (the mixer's master is always unity, and the mixer resets it to unity); a notice in every doc | a warning in force (bypassed at unity: levels are unaffected) |
| `Meters` | logged only | a warning in force (meters stop) |
| `Mixer` (rebuild) | every slot's gains, every output, the master (`Patches::rebuilt`); quarantined slots are free again and the warnings in force are cleared; a notice in every doc | — |

A stage that keeps faulting (further apart than the mixer's window, or rebuild after rebuild) is logged and told at most once a second of sample time; its settings are sent again every time, and a disabled unit is always told. A report lost to a full event queue would leave its unit silent: `health` compares the mixer's `faulted_stages` counter as read at the previous check (every report it counted then has been drained since) with the reports handled, and on a shortfall logs it and sends every slot, output and the master again (`Patches::resend_all`, which changes nothing the mixer did not reset). A lost *disabled* report is found from the mixer's published flags (`disabled_units`): a unit disabled at the previous check and still disabled now (a rebuild since re-enables it) that the control thread does not know of is logged and answered as if reported (`Control::lost_disabled_reports`). Tested in `control/faults.rs` (the notices, the slot move, the warning in force and the rebuild; a lost report), `control/patches.rs` and `control/voices.rs`.

## Reconciliation of lost events

The mixer drops events when its queue (1024) is full and counts them (`dropped_events`). A lost `VoiceFinished` would leave a cue running for ever. The voice-meter read (every meters period, ~30 Hz; once per wake for every doc, M4.15e) lists every voice the mixer holds, paused ones included; each doc checks its own started voices against the list (voice ids are unique engine-wide). A started voice whose start sample was rendered before the previous read and that is missing from **two reads in a row**, while `dropped_events > 0`, is taken as ended: `ActionEnded` on the read's sample (or `ActionFailed { stream_failed }` if its stream failed). A voice that no meter read ever listed was never taken by the mixer: its lost report was a rejection, so it fails (`StartFailed { voice_rejected }`: it never played, so the cue is skipped) instead. (A rejected voice of known length whose rejection is lost completes on its planned end if that comes before the two reads.) The first loss is logged (`warn`). Tested by overflowing the queue with loop events while the control thread is held off (`control/feedback.rs`).

## Outbound

- `runtime { seq, changes }`: one message per engine call with changes, from `RuntimeChange::from_action` read right after the call (a broken state carries its reason), plus binary notices as `warning { notice }`: `probe_wait`, `probe_timeout`, `stream_timeout`, `cold_start`, `underrun`, `bad_plan`, `stream_failed`, `audio_fault` (a voice dropped after repeated faults, a patch, device output, master or the mixer reset after a fault, a patch disabled; Mixer faults), `device_lost` (the moment a device is lost).
- `warnings`: the workspace-level list, replaced when it changes, rebuilt at most once per tick: `damaged_media`, `preload_over_budget`, `preload_failed`, `bad_plan` (per cue), `device_lost` (while an outage lasts), `device_unrecoverable`, `outputs_dropped` (the device has fewer channels than the mixer's outputs; and per patch that maps more channels than the device has), `mixer_patches_exhausted` (per patch that got no mixer slot), `output_delay_conflict`, `device_stalled` (the stall watchdog's first stage), `realtime_allocation`, `audio_fault` (a device output, the master or the meters disabled after repeated faults, until a rebuild; Mixer faults), `media_volume_not_responding` (per stalled volume), `media_watch_stopped` (Media watch). Broken cues are not in this list: DX-01's per-cue rows come from `problems` (the snapshot and `runtime` `problem` changes), which carry the cue id, so a cue list needs no second copy and an edit pays nothing for them. The `bad_plan` check keeps each cue's result and rebuilds a cue's plan only when its trims/markers or its file's probe change (`plan_builds()`: an edit of one cue in a 2,000-cue show builds at most one plan; tested). The same plans give each audio cue's nominal length (`total_frames` of its table from the top; `None` if it loops forever or has no plan): after each rebuild of the list the loop sends the lengths that changed since it last told the engine (`PlanChecks::take_changes`, `Input::CueLengths`; `None` for a cue gone, unprobed or unplayable), which a playlist halted by a broken child times its auto-follow by (docs/cue-engine.md, "Halted playlist"; tested in `control/media.rs`). The same pass gives clients each audio cue's media lengths (file, trimmed range, duration with play counts; M5.4d): the ones that changed since they were last sent go out as one `runtime` message of `media_duration` changes, with every field absent for a cue whose file is no longer playable or that is gone, and the snapshot's `media_durations` is what was last sent (`PlanChecks::take_changes`, docs/protocol.md "Media durations"; tested in `control/media_durations.rs`, including a 2,000-cue show where one edit or one missing file sends one change and no snapshot).
- `progress`: show cues with a playing voice (elapsed and remaining in the action, remaining `null` while it loops for ever), and the cue engine's timers at the rendered sample (`CueEngine::timers`, M4.2e: actions of cues without a voice join `items`, pre-waits and post-waits go in `waits`), at most 30 Hz of sample time, only while one plays or counts. Read on the report pass of the doc's tick; no wake is added for it.
- `meters`: per mapped patch the device outputs it is routed to, per cue its voices' peaks per cue output (`read_output_meters_into` / `read_voice_meters_into` into preallocated buffers), at most 30 Hz, while audio plays plus one message after.
- `log`: engine faults (`error`; blocks replaced with silence, voices dropped after repeated faults, each mixer stage fault, at most once a second per stage, with the `faulted_stages` count; lost stage-fault reports), audio-thread allocations (`error`, M3.21), lost mixer events (`warn`), unsignalled model changes (`error`), device loss, with the number of cues it stopped (`error`), failed reopen attempts and host errors that need no reopen (`warn`), a device back (`info`).
- `status` (when `ControlConfig::status` is set): system health about once a second of wall-clock time, and early on a change; lossy like `meters`. Also every `log` above, and the cue starts, stops, failures, GOs, triggers and document events, go to the show log (`control/observe.rs`, [logging.md](logging.md)); `log_tail` answers from its ring. A network layer sends `Inbox::Trigger { source, detail }` just before each client or OSC transport action (not edits or requests); the loop logs at most 5 per source per 10 s and summarises the rest.
- The outbound channel is bounded (`OUTBOUND_CAPACITY`). Meters and progress are dropped first, as soon as it is half full (the next ones replace them). A sequenced message (`runtime`, `model_changed`) or log that does not fit is dropped; clients recover from the `seq`/`revision` gap with a snapshot. A `document` or `warnings` message that does not fit is sent again, newest, once there is room. Drops are logged (`warn`) once there is room.

## Devices (M4.2b, NFR-08)

One output device (REQUIREMENTS §21: single device, up to 64 outputs), shared by every open doc: a loss stops every doc's cues on it, a return makes every doc's patches playable again (M4.15e, [Several docs](#several-docs-m415e)). `host::run` opens the default device, by its concrete id, at start; the stream never follows the system default (docs/audio.md, Device layer).

**Device threads.** Listing, opening and closing a device can block in the host (CoreAudio holds locks while a device goes), and a cpal stream may not leave the thread that opened it. So the `openlab-device` thread owns the device layer (`DeviceLayer`: `CpalDevices`, or a stand-in in tests) and the open stream, carries out `Open { mixer }` and `Close` in order, and the `openlab-device-list` thread reads the list (`DeviceLister`), so a hung open or close cannot stop hot-plug from being seen. Both answer through the control inbox (`Inbox::Device`). A panic inside the layer is caught on its thread and answered as a failure (a panic during an open or close loses the mixer: `device_unrecoverable`). The control thread never calls the device layer; a GO, a command or a reply never waits for a device (tested with an open that blocks until the test releases it). At most one list read and one open or close are in flight. When the control loop ends, the device thread drops the stream (and the mixer) on its own side. The first open (`devices::start`) is waited for at most `FIRST_OPEN_TIMEOUT` (10 s); then the engine stops with "no answer from the device".

**Supervision** (`devices::Device`, every tick, wall clock injected as `WallClock`):

- **List** every `DEVICE_POLL` (1 s): the last answer serves `list_devices`. A change re-resolves the patches (cheap; they change only through a loss or reopen, see Patches).
- **Loss**: `DeviceMonitor::needs_reopen()` (lost, invalidated, rerouted), or the stream's device gone from the list (hosts that stop calling back without an error): missing from two reads in a row, or from one read while the stream has not called back since the previous read (one read can miss a device that is busy reconfiguring; cpal leaves out a device whose configurations cannot be read at that moment). Other host errors (real-time priority denied, bad buffers) are logged (`warn`); `take_errors` is read here only (single consumer).
- **Stall watchdog** (M4.2g): a stream that stops calling back with no error while its device is still listed, in two stages. Each tick, while the stream is up, the supervisor compares `DeviceMonitor::callbacks()` with the count it last saw. **Silent for `stall_limit` = max(`STALL_WARN_MIN` 500 ms, 20 buffer periods)**: a `warn` log and the `device_stalled` workspace warning; nothing stops (a 600 ms dropout that recovers on its own is not worth ending the show for). The warning goes only after callbacks have run for one warning limit with no silence of that length (a device that stutters keeps it up instead of flickering), and an `info` log says so; the warn log is written at most once per `STALL_LOG_EVERY` (10 s) with the number of stalls since, and the clearing is logged only if the raise was. **Intermittent:** over a sliding `STALL_WINDOW` (10 s) of watched time, a stream silent for half of it or more (once `STALL_WINDOW_MIN` 8 s were watched; the first-callback grace is not counted) is lost with reason `stalled (intermittent)`: any single callback would otherwise reset the 3 s limit of a device that calls back every 0.5-3 s. **Silent for `stall_loss_limit` = max(`STALL_LOSS_MIN` 3 s, 50 buffer periods)**: `DeviceEvent::Lost` with reason `stalled`, handled exactly like an unplug (cues on the device stop at once, no automatic resume, close then the usual reopen with backoff; cues un-break when it is back; the loss replaces the warning). A device that left the list is found by the list check first ("no longer listed"). Limits are sized from the stream's `block_frames` and `sample_rate` when it opens (unknown buffer: the floors). **Only silence the supervisor watched counts:** a gap between two samples above max(`STALL_MAX_GAP` 100 ms, warning limit / 8) (the process was frozen, a thread starved) starts the window over, and each stage needs `STALL_MIN_SAMPLES` (10) samples inside it, so a frozen process (both threads stopped, the control thread waking first) is never a stall. **Grace:** a stream gets one loss limit for its first callback after an open (a slow first IOProc, a Bluetooth route), and again after a wake from sleep. Sleep is detected by a second injected clock that counts sleep (`SleepClock`, `SystemTime::now`): on macOS the monotonic `Instant` stops during sleep, so it shows no gap; the system clock moving on more than `SLEEP_SLACK` (1 s) further than the monotonic one between two samples is a wake (an NTP step forward does the same, harmlessly). Only a stream that is up is watched (not while closing, down or opening; openLab never pauses a stream, a silent mixer still calls back). The audio thread does nothing new: the callback already counts itself in a relaxed atomic. Rationale and numbers: docs/handoff/decisions/m4-2g-watchdog.md.
- **Close and reopen**: on a loss the stream is closed on the device thread; the mixer comes back at once or as `MixerPending`, polled every tick. Reopen attempts on the same device id follow `reopen_delay_ms` (250 ms doubling to 4 s) by the number of opens since the stream last stayed up `STABLE_UP` (5 s): a device that keeps dropping out right after each reopen backs off further instead of starting again at 250 ms. A failure is logged with the next delay; the device coming back into the list (absent from the previous read) makes the next attempt immediate. A reopened stream continues the mixer as it was (voices, queues, clock).
- **Another buffer size** after a reopen: the lookahead (`CueEngine::set_lookahead`), the `now` offset and the wake rule follow the new block, so every deadline is still committed before the callback that renders it (tested with a device back at 4× the block: the auto-follow lands on its sample). `now` never goes back (a smaller block keeps it where it was until sample time passes it). A callback already under way when the reopen is handled can still miss events of its first block (inherent: the size is known only once the stream runs).
- **Watchdog** (`DEVICE_JOB_TIMEOUT`, 10 s wall clock): an open or close the device thread has not finished, or a mixer the host has not handed back, after that long makes the device unrecoverable: an `error` log and the `device_unrecoverable` warning (naming what is stuck and that openLab must be restarted) replace "reconnecting". A late answer still counts (the warning goes, an `info` log says so). A list read that does not finish is logged once (`error`) and listed as `device_list_stuck`.
- Allocation violations are summed over every stream (M3.21).

**Device-loss policy** (progress archive M4.2g, user decision 2026-10-27, measured on QLab 5; it replaces the M3.22 grace period and exact-sample resume, which are gone):

- **When the device is lost** (`DeviceEvent::Lost`: `needs_reopen`, or gone from the list), at once and whatever the length of the outage: the patches on it are reported `device_missing` (`Availability`: loaded cues on them unload, a start is refused as broken, idle cues show broken), and every active **audio** run ends with `ActionFailed { device_lost }`: pre-waiting, playing (voice started in the mixer, or waiting for its probe), paused, fading, stopping and post-waiting alike, with or without a voice. That is a hard stop with no fade: the cue is `broken` with reason `device_lost`, its voice and stream are released, and its **pre-wait, auto-continue and auto-follow are cancelled** (core, `action_failed`), so nothing scheduled before the outage starts by itself after it. A group follows its children's failures (a timeline group whose children were hit ends whole). Every voice the mixer holds is stopped too (paused ones, fading tails, orphans), dated on the first sample the mixer renders after the outage (`Voices::stop_date`), so nothing sounds when the device returns. An `error` log counts the stopped cues and a `device_lost` runtime notice and workspace warning go out. Loaded runs only unload (the patch status does that).
- **Stopped or broken until the next GO.** QLab 5 shows such a cue with a pause mark that Resume All only clears, and GO restarts it from 0 (its progress was reset at the unplug). openLab has no pause mark, so the cue is shown **broken (`device_lost`) while the device is away** (also true of any cue routed to it) and **idle once it is back**: Resume All does nothing to it, GO plays it from its start. This is the closest match: the cue is neither paused nor resumable, and its progress is gone.
- **No automatic resume, and nothing scheduled before the loss fires after it.** A 3 s and a 20 s outage behave the same. After failing the audio runs, the loop feeds `Input::DeviceLost`, which hard-stops every other active run (memo, Wait, control, Fade and group cues, and runs that were already broken but still hold a pending continue): every pre-wait, post-wait, auto-continue and auto-follow set before the loss is cancelled, so no cue fires by itself when the device returns; only the operator's GO restarts the show. QLab-confirmed for waits too (check Q13, M2.27): an interface unplugged during a pre-wait or post-wait starts nothing by itself after it is plugged back, and the countdowns do not keep running. Loaded cues and settled broken cues keep their state. Tested: a Start cue's pre-wait, a memo's auto-continue, a group's own auto-continue after its children were lost, a group's pre-wait, and a cue broken before the loss (missing file) with an auto-continue.
- **Sample time during an outage.** While no stream runs, `samples_rendered` stands still, so the engine's clock is frozen. After the loss nothing that was scheduled is left to wait on it, so it matters only for what the operator starts during the outage (a GO on a cue not routed to the device, e.g. a memo with a wait: its timing stalls until the device returns). It is kept because it is the only time base (one device, REQUIREMENTS §21) and replacing it would need a wall-clock timeline for no audible gain; removing it is not needed for correctness.
- **Back**: the stream is reopened (backoff below), the patches are reported `mapped` again: cues broken by `device_lost`, and idle cues routed to it, become playable (docs/cue-engine.md, Broken cues). The `device_lost` warning goes.
- **GO during an outage** (and any start of a cue on the device): refused as broken (`cue_broken`); it is not queued for the return. Cues with no output on the device run as usual (on the frozen clock).
- **Stops and pauses during an outage** find nothing playing on the device (the dating of a pause on the cut sample, with its `ActionLength` correction, is no longer exercised by any test: nothing plays during an outage any more; it is kept only because it is harmless). The ones that reach a voice (orphans) are dated on the first sample the mixer renders when it is back, never before the voice's own start. **Panic during an outage** stops everything at once (a panic fade could only play after the outage; the loop makes it a hard stop with a second Panic when a panic fade was already under way).
- **What stays from M4.2b** and why: the reopen backoff and the immediate retry when the device is listed again; the hot-plug list; the device-job watchdog (`device_unrecoverable`); output delays; the buffer-size change after a reopen (`set_lookahead`); the frozen clock (above); the stop dating on the cut sample (a stop sent to a voice while the mixer is silent must not let it play one more block). **Removed:** `DEVICE_LOSS_GRACE`, `GRACE_WINDOW`, the downtime accounting (flapping window), `DeviceEvent::GraceExpired`, the exact-sample resume. A device that flaps simply stops the cues playing on it each time; no voices or streams leak (tested).

**Tests** (`tests/control/devices.rs`): a stand-in device layer whose stream holds the mixer in an `OutputHost` the test renders block by block (`tests/show/device.rs`), on the real device thread, with a test-driven wall clock; the driver waits for the device thread's answers on the inbox, never sleeps. Hot-plug and `list_devices`, a loss found only from the list, the M4.2g policy (a cue playing on a lost device stops at once, frees its voice, does not auto-follow and does not come back after 3 s or 20 s; Resume All does nothing, GO restarts it from the start; cues routed to the device are broken until it returns; a paused cue; flapping leaks nothing), a slow open, Panic, stop, pause and GO during an outage, a mixer held by the host after close, dropped outputs; the stall watchdog (warning at 500 ms and recovery, loss at 3 s, a stuttering device lost as intermittent with bounded logs, log rate limit, the 10-sample rule, callbacks resuming just before it, first-callback grace, process freeze, sparse supervisor, sleep with diverging clocks, streams that are not up, the list reason, reopen then a cue plays again); output delays on the offline driver.

## Network output (M4.6, CT-30, PB-10, NFR-07)

`control/netout.rs`. The cue engine's `SendOsc` action is encoded on the control thread (`rosc`, the encoder the OSC listener uses; UDP as one datagram, TCP as one SLIP frame, OSC 1.1, the framing QLab 5's own TCP listener reads) and handed to a **worker thread per destination** (network patch) through a bounded queue (`LINK_QUEUE`, 32). The control thread never does socket I/O, name look-ups or waits: a destination that is slow, dead or stuck inside a connect delays only its own messages. Workers start on first use (at most `MAX_LINKS`, 64) and end when their destination changes or the engine stops. A message that waits more than 1 s (`MAX_MESSAGE_AGE_MS`, measured on the transport's monotonic clock) is dropped with "destination too late"; turning the override on also drops what is queued; the sender uses the addresses the last look-up found (IPv4 first); an idle sender is freed when 64 exist. A queue that is full refuses the message; a failed send (no route, connection refused, TCP timeout of 2 s) comes back as `Inbox::Net(NetAnswer::SendFailed)`. Both become a runtime `notice` warning `network_send_failed` for the cue (and a show-log line); the cue has completed by then, as in QLab. UDP leaves from one socket per address family, so a receiver sees one stable source port. TCP connects for each message and closes after it.

**Override (PB-10).** `Request::SetOutputOverrides { network_disabled }` sets an engine-wide flag (one flag the engine shares with every doc's `NetOut` and send threads; set or cleared through any doc, M4.15e): every open workspace, held only in memory (not in a show file, a machine setting or an undo step; a restarted engine starts with output on, as QLab's Overrides window does). With it set `SendOsc` is received and dropped (logged at info, nothing queued), so Network cues still run, complete and continue. The flag is `network_output_disabled` in every `status` message, and a change sends one early (docs/protocol.md). The UI must show it plainly (progress archive M5).

**Reachability (NFR-07).** What can be decided from the model is decided by core (an unusable host or port, a malformed message, a missing patch: docs/cue-engine.md). Whether a host **name** resolves is **not** checked before GO, as QLab 5 does not flag an unreachable destination (manual pp. 371-372: only a missing patch, an incomplete patch and an invalid message break a Network cue). Names are still looked up so the sender never resolves per message: when a workspace opens or its network patches change, `NetOut::sync` starts a look-up (name resolution only, `getaddrinfo`, on its own short-lived thread, at most `MAX_LOOKUPS` = 8 at once, and `MAX_TRACKED` = 256 names followed) and the answer fills that sender's address cache; nothing is reported to the cue engine. A name that never resolved is logged once per run of failures; a send to it (empty cache) resolves the name itself on the destination's worker, never on the control thread, and a failure there is a `network_send_failed` warning. Look-up threads are bounded (at most 8 alive in the whole engine, every doc's together (`LookupThreads`: a look-up holds its slot until its doc takes the answer; a closed doc's look-ups hold theirs until their thread ends), timed-out and forgotten ones counted until they answer, one per name in a doc); if hung ones fill every slot a log line says so and sends to the waiting names resolve the name themselves. A failed look-up is **repeated every 10 s of sample time** (which stands still during an audio outage: a failed name is then retried once audio is back) (`RETRY_AFTER`), so a network that came up after the show opened is followed by itself; a look-up that has not answered in 20 s counts as failed (its thread is not waited for). A name that has resolved is **looked up again every 60 s of sample time** (`REFRESH_AFTER`, the same slots, limits and one-thread-per-name rule as retries) so a host that changed address (a DHCP lease, a rebooted console) is not sent to at its old address; a failed **TCP** send clears that destination's addresses and asks for a look-up at once (a failed UDP send proves nothing about the address). A refresh that fails (error or timeout) for a name that resolved before keeps its last-known addresses (one log line per run of failures, retried every 10 s). Each sender holds its own snapshot of the addresses, so a replaced sender's old worker never sees the new destination's. There is no periodic probing of the destination: nothing is sent to a host before a cue sends to it, UDP has no way to tell whether anyone listens, and QLab does not check either. A name that resolves when the show opens but not at GO is a send failure (a warning), not a stall. IP addresses are never looked up.

Tests: `tests/control/network.rs` (exact bytes over a real UDP socket and a real TCP listener on 127.0.0.1, the override, unusable destinations, a failing and a stuck destination, a full queue, look-up retry in virtual time) with `OfflineShow::settle_net()` to wait for workers.

## Offline driver

`OfflineShow` builds the mixer, the control state and an `OfflineRenderer`. `step()` hands the inbox to the control state, **settles** the streams, renders one block (captured) and ticks. Rendering faster than real time would let the disk workers fall behind, which a device never allows for long, so settling waits (blocking, outside `tick`, with a 30 s timeout counted in `stalls()`) until every playing stream has written what the block will read and every prepared stream is primed; renders are exact and repeatable. `settle_media()` waits for every probe and started preload. `render_only(frames)` renders with no tick (a late control thread). `send`/`transport` hand a message in and return its replies; `take_outbound` returns the broadcasts.

## Performance budgets (NFR-24, NFR-25, M4.12)

`tests/perf.rs` builds a 2,110-cue show (60 groups of 10 audio cues, 1,200 audio cues with their own files, fades, memos with notes, a few slice cues; about 3.8 MB of JSON) in the test.

- **Deterministic (every `cargo test`)**: the idle loop is run on virtual time as `runner::run` runs it (`wait_hint`, render, `tick`). With a workspace open and nothing running it wakes exactly once per `MAX_WAIT` (5 ms), never zero-wait (a spin), does no work on a wake (nothing sent, no plans rebuilt), and an empty workspace wakes at the same rate. An edit sends one `model_changed` and replans no slice cue. A probe answer scans nothing: the media catalog counts the cues that ask for a preload as the workspace and its edits come in (it used to scan every cue on the first answer after each edit, and before that on every answer, which was quadratic in the number of files). Incremental bookkeeping (`cue_engine/incremental.rs`: `an_edit_costs_what_it_touched`) is pinned by counters: a rename recomputes one cue's problems, an edit of a fade's target two, a move or an add or a removal one.
- **Timed (`#[ignore]`, release, CI "Performance budget gate" on the Intel runner)**: the CI budget is the requirement divided by 2, the headroom cpu_budget keeps for a 2014 Mac mini: open (read, parse, validate, control state, probes, snapshot built and encoded) < 1.5 s; each edit (command, `model_changed`, engine follow-up, next tick) < 12 ms (3/4 of a 60 Hz frame rather than half: edits take 3-5 ms on a dev machine, so 8 ms would leave a shared Intel runner too little room); one idle tick under 1% of a core at one wake per 5 ms (NFR-25 is 2%); four times the cues costs under 12x the time (linear is 4x, quadratic 16x; rename measures about 2.7x: what is left per edit is the linear passes named under Known cost). Best of five runs per gate. The media watch (M2.25) takes at most 1% of a core with 2,000 files, gated at half (pass period 4 s at 2 ms a file; the Intel runner measured 84-143 ms for ten passes at the old 3 s period, 0.3-0.5%, nearly all the stat syscalls). On a dev machine: open about 50 ms, edit 0.05-1.8 ms (3-5 ms before M4.12a; batch of 200 1.1 ms, add 0.43 ms), idle tick 0.3 us.
- **Incremental (M4.12a)**: an edit no longer rebuilds the cue engine's per-cue problem facts or the media catalog's key set for the whole show; both follow the edit's footprint (docs/cue-engine.md "Broken cues" gives the rule for cues that depend on each other). They were about 1 us per cue, 2-3 ms at 2,000 cues; an edit now costs 0.4-0.8 ms there (a 200-cue batch 2.2 ms).
- **Incremental (M4.12c)**: the per-edit passes that were left now follow the footprint too. The cue index keeps every cue's place (one position map per container), so locating a cue and finding what an edit touched no longer scan sibling lists; `model_changes` reads the touched cues through the catalog's index instead of walking the cue lists; the cue engine's chain limit, playhead sync and "cues present" check read the index (a playhead is placed from what the edit touched around it, and nothing is read when nothing was added, removed or moved); the slice-plan checks (`PlanChecks`) follow the media catalog's plan changes, so a tick after an edit examines the touched audio cues and the cues whose probes changed, not every audio cue. Counters pin this (`whole_show_passes` in the cue engine, `examined` and `walks` in `PlanChecks`; `cue_engine/incremental.rs`, `control/protocol.rs`). A rename at 2,000 cues went from 589 us to 136 us (best of five, final run), and four times the cues now costs 2.7x the time (5.0x before; linear is 4x, the rest being the passes below).
- **Pre-show check** (`preshow_check`, `control/preshow.rs`, SM-06/NFR-07): built on the control thread from state it holds, with no I/O: `CueEngine::broken_cues()` (the static problems, which already fold in the media probes, the media watch and the patch `Availability`), the patch resolutions, the workspace's cues (for lists, numbers, names, and which cues use which patch or destination) and the `warnings` list (refreshed first if it is stale). `summary.total` counts `broken_cues` plus the `system` entries that are problems (`preload_over_budget` is information: listed, not counted); media, patches and destinations are the causes of broken cues, listed with the cues they break, and a patch no cue uses is listed but not counted. Media is therefore as fresh as the last probe and watch event; it is not re-read from disk at request time. Network destinations are reported `not_checked` when they exist (probing is M4.6) and `missing` when a cue names one the workspace lacks. Tested in `tests/control/preshow.rs`. The macOS app (M5.22) runs it from Window > Pre-Show Check (Shift-Cmd-W, enabled while the workspace's engine connection is up) in a floating panel that never takes the keys from the workspace window: entries grouped as broken cues, media files, patches without a device, network destinations and engine warnings (empty groups left out, the engine's order kept, information-only entries dimmed); choosing an entry makes its workspace window key (so the next GO goes there, not to another open workspace) and selects its cue without moving the playhead and, in Edit Mode, shows the inspector (Basics tab for file and target problems). A cue deleted since the check is marked and cannot be chosen; Check Again runs it once more, and a lost connection or failed request clears the list rather than leave an old report standing (`mac/openLab/PreshowReport.swift`, `PreshowWindowController.swift`; tests `PreshowTests`, `PreshowUITests`).
- **Known cost** (#411): `prime_set` still walks the whole show for the probes a set of files needs, and `refresh_warnings` still scans the cues' media for warnings; each grows with the show but only on the edits that use it.
- **Contract**: the control loop cannot edit without signalling ([Model changes](#model-changes-m41a)); a caller of core that edits without signalling `model_changed` / `model_changed_cues`, or names a footprint that misses a cue, breaks the incremental scheme; every build follows it only as far as the outline check and the guards reach, and debug builds' edit cross-check counts the rest (docs/cue-engine.md "Model edits"). After such an edit that moves cues, the cue engine's playhead catches up at the next signalled structural edit or at the next GO, not at any call in between, and lands on the next surviving cue as a full rebuild does (docs/cue-engine.md "Model edits").
- **Two docs (M4.15i)**: a second 2,000-cue doc (another show file of the same shape) open beside the first. Deterministic: the idle loop wakes exactly as with one doc (once per `MAX_WAIT`; `two_open_docs_idle_at_one_docs_wake_rate`). Timed, in the same gate: an idle tick with both open costs at most 3x one doc's (linear is 2x) and stays under 1% of a core; renaming a cue and setting 200 cues in the second doc cost at most 1.5x the one-doc edit plus 0.5 ms, and under 12 ms; installing a 2,000-cue doc (the control thread's part: `Control::handle` of the document worker's answer; the read and build are off-thread), the wake after it, closing it (`close_doc`) and the wake after that each take under half of one audio block (ARCHITECTURE §3.1: 256 frames at 48 kHz, 5.3 ms, or the show's block if shorter), with the watch thread running as live (in manual watch mode its work would be on the control thread) while the first doc plays a cue on without a late start; 64 stereo cues fading in throughout, 32 in each of two docs, render at 48 kHz in 512-frame blocks at least 10x real time (cpu_budget's NFR-23 budget) and at most 1.25x slower than 64 in one doc (only the mixer callback is timed: `OfflineShow::step_timed`). The first measurement put the install at 2-5 ms: resolving 1,800 media paths, building plan-change keys the full check never reads and copying and sorting every key on the control thread; the paths are now resolved on the document worker (an index resolved against another folder is resolved again), and a closed doc's watches are taken out in one pass, and a Panic with no runtime skips its walk of every cue. On a dev machine (Apple silicon): install 0.58 ms (was 2.0-5.1), wake after it 0.43 ms, close 0.53 ms (was 1.5), idle tick 0.31 us (1.6x one doc), edits 0.9x one doc's, render 96x real time in both cases.

## Process lifecycle (M4.9, M4.15g; ARCHITECTURE §8)

`host::run(Options)` (`openlab-engine [--open SHOW_FILE]... [--app-support DIR] [--watch-stdin] [--relaunch-app BUNDLE_ID]`; `--version` prints the version on stdout and exits 0; any other argument, a flag without its value or an invalid bundle id is a usage error: the usage line on stderr and exit 2, before anything starts):

- **Start.** The shutdown signals are blocked first (`platform::signals`, before any thread exists, so every thread inherits the mask). Then the instance lock (below) and the signal thread, so a start stuck in the audio system still answers a signal; the show log, the panic hook and the run marker (`supervise`, docs/logging.md); the `engine.json` check; the default output device, the mixer, the UI server and OSC; `Control::empty`; the `--open` requests; from here a signal is a graceful shutdown; `engine.json`; the stdin thread (with `--watch-stdin`); the control thread. The engine starts with **no workspace open**: the client decides (recovery check, last workspaces, none) with `new` / `open` (which offers recovery) / `open_recovery`. `--open` (dev and tests) sends that same app-scope `open`, without a recovery choice, and prints each outcome on stderr (`opened PATH (doc N)`, `could not open PATH: ...`, or `not opened PATH: an autosave newer ...`); a failure leaves the engine running. A line `listening on 127.0.0.1:PORT` on stderr says the engine is up.
- **`engine.json`** (`host::engine_file`), at `<app-support>/openLab/engine.json` (`AppDirs::engine_file_path`): `{"pid", "port", "token", "version", "protocol_version", "started_ms", "stopping"}` (the app reads `port`, `token`, `pid` and `stopping`, and ignores the rest). `stopping` is `false` while the engine runs and is rewritten to `true` (atomically, as below) as soon as its shutdown begins (see Graceful shutdown); the file stays until the very end (no second engine is started into the lock meanwhile). The contract for a client that finds `stopping: true`: do not attach; wait for that pid to exit, then find or start the next engine. The macOS app does so (see *Stopping engine* below). A file without `stopping` (an older engine's) reads as `false`. Written by `persist::write_engine_file` (the show saves' atomic writer): to `engine.json.<pid>-<n>.tmp` with mode 0600, fsynced, renamed into place, folder synced, and a crashed run's temp files a minute or more older removed: a reader never sees half a file, and the token is the user's only. Removed on a graceful exit only while it still holds this run's pid and token; a crash leaves it. **Stale** = its pid holds no run marker lock (`run_marker::is_live`; a crashed run's lock went with its process): a start replaces it. **Single instance**: the first act of a start (before the log, the run marker, the device, the port or this file) is an exclusive lock on `<app-support>/openLab/engine.lock` (`host::instance_lock`, `AppDirs::engine_lock_path`; std `File::try_lock`: `flock` on Unix, `LockFileEx` on Windows), held with the open file for the life of the process, so it goes with a crash too and a leftover file never refuses a start. The holder writes its pid into the file. A start that finds the lock held fails at once with `another openLab engine is running (pid N, port P)` (exit 1; pid and port from `engine.json` when it is the holder's, `pid N, starting or stopping` or `starting or stopping` while the other has not written it yet or has already removed it in its last moments) and touches nothing of the other's: two engines started together can no longer both pass the check and race for the device, OSC and this file. Where the lock cannot be taken (an unwritable folder, a filesystem without locks, a non-file named `engine.lock`) a stderr line says so and the start goes on with the older check behind it: a start while the file names a live engine fails the same way; the app attaches to that engine (or, if it does not answer, ends it by its pid before starting another). Not writable: the start fails (`could not write ...`), as no client could find the engine. Without an app-support folder there is no file and a stderr line says so.
- **Graceful shutdown**: `goodbye { shutdown: true }` from any client, `SIGTERM`, `SIGINT` or `SIGHUP` (macOS: a `sigwait` thread sends `Inbox::Shutdown` and logs the signal), or stdin closing with `--watch-stdin`. **Stopping**: the first of these (or else the end of the control loop, however it ended) sets the engine's `net::Stopping` flag at once, long before the server stops: from then on an app connection that ends is not relaunched (logged at `info`), a relaunch already waiting gives up, and an `openlab-stopping` thread rewrites `engine.json` with `stopping: true` (on its own thread, so the control loop and the final recovery writes never wait for it; the mark holds this run's `engine.json` while it writes, so on a hung disk the final removal waits behind it until the forced exit at `EXIT_DEADLINE`, and a file left behind then names a dead pid, which the next start treats as stale; a mark that comes after the file was taken out for removal writes nothing). The loop ends; `Control::shutdown` hard-stops every doc and writes the recovery file of every doc with unsaved changes ([Documents](#documents-m44-m415f), bounded by `SHUTDOWN_WAIT`); the control state is dropped (writer drop bounded by `persist::DROP_WAIT`; the device thread drops the stream); the server stops; the log is flushed (bounded); the run marker goes; `engine.json` is removed last, so a start until then is refused naming this engine (and the app sees an engine to wait for, not a gap to start another into); exit 0. A panic on the control thread is a crash: non-zero exit, marker and `engine.json` left.
- **Forced exit** (`host::stop`): a shutdown signal before the control loop runs (a start stuck in a device open, which `FIRST_OPEN_TIMEOUT` only bounds for the first open's answer) exits at once with 0 (no workspace is open yet). Once the shutdown is under way (after `goodbye`, stdin or a signal), a first signal only says so on stderr and a second one exits at once with 1 ("press Ctrl-C again"). One deadline bounds the whole exit: `EXIT_DEADLINE` (24 s) from the first signal while running or the end of the control loop, whichever comes first. It covers the graceful path at its worst (final recovery writes 10 s, then the save and settings writers' bounded drops 5 + 5 s, then the log flush 3 s) and stays under the app's 25 s before SIGKILL; past it the exit is forced with 1. A forced exit removes this run's `engine.json`, leaves the run marker (the next start reports the unclean end), says why on stderr and ends with `_exit` (`platform::exit::exit_now`; `std::process::exit` on Windows), so no exit handler that a thread stuck in the audio system could block runs. Tests: `host::stop` (each phase, a signal while running sets stopping, the deadline after a signal and after the loop, a first signal after the loop), `host` (stdin closing sets stopping; `engine.json` marked stopping and never brought back after its removal), `host::engine_file` (`mark_stopping`), `tests/net/ws.rs` (no relaunch once stopping), `platform::exit` (a child process: the exit code, no exit handler run), `host` (`engine.json` removed last, left by a crash).
- **UI relaunch** (`--relaunch-app BUNDLE_ID`, given by the app that starts the engine; a plain bundle id, else a usage error): an app connection that ends without `goodbye` is relaunched after 1 s, at most 3 times a minute, unless the app's process (the `pid` of its `hello`) still runs or the engine is stopping (docs/network.md, Connection). Without the flag (dev, tests) it is only logged.
- **Sleep prevention** (SM-07; `platform::power`): each wake the loop works out whether any doc is in Show Mode (`set_show_mode`) or has an active cue (`CueEngine::has_active_cues`) and, when that changes, says so on `ControlConfig::awake`; the `openlab-power` thread holds an IOKit `PreventUserIdleDisplaySleep` assertion while it is true (no idle system sleep, display sleep or screen saver), logging each change, and a failure once. Shutdown lets it go; the OS drops it if the process dies. Not on Windows yet (a warning in the log when it would be needed). Tests: `tests/control/shutdown.rs` (Show Mode in `document` and the snapshot, awake while in it or while a cue runs, let go at shutdown), `platform::power`.
- Windows and Linux: no signal handling (the default action ends the process at once; the Windows UI is to send `goodbye { shutdown: true }`).
- **The app (M5.2; `mac/openLab/Engine/EngineSupervisor.swift`, `EngineProcesses.swift`, `EngineSession.swift`, `EngineAlarm.swift`)**. *Launch*: one copy of the app runs: a second one with the same bundle id (another download, `open -n`) builds no menu and no engine session, fronts the copy launched first (earliest launch date, then lowest pid) and exits, since its Quit would end the shows the first runs (the fake engine and the unit-test host skip this). It fronts the first once it has finished launching: from macOS 14 activation is cooperative, so it yields activation to the first (`yieldActivation(to:)`) and then requests the first's activation from itself (`activate(from:options:)`); on 12 and 13 it activates it ignoring other apps (`AppLaunch.swift`). no `engine.json`, an unreadable one, or one whose pid is not a live `openlab-engine` (checked with `kill(pid, 0)` and the process's executable name, so a reused pid is never signalled) starts the engine as above (`posix_spawn`, own process group, stdin and stdout on `/dev/null`, stderr appended to `engine-stderr.log` beside `engine.json` (emptied at an engine start when over 1 MiB; a file and not a pipe, because the engine outlives the app and a pipe with no reader fails its writes; the app logs the new lines to its engine log from a utility queue, reading at most 64 KiB at a time, cutting a line at 2000 characters and logging at most 200 lines per start; the app opens the file itself, and if that fails for any reason (read-only, a directory, gone) the engine gets `/dev/null` and still starts), `--relaunch-app <bundle id>`); a stale file also marks the autosaves for offering. A live engine that answers is attached. *Stopping engine*: one whose `engine.json` says `stopping: true` is never attached to (no connection is opened to it) and never signalled; the app waits for its pid to exit (polling, up to 25 s, just past the engine's own 24 s `EXIT_DEADLINE`), then starts a new engine, with no alarm. Still alive after that, it is reported once ("still shutting down", taken down when an engine answers) and waited for until it exits. After such a wait the new engine's autosaves are always offered (none: nothing is shown), since the stopped engine may have been forced out at its deadline before its final recovery writes finished, and its forced exit removes `engine.json` like a clean one. An engine this app was connected to that leaves a `stopping: true` file behind (killed, or the removal blocked on a hung disk) is alarmed as a stop, not a crash. One whose connections are refused or reset 3 times (a socket that opens but sends no `welcome` within 10 s is busy, not silent: its control loop may be stalled while the audio thread plays, so it is never ended; after 3 such attempts the alarm says the engine is not responding and the app keeps retrying), while no connection has been made in this app run, gets SIGTERM, 25 s to exit, then SIGKILL, then a new engine (all logged). *Running*: an engine this app run has talked to is never signalled; a dropped connection is retried with backoff for as long as its pid lives. Once the pid is gone every window stops showing that run's cues as live (their running, paused and waiting states, progress and countdowns are cleared: those cues stopped with it) and the alarm goes up (a floating panel: above every window, a critical Dock bounce, not modal and never key by itself, so Esc and the transport keys keep working) as a crash when `engine.json` was left behind, else as a stop, and a new engine is started (at most 3 starts a minute, then an alarm). *Reattach*: when the app connection reaches another run (another token), every window's store is detached and rebound one at a time: a show with a path is reopened with `open` (on `recovery_offer`: `restore` if the window had unsaved changes, else `ignore`; `already_open` (a reopen cut short): the doc that has it, counted as restored when that doc has unsaved changes and, for a window that had unsaved changes, as edits lost when it is clean; a window with unsaved changes and no autosave newer than its file is reopened from the file, and the alarm and its log say its edits are lost), an untitled one with `open_recovery` of its workspace id's autosave (a clean one with `new`); a window that cannot be rebound closes and is listed in the alarm. A bound connection is pinned to its run's token and never says `hello` with an old doc id to a new run. Then `scan_recovery` entries no open window holds are offered behind the alarm's Restore button (one prompt each, at most 8 workspaces). A File > New or Open during the reattach gets its window at once unless a waiting window will claim the path that was opened (the engine answers `opened` before it lists the doc, so the decision uses the requested path). A current autosave of an open workspace belongs to its window and is not offered: matched by workspace id and the `path_hash` of `workspaces` (another copy of the show, same id at another path, is offered); a window known to be untitled holds only its hashless autosave; where the hash is not known (an engine without the field, a Save As the list has not caught up with) the workspace id alone decides. When the alarm offers a set-aside autosave of a workspace the reattach reopened from its file with its edits lost, the line says an earlier autosave was set aside and can be restored (matched by workspace id); the window's own log line does not claim the edits are gone for good. One set aside as stale (`stale: true`) is offered even when its workspace is open, since it may hold the newest work (file times are unreliable), and its prompt says it was set aside. The exception is an autosave that was itself loaded into a window in this app run: opened with `open_recovery` (matched by its workspace id, path hash and time) or restored with `open` + `restore` (matched by the offer's time and the window's workspace id). A time alone never hides one: a window saved after a set-aside autosave never held its edits (`AutosaveCover.swift`). The same offer is in File > Recover Autosaves… whenever the engine is connected, so an autosave whose offer was dismissed (or never made: a quit during a reattach, an untitled workspace) stays reachable. *Quit*: the prompts, then `close { doc, discard_changes: true }` for each workspace answered Don't Save (only once no later prompt cancelled the quit; the shutdown would otherwise write a recovery file for it; a failed or stalled close is logged and the quit goes on), then `goodbye { shutdown: true }`; the engine leaving after it is no alarm. An engine this app run started that no connection has reached yet (a quit while it comes up, or Quit Anyway while a new one starts after a crash) plays nothing and gets SIGTERM instead (no "not responding" prompt for it): left alone it would run on with the audio device open, since only a dropped app connection makes it relaunch the app. No engine is started once the quit is decided; an engine this run talked to, or one it did not start, is never signalled. UI tests use the in-process fake and never start a real engine. Tests: `mac/openLabTests/EngineLifecycleTests.swift`, `EngineSessionTests.swift`, `openLabUITests/EngineAlarmUITests.swift`.

Tests: `tests/cli.rs` (the binary: `engine.json` written private with this pid, `--open` of a missing file leaves the engine running, SIGTERM (stdin elsewhere) exits 0 and removes the file and the marker; skipped with a note when the machine has no output device), `host` unit tests (a start while another engine runs is refused), `host::engine_file` (atomic, private, stale and hostile files, removal only of this run's file), `run_marker` (`is_live`), `platform::signals`.

## Relink (M1.17)

`relink { folder }` (bound connection, its doc; WS-03, NFR-04): `Control::relink` clones the workspace and starts an `openlab-relink` thread with it (a `RelinkJob`); the thread checks the folder (`not_found`, `bad_request` if it is a file), runs `find_in_folder` within `ControlConfig::relink_limits` (core's defaults: 16 levels, 50 000 folders, 200 000 files, 20 s; with no media missing it does not walk the folder and answers at once) and posts `DocAnswer::Relinked`. The control thread never touches the folder. It then drops matches whose cue no longer has the reference the walk started from (an edit made meanwhile wins), applies the rest with `relink_command` through `History` (one undo step, `model_changed`, dirty) and answers with the counts and `truncated`. The walk has a slot of its own beside the document-request slot (`Docs::relink`; one walk at a time engine-wide, a second `relink` is `command_refused`), so `open`, `open_recovery` and `scan_recovery` are neither refused nor queued behind a walk that takes its whole time budget; the walk works on its copy and its matches are checked against the doc when they are applied, so nothing it does races an open or an edit. The stall check allows the walk's own time budget on top of `doc_timeout`; a walk stuck in a hung volume fails with `io` and its thread is abandoned and counted with the stuck document workers (`MAX_STUCK_WORKERS`: past it, requests that read are refused with `io`). If the thread cannot be started the request answers `internal`. If the doc closes during the walk the answer is `no_workspace`.
