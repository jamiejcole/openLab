# openLab cue engine (`openlab-core::cue_engine`)

How cues run: lifecycle states, timing, continue modes, groups, GO and the playhead. Architecture context: [ARCHITECTURE §3.2–3.3](ARCHITECTURE.md#32-clock-and-scheduling-nfr-202122). Requirement IDs refer to [`REQUIREMENTS.md`](../REQUIREMENTS.md).

Status: M2.1–M2.8, M2.10, M2.11, M2.14, M2.15 (CUE-02, CUE-03, CUE-04, CUE-05 with preview/audition on the engine side (the separate audition output, PB-09, is later), CUE-06 and NFR-07 engine side, CT-10 audio levels, CT-11..CT-17, CT-19..CT-22, PB-01..PB-05, CL-06 engine side). See [Not yet](#not-yet).

Two rules decided by the user (M2.13):

1. **Second trigger is ignored** by default. Start, GO or a continue on a cue that is already active (pre-waiting, running, post-waiting, fading or stopping) does nothing: no restart, no voice action, timers untouched; it reports a `TriggerIgnored { cue, state }` warning. GO still counts as a GO and moves the playhead as usual. A trigger on a **paused** cue resumes it. This is the cue's `second_trigger` option `nothing`; the other options (M2.14, QLab 5) are in [Second trigger](#second-trigger-m214).
2. **Auto-continue does not depend on success; auto-follow does.** A cue that breaks keeps its auto-continue, which fires the next cue on its original schedule (action start + post-wait), also when it breaks during the pre-wait (then the action is skipped, as for a disarmed cue, and the timing kept). A broken cue never fires its auto-follow. It reports `broken` while the continue is pending; Stop or Reset cancels the pending continue as on any cue. Its voice is released the moment it breaks.

## Shape

```rust
let config = EngineConfig::new(sample_rate, lookahead, seed)?; // checked: 1..=384000 Hz, lookahead ≤ 1 s
let mut engine = CueEngine::new(config);
let actions: Vec<Action> = engine.handle(&workspace, input, now);
let wake: Option<SampleTime> = engine.next_deadline();
```

- Pure and deterministic: no threads, clocks or I/O. The same workspace, inputs, times and seed always give the same actions in the same order (all internal maps are ordered).
- **Randomness** (random groups, shuffled playlists) comes from a SplitMix64 generator in core, seeded with `EngineConfig::seed`. Tests pass a fixed seed and are reproducible; the engine binary seeds it from OS entropy at startup (M4.2), so shows differ between runs.
- `handle` gets the **current** workspace every call. It first applies edits made since the last call (see [Model edits](#model-edits)), then carries out due deadlines, then the input, then deadlines again. The whole-workspace work of following edits (stopping deleted cues, moving playheads, recounting the chain limit, rebuilding the static problems) happens only on the first call after `model_changed()`; see [Model edits](#model-edits) for what a missed signal does.
- `Action`s are core types; the engine binary turns voice actions into mixer and disk-stream commands (M4.2). Core does not depend on `openlab-audio`.
- Queries: `state(cue)`, `cue_states()` (every non-idle cue, statically broken ones included), `broken_reason(cue)` (a break at run time), `problems(cue)` and `broken_cues()` (static problems, see [Broken cues](#broken-cues-cue-06-nfr-07)), `panic_end()` (see [Panic](#panic-pb-03)), `run_of(cue)` (`None` for a cue that owns no voice: idle, or broken at run time or started broken), `playhead(list)`, `standing_by(ws, list)` (CL-06), `playhead_positions(ws, list)`, `chain_limit(ws)`, `fade_level(cue, param, at)`, `fade_ramps(cue, at)` (see [Fade cues](#fade-cues-ct-10)).
- One engine per open workspace. A newly opened workspace gets a new engine; call `handle(ws, Tick, now)` once so the playheads are reported.

## Time

- `SampleTime` is a `u64` frame count at the device rate, the same clock as the mixer's `samples_rendered` (ARCHITECTURE §3.2). `EngineConfig::sample_rate` is the device rate.
- The show file stores seconds. Every conversion goes through `seconds_to_samples`: round to the nearest sample, halves away from zero; negative and NaN give 0; values beyond `u64` (and +∞) saturate. Times are converted when they are used (see Model edits).
- All time arithmetic saturates; nothing panics on extreme values.
- **`now`** is the scheduling time: the earliest sample a command can still hit. The control loop passes `samples_rendered + one block`. `now` should not go backwards; if it does (a device restart), nothing panics: pending deadlines simply wait, and double-GO protection does not block (see GO).

### Deadlines, lookahead and late ticks

- Every timer is an absolute sample deadline. Each transition is computed **at its deadline sample `T`**, never at the time of the call: a successor triggered by a timer that expired at `T` starts its pre-wait at `T`, whenever the call happens. Late calls never make later cues drift.
- A call carries out every deadline in `..now + lookahead` (end excluded; with lookahead 0, every deadline up to and including `now`), earliest first (ties: the cue started first goes first, so causes come before effects).
- `EngineConfig::lookahead` (samples) lets a deadline that falls inside the next block be committed on its exact sample even though the control loop wakes with jitter. The control loop sets it to one block: with `now = samples_rendered + block`, the window `now .. now + block` is exactly the next block, so no voice start lands beyond it (docs/audio.md). It calls `Tick` when `is_due(now)`: `next_deadline() <= now + max(lookahead, 1) − 1`, so with lookahead 0 a deadline at `now` is ticked at `now`. `EngineConfig::new` refuses a lookahead longer than one second of samples and rates outside 1 to 384000 Hz. Deadlines inside the window are committed: an operator input in the same call cannot withdraw them (exactly like commands already in the mixer's queue), so a stop issued at `now` for a voice committed to start at `T > now` is sent for `T`, and a pause freezes timers at `now`.
- **Commands for one voice never go backwards in time.** Each run remembers the latest sample a command for its voice was sent for (start, stop, pause, resume, ramp, devamp). A later command for that voice — also from a later call, and also an operator input that comes after a control or Fade cue committed something in the window — is dated no earlier: a Fade taking over a level whose ramp is committed for `T` ramps from `T`; a pause after a committed ramp or devamp freezes the timers on that sample; a stop after a committed pause stops there; a resume is never dated before its pause (it then resumes as of the pause). A remembered sample beyond the call's horizon can only come from a clock that went back (device restart) and is ignored.
- **Late rule**: a voice whose deadline `T` has already passed (`T < now`, a late tick) starts at `max(T, now) = now`, from its start offset (the head of the sound is not cut), with a `LateStart { late_by }` warning. Its state change still reports `at: T`, and every timer derived from it counts from `T`.

## States (CUE-04)

Each cue reports exactly one state:

| State | Meaning |
|---|---|
| `idle` | Nothing to do. Idle cues have no runtime. |
| `loaded` | Loaded (optionally to a time) and ready to start. |
| `pre-waiting` | Started; the pre-wait is counting down. |
| `running` | The action is under way (post-wait may be counting too). |
| `paused` | Pre-wait, action and post-wait are frozen. |
| `post-waiting` | The action is complete; the post-wait is still counting down to the next cue. |
| `fading` | An audio cue in its action whose levels a running Fade cue is moving (see [Fade cues](#fade-cues-ct-10)). |
| `stopping` | Fading out before it stops (a stop with a fade). |
| `broken` | Cannot run. **At run time** (feedback): owns no voice and cannot start until reset; its pending auto-continue still fires on schedule. Reasons: `voice_rejected`, `stream_failed`, `device_lost`. **Static** (problems found before it runs: missing media, device or target; see [Broken cues](#broken-cues-cue-06-nfr-07)): reported while the cue has no runtime, until the problems are fixed. |

Internally a started cue is a **run**: `{pre-wait deadline, action progress (start, end if known), post-wait deadline, paused-at, fade-out end}`. Post-wait is a timer owned by the cue, not a phase: a cue is `running` while its post-wait elapses, and `post-waiting` only once its action has completed and the post-wait has not. The reported state is derived: broken › paused › stopping › fading › pre-waiting › running › post-waiting.

A start always reports `pre-waiting` first, even for a zero pre-wait (followed by `running` in the same call).

Each voice segment has a `RunId`, unique for the engine's lifetime (the binary can use it as the mixer `VoiceId`). Loading or starting creates it; starting a loaded cue keeps it; **every resume gives the run a fresh id** (`ResumeVoice { run: fresh, paused: previous }`), so feedback still on its way for the paused segment is stale whenever it arrives. `run_of(cue)` is the current id.

## Timing and continue modes (CUE-02, CUE-03)

Started at `S` with pre-wait `P`, post-wait `W`:

- The action starts at `A = S + P`.
- **Action duration**: Audio — unknown to core; the action completes on `ActionEnded` feedback (`VoiceFinished`), and a cue that loops forever never completes until it is stopped (or devamped, M2.5). Wait — its `duration` (CT-20). Memo — 0; it does nothing (CT-21). Group — until no child is busy (see [Groups](#groups-ct-22)). Fade — its `duration` (see [Fade cues](#fade-cues-ct-10)). Start, Stop, Pause, Load, Reset, Devamp, GoTo, Arm, Disarm — 0: they act on their target when the action starts (see [Control cues](#control-cues-ct-11ct-19)). Disarmed cues (CUE-07, as the engine sees them: see Arm/Disarm) — 0: the action is skipped (no voice, no control action, no fade), but pre-wait, post-wait and continue mode still apply. Network cues (M4.6) — 0, with an `Unsupported` warning (see Not yet).
- **Do not continue**: nothing else is triggered; the post-wait is not used.
- **Auto-continue**: the next cue is triggered at `A + W` (post-wait counted from the action start; `W = 0` triggers it at `A`). The post-wait timer is armed when the action starts.
- **Auto-follow**: the next cue is triggered when the action completes: at the `at` of `ActionEnded` (clamped to no earlier than `A`), or at `A + duration` for known durations. The post-wait is ignored.
- "The next cue" is the cue after this one in its list (or group) **when the trigger fires**. The last cue triggers nothing. Inside timeline, playlist and random groups the group runs its children and their continue modes are ignored (see [Groups](#groups-ct-22)).
- Triggering a cue is the Start operation (so an active successor applies its [second-trigger option](#second-trigger-m214): by default it ignores the trigger, and a paused one resumes).
- A cue is finished (idle) when its action is complete and no post-wait or fade-out is pending.
- Stopping or resetting a cue cancels its pending post-wait and its auto-follow. A cue that breaks cancels its auto-follow but keeps its auto-continue (rule 2 above).

### Load to time

`Load { time }` loads the cue `t = time` seconds into its timeline (pre-wait, then action). The split into pre-wait and action is made **at load**, with the pre-wait the cue has then (so `LoadVoice.offset` and the later `StartVoice.offset` always agree); a pre-wait edited between the load and the start does not change it. When it starts at `S`:

- `t < P`: the pre-wait has `P − t` left; the action starts from its beginning.
- `t ≥ P`: the action starts at `S`, `a = t − P` into the action (`StartVoice.offset`, also `LoadVoice.offset`). The post-wait has `W − a` left and a known duration `D − a` (both at least 0, so an elapsed post-wait triggers the next cue at `S`).

### Chains and the chain bound

Zero-wait chains run inside one call: an auto-continue chain of zero waits starts every cue on the same sample. Commands do not check references (M1-B) and edits can create trigger cycles, so **the calls at one `now` start at most `chain_limit(ws)` = number of cues in the workspace (all depths) + 64 cues between them** (the budget of a call is what the earlier calls at the same `now` left; a call at another `now` has the whole limit). Every start that creates or resumes a runtime counts, including children started by their group; a trigger that starts nothing (`TriggerIgnored`, `CueBroken`, `UnknownCue`) costs nothing, so repeated ignored triggers within one block (a stuck controller key) never use up the budget a GO in that block needs, and a cycle still ends because each of its laps creates or resumes a runtime (a looping playlist of zero-length children is such a cycle: it is cut at the limit and the group then completes). Without a cycle a call starts each cue at most once, so only a cycle reaches it. Start cues, GoTo-and-GO and Devamp's "start next cue" count like any start, and so does what a [second trigger](#second-trigger-m214) starts (a restart, a playlist's next or previous child), so control-cue cycles (A starts B starts A, GoTo loops; load-time validation warns about them, edits can still make them) are bounded the same way. A start beyond the limit is dropped with a `ChainLimit` warning (an operator GO that finds the budget already spent is ignored with `GoIgnored { reason: chain_limit }`: no start, no playhead move, and the double-GO interval is not restarted, so the operator can press GO again); a **playlist** stops starting children when 8 starts are left (`PLAYLIST_RESERVE`, also a `ChainLimit` warning), so a looping playlist of zero-length children, which would spend the whole call, still lets the cue after its group start; the chain is cut, not deferred, so a cycle can never hang a call or keep re-firing on later ticks at the same sample. As a second line of defence the deadline loop has its own step guard.

**Across calls**: a cycle that makes no time progress cannot outlive the call it starts in. All its deadlines lie on one sample, which falls inside that call's window, so the whole cycle runs (and is cut) there; nothing of it is left pending. A cycle can only reach a later call through time: a non-zero pre-wait, post-wait, Wait or Fade duration, which moves the timeline on (it keeps running, one lap per period, like any timed loop — not a hang, and Stop/Reset/panic end it), or through feedback from the mixer, which is dated at mixer time (an end report is no earlier than the voice's real start, which is never before the `now` of the call that started it; a devamp answer is no earlier than the devamp command). Feedback can be dated on the very sample that started the lap — a voice that ends on its start sample (loaded or started at or past the end of its file: core does not know file lengths) — and a binary may hand it over at that same `now`. That is why the budget is per sample, not per call: such a lap repeats in call after call at one `now` only until the sample's budget is spent, and is then cut as within a call (a looping playlist completes, a Start cycle stops). In the real binary `now` has moved on by at least a block by the time the mixer reports what it rendered, so such a lap then runs once per block, like a timed loop. A cue that acts while its own action is under way also ignores a trigger back to itself (a Start cue targeting itself: `TriggerIgnored`).

## Groups (CT-22)

A Group cue is a cue like any other: its own pre-wait, post-wait and continue mode, the [operations](#operations-cue-05) and the second-trigger rule. Its **action** is running its children; behaviour follows QLab 5's group modes.

### Its action

- The action starts when the group's pre-wait elapses, at `A`, and starts children at `A` according to the mode (each child then runs its own pre-wait).
- A child is **busy** while it has a runtime that is not idle, loaded or settled broken: pre-waiting, running, post-waiting, paused, stopping, or broken with an auto-continue still pending.
- The action **completes** on the sample its last busy child stops being busy (completes, settles broken, is stopped, reset or deleted), and then the group's continue mode applies as for any cue: auto-follow triggers the cue after the group at that sample; auto-continue fires `A + post-wait` (a post-wait longer than the children makes the group `post-waiting`).
- **Success**: a group whose run saw a child break (feedback, or a broken child it could not start) does not auto-follow; its auto-continue still fires (rule 2 above, applied to the group). Nested groups pass this on: an inner group that saw a break counts as a broken child of the outer one.
- **Stopped children**: if the last busy child left by being stopped, reset or deleted, the group stops too (idle, its post-wait and auto-follow cancelled) instead of completing. Stopping a child while another is still busy only stops that child.
- An empty or disarmed group's action completes at once (a disarmed group starts no children).
- Feedback (`ActionEnded`/`ActionFailed`) never concerns a group; any naming one is ignored.

### Modes

| Mode | On action start | Children's continue modes | Playhead after GO on the group |
|---|---|---|---|
| Timeline (start all simultaneously) | every child, at `A` | ignored | after the group's continue chain |
| Start first and go to next | the first child | apply: children chain within the group | after the group's continue chain |
| Start first and enter | the first child | apply | into the group: after the first child's chain (disarmed: past the group) |
| Playlist | the first child (shuffled: the first of a shuffled pass) | ignored | after the group's continue chain |
| Start random | one random child | ignored | after the group's continue chain |

- **Playlist**: each next child starts on the sample the previous child's action completes (its pre-wait then counts). A child that breaks (feedback) moves the playlist on at the moment it breaks; a broken child that cannot start is skipped at once; both mark the run as not successful. Without loop the group completes after the last child. With loop it wraps to the first and never completes on its own (stop it, or devamp it: see [Devamp](#devamp-ct-16)). With shuffle each pass plays every child exactly once in a fresh random order. Unshuffled, the next child is the one after the current one as the group stands when the trigger fires (a reorder applies to the next child; a removed current child is followed by the child that took its place). Shuffled, a pass's order is fixed when the pass starts; children removed meanwhile are skipped and children added play from the next pass. A pass in which no child could start ends the playlist; so does the chain limit. A shuffled pass never opens with the child that closed the previous pass (when there are two or more). **Paused playlist**: if the current child's end or failure report arrives while the group is paused (it was in flight when the pause came: the end is dated before the pause), the playlist moves on when the group resumes — the next child starts on the resume sample, as if the playlist had moved on just as it was paused; if that was the last child (no loop), the group completes on the resume sample instead, with its continue as usual (auto-follow fires unless a child broke). A pause never ends a playlist early or skips its remaining children.
- **Random** (follows QLab 5: round-robin): every playable child — armed, without static problems and not already busy (e.g. started on its own during the group's pre-wait) — plays once before any child plays again. Each action start picks uniformly, from the seeded generator, among the playable children **not yet picked in the current cycle**, taken as the group stands at that moment: a child added mid-cycle joins the current cycle, a removed one drops out, a disarmed (or broken, or busy) one is passed over while it is so and is a candidate again once it is playable and still unpicked. When no candidate is left, a new cycle starts; it never opens with the child picked last when there are two or more playable children, so a child never plays twice in a row across the boundary either. If no child is playable at all, the same rule runs over all the children, so one child is always picked (its start then skips it as disarmed or broken, as for any child). The cycle lives in the engine only: it is not saved, survives Stop/Reset/Panic, and starts afresh with a new engine (the workspace opened again), as QLab's resets when the workspace opens. Deterministic for a given seed.

### A child started on its own

Starting a cue inside a group that is idle or loaded (`Start`, or GO with the playhead on a child) makes every idle group around it **run as adopted**: it reports `running` from that sample and completes (goes idle) when no child is busy, but starts no other children and fires no continue of its own. A child started while its group is post-waiting puts the group back to `running`, its post-wait still counting; it completes again without auto-follow. A child started while its group pre-waits runs on its own; when the group's action starts, that child gets a second trigger (it is already active): its option applies, by default it ignores it.

### State of a group

The group's own run gives its state, so it is exactly one state: `pre-waiting` during its pre-wait, `running` while its action is under way (any child busy), `post-waiting` after it with the post-wait pending, `paused` when the group was paused, `stopping` while a stop with fade waits for its children, `idle` otherwise. A paused child alone does not pause its group.

### Operations on a group

Each applies to the group and to its descendants (every depth):

- **Stop** stops every descendant with a runtime, children before their groups, then the group. Hard stop: everything idle at once. Stop with fade: each playing voice fades out (silent actions stop at once); a group **in its action** with a child still fading reports `stopping` and goes idle when its last child has stopped. A group (like any cue) that has not reached its action — pre-waiting, or loaded — stops at once: its pending action is cancelled and it never starts children; children it already had running fade as above. A second stop is a hard stop. A stopping group cannot be paused (as for any stopping cue).
- **Pause** pauses the group and every active descendant (voices get `PauseVoice`); every timer keeps the time it had left. **Resume** (and Start/GO on a paused group, by the second-trigger rule with the option `nothing`) resumes the group and every paused descendant; a group whose last child left while it was paused ends then.
- **Reset** resets every descendant (clearing broken children) and the group.
- **Load** loads the group and the children its action starts first: timeline — all children; start-first modes and an unshuffled playlist — the first child; shuffled playlist and random — none. Load to time `t` loads them `t − group pre-wait` seconds (at least 0) into their own timelines, so a loaded timeline group starts its children at that point.
- **Start** on an active group applies the **group's** second-trigger option to the group as a whole (default: ignored, `TriggerIgnored`, its children untouched); see [Second trigger](#second-trigger-m214).

### Nesting and bounds

Groups nest to `MAX_GROUP_DEPTH` (validation and commands enforce it). The engine's own walks over descendants and over the list (positions, `locate`) are iterative. Looking a cue or its ancestors up uses the model's recursive search (`Workspace::find_cue`, `tree::find_path`), whose depth is bounded by `MAX_GROUP_DEPTH` in every validated workspace (and by the JSON parser's limit on load); a tree hundreds of levels deep built directly still works (tested). Every start inside a group counts towards the call's chain limit.

## GO and double-GO (PB-01, PB-02)

- `Go { list }` starts the cue at the list's playhead at `now` and moves the playhead to the cue after the last cue of its continue chain: from the playhead cue, every following cue reached through auto-continue/auto-follow (as the model stands) is skipped. If the chain runs to the end of the list, the playhead goes past the end. Groups (follows QLab 5): GO on an armed "start first and enter" group moves the playhead **into** it, to the child after the first child's continue chain (a disarmed one starts nothing and is skipped as a unit, like any disarmed cue). Every other group — timeline, start first and go to next, playlist, random — is one unit for the playhead: GO on it, or a chain reaching it, moves the playhead to the cue after the group's chain, never onto its children. GO on a cue inside a group (any mode, as in QLab 5) starts that cue only; its idle groups run adopted (see Groups). The playhead then moves to the cue after its continue chain among its siblings: in "start first" groups the children's continue modes chain; in timeline, playlist and random groups they are ignored, so it is the next sibling. Past the group's last child the playhead leaves the group to the cue after the **group's** continue chain (and so on outwards; the group's own auto-continue/follow targets are skipped as at the top level). So a playhead put explicitly on a child of a group that GO does not enter (a jump, `SetPlayhead`) stays among that group's children, GO by GO, until it leaves the group — the same path `PlayheadNext` takes from there (QLab 5 documents only the entered mode; this keeps GO and stepping in step).
- GO on a cue that is already active applies the cue's [second-trigger option](#second-trigger-m214) (default: ignored for that cue, `TriggerIgnored`), but the GO counts and the playhead moves on. GO on a paused cue resumes it (also one that broke while paused: its frozen timers run again). GO on a broken cue does not start it (`CueBroken` warning) but still counts as a GO and moves the playhead on, so the show can continue with the next GO. A cue with static problems keeps its timing, so its auto-continue fires (see [Broken cues](#broken-cues-cue-06-nfr-07)).
- Ignored GOs report `GoIgnored { reason }`: `no_cue` (playhead past the end, or empty list), `unknown_list`, `double_go`, or `chain_limit` (the chain budget of the GO's `now` was spent by a trigger cycle before the GO, in that call or an earlier one at the same `now`: see [Chains](#chains-and-the-chain-bound)).
- The GO of a GoTo cue with "and GO" works the same way on the target's list, dated on the GoTo cue's action start, but it is not an operator GO: double-GO protection never blocks it and it does not restart the interval (see [GoTo](#goto-ct-17)).
- **Double-GO**: a GO less than `min_go_interval` after the previous **accepted** GO (in samples, any list) is ignored; one exactly at the interval is accepted. Ignored GOs do not restart the interval. 0 = off. If `now` is earlier than the last accepted GO (clock restart), the GO is accepted.

## Playhead (PB-05, CL-06)

- Each cue list has a playhead: the standing-by cue, or `None` past the end of the list or for an empty list. A new list stands on its first cue. `PlayheadChanged` reports every move, including the initial one.
- **Positions** (M2.11): as in QLab 5, the playhead can stand on any cue of its list, at any depth and in a group of any mode. In order, the positions are the list's cues depth-first, a group before its children: `1, 2, 2.1, 2.2, 3`. `playhead_positions(ws, list)` lists them. (With duplicate ids, an invalid workspace, the first occurrence counts.)
- **Stepping** (follows QLab 5: only "start first and enter" groups are entered; collapsing a group in the UI changes nothing): `PlayheadNext` and `PlayheadPrevious` step through the positions with the children of every other group (timeline, start first and go to next, playlist, random) left out, so such a group is passed over as a unit, both ways. The exception is a group the playhead already stands inside (put there explicitly): its children are stepped through, so stepping goes on among the siblings and then leaves the group, as GO from a child does. An enter group is entered by mode alone (also when disarmed: navigation fires nothing). `PlayheadNext`: one step down (from an enter group to its first child; from a group's last child out to the cue after the group); from the last step to past the end, which stays. `PlayheadPrevious`: one step up (from the cue after an enter group to its last descendant that stepping reaches; from the cue after any other group to the group itself); from past the end to the last step; the first stays. `playhead_positions` still lists every cue: explicit navigation reaches any of them. `SetPlayhead { cue }` (by id; `None` = past the end) and `SetPlayheadByNumber` (exact number match, first in position order) take cues of that list; a cue not in the list warns `NotInList`, an unknown number `NumberNotFound`; both leave the playhead. Navigation never fires anything.
- Edits: a reordered or moved playhead cue that is still in the list keeps the playhead. A deleted one (or one inside a deleted group) gives way to the first position that came after it and still exists, or past the end. An empty list that gains cues stands on its first cue. A deleted list loses its playhead.

## Operations (CUE-05)

`now` is when the operation comes. Voice actions apply to armed Audio cues only.

| From \ op | Start | Stop | Stop with fade | Pause | Resume | Load (to time) | Reset |
|---|---|---|---|---|---|---|---|
| idle | pre-waiting (new run) | idle | idle | idle | idle | loaded, `LoadVoice` | idle |
| loaded | pre-waiting (same run, loaded offset) | idle, `UnloadVoice` | idle, `UnloadVoice` | loaded | loaded | loaded (reload: `UnloadVoice`, `LoadVoice`, new run) | idle, `UnloadVoice` |
| pre-waiting | pre-waiting, `TriggerIgnored` | idle (action and continue cancelled) | idle | paused | pre-waiting | pre-waiting, `LoadIgnored` | idle |
| running | running, `TriggerIgnored` | idle, `StopVoice` | stopping, `StopVoice` with fade (silent actions: idle at once) | paused, `PauseVoice` | running | running, `LoadIgnored` | idle, `StopVoice` |
| paused | resumes (as Resume) | idle, `StopVoice` | idle, `StopVoice` (hard) | paused | the frozen state, `ResumeVoice` | paused, `LoadIgnored` | idle, `StopVoice` |
| post-waiting | post-waiting, `TriggerIgnored` | idle (next cue cancelled) | idle | paused | post-waiting | post-waiting, `LoadIgnored` | idle |
| stopping | stopping, `TriggerIgnored` | idle, `StopVoice` (hard) | idle, `StopVoice` (hard) | stopping | stopping | stopping, `LoadIgnored` | idle, `StopVoice` (hard) |
| broken | broken, `CueBroken` (static problems: its timing runs, see [Broken cues](#broken-cues-cue-06-nfr-07)); a broken cue that is also paused resumes, as any paused cue | broken (pending auto-continue cancelled) | broken (same) | broken (its timers freeze) | broken (its timers continue) | broken, `CueBroken` | idle (pending auto-continue cancelled); a cue with static problems stays broken |

Events:

| From | Event | To |
|---|---|---|
| pre-waiting | pre-wait elapses at `T` | running; `StartVoice { at: max(T, now) }` |
| running | post-wait elapses at `T` (auto-continue) | running; next cue triggered at `T` |
| running | action completes at `T` (feedback, or known duration) | post-waiting if a post-wait is pending, else idle; auto-follow triggers the next cue at `T` |
| post-waiting | post-wait elapses at `T` | idle; next cue triggered at `T` |
| stopping | fade-out ends (`stop at + fade frames`, or `ActionEnded` first) | idle |
| loaded, any active | `ActionFailed` for the current run | broken: the run's voice is released at once (`StopVoice`, or `UnloadVoice` if it never started). Auto-follow is cancelled; a pending or still-to-be-armed auto-continue fires on its original schedule (a pre-waiting cue skips its action at the action start and arms the post-wait as usual; a paused one stays held until resumed). A broken cue owns no voice, so Stop and Reset have nothing left to silence |
| paused | time passes | paused (nothing runs) |
| any non-idle | cue deleted from the workspace | idle; `StopVoice`/`UnloadVoice`, `CueRemoved` warning if it was active |
| any non-idle | its id now names a cue of the other sort (group vs. not; duplicate ids or a replaced cue) | idle, as if deleted |
| group pre-waiting | pre-wait elapses at `T` | running; children started at `T` per mode (none busy: the action completes at `T`) |
| group running | last busy child completes or settles broken at `T` | post-waiting if a post-wait is pending, else idle; auto-follow at `T` unless a child broke |
| group running | last busy child stopped, reset or deleted at `T` | idle (continue cancelled) |
| group running (playlist) | current child's action completes, or it breaks, at `T` | running; next child started at `T` (or the group completes, above) |
| group stopping | last busy child has stopped | idle |
| group idle / loaded | a child starts on its own at `T` | running (adopted) |
| group post-waiting | a child starts on its own at `T` | running, post-wait still counting |

- **Pause** freezes every timer at `now`; **resume** at `R` moves every pending deadline `R − now_paused` later, so pre-wait, action and post-wait keep exactly the time they had left. `PauseVoice`/`ResumeVoice` carry the position the voice has actually reached in the action (`offset`, counted from the voice's real start sample, so a late start or a pause before a start committed in the lookahead window is exact), so the binary can pause in the mixer or stop and restart from the offset.
- **Stop with fade** fades a playing voice out over the fade's length (`StopVoice.fade`) and ends the cue when the fade ends — without waiting for feedback, which can be lost if the event queue overflows. A second stop is a hard stop.
- A stop or pause never lands before the voice's own start sample (`at` = `max(now, voice start)`), so in the mixer it cannot be overtaken by a start already committed.
- Operations on a cue id that is not in the workspace warn `UnknownCue` and do nothing.
- On a Group, every operation also reaches its descendants; see [Operations on a group](#operations-on-a-group).
- The `Start` column is for the option `nothing`; any other [second-trigger option](#second-trigger-m214) replaces the `TriggerIgnored` and resume entries.

## Second trigger (M2.14)

Each cue has a `second_trigger` option and a `second_trigger_on_release` flag (show file: docs/file-format.md §5.1; edited with `CueProperty::SecondTrigger` / `SecondTriggerOnRelease`, undoable, batchable). Behaviour follows QLab 5 ("second trigger"). The option applies to **every trigger that would start the cue while it is active**: `Start`, GO, a Start cue, GoTo-and-GO, a continue (auto-continue, auto-follow, Devamp's "start next cue"), a group starting its children, and so whatever input the binary maps hotkeys, OSC and protocol starts to. Double-GO protection is separate and filters GOs first. **Active** = pre-waiting, running, post-waiting, paused, fading or stopping.

| Option | Effect on the active cue (dated on the trigger, `at`) |
|---|---|
| `nothing` (default) | ignored: `TriggerIgnored { cue, state }`; a paused cue resumes (rule 1) |
| `panic` | the cue's own panic: it and everything in it fade out as in [Panic](#panic-pb-03), ending `panic_duration` after the trigger (0: stops at once). Not a workspace panic: other cues and `panic_end()` are untouched. Its cues count as fading out in a panic, so a further trigger restarts them (below) |
| `stop`, `hard_stop` | stops the cue and everything in it at once (as `Stop` without fade). QLab's two differ only for audio effects (a hard stop cuts their tails), which v0.0.1 does not have |
| `hard_stop_and_restart` | hard-stops it and everything in it and starts it afresh at once (a new run and `RunId`, its pre-wait from the top). The start is charged to the chain budget, so a cycle of restarts ends at the chain limit (a `ChainLimit` warning; a restart that finds the budget spent does nothing, not even the stop). A restarted child that was its playlist's current child stays the current child. A cue with static problems is stopped and its new run keeps its timing without starting (`CueBroken`), as any start |
| `devamp` | as a Devamp cue on itself without "start next cue" or "stop target when slice ends": an audio cue playing in its action gets `DevampVoice`; a looping playlist finishes its current child and completes; a cue paused in its action keeps it for the resume. A cue that cannot devamp (another kind, not in its action, stopping, a non-looping or adopted group, one already pending) does nothing but warn `DevampIgnored { cue }` |
| `play_next`, `play_previous` | Playlist groups only, on a playlist playing a child (in its action, not stopping, adopted or devamped; paused too): the child playing is hard-stopped and the child after (before) it starts on `at`, wrapping when the playlist loops. Without loop, `play_next` past the last child completes the group as if that child had ended (its continue applies), and `play_previous` on the first child plays it again from the top. Shuffled, the pass's order is followed (after its end a new pass, as usual; `play_previous` from its first child wraps to its last with loop). A paused playlist resumes on the new child. The new child's start is charged like any playlist move (it is not made when only `PLAYLIST_RESERVE` starts are left: `ChainLimit`, nothing changes). On a playlist not playing a child: `TriggerIgnored`. On any other cue they act as `nothing` (validation warns `SecondTriggerNeedsPlaylist`; the value is kept, so a group-mode change makes it apply) |

- **Broken**: a cue broken at run time or started broken is not affected by its option: `CueBroken` (a paused one resumes), as before.
- **Paused** (orchestrator decision, to confirm against QLab: PROGRESS M2.14): with `nothing` the trigger resumes the cue; with any other option the option applies (stop stops it without resuming, restart restarts from the top, panic hard-stops it as the panic does a paused cue, devamp is held for the resume).
- **Fading out in a panic** (a workspace Panic or the cue's own): a trigger hard-stops it and starts it afresh whatever its option (see [Panic](#panic-pb-03)).
- **Groups**: the option of the cue that was triggered applies. A group's option acts on the group as a whole; a child's applies when the child itself is triggered (by any source, including its group starting it: a timeline group starting a child that is already busy applies the child's option).
- **On release**: `Input::TriggerReleased { cue }` (the binary sends it on hotkey or MIDI key-up, M4; QLab offers it for hotkey, MIDI and cart triggers). It is a second trigger only if the cue has `second_trigger_on_release`, is active (not broken, not fading out in a panic) and its option is not `nothing`: then the option applies as above, on `now`. Otherwise it does nothing and says nothing (a release never starts or resumes a cue). With `panic` or `stop` this gives sampler behaviour: press to start, release to fade or stop, press again to start afresh. An unknown cue warns `UnknownCue`.
- Stop, panic and devamp start nothing and cost no chain budget; restart and play next/previous are charged for what they start.

## Preview (CUE-05, PB-09)

`Input::Preview { cue }` plays an audio cue **to listen to it**, outside the show; `Input::StopPreview { cue }` ends it (`None`: every preview). In v0.0.1 only the operation exists engine-side: the audition output itself (PB-09, untagged) needs a setting the show file does not have yet, so until then the binary plays previews on the cue's own patch (M4.2; see PROGRESS).

- **What plays**: the cue's audio from the start of its action, now (`Action::PreviewStart { cue, run, at }`, `at = now`): no pre-wait, no post-wait, no continue mode, no load-to-time. Loops and slices play as the cue says; an infinite loop plays until stopped. Disarmed cues can be previewed (arming is about the show; QLab confirmation: M2.20). Other kinds are `PreviewIgnored { reason: not_audio }` and do nothing; unknown cues warn `UnknownCue`; a cue with static problems warns `CueBroken` and plays nothing.
- **Invisible to the show**: a preview has no `CueState` (the cue keeps whatever show state it has), moves no playhead, does not touch double-GO protection, never triggers a continue, auto-follow or "start next cue", does not make a group run adopted, uses none of the call's chain budget, and does not use the show's `RunId`s: previews are numbered from `PREVIEW_RUN_BASE` (2^63), so the show's ids are the same whether or not anything was previewed, and a preview id can still be the mixer's voice id. The same cue can play in the show and in a preview at once; each ignores the other's stop, reset and end reports (feedback is matched on cue **and** run).
- **Reported**: `Action::PreviewChanged { cue, active, at }` on start and on every end; `is_previewing(cue)`, `previewing()`, `preview_run(cue)`.
- **Second preview** of a cue that is being previewed: ignored (`PreviewIgnored { reason: already_previewing }`), as a second trigger is; a UI that toggles sends `StopPreview` while `is_previewing`.
- **End**: the voice ends by itself (`ActionEnded` with the preview's `run`: `PreviewChanged { active: false }`), `StopPreview` (the preview is over as of now: `PreviewStop { cue, run, at: max(now, start), fade }` with a linear `PREVIEW_STOP_FADE_SECONDS` (50 ms) fade-out, so a stop does not click in the operator's headphones; the fade is the mixer's, the engine does not wait for it and a late end report is stale), a failure (`ActionFailed` with its `run`: `PreviewStop` hard, `PreviewChanged`, `PreviewFailed` warning; the cue is **not** broken in the show), the cue being deleted or no longer an audio cue (hard stop, at the next signalled call).
- **Panic** stops every preview at once (hard `PreviewStop`, no fade): Panic means everything. **Pause All / Resume All** leave previews alone (a preview cannot be paused; it is not part of the show). Stop, Pause, Reset, Load and Start on the cue concern the show only.

## Control cues (CT-11..CT-19)

A control cue is a cue like any other (pre-wait, post-wait, continue mode, operations, second-trigger rule). At its **action start** `A` (after its own pre-wait) it acts on its target **as if the operator had done the operation** at that moment, and its own action then completes at once (so auto-follow fires at `A`). Its own continue mode applies as for any cue. Behaviour follows QLab 5.

- The operation is dated on `A`: an operation in the lookahead window acts on its own sample (`StopVoice { at: A }`, not `now`); a late one (`A < now`) acts at `now`, except a start, which is dated `A` like any trigger so later timing keeps its schedule (the late rule then applies to voices).
- The cue is still in its action while it acts, so a trigger from its target back to it is ignored (`TriggerIgnored`).
- **Targets**: a cue with no target, a missing target, itself as target or a target of the wrong kind has static problems (see [Broken cues](#broken-cues-cue-06-nfr-07)): it is `broken` and its action never runs. The run-time checks (`NoTarget`, `TargetMissing`, `TargetWrongKind`: the cue does nothing, its timing and continue apply) remain for static problems that are out of date (a model change the binary did not signal, release builds only).
- Targets that are groups use the group operations ([Operations on a group](#operations-on-a-group)): Stop/Pause/Load/Reset reach every descendant, Start starts the group in its mode, a target inside a group runs its idle groups adopted.

| Cue | Action at `A` |
|---|---|
| Start (CT-11) | the Start operation on the target, dated `A`: idle/loaded → starts; active → its [second-trigger option](#second-trigger-m214) (default: paused → resumes, otherwise `TriggerIgnored`); broken → `CueBroken`. A disarmed target is skipped as on GO. |
| Stop (CT-12) | Stop with the cue's fade (`fade_out`, duration 0 = hard stop). |
| Pause (CT-13) | Pause (a paused or idle target is left as it is). |
| Load (CT-14) | Load to `load_to_time` (an active target: `LoadIgnored`; broken: `CueBroken`). |
| Reset (CT-15) | Reset (clears broken). It does not undo Arm/Disarm changes. |
| Devamp (CT-16) | see [Devamp](#devamp-ct-16) |
| GoTo (CT-17) | see [GoTo](#goto-ct-17) |
| Arm / Disarm (CT-19) | see [Arm and Disarm](#arm-and-disarm-ct-19) |
| Wait (CT-20) | nothing; its action lasts its duration |
| Memo (CT-21) | nothing; its action completes at once |

### GoTo (CT-17)

- Moves the playhead of the **target's** cue list (any list of the workspace, not only the GoTo cue's own) to the target, at any depth (the playhead may stand on any cue, see [Playhead](#playhead-pb-05-cl-06)).
- With "and GO" it then GOes on that list, dated `A`: the target starts and the playhead moves past its continue chain (or into an armed "start first and enter" group), exactly as an operator GO. As in QLab, this is not an operator GO: double-GO protection does not block it and it does not restart the double-GO interval.

### Arm and Disarm (CT-19)

- The engine cannot change the `&Workspace`. An Arm/Disarm cue emits `SetArmed { cue, armed }` and records the change as an **override** that the engine honours for the rest of that call: a Disarm followed by a trigger of the target in the same chain sees the target disarmed (its action is skipped, a Load sends no `LoadVoice`, GO does not enter a disarmed "start first and enter" group).
- Only the target itself changes (a group's children keep theirs). A running target keeps running; the change applies to its next action. Arming an already armed cue (as the engine sees it) does nothing and emits nothing.
- The binary applies every `SetArmed` to the model before the next `handle` call (M4.2 contract), so each call starts by dropping all overrides: from then on the model rules, including an operator edit of `armed` made right after.

### Devamp (CT-16)

- **"Start next cue" is the Devamp cue's continue** (QLab: with it, the Devamp cue acts as if it auto-continued when the slice ends). On an armed Devamp cue it replaces the cue's own continue mode: the next cue starts once, when the loop is left, never also at the Devamp cue's action start, and the Devamp cue's post-wait is not used. For the playhead it counts as a continue: GO on it moves the playhead past the cue it will start (and on along that cue's chain). Without "start next cue" (or on a disarmed Devamp cue) its own continue mode applies as usual.
- **Audio target** that is playing (in its action with a started voice; not paused, stopping or broken; for a paused one see **Pause** below): emits `DevampVoice { cue: target, run, at: max(A, now, voice start), stop }` (`stop` = "stop target when slice ends"). The audio side answers:
  - `DevampScheduled { at: L }`: the voice leaves its loop on `L`. With "start next cue", the cue **after the Devamp cue** (QLab: the Devamp cue then acts as if it auto-continued when the slice ends; looked up as for any continue when it fires) starts on exactly `L` — a deadline, so it lands on `L` inside the lookahead window, and late at `now` (with `L` as its timing) otherwise. The target plays on into its next slice (or ends there with `stop`) and completes on its end report as usual. If the target's end report comes before that deadline was carried out (the voice ended at `T ≤ L`), the next cue starts on `min(L, T)`, so it never waits past the end of the cue it follows. **Pause**: a pending devamp survives a pause of its target (QLab). On resume it is sent again for the resumed segment (`DevampVoice` with the fresh run id, dated on the resume), and any `L` already known is forgotten: the next cue starts on the `L` the new answer gives. Answers for the paused segment's id are stale and ignored. **A Devamp fired at a paused target** (paused in its action) is kept, neither ignored nor taken for a resume (user decision 2026-10-25): the cue stays paused, nothing is sent to the paused segment, and the devamp is pending exactly like one sent before the pause, so the resume sends it (`DevampVoice` for the fresh run, dated on the resume, right after the `ResumeVoice`): the cue finishes the loop pass it was paused in and then leaves the loop, with "start next cue" on the answer's `L` as usual. One `DevampVoice`, after the resume, so no command for the voice is dated before an earlier one. A second Devamp meanwhile is `DevampIgnored` (one at a time); a stop or reset of the paused target drops it.
  - `DevampIgnored`: nothing to leave (no slice table, as for a cue that is not looping); `DevampIgnored { cue: target }` warning, no next cue.
  - A stopped, reset, deleted or broken target cancels a pending devamp (and its next cue).
- One devamp at a time per voice: a second Devamp while one is pending sends nothing and warns `DevampIgnored` (the audio side would ignore it, and its answer could not be told apart).
- **Looping playlist group** (M2.15) that is running (not stopping, not adopted): it finishes its current child and then **completes** instead of moving on or wrapping; its continue applies (auto-follow fires unless a child broke), and with "start next cue" the cue after the Devamp cue starts on the same sample. A paused playlist completes when its child completes after the resume. "Stop target when slice ends" makes no difference for a playlist.
- A group that is not a looping playlist (or is adopted, or already devamped): `DevampIgnored`, nothing changes. A target that is not running (idle, loaded, pre-waiting or paused in its pre-wait, stopping, broken): `TargetNotRunning`. Any other kind: `TargetWrongKind`.

## Fade cues (CT-10)

Audio levels only in v0.0.1 (§21). A Fade is **absolute** (QLab): over its duration, with its curve, it moves the target's levels from their current values to the Fade's values.

- **What it fades**: at its action start `A`, every **playing** audio cue it targets: the target itself, or for a Group target every audio cue inside it (any depth) that is playing then (absolute, the same values for each). Playing = in its action with a started voice (running, fading, paused or stopping), not broken. Cues that start later are not faded.
- **Which levels**: the Fade's `master_db`, each set `output_db[o]` and each listed crosspoint, per target. Indices beyond that target's outputs (`output_db` past `outputs.len()`, a crosspoint output past it, a crosspoint input of 64 or more) are ignored; crosspoint inputs beyond the file's channels are ignored by the mixer. A muted output or crosspoint of the target is not faded (a fade never changes mutes, so its gain stays 0). An unlisted crosspoint of the target is silent and fades up from silence.
- **Ramps**: per target and level, `Ramp { cue, run, at: S, param, gain, frames: E − S, curve }` with `S = max(A, now, voice start, the voice's last committed command)` and `E = A + duration` (minus a load-to-time offset). So a ramp never names a voice before the mixer has it, a late fade starts late but still ends on `E`, and `gain` is linear (`db_to_gain`, the mixer's conversion). Duration 0 sets the levels on `S`.
- **Current levels**: the mixer starts every ramp from the value the gain has on its first sample (docs/audio.md, Ramp definition), so a fade interrupted by another fade (or a second fade after a first) continues without a jump. The engine tracks the same thing: each running audio cue keeps the gains Fade cues have set or are moving, as `from → to over frames from start`, evaluated with the mixer's formula (`ramp_gain`, `curve_shape`, `db_to_gain`; `tests/level_maths.rs` checks that they match `openlab_audio::ramp_value`, `Curve::shape` and the dB conversion bit for bit). The mixer itself evaluates fade curves within `openlab_audio::RAMP_TOLERANCE` (1e-6 relative, in practice up to one f32 step) of `ramp_value`, not bit for bit, so a held or resumed fade continues from the engine's level to within that tolerance, which is inaudible. Untouched levels are the model's. `fade_level(cue, param, at)` reads one level (`None` = untouched); `fade_ramps(cue, at)` lists every faded level with its value, target, end sample and curve. A ramp of 0 frames (a Fade of duration 0) is tracked the way the mixer hears it: a linear ramp over the de-zipper time (5 ms, at least one sample; docs/audio.md, De-zipper), except on the voice's own start sample, where it is immediate (its first start: a resume keeps the same mixer voice, so a 0-frame ramp on a resume sample is de-zippered too). The `Ramp` action still carries `frames: 0`; `fade_ramps` reports the de-zipper as the moving ramp it is (linear, ending 5 ms later). A hold (a paused Fade) is a ramp from the current value to itself, so it changes nothing. These levels belong to the cue's run: a stopped and restarted cue starts from the model's levels again (Reset restores its saved levels, CT-15).
- **Ownership**: each level is moved by the Fade that last ramped it. A later Fade takes it over; the earlier Fade then no longer touches it (pausing or stopping it sends nothing for that level).
- **Completion**: the Fade's action completes on `E` (auto-follow fires then); its targets have reached its values. With **stop target when done** the target (a group: with everything in it) is hard-stopped on `E` — exactly on the sample the ramp ends — before the auto-follow fires. It stops the target whatever it is doing then.
- **Pause** of the Fade cue holds its ramps where they are on the pause sample `P` (`Ramp { at: max(P, ramp start), gain: current value, frames: 0 }`, the mixer's value on that sample, so nothing moves); **resume** at `R` ramps each held level from there to the Fade's value, ending on the Fade's shifted end (`E + R − P`), with the same curve over the remaining frames (continuous; the remaining path is a fresh curve from the held value, not the tail of the original one). **Stop** (or Reset, or deleting it) holds the ramps where they are and never stops the target. A held level whose ramp had already ended sends nothing.
- **State**: the Fade cue reports `running` during its fade. Each audio cue it is moving reports `fading` (CUE-04) while it is in its action and a running, unpaused Fade with a non-zero ramp on it exists; it returns to `running` when that Fade completes, pauses or stops. Paused, stopping and broken take precedence. A group target reports its own state (`running`); its faded children report `fading`. Second triggers on a fading cue follow its second-trigger option like on any active cue.
- **Not playing**: if nothing it targets is playing at `A`, the Fade warns `TargetNotRunning` and does nothing, but still runs its duration (its timing and continue apply, as in QLab; "stop target when done" then stops the target on `E` if it is running by then). A target of another kind: `TargetWrongKind`; none or missing: `NoTarget`/`TargetMissing`.
- Feedback never breaks a Fade cue (it owns no voice).

## Broken cues (CUE-06, NFR-07)

Problems that keep a cue from running are found **before it is triggered** (NFR-07), so the operator sees them in the list, the inspector and the pre-show check. Core does no I/O: the binary reports what it learns about media and devices as inputs; target and reference problems come from the model. A cue can have several problems (`CueProblem`, in this order: target, media, patch/device):

| Problem | Cue kinds | From |
|---|---|---|
| `no_target` | targeting cues (Fade, Start, Stop, Pause, Load, Reset, Devamp, GoTo, Arm, Disarm) | the model: target not set |
| `target_missing { target }` | targeting cues | the model: target not in the workspace |
| `target_self` | targeting cues | the model: the cue targets itself |
| `target_wrong_kind { target }` | Fade (needs Audio or Group), Devamp (needs Audio or a playlist group) | the model (the same rule as load-time validation) |
| `no_media` | Audio | the model: no file assigned |
| `media_missing { media }`, `media_unsupported { media, reason }` | Audio | `Input::MediaStatus` for the cue's media reference |
| `patch_missing { patch }` | Audio | the model: patch not in the workspace |
| `device_unavailable { patch, resolution }` | Audio | `Input::PatchStatus`: any resolution but `mapped` (unmapped, device missing, channels missing, output count mismatch) |
| `network_patch_missing { patch }` | Network | the model: destination not in the workspace |
| `started_broken` | any | shown alone while a cue that was triggered with problems, fixed since, still has that run pending (it reports `broken` until the run ends; see Triggering) |

- **Not problems**: damaged media that plays (M3 probe warnings: the binary reports it `available` and shows its warnings itself); a trigger cycle (load-time validation warns; the engine bounds it at run time, see [Chains](#chains-and-the-chain-bound), since a timed loop of Start cues is legitimate); a disarmed cue (it is still broken if it has problems). A **group** is never broken because of its children: it runs, and its broken children are skipped as usual. As in QLab 5, it shows a **warning** instead while any descendant (any depth) is shown with problems (`started_broken` included): `has_broken_descendant(group)` (false for a cue that is not a group), and `Action::GroupWarningChanged { group, warning }` on every change (also `false` once for a deleted group that had one). It follows the incremental scheme below: a status input or a run's end updates only the groups around the cues whose problems changed (a parent index built with the model's part); the rebuild after `model_changed()` recounts them. Run-time breaks (`broken_reason`) do not count. The pre-show list is unchanged: it lists the broken cues themselves.
- **Inputs**: `MediaStatus { media, status }` with `status` `available`, `missing`, `unsupported { reason }` or `unknown` (forgets the report: assumed playable), keyed by the cue's `MediaRef` exactly as stored, so every Audio cue on that reference shares it. `PatchStatus { patch, resolution }` with `resolve_patch`'s `PatchResolution`. `Availability { media: [(media, status)], patches: [(patch, resolution)] }` carries many of both in one call (workspace open, a rescan, a drive that went away). Nothing reported yet = no problem: the engine cannot know a file is missing until the binary says so.
- **Incremental** (a show can have thousands of cues and files): the model's part (targets, patches, media references, with indexes from media reference and patch to their cues) is rebuilt only on the first call after `model_changed()` — the binary calls it after every model change (M4.2 contract) — so model edits count from that call (a deleted target breaks its control cues, a retarget fixes them). A status input recomputes only the cues on that media reference or patch, and an unchanged report nothing. A call with nothing new costs nothing; `problem_checks()` counts the cues computed (tested: O(affected)). Debug builds also recompute everything on each call without the signal and count a mismatch in `unsignalled_model_changes()` (and correct it), so tests catch a forgotten signal. Release builds trust the signal, except that a cue about to be refused for its problems (Start, GO, a continue, Load, its action start) first has its problems recomputed from the current workspace: if they no longer match, the problems are rebuilt and the mismatch counted in `unsignalled_model_changes()`, so a cue fixed by an unsignalled edit is never refused for its old problem. Healthy cues pay nothing for this. Each cue whose problems changed gets `ProblemsChanged { cue, problems }` (the full new list; empty = fixed) and, if its reported state changed, `StateChanged` (`idle` ↔ `broken`) dated `now`. The first call reports every broken cue. A deleted broken cue reports `idle` once.
- **State**: a cue with problems and no runtime reports `broken`. A cue with a runtime keeps reporting its runtime state (a playing cue whose file is reported missing plays on; whatever the audio side then does arrives as feedback) and reports `broken` when its runtime ends. A **loaded** cue that gets problems is unloaded (`UnloadVoice`) and reports `broken`. A cue that gets problems during its pre-wait skips its action when the pre-wait ends (as below) and reports `broken` from then.
- **Triggering** (Start, GO, a continue, a Start/GoTo cue): a cue with problems does not start (`CueBroken` warning) but keeps its timing exactly like a disarmed cue (user decision, M2.13): pre-wait, then its action is skipped, then its post-wait. Its auto-continue fires on schedule; it never auto-follows; it reports `broken` throughout (no `pre-waiting`). GO moves the playhead past its continue chain as usual, except that a broken cue's auto-follow never fires and so does not continue the chain: GO on a broken auto-follow cue leaves the playhead on the cue it would have followed into, so that cue is not lost (its auto-continue does fire, and is skipped over as usual). A broken Devamp cue sends no devamp, so its "start next cue" never fires and, as for a disarmed one, its own continue mode applies (also for the playhead). Stop or Reset cancels its pending continue. A group with such a child runs the child's timing and, as for a child that broke at run time, does not auto-follow. Fixing the problems while that run is pending does not start the skipped action; the run ends as it was, and meanwhile the cue shows `started_broken` (so a broken cue always has a reason to show), then `[]` when the run ends. Load warns `CueBroken` and loads nothing. Reset does not clear static problems.
- **Pre-show** (NFR-07, M4.8): `broken_cues()` lists every cue shown with problems and its problems, in workspace order (lists in order, cues depth-first). Breaks at run time are not static and are in `broken_reason(cue)` / `cue_states()`.
- `CueProblem` implements `Display` with an English sentence for logs; the UI localises from the variant (CUE-06 "human-readable").

## Panic (PB-03)

`Input::Panic` stops everything, as QLab's Panic: every cue of every list, at every depth.

- **Fade**: every playing voice (an audio cue in its action, not paused) gets `StopVoice { at, fade: { frames: E − at, curve: PANIC_CURVE } }`, with `E = now + panic_duration` and `at` as for any stop (no earlier than `now`, the voice's start or a committed command), so every voice reaches silence and **stops on the same sample `E`**; the cue reports `stopping` and goes `idle` on `E` without waiting for feedback. `PANIC_CURVE` is linear (the setting has only a duration). The stop gain multiplies the voice's other gains, so the fade starts from wherever the voice is.
- **Takeover**: a Fade cue moving levels is stopped, which holds its ramps where they are (see [Fade cues](#fade-cues-ct-10)); the panic then fades the voice out from there. A cue already fading out with a stop that would end after `E` gets the panic's `StopVoice` (the mixer restarts the stop gain's ramp from its current value, so it ends on `E`); one that ends on or before `E` keeps its stop.
- **Everything else stops at once**: pre-waiting, post-waiting, paused (a paused voice is silent: hard stop), loaded (`UnloadVoice`) and silent cues (Wait, Memo, control, Fade). So nothing pending fires: pre-waits, post-wait auto-continues, auto-follows, a Devamp cue's "start next cue" (also when the voice would leave its loop during the panic fade), playlists moving on, "stop target when done". A group in its action with a child still fading reports `stopping` and goes idle when its last child stops (on `E`). A cue broken at run time with a pending auto-continue stays broken; the continue is cancelled.
- **Second press**: a Panic before `E` (while `panic_end()` is `Some(E)` and `now < E`) hard-stops everything at once, including cues started since. `panic_duration` 0 is always that hard stop. A Panic on or after `E` is a new panic with its own fade; so is one after the clock went back to before the panic (a device restart ends the panic window).
- **After it**: nothing is active, loaded or pending (`next_deadline()` is `None`, `cue_states()` holds only broken cues, `panic_end()` is `None` from the first call on or after `E`). Fade levels go with their runs. Playheads do not move. Arm/Disarm overrides only last for the call that made them anyway.
- **GO during the panic fade** is accepted and starts cues normally (QLab does not lock the workspace during a panic); the panic's end does not touch them, a second Panic does. A cue still **fading out in the panic** is not active for the second-trigger rule (operator intent: recovering from a panic): Start, GO or a continue on it hard-stops its fading voice and starts it afresh (a new run and `RunId`; the mixer cuts a hard stop on its sample without de-click, so the cut of a partly faded voice can click: PROGRESS M2.18); on a group, it hard-stops everything in the group and starts the group again. A child started on its own while its group fades out in the panic (and every group around it doing so) makes the group run on, adopted, instead of staying `stopping`: it ends when its last child does, with no continue. A cue whose own stop fade the panic kept (it ends sooner) counts as fading out in the panic too. A cue fading out because of an ordinary stop with fade, with no panic, keeps the second-trigger rule (its option; default `TriggerIgnored`). A cue's own `panic` second trigger fades it out "in a panic" in this sense too. Panic does not touch double-GO protection: a GO within `min_go_interval` of the last accepted GO is still ignored.

## Pause All and Resume All (PB-04)

- `Input::PauseAll` pauses every active cue of every list at every depth, groups before their children, with the Pause operation (so every pause rule holds: timers, voices `PauseVoice`, Fade cues holding their ramps, devamps kept). Stopping, loaded, idle and broken cues are left as they are (as Pause leaves them).
- `Input::ResumeAll` resumes **every** paused cue, however it was paused (Pause All, a Pause cue, the operator), as QLab's Resume All does; groups first, so a group resumes with its paused children (the group rules for resume apply, incl. a playlist moving on). Every resume gives the run a fresh `RunId` and re-sends a pending devamp, as Resume does. With nothing paused it does nothing.

## Actions for the binary (M4.2 contract)

Besides the voice actions above:

- `Ramp { cue, run, at, param, gain, frames, curve }` → mixer `Ramp { voice: run, target: param (Master / CueOutput(o) / Crosspoint{input, output}), gain, fade: Fade { frames, curve } }` (curves map one to one). The binary must not apply gangs to it (the Fade's values are already per output).
- `DevampVoice { cue, run, at, stop }` → mixer `Devamp { voice: run, stop }` at `at`; its `DevampScheduled`/`DevampIgnored` events go back as `Input::DevampScheduled { cue, run, at }` / `Input::DevampIgnored { cue, run }` for that voice. After a `ResumeVoice` the engine re-sends a pending devamp for the fresh run: a binary that pauses by stop and restart sends it to the restarted voice; one with a native pause that kept the first devamp answers it with the `DevampScheduled` it has (tagged with the fresh run), not with `DevampIgnored`.
- `SetArmed { cue, armed }` → set the cue's `armed` in the model as a runtime change (not an undo step) **before the next `handle` call**: the engine honours it only for the rest of the call that made it. (A later save then stores it; see PROGRESS M2.17.)
- **Model changes** (M2-D): call `engine.model_changed()` after every change to the workspace (a command, undo, redo, relink, an applied `SetArmed`, a newly opened workspace) before the next `handle` call. A change not signalled leaves the static problems, the playheads and the chain limit out of date in release builds (see [Model edits](#model-edits) for the guards); log any increase of `unsignalled_model_changes()`, it means an edit path misses the signal.
- **Availability inputs** (M2.8): send `Input::MediaStatus { media, status }` for each media reference the workspace uses once the probe (M3, off the control thread) has an answer: on workspace open, when a cue gets a new file, on relink, and when a file disappears or comes back (file-system watching, or a failed stream); damaged-but-playable files are `available`. Send many at once as one `Input::Availability` (open, rescan, a drive unplugged). Send `Input::PatchStatus { patch, resolution }` with `resolve_patch` for each patch on open, when the device list changes (hot-plug, device loss) and when the operator edits a patch mapping (WS-07). A binary that plays an unmapped patch on a default device sends the `mapped` resolution it uses. Show `ProblemsChanged` in the list and inspector (CUE-06), show `GroupWarningChanged` as a warning on the group (not as broken; `has_broken_descendant` gives the current value, e.g. for a fresh client), and use `broken_cues()` for the pre-show check (M4.8). A device lost while voices play still reports `ActionFailed { reason: device_lost }` for those runs.
- **Preview** (CUE-05): `Input::Preview` / `StopPreview` for the cue's preview key and protocol commands. `PreviewStart { cue, run, at }` → open the cue's stream and start a voice with id `run` at `at`, from the start of the cue's action, on the **audition output** (PB-09; until the audition patch exists, the cue's own patch), with the cue's levels as the model has them; `PreviewStop { cue, run, at, fade }` → stop that voice on `at` with the fade (the mixer's `StopVoice`); map the voice's `VoiceFinished` / failure to `Input::ActionEnded` / `ActionFailed` with `cue` and `run` as for show voices (a preview's `run` is recognised by the engine). `PreviewChanged` drives the preview button's state. Fade Ramps, Devamp and Pause do not apply to previews.
- **Second trigger on release** (M2.14): send `Input::TriggerReleased { cue }` when a hotkey or MIDI key (note-off) that triggered `cue` is released (cart triggers too, when carts exist); the engine decides whether it acts.
- **Panic** (PB-03): `Input::Panic` for the Panic / Stop All transport key and protocol command; it carries out its own `StopVoice` fades (no separate mixer panic is needed). `Input::PauseAll` / `Input::ResumeAll` for the Pause All / Resume All keys.
- A voice that the binary pauses by stopping and restarting (M3.18) must restart with the Fade levels and ramps the engine reports with `fade_ramps(cue, at)` on the resume sample: start with each `value`, then send `Ramp { gain: to, frames: end − at, curve }` for each one still moving (`end > at`; a fresh curve from there, like a resumed Fade). Fade ramps on a paused voice must apply as on a playing one.

## Feedback

- `ActionEnded { cue, run, at }` (from `VoiceFinished`) and `ActionFailed { cue, run, reason }` are matched on **cue and run**. Feedback for an idle cue, an unknown cue, or an old run (the cue has been stopped, reset, resumed or started again since) is ignored without any action.
- `ActionEnded` completes an audio action at `at` (clamped to no earlier than its start), or ends a fade-out stop. While the cue is paused, an `ActionEnded` dated at or after the pause sample is ignored: a paused voice cannot end by itself, so such a report comes from carrying out the pause (e.g. as a stop). An end dated before the pause (the voice ended just before the pause applied) still completes the action and fires auto-follow. Once the cue has resumed, reports for the paused segment carry its old id and are ignored like any stale id, so a pause's late end report can never complete the resumed cue. A genuine end of the resumed voice carries the fresh id and completes the cue as usual (a binary that resumes a voice which had already ended reports that end with the fresh id). A hard stop forgets the run immediately, so the voice's `Stopped` report that follows is stale and ignored.
- `DevampScheduled { cue, run, at }` and `DevampIgnored { cue, run }` answer a `DevampVoice` (see [Devamp](#devamp-ct-16)); they too are matched on cue and run and ignored when stale. `LoopReached`/`SliceEnded` are not inputs: the engine does not need them.
- Feedback never concerns a Group or a running Fade cue (neither owns a voice); any naming one is ignored.

## Model edits

Each call compares the workspace with what the engine knows. **Only the first call after `model_changed()` does** (M2.12; the binary signals every change, M4.2): stopping deleted cues, moving playheads, recounting the chain limit and rebuilding the static problems are whole-workspace passes that a Tick on a big show must not pay (`model_syncs()` counts them). Debug builds run them on every call and count a change nobody signalled in `unsignalled_model_changes()`. Release builds trust the signal, with a guard wherever a missed one could refuse or drop a cue or a GO, so the worst a missed signal costs is a late edit, never a lost start: a cue about to be refused for its problems is rechecked; a spent chain budget is recounted once (cues added unsignalled raised the real limit) and raised if the recount is higher; a GO whose playhead cue is gone resyncs that list's playhead instead of being ignored. A deleted cue that is still running when nobody signalled keeps its runtime until the next signalled call.

The passes compare the workspace with what the engine knows:

- A cue with a runtime that is no longer in the workspace is hard-stopped and forgotten.
- Changed times apply to **timers not yet started**: the pre-wait is fixed when the cue starts; the post-wait, a Wait duration and the continue mode (auto-follow) are fixed when the action starts. The next cue is looked up when the trigger fires.
- Playheads follow edits as described above; double-GO reads `min_go_interval` at each GO.
- **Running groups**: a deleted child is stopped like any deleted cue (if it was the group's last busy child, the group stops). A deleted group stops with all its descendants. A child added to a running timeline is not started (children start only when the action starts); a playlist plays it when it comes up (unshuffled) or from the next pass (shuffled). Reordering applies to children started later (see Playlist). A busy child moved out of its group keeps running on its own; a group left with no busy child by an edit (child moved out, mode changed) stops at once. A group's mode is read when its action starts and again whenever it acts (a playlist changed to another mode stops moving on and completes with its current child; loop and shuffle are read when it moves on or starts a pass; a child's continue is checked against the mode when it fires). A cue whose kind changes to or from Group while it runs is stopped.
- **Control and Fade cues** read their target and settings when their action starts (a Fade's levels, curve and "stop target when done" are fixed then; its duration is fixed with its end).
- **Arm/Disarm** changes the engine made (`SetArmed`) are honoured for the rest of the call; each call starts from the model (which the binary has updated).

## Warnings

`Action::Warning(EngineWarning)` never stops anything: `UnknownList`, `UnknownCue`, `NotInList`, `NumberNotFound`, `CueBroken` (a start or load of a broken cue), `TriggerIgnored`, `LoadIgnored`, `Unsupported`, `LateStart`, `ChainLimit`, `CueRemoved`, `NoTarget`, `TargetMissing`, `TargetWrongKind`, `TargetNotRunning`, `DevampIgnored`, `PreviewIgnored`, `PreviewFailed`. They are structured so the UI can localise them.

## Not yet

- **Groups**: playlist crossfades and per-group options beyond loop/shuffle.
- **Network** cues (M4.6): their action completes at once with an `Unsupported` warning and does nothing; pre-wait, post-wait and continue mode apply.
- **Target** cues (CT-18) are not in v0.0.1; video fades (CT-10 video part) are v0.0.2.
- **Network reachability** of a Network cue's destination (NFR-07 "unreachable network targets"): only a missing destination is a problem until Network cues run (M4.6).
- **Priming**: `Loaded` means "loaded by an operation"; keeping cues near the playhead primed (ARCHITECTURE §3.5) is the binary's job (M4.2).
