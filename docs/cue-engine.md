# openLab cue engine (`openlab-core::cue_engine`)

How cues run: lifecycle states, timing, continue modes, groups, GO and the playhead. Architecture context: [ARCHITECTURE §3.2–3.3](ARCHITECTURE.md#32-clock-and-scheduling-nfr-202122). Requirement IDs refer to [`REQUIREMENTS.md`](../REQUIREMENTS.md).

Status: M2.1–M2.8, M2.10, M2.11, M2.14, M2.15, M2.24, M2.27, M2.28 (CUE-02, CUE-03, CUE-04, CUE-05 with preview/audition on the engine side (the separate audition output, PB-09, is later), CUE-06 and NFR-07 engine side, CT-10 audio levels, CT-11..CT-17, CT-19..CT-22, PB-01..PB-05, CL-06 engine side). See [Not yet](#not-yet).

QLab 5 details that the published docs settle or leave open (groups, control cues, Fade, Panic, preview) are recorded point by point in [handoff/decisions/qlab-confirm.md](handoff/decisions/qlab-confirm.md); behaviour marked "unconfirmed" there is a decision, not a QLab fact.

Two rules decided by the user (M2.13):

1. **Second trigger is ignored** by default. Start, GO or a continue on a cue that is already active (pre-waiting, running, post-waiting, fading or stopping) does nothing: no restart, no voice action, timers untouched; it reports a `TriggerIgnored { cue, state }` warning. GO still counts as a GO and moves the playhead as usual. A trigger on a **paused** cue resumes it, whatever its second-trigger option (QLab check S1, M2.28). This is the cue's `second_trigger` option `nothing`; the other options (M2.14, QLab 5) are in [Second trigger](#second-trigger-m214).
2. **Auto-continue does not depend on success; auto-follow does.** A cue that breaks keeps its auto-continue, which fires the next cue on its original schedule (action start + post-wait), also when it breaks during the pre-wait (then the action is skipped, as for a disarmed cue, and the timing kept). A cue that breaks **at run time** after its voice has played audio (feedback: `ActionFailed`) never fires its auto-follow. A cue **with static problems** (see [Broken cues](#broken-cues-cue-06-nfr-07)) is skipped like a disarmed cue instead, so its auto-follow fires too, at its action start (M2.24, QLab check P5: GO on a broken auto-follow cue starts the next cue). So is a cue whose voice fails **before it produced any audio** (feedback: `StartFailed`: its file went away after the probe and its stream could not open, a prime failed, the mixer refused its first start): its auto-follow fires on the failure, as QLab does for a file moved to the Trash (P5, M2.24 fix round 1). It reports `broken` while the continue is pending; Stop or Reset cancels the pending continue as on any cue. Its voice is released the moment it breaks. This rule holds for single cues and for the children of timeline, random and "start first" groups; a **playlist** whose current child breaks while playing halts and keeps the group's auto-follow instead (M2.27, QLab check Q2: see [Playlist](#modes), "Halted playlist").

## Shape

```rust
let config = EngineConfig::new(sample_rate, lookahead, seed)?; // checked: 1..=384000 Hz, lookahead ≤ 1 s
let mut engine = CueEngine::new(config);
let actions: Vec<Action> = engine.handle(&workspace, input, now);
let wake: Option<SampleTime> = engine.next_deadline();
```

- Pure and deterministic: no threads, clocks or I/O. The same workspace, inputs, times and seed always give the same actions in the same order (all internal maps are ordered).
- **Randomness** (random groups, shuffled playlists) comes from a SplitMix64 generator in core, seeded with `EngineConfig::seed`. Tests pass a fixed seed and are reproducible; the engine binary seeds it from OS entropy at startup (M4.2), so shows differ between runs.
- `handle` gets the **current** workspace every call. It first applies edits made since the last call (see [Model edits](#model-edits)), then carries out due deadlines, then the input, then deadlines again. The whole-workspace work of following edits (stopping deleted cues, moving playheads, recounting the chain limit, rebuilding the static problems) happens only on the first call after `model_changed()`; see [Model edits](#model-edits) for what a missed signal does.
- `Action`s are core types; the engine binary turns voice actions into mixer and disk-stream commands (M4.2). Core does not depend on `openlab-audio`.
- Queries: `state(cue)`, `cue_states()` (every non-idle cue, statically broken ones included), `broken_reason(cue)` (a break at run time), `problems(cue)` and `broken_cues()` (static problems, see [Broken cues](#broken-cues-cue-06-nfr-07)), `panic_end()` (see [Panic](#panic-pb-03)), `is_paused(cue)` (paused, including a cue that broke while paused), `is_halted(cue)` and `nominal_length(cue)` (see "Halted playlist" under [Modes](#modes)), `run_of(cue)` (`None` for a cue that owns no voice: idle, or broken at run time or started broken), `timers(at)` (see [Timer progress](#timer-progress-m42e)), `playhead(list)`, `standing_by(ws, list)` (CL-06), `playhead_positions(ws, list)`, `chain_limit(ws)`, `fade_level(cue, param, at)`, `fade_ramps(cue, at)` (see [Fade cues](#fade-cues-ct-10)).
- One engine per open workspace. A newly opened workspace gets a new engine; call `handle(ws, Tick, now)` once so the playheads are reported.

## Time

- `SampleTime` is a `u64` frame count at the device rate, the same clock as the mixer's `samples_rendered` (ARCHITECTURE §3.2). `EngineConfig::sample_rate` is the device rate.
- The show file stores seconds. Every conversion goes through `seconds_to_samples`: round to the nearest sample, halves away from zero; negative and NaN give 0; values beyond `u64` (and +∞) saturate. Times are converted when they are used (see Model edits).
- All time arithmetic saturates; nothing panics on extreme values.
- **`now`** is the scheduling time: the earliest sample a command can still hit. The control loop passes `samples_rendered + one block`. `now` should not go backwards; if it does (a device restart), nothing panics: pending deadlines simply wait, and double-GO protection does not block (see GO).

### Deadlines, lookahead and late ticks

- Every timer is an absolute sample deadline. Each transition is computed **at its deadline sample `T`**, never at the time of the call: a successor triggered by a timer that expired at `T` starts its pre-wait at `T`, whenever the call happens. Late calls never make later cues drift.
- A call carries out every deadline in `..now + lookahead` (end excluded; with lookahead 0, every deadline up to and including `now`), earliest first (ties: the cue started first goes first, so causes come before effects).
- `EngineConfig::lookahead` (samples) lets a deadline that falls inside the next block be committed on its exact sample even though the control loop wakes with jitter. The control loop sets it to one block: with `now = samples_rendered + block`, the window `now .. now + block` is exactly the next block, so no voice start lands beyond it (docs/audio.md). It calls `Tick` when `is_due(now)`: `next_deadline() <= now + max(lookahead, 1) − 1`, so with lookahead 0 a deadline at `now` is ticked at `now`. `EngineConfig::new` refuses a lookahead longer than one second of samples and rates outside 1 to 384000 Hz. Deadlines inside the window are committed: an operator input in the same call cannot withdraw them (exactly like commands already in the mixer's queue), so a stop issued at `now` for a voice committed to start at `T > now` is sent for `T`, and a pause freezes timers at `now`.
- `CueEngine::set_lookahead(frames)` changes it between calls, when the binary's device comes back with another block size (M4.2b): the next call commits deadlines in the new window; commands already committed keep their samples (each run remembers the latest sample it committed). At most one second; on error nothing changes.
- **Commands for one voice never go backwards in time.** Each run remembers the latest sample a command for its voice was sent for (start, stop, pause, resume, ramp, devamp). A later command for that voice — also from a later call, and also an operator input that comes after a control or Fade cue committed something in the window — is dated no earlier: a Fade taking over a level whose ramp is committed for `T` ramps from `T`; a pause after a committed ramp or devamp freezes the timers on that sample; a stop after a committed pause stops there; a resume is never dated before its pause (it then resumes as of the pause). A remembered sample beyond the call's horizon can only come from a clock that went back (device restart) and is ignored.
- **Late rule**: a voice whose deadline `T` has already passed (`T < now`, a late tick) starts at `max(T, now) = now`, from its start offset (the head of the sound is not cut), with a `LateStart { late_by }` warning. Its state change still reports `at: T`, and every timer derived from it counts from `T`.

## States (CUE-04)

Each cue reports exactly one state:

| State | Meaning |
|---|---|
| `idle` | Nothing to do. Idle cues have no runtime. |
| `loaded` | Loaded (optionally to a time) and ready to start. |
| `pre-waiting` | Started; the pre-wait is counting down. |
| `running` | The action is under way (post-wait may be counting too). |
| `paused` | Pre-wait, action and post-wait are frozen. |
| `post-waiting` | The action is complete; the post-wait is still counting down to the next cue. |
| `fading` | An audio cue in its action whose levels a running Fade cue is moving (see [Fade cues](#fade-cues-ct-10)). |
| `stopping` | Fading out before it stops (a stop with a fade). |
| `broken` | Cannot run. **At run time** (feedback): owns no voice and cannot start until reset (a `device_lost` break also clears once the cue's patch is reported `mapped` again, by `PatchStatus` or when the run settles with its patch mapped; a patch never reported does not count. A run that broke with a pending auto-continue keeps showing `broken` until that continue fires, also when its device is back meanwhile: the break is part of the run, which keeps its continue's schedule; clearing it early would show a run with no voice as running or post-waiting, and the cue could still not start before the run ends); its pending auto-continue still fires on schedule, except after `device_lost`, which ends the run for good: pre-wait, auto-continue and auto-follow are all cancelled (M4.2g). `Input::DeviceLost` (sent by the binary after it failed the audio runs) hard-stops every other active run, so nothing scheduled before the loss fires after it. Reasons: `voice_rejected`, `stream_failed`, `device_lost`. **Static** (problems found before it runs: missing media, device or target; see [Broken cues](#broken-cues-cue-06-nfr-07)): reported while the cue has no runtime, until the problems are fixed. |

Internally a started cue is a **run**: `{pre-wait deadline, action progress (start, end if known), post-wait deadline, paused-at, fade-out end}`. Post-wait is a timer owned by the cue, not a phase: a cue is `running` while its post-wait elapses, and `post-waiting` only once its action has completed and the post-wait has not. The reported state is derived: broken › paused › stopping › fading › pre-waiting › running › post-waiting.

A start always reports `pre-waiting` first, even for a zero pre-wait (followed by `running` in the same call).

Each voice segment has a `RunId`, unique for the engine's lifetime (the binary can use it as the mixer `VoiceId`). Loading or starting creates it; starting a loaded cue keeps it; **every resume gives the run a fresh id** (`ResumeVoice { run: fresh, paused: previous }`), so feedback still on its way for the paused segment is stale whenever it arrives. `run_of(cue)` is the current id.

### Timer progress (M4.2e)

`timers(at)` lists every timer counting at rendered sample `at`, for the binary's `progress` message (docs/protocol.md): `TimerProgress { cue, timer, elapsed, remaining }` in samples, by cue and then pre-wait, action, post-wait. It is pure (time passed in) and allocates nothing (an iterator over the runs).

- **Pre-wait** (`pre-waiting`): `remaining` to the action start, `elapsed` = the whole pre-wait − `remaining`. The whole pre-wait is the cue's at the start (at the load for a loaded cue), so a load to time `t` inside the pre-wait shows `t` elapsed.
- **Action** of a cue **without a voice** (Wait, Fade, Group, memo and control cues; an audio cue's comes from its voice): `elapsed` = the action offset (load to time) + samples since the action start; `remaining` to its end, `None` while the end is not known (a group with a busy child). A broken run (at run time or by static problems) skips its action, so shows none.
- **Post-wait** (an auto-continue's, counted from the action start; also a halted playlist's wait for its auto-follow): `remaining` to the continue, `elapsed` = the whole post-wait − `remaining`. Shown while the action runs too, so one cue can have two timers.
- A **paused** run's timers stand on the pause sample; a pause committed ahead of `at` (lookahead) freezes them once `at` reaches it. A timer whose start is ahead of `at` (a start committed in the lookahead window) shows its whole length, never more, and `elapsed` 0. A deadline that is due but not yet ticked shows `remaining` 0.
- Idle, loaded and settled-broken cues have no timers; Stop, Reset and Panic clear them with the run.

## Timing and continue modes (CUE-02, CUE-03)

Started at `S` with pre-wait `P`, post-wait `W`:

- The action starts at `A = S + P`.
- **Action duration**: Audio — unknown to core; the action completes on `ActionEnded` feedback (`VoiceFinished`), and a cue that loops forever never completes until it is stopped (or devamped, M2.5). Wait — its `duration` (CT-20). Memo — 0; it does nothing (CT-21). Group — until no run that started in it (a child's) is busy (see [Groups](#groups-ct-22)). Fade — its `duration` (see [Fade cues](#fade-cues-ct-10)). Start, Stop, Pause, Load, Reset, Devamp, GoTo, Arm, Disarm — 0: they act on their target when the action starts (see [Control cues](#control-cues-ct-11ct-19)). Disarmed cues (CUE-07, as the engine sees them: see Arm/Disarm) — 0: the action is skipped (no voice, no control action, no fade), but pre-wait, post-wait and continue mode still apply. Network cues (M4.6) — 0: the message is sent when the action starts (see [Network cues](#network-cues-ct-30)).
- **Do not continue**: nothing else is triggered; the post-wait is not used.
- **Auto-continue**: the next cue is triggered at `A + W` (post-wait counted from the action start; `W = 0` triggers it at `A`). The post-wait timer is armed when the action starts.
- **Auto-follow**: the next cue is triggered when the action completes: at the `at` of `ActionEnded` (clamped to no earlier than `A`), or at `A + duration` for known durations. The post-wait is ignored.
- "The next cue" is the cue after this one in its list (or group) **when the trigger fires**. The last cue triggers nothing. Inside timeline and playlist groups the group runs its children and their continue modes are ignored; in random groups they apply (see [Groups](#groups-ct-22)).
- Triggering a cue is the Start operation (so an active successor applies its [second-trigger option](#second-trigger-m214): by default it ignores the trigger, and a paused one resumes).
- A cue is finished (idle) when its action is complete and no post-wait or fade-out is pending.
- Stopping or resetting a cue cancels its pending post-wait and its auto-follow. A cue that breaks at run time cancels its auto-follow but keeps its auto-continue (rule 2 above).

### Load to time

`Load { time }` loads the cue `t = time` seconds into its timeline (pre-wait, then action). The split into pre-wait and action is made **at load**, with the pre-wait the cue has then (so `LoadVoice.offset` and the later `StartVoice.offset` always agree); a pre-wait edited between the load and the start does not change it. When it starts at `S`:

- `t < P`: the pre-wait has `P − t` left; the action starts from its beginning.
- `t ≥ P`: the action starts at `S`, `a = t − P` into the action (`StartVoice.offset`, also `LoadVoice.offset`). The post-wait has `W − a` left and a known duration `D − a` (both at least 0, so an elapsed post-wait triggers the next cue at `S`).

**Past the end (M4.11b; follows QLab 5, see `docs/handoff/decisions/m4-11b.md`; unconfirmed against QLab).** `t` is a position on the cue's own timeline (pre-wait, then action). Only the **action** is clamped to its length; the post-wait is not, and counts from the unclamped `t` (`W − (t − P)` left, none if that is 0 or less, so the continue comes at the start). The same rule holds for every kind. Loading to a time past the cue's length (pre-wait + action) loads it **to its end**: it sits `loaded`, does not complete, fires no continue and logs no warning. Starting it then ends its action at once, on its start sample.

- Playlist (not looping) and random groups: the group's action has a nominal span, the sum of its children's spans (pre-wait + action, from `Input::CueLengths` for audio) for a playlist, shuffled or not, or the span of the child chosen at GO for a random group. Loaded to a time at or past it, the group's action ends at once on the GO (no child plays; a child the load reached stays loaded) and its continue and post-wait follow the rule above. Below the span the existing child loading stays (the child the load reaches is loaded at the remainder, the later ones play in full). A span that is unknown (unprobed audio, a child with no known length) or endless (a looping playlist, which wraps like an infinite loop) clamps nothing. Random's pick counts as played in its cycle even when nothing starts.
- Wait, Fade, Memo, controls, other groups: nothing is clamped at load; at the action start the end is `start + (D − a)` saturating at 0, so the action is over on the start sample, and the group's children clamp on their own timelines. Armedness and kinds are only looked at at the start, so a cue disarmed at load and armed before GO keeps its load time.
- Audio: `LoadVoice.offset` and `StartVoice.offset` carry `t − P` as asked and the binary clamps. An offset at or past the end of the plan (trims, slices and finite loops counted) is an empty plan: the start ends on its own sample, and the binary reports `ActionLength { frames: offset }` (plus the delay of a start the probe held up) so the core dates the end, and a chained successor, on that sample instead of on a late `ActionEnded` (a `late_start` warning). An **infinite loop** has no end to clamp to: the offset wraps within the loop (`skip` takes the offset modulo the loop's length), so it is never "past the end".

### Chains and the chain bound

Zero-wait chains run inside one call: an auto-continue chain of zero waits starts every cue on the same sample. Commands do not check references (M1-B) and edits can create trigger cycles, so **the calls at one `now` start at most `chain_limit(ws)` = number of cues in the workspace (all depths) + 64 cues between them** (the budget of a call is what the earlier calls at the same `now` left; a call at another `now` has the whole limit). Every start that creates or resumes a runtime counts, including children started by their group; a trigger that starts nothing (`TriggerIgnored`, `CueBroken`, `UnknownCue`) costs nothing, so repeated ignored triggers within one block (a stuck controller key) never use up the budget a GO in that block needs, and a cycle still ends because each of its laps creates or resumes a runtime (a looping playlist of zero-length children is such a cycle: it is cut at the limit and the group then completes). Without a cycle a call starts each cue at most once, so only a cycle reaches it. Start cues, GoTo-and-GO and Devamp's "start next cue" count like any start, and so does what a [second trigger](#second-trigger-m214) starts (a restart, a playlist's next or previous child), so control-cue cycles (A starts B starts A, GoTo loops; load-time validation warns about them, edits can still make them) are bounded the same way. A start beyond the limit is dropped with a `ChainLimit` warning (an operator GO that finds the budget already spent is ignored with `GoIgnored { reason: chain_limit }`: no start, no playhead move, and the double-GO interval is not restarted, so the operator can press GO again); a **playlist** stops starting children when 8 starts are left (`PLAYLIST_RESERVE`, also a `ChainLimit` warning), so a looping playlist of zero-length children, which would spend the whole call, still lets the cue after its group start; the chain is cut, not deferred, so a cycle can never hang a call or keep re-firing on later ticks at the same sample. As a second line of defence the deadline loop has its own step guard.

**Across calls**: a cycle that makes no time progress cannot outlive the call it starts in. All its deadlines lie on one sample, which falls inside that call's window, so the whole cycle runs (and is cut) there; nothing of it is left pending. A cycle can only reach a later call through time: a non-zero pre-wait, post-wait, Wait or Fade duration, which moves the timeline on (it keeps running, one lap per period, like any timed loop — not a hang, and Stop/Reset/panic end it), or through feedback from the mixer, which is dated at mixer time (an end report is no earlier than the voice's real start, which is never before the `now` of the call that started it; a devamp answer is no earlier than the devamp command). Feedback can be dated on the very sample that started the lap — a voice that ends on its start sample (loaded or started at or past the end of its file: core does not know file lengths) — and a binary may hand it over at that same `now`. That is why the budget is per sample, not per call: such a lap repeats in call after call at one `now` only until the sample's budget is spent, and is then cut as within a call (a looping playlist completes, a Start cycle stops). In the real binary `now` has moved on by at least a block by the time the mixer reports what it rendered, so such a lap then runs once per block, like a timed loop. A cue that acts while its own action is under way also ignores a trigger back to itself (a Start cue targeting itself: `TriggerIgnored`).

## Groups (CT-22)

A Group cue is a cue like any other: its own pre-wait, post-wait and continue mode, the [operations](#operations-cue-05) and the second-trigger rule. Its **action** is running its children; behaviour follows QLab 5's group modes.

### Its action

- The action starts when the group's pre-wait elapses, at `A`, and starts children at `A` according to the mode (each child then runs its own pre-wait).
- A child is **busy** while it has a runtime that is not idle, loaded or settled broken: pre-waiting, running, post-waiting, paused, stopping, or broken with an auto-continue still pending.
- The action **completes** on the sample its last busy child stops being busy (completes, settles broken, is stopped, reset or deleted), and then the group's continue mode applies as for any cue: auto-follow triggers the cue after the group at that sample; auto-continue fires `A + post-wait` (a post-wait longer than the children makes the group `post-waiting`).
- **Success**: a group whose run saw a child break **at run time** (feedback) does not auto-follow; its auto-continue still fires (rule 2 above, applied to the group). The exception is a playlist halted by its current child breaking while it plays: it keeps its auto-follow, timed by its children's nominal lengths (QLab check Q2, "Halted playlist" under [Modes](#modes)). Nested groups pass this on: an inner group that saw such a break counts as a broken child of the outer one. A child that is broken when the group gets to it (static problems, or broken at run time earlier and not reset) is skipped and does not stop the group from auto-following (M2.24, QLab check G2: a playlist skips its broken child and auto-follows out of the group).
- **Stopped children**: if the last busy child left by being stopped, reset or deleted, the group stops too (idle, its post-wait and auto-follow cancelled) instead of completing. Stopping a child while another is still busy only stops that child.
- An empty or disarmed group's action completes at once (a disarmed group starts no children).
- Feedback (`ActionEnded`/`ActionFailed`) never concerns a group; any naming one is ignored.

### Modes

| Mode | On action start | Children's continue modes | Playhead after GO on the group |
|---|---|---|---|
| Timeline (start all simultaneously) | every child, at `A` | ignored | after the group's continue chain |
| Start first and go to next | the first child | apply: children chain within the group | after the group's continue chain |
| Start first and enter | the first child | apply | into the group: after the first child's chain (disarmed: past the group) |
| Playlist | the first child (shuffled: the first of a shuffled pass) | ignored | after the group's continue chain |
| Start random | one random child | apply: the chosen child's continue starts the child after it (QLab check G1) | after the group's continue chain |

- **Playlist**: each next child starts on the sample the previous child's action completes (its pre-wait then counts). A child that fails before it produced any audio (`StartFailed`) is skipped: the playlist moves on at the moment it fails, as for a broken child. A child that breaks **while playing** (`ActionFailed`, not `device_lost`) halts the playlist (below). A child that fails with `device_lost`, or while it is being stopped or panicked, leaves as a stopped child (see "Stopped children" above): the playlist starts no further child (see [Panic](#panic-pb-03)). A child that is broken when the playlist gets to it is skipped (QLab check G2): one with static problems keeps its timing, as any broken cue, so the next child starts when that has run; one broken at run time and not reset is passed over at once. Without loop the group completes after the last child. With loop it wraps to the first and never completes on its own (stop it, or devamp it: see [Devamp](#devamp-ct-16)). With shuffle each pass plays every child exactly once in a fresh random order. Unshuffled, the next child is the one after the current one as the group stands when the trigger fires (a reorder applies to the next child; a removed current child is followed by the child that took its place). Shuffled, a pass's order is fixed when the pass starts; children removed meanwhile are skipped and children added play from the next pass. A pass in which no child could start ends the playlist; so does the chain limit. A shuffled pass never opens with the child that closed the previous pass (when there are two or more). **Paused playlist**: if the current child's end report (or a failure before it played) arrives while the group is paused (it was in flight when the pause came: the end is dated before the pause), the playlist moves on when the group resumes — the next child starts on the resume sample, as if the playlist had moved on just as it was paused; if that was the last child (no loop), the group completes on the resume sample instead, with its continue as usual. A failure while playing that arrives during the pause halts the playlist, as below, its deadlines counted from the resume. A pause never ends a playlist early or skips its remaining children.
- **Halted playlist** (M2.27; measured by the user in QLab 5, check Q2, 2026-10-27: playlist [c1, c2, c3] of 10 s each, auto-follow, cue X after it; c2's file deleted while c2 played: c2 shows broken, c3 never plays, the group's progress runs on to c2's nominal end and the group then shows finished, and X starts by auto-follow 30 s after the group's start). When the current child of a running playlist breaks while playing (`ActionFailed`, not `device_lost`; not while it is being stopped or panicked), the playlist **starts no further child**. Its action goes on, with no busy child, until the broken child's **nominal end** — its known end (`ActionLength`), else its action start plus its nominal length (`Input::CueLengths`) — and completes there (`running` until then; `is_halted(cue)`). Its **auto-follow is kept**: it fires on the sample the playlist would have ended on had every child played its nominal timing, i.e. that end plus, for every child the playlist would still have played (in list order after the broken child; shuffled: the rest of the pass's order), its pre-wait plus its nominal action (audio: `CueLengths`; Wait and Fade: their duration; memo, control and Network cues: 0; a disarmed child or one with static problems: its pre-wait only; a child broken at run time and not reset: nothing; a nested timeline: its longest child; a nested non-looping playlist: the sum of its children). Between the completion and the follow the group shows **post-waiting** (QLab shows it finished; the engine has no finished state that keeps a pending deadline), and Stop, Pause/Resume (the wait moves by the pause), Reset and Panic act on that wait as on any post-wait. The follow is cancelled (the group completes at the broken child's nominal end and stops there) when the playlist **loops** (it would never have ended) or when any of those lengths is **not known or endless** (an audio cue not probed or looping forever, a nested looping playlist, a nested random or "start first" group); if the broken child's own end is not known the group completes at once, with no follow. The group's auto-continue, if it has one, keeps its schedule as before. The follow's time is fixed when the halt starts: edits and `CueLengths` that arrive during the halt do not move it. A child started on its own during the halt is a busy child of the group like any other (the existing rule): stopping it stops the group and so cancels its follow (QLab's behaviour here is not known). A "play next/previous" second trigger on a halted playlist moves it on (the halt ends; the group does not follow, as a child broke). A devamped playlist is not halted (it was ending with that child anyway): it completes at the break with no follow, as before.
- **Random** (follows QLab 5: round-robin): every playable child — armed, without static problems and not already busy (e.g. started on its own during the group's pre-wait) — plays once before any child plays again. Each action start picks uniformly, from the seeded generator, among the playable children **not yet picked in the current cycle**, taken as the group stands at that moment: a child added mid-cycle joins the current cycle, a removed one drops out, a disarmed (or broken, or busy) one is passed over while it is so and is a candidate again once it is playable and still unpicked. When no candidate is left, a new cycle starts; it never opens with the child picked last when there are two or more playable children, so a child never plays twice in a row across the boundary either. If no child is playable at all, the same rule runs over all the children, so one child is always picked (its start then skips it as disarmed or broken, as for any child). The cycle lives in the engine only: it is not saved, survives Stop/Reset/Panic, and starts afresh with a new engine (the workspace opened again), as QLab's resets when the workspace opens. Deterministic for a given seed.

### A child started on its own

Follows QLab 5 (M2.24, QLab checks G4/G5). Starting a cue inside a group (`Start`, GO with the playhead on a child, a Start cue, a hotkey) **does not make the group run**: a group that is idle or loaded stays so (or `broken`, see [State of a group](#state-of-a-group)), with no runtime, no progress and no continue of its own; a group that has a run of its own (pre-waiting, running, post-waiting) keeps it as it is (a running group counts the child as busy, as any child of its action; a post-waiting one just goes on post-waiting). The child runs on its own; Stop, Pause, Resume and Reset on the group still reach it (they act on every descendant), and so do Panic, Pause All and Resume All.

- **Timeline, random and "start first" groups**: only that child plays, with its own continue mode where the group's mode applies children's continues (random, "start first"), none in a timeline. QLab-confirmed for random and "start first" groups (check Q3, children without continues of their own): only that child plays and the playhead goes to the next cue in the list, the next child. QLab-confirmed for a stopped auto-follow playlist P [10, 11] followed by 2 and 3 (check Q1): GO on 10 plays 10 and 11, the playhead goes to 2 and 2 does not start; GO on P puts the playhead on 3 and 2 auto-follows; GO on 11 puts the playhead on 2.
- **Playlist** (follow-through): the child plays, and when its action completes (or it breaks) the child after it starts on that sample, and so on through the rest of the playlist's children, in list order, each started on its own the same way. Children a start refuses at once (broken at run time and not reset) are passed over (at most one round of them per call); a child with static problems keeps its timing and is skipped as any broken cue. Without loop the last child ends it; **with loop it wraps** to the first child and keeps going round until stopped (Stop or Reset on the group or the playing child, Panic) (M2.27, QLab check Q4). Shuffle is not used: the children play in list order also with shuffle on (QLab check Q4). The group fires no continue (it never ran). This applies to any child of a playlist group that has no run of its own when the child's action completes, however it was started: a child that ends while its playlist **post-waits** (the group has a run) does not carry the playlist on (QLab-confirmed, check Q5); one that ends after the post-wait does (not tested in QLab). Only a run that **started as a child of that playlist**, and is still its child, carries it on: a cue moved into a playlist (from the top level or another group) while it runs, pre-waits or is held paused starts none of that playlist's children when it ends, nor does a running playlist move on for it (it is not the playlist's current child); its end is not held across Pause All for the playlist either (assumed, `docs/todo/open-qlab-questions.md` #45). Each start counts towards the chain budget like any continue, so a looping follow-through of zero-length children is cut at the chain limit (`ChainLimit`) instead of spinning. Open question (QLab check Q4, observed, not acted on): turning shuffle on while a looping playlist played kept list order in QLab; whether that holds for a playlist running on its own (and from which pass on a shuffle edit applies) is not settled.
- A child started while its group pre-waits runs on its own; when the group's action starts, that child gets a second trigger (it is already active): its option applies, by default it ignores it.
- A group fading out in a panic is the exception: see [Panic](#panic-pb-03).

### State of a group

The group's own run gives its state, so it is exactly one state: `pre-waiting` during its pre-wait, `running` while its action is under way (any child busy), `post-waiting` after it with the post-wait pending, `paused` when the group was paused, `stopping` while a stop with fade waits for its children; with no run, `broken` while a descendant is shown with problems (QLab check G6, see [Broken cues](#broken-cues-cue-06-nfr-07)), `idle` otherwise. A paused child alone does not pause its group, and a child started on its own does not make it run.

### Operations on a group

Each applies to the group and to its descendants (every depth):

- **Stop** stops every descendant with a runtime, children before their groups, then the group. Hard stop: everything idle at once. Stop with fade: each playing voice fades out (silent actions stop at once); a group **in its action** with a child still fading reports `stopping` and goes idle when its last child has stopped. A group (like any cue) that has not reached its action — pre-waiting, or loaded — stops at once: its pending action is cancelled and it never starts children; children it already had running fade as above. A second stop is a hard stop. A stopping group cannot be paused (as for any stopping cue).
- **Pause** pauses the group and every active descendant (voices get `PauseVoice`); every timer keeps the time it had left. **Resume** (and Start/GO on a paused group, which resumes it whatever its second-trigger option) resumes the group and every paused descendant; a group whose last child left while it was paused ends then.
- **Reset** resets every descendant (clearing broken children) and the group.
- **Load** loads the group and the children its action starts first: timeline — all children; start-first modes and an unshuffled playlist — the first child; shuffled playlist and random — none. Load to time `t` loads them `t − group pre-wait` seconds (at least 0) into their own timelines, so a loaded timeline group starts its children at that point. A playlist (not looping) or random group loaded at or past its nominal span has nothing left to play: its action ends at once on GO and its post-wait follows `W − (t − P)` (see [Load to time](#load-to-time)).
- **Start** on an active group applies the **group's** second-trigger option to the group as a whole (default: ignored, `TriggerIgnored`, its children untouched); see [Second trigger](#second-trigger-m214).

### Nesting and bounds

Groups nest to `MAX_GROUP_DEPTH` (validation and commands enforce it). The engine's own walks over descendants and over the list (positions, `locate`) are iterative. Looking a cue or its ancestors up uses the model's recursive search (`Workspace::find_cue`, `tree::find_path`), whose depth is bounded by `MAX_GROUP_DEPTH` in every validated workspace (and by the JSON parser's limit on load); a tree hundreds of levels deep built directly still works (tested). Every start inside a group counts towards the call's chain limit.

## GO and double-GO (PB-01, PB-02)

- `Go { list }` starts the cue at the list's playhead at `now` and moves the playhead to the cue after the last cue of its continue chain: from the playhead cue, every following cue reached through auto-continue/auto-follow (as the model stands) is skipped. If the chain runs to the end of the list, the playhead goes past the end. Groups (follows QLab 5): GO on an armed "start first and enter" group moves the playhead **into** it, to the child after the first child's continue chain (a disarmed one starts nothing and is skipped as a unit, like any disarmed cue). Every other group — timeline, start first and go to next, playlist, random — is one unit for the playhead: GO on it, or a chain reaching it, moves the playhead to the cue after the group's chain, never onto its children. GO on a cue inside a group (any mode, as in QLab 5) starts that cue; its groups do not run (see [A child started on its own](#a-child-started-on-its-own)). The playhead then moves to the cue after its continue chain among its siblings: in "start first" and random groups the children's continue modes chain; in timeline groups they are ignored, so it is the next sibling (QLab check G5). In a **playlist** the rest of the children play on from it, so the playhead leaves the group at once (QLab check G5), as below. Past the group's last child the playhead leaves the group (and so on outwards). Leaving a group whose continue fires or has fired (it has a run, or its run fired its continue during the playhead's current visit: since the playhead entered the group, or since the GO on the group that entered it), it goes to the cue after the **group's** continue chain, whose targets play anyway; a visit ends when the playhead finds itself inside the group any other way (`SetPlayhead`, `SetPlayheadByNumber`, `PlayheadNext`/`PlayheadPrevious` from outside, a GoTo, or an edit: the playhead's cue moved into the group, or the playhead moved into it because its cue was deleted), so what the group fired earlier in the show never hides its targets (M2.24 fix rounds 2–3). The engine compares the groups around the playhead with those of the last time it looked (after every move and every followed edit), so an edit that leaves the playhead in the same groups (its cue deleted, the next one in the group taking over) keeps the visit; leaving a group that has no run and fired nothing (the usual case after GO on a child, since a child started on its own does not make its group run), it stands on the cue right after the group, so the group's continue targets are not lost (M2.24 fix round 1; QLab: "the next cue outside of the group"). So a playhead put explicitly on a child of a group that GO does not enter (a jump, `SetPlayhead`) stays among that group's children, GO by GO, until it leaves the group — the same path `PlayheadNext` takes from there (QLab 5 documents only the entered mode; this keeps GO and stepping in step).
- GO on a cue that is already active applies the cue's [second-trigger option](#second-trigger-m214) (default: ignored for that cue, `TriggerIgnored`), but the GO counts and the playhead moves on. GO on a paused cue resumes it (also one that broke while paused: its frozen timers run again). GO on a broken cue does not start it (`CueBroken` warning) but still counts as a GO and moves the playhead on, so the show can continue with the next GO. A cue with static problems keeps its timing, so its continue fires, an auto-follow too (QLab check P5; see [Broken cues](#broken-cues-cue-06-nfr-07)).
- Ignored GOs report `GoIgnored { reason }`: `no_cue` (playhead past the end, or empty list), `unknown_list`, `double_go`, or `chain_limit` (the chain budget of the GO's `now` was spent by a trigger cycle before the GO, in that call or an earlier one at the same `now`: see [Chains](#chains-and-the-chain-bound)).
- The GO of a GoTo cue with "and GO" works the same way on the target's list, dated on the GoTo cue's action start, but it is not an operator GO: double-GO protection never blocks it and it does not restart the interval (see [GoTo](#goto-ct-17)).
- **Double-GO**: a GO less than `min_go_interval` after the previous **accepted** GO (in samples, any list) is ignored; one exactly at the interval is accepted. Ignored GOs do not restart the interval. 0 = off. If `now` is earlier than the last accepted GO (clock restart), the GO is accepted.

## Playhead (PB-05, CL-06)

- Each cue list has a playhead: the standing-by cue, or `None` past the end of the list or for an empty list. A new list stands on its first cue. `PlayheadChanged` reports every move, including the initial one.
- **Positions** (M2.11): as in QLab 5, the playhead can stand on any cue of its list, at any depth and in a group of any mode. In order, the positions are the list's cues depth-first, a group before its children: `1, 2, 2.1, 2.2, 3`. `playhead_positions(ws, list)` lists them. (With duplicate ids, an invalid workspace, the first occurrence counts.)
- **Stepping** (follows QLab 5: only "start first and enter" groups are entered; collapsing a group in the UI changes nothing): `PlayheadNext` and `PlayheadPrevious` step through the positions with the children of every other group (timeline, start first and go to next, playlist, random) left out, so such a group is passed over as a unit, both ways. The exception is a group the playhead already stands inside (put there explicitly): its children are stepped through, so stepping goes on among the siblings and then leaves the group, as GO from a child does. An enter group is entered by mode alone (also when disarmed: navigation fires nothing). `PlayheadNext`: one step down (from an enter group to its first child; from a group's last child out to the cue after the group); from the last step to past the end, which stays. `PlayheadPrevious`: one step up (from the cue after an enter group to its last descendant that stepping reaches; from the cue after any other group to the group itself); from past the end to the last step; the first stays. `playhead_positions` still lists every cue: explicit navigation reaches any of them. `SetPlayhead { cue }` (by id; `None` = past the end) and `SetPlayheadByNumber` (exact number match, first in position order) take cues of that list; a cue not in the list warns `NotInList`, an unknown number `NumberNotFound`; both leave the playhead. Navigation never fires anything.
- Edits: a reordered or moved playhead cue that is still in the list keeps the playhead. A deleted one (or one inside a deleted group) gives way to the first position that came after it and still exists, or past the end. An empty list that gains cues stands on its first cue. A deleted list loses its playhead.

## Operations (CUE-05)

`now` is when the operation comes. Voice actions apply to armed Audio cues only.

| From \ op | Start | Stop | Stop with fade | Pause | Resume | Load (to time) | Reset |
|---|---|---|---|---|---|---|---|
| idle | pre-waiting (new run) | idle | idle | idle | idle | loaded, `LoadVoice` | idle |
| loaded | pre-waiting (same run, loaded offset) | idle, `UnloadVoice` | idle, `UnloadVoice` | loaded | loaded | loaded (reload: `UnloadVoice`, `LoadVoice`, new run) | idle, `UnloadVoice` |
| pre-waiting | pre-waiting, `TriggerIgnored` | idle (action and continue cancelled) | idle | paused | pre-waiting | pre-waiting, `LoadIgnored` | idle |
| running | running, `TriggerIgnored` | idle, `StopVoice` | stopping, `StopVoice` with fade (silent actions: idle at once) | paused, `PauseVoice` | running | running, `LoadIgnored` | idle, `StopVoice` |
| paused | resumes (as Resume) | idle, `StopVoice` | idle, `StopVoice` (hard) | paused | the frozen state, `ResumeVoice` | paused, `LoadIgnored` | idle, `StopVoice` |
| post-waiting | post-waiting, `TriggerIgnored` | idle (next cue cancelled) | idle | paused | post-waiting | post-waiting, `LoadIgnored` | idle |
| stopping | stopping, `TriggerIgnored` | idle, `StopVoice` (hard) | idle, `StopVoice` (hard) | stopping | stopping | stopping, `LoadIgnored` | idle, `StopVoice` (hard) |
| broken | broken, `CueBroken` (static problems: its timing runs, see [Broken cues](#broken-cues-cue-06-nfr-07)); a broken cue that is also paused resumes, as any paused cue | broken (pending auto-continue cancelled) | broken (same) | broken (its timers freeze) | broken (its timers continue) | broken, `CueBroken` | idle (pending auto-continue cancelled); a cue with static problems stays broken |

Events:

| From | Event | To |
|---|---|---|
| pre-waiting | pre-wait elapses at `T` | running; `StartVoice { at: max(T, now) }` |
| running | post-wait elapses at `T` (auto-continue) | running; next cue triggered at `T` |
| running | action completes at `T` (feedback, or known duration) | post-waiting if a post-wait is pending, else idle; auto-follow triggers the next cue at `T` |
| post-waiting | post-wait elapses at `T` | idle; next cue triggered at `T` |
| stopping | fade-out ends (`stop at + fade frames`, or `ActionEnded` first) | idle |
| loaded, any active | `ActionFailed` for the current run | broken: the run's voice is released at once (`StopVoice`, or `UnloadVoice` if it never started). Auto-follow is cancelled; a pending or still-to-be-armed auto-continue fires on its original schedule (a pre-waiting cue skips its action at the action start and arms the post-wait as usual; a paused one stays held until resumed). A broken cue owns no voice, so Stop and Reset have nothing left to silence |
| paused | time passes | paused (nothing runs) |
| any non-idle | cue deleted from the workspace | idle; `StopVoice`/`UnloadVoice`, `CueRemoved` warning if it was active. A `RemoveCue`, a list edit, or an undo or redo that removes the cue (an undo of its add, a redo of its delete; QLab 5 performs it) gets here with an active cue, and all stop it alike (docs/commands.md "Undo and redo while cues play") |
| any non-idle | its id now names a cue of the other sort (group vs. not; duplicate ids or a replaced cue) | idle, as if deleted |
| group pre-waiting | pre-wait elapses at `T` | running; children started at `T` per mode (none busy: the action completes at `T`) |
| group running | last busy child completes or settles broken at `T` | post-waiting if a post-wait is pending, else idle; auto-follow at `T` unless a child broke |
| group running | last busy child stopped, reset or deleted at `T` | idle (continue cancelled) |
| group running (playlist) | current child's action completes, or it breaks, at `T` | running; next child started at `T` (or the group completes, above) |
| group stopping | last busy child has stopped | idle |
| group (any state) | a child starts on its own at `T` | unchanged (a group fading out in a panic ends at `T`) |
| playlist child, its group has no run | its action completes or it breaks at `T` | the next playlist child that can start starts at `T` (follow-through) |

- **Pause** freezes every timer at `now`; **resume** at `R` moves every pending deadline `R − now_paused` later, so pre-wait, action and post-wait keep exactly the time they had left. `PauseVoice`/`ResumeVoice` carry the position the voice has actually reached in the action (`offset`, counted from the voice's real start sample, so a late start or a pause before a start committed in the lookahead window is exact), so the binary can pause in the mixer or stop and restart from the offset (a binary that stops to pause must not report that stop as the voice's end: see `ActionEnded`).
- **Stop with fade** fades a playing voice out over the fade's length (`StopVoice.fade`) and ends the cue when the fade ends — without waiting for feedback, which can be lost if the event queue overflows. A second stop is a hard stop.
- A stop or pause never lands before the voice's own start sample (`at` = `max(now, voice start)`), so in the mixer it cannot be overtaken by a start already committed.
- Operations on a cue id that is not in the workspace warn `UnknownCue` and do nothing.
- On a Group, every operation also reaches its descendants; see [Operations on a group](#operations-on-a-group).
- The `Start` column is for the option `nothing`; any other [second-trigger option](#second-trigger-m214) replaces the `TriggerIgnored` entries (a paused cue resumes whatever its option, QLab check S1).

## Second trigger (M2.14)

Each cue has a `second_trigger` option and a `second_trigger_on_release` flag (show file: docs/file-format.md §5.1; edited with `CueProperty::SecondTrigger` / `SecondTriggerOnRelease`, undoable, batchable). Behaviour follows QLab 5 ("second trigger"). The option applies to **every trigger that would start the cue while it is active**: `Start`, GO, a Start cue, GoTo-and-GO, a continue (auto-continue, auto-follow, Devamp's "start next cue"), a group starting its children, and so whatever input the binary maps hotkeys, OSC and protocol starts to. Double-GO protection is separate and filters GOs first. **Active** = pre-waiting, running, post-waiting, paused, fading or stopping.

| Option | Effect on the active cue (dated on the trigger, `at`) |
|---|---|
| `nothing` (default) | ignored: `TriggerIgnored { cue, state }`; a paused cue resumes (rule 1) |
| `panic` | the cue's own panic: it and everything in it fade out as in [Panic](#panic-pb-03), ending `panic_duration` after the trigger (0: stops at once). Not a workspace panic: other cues and `panic_end()` are untouched. Its cues count as fading out in a panic, so a further trigger restarts them (below) |
| `stop`, `hard_stop` | stops the cue and everything in it at once (as `Stop` without fade). QLab's two differ only for audio effects (a hard stop cuts their tails), which v0.0.1 does not have |
| `hard_stop_and_restart` | hard-stops it and everything in it and starts it afresh at once (a new run and `RunId`, its pre-wait from the top). **At most once per sample**: a run triggered on the trigger's own sample (also the run a restart just made) ignores it (`TriggerIgnored`), so a cue whose own continue or Start-cue chain leads back to it (A auto-continues into a Start cue targeting A) is restarted once per trigger, not until the chain limit. Load-time validation does not warn about such layouts (the trigger-cycle check covers only Start/GoTo-and-GO chains, not continues). The start is charged to the chain budget (a `ChainLimit` warning; a restart that finds the budget spent does nothing, not even the stop). A restarted child that was its playlist's current child stays the current child. A cue with static problems is stopped and its new run keeps its timing without starting (`CueBroken`), as any start |
| `devamp` | as a Devamp cue on itself without "start next cue" or "stop target when slice ends": an audio cue playing in its action gets `DevampVoice`; a looping playlist finishes its current child and completes; a cue paused in its action (reached only by a release, see below) keeps it for the resume. It leaves the loop playing, as a Devamp cue in the mode `current_slice` does. A cue that cannot devamp (another kind, not in its action, stopping, a non-looping group, one already pending) does nothing but warn `DevampIgnored { cue }` |
| `play_next`, `play_previous` | Playlist groups only, on a playlist playing a child (in its action, not stopping or devamped; paused too): the child playing is hard-stopped and the child after (before) it starts on `at`, wrapping when the playlist loops. Without loop, `play_next` past the last child completes the group as if that child had ended (its continue applies), and `play_previous` on the first child **stops the group** (as `stop`: its continue is cancelled; QLab check S4, M2.28; on a later child it goes back one). With loop, `play_previous` on the first child wraps to the last (not measured in QLab: the check used a playlist without loop). Shuffled, the pass's order is followed (after its end a new pass, as usual; `play_previous` from its first child wraps to its last with loop, and stops the group without). A paused playlist (reached only by a release) resumes on the new child. Going back passes over children a start would refuse (static problems, disarmed, broken), as moving on does. **At most once per sample** per playlist: a further `play_next`/`play_previous` on the same sample is `TriggerIgnored`. The new child's start is charged like any playlist move (it is not made when only `PLAYLIST_RESERVE` starts are left: `ChainLimit`, nothing changes). On a playlist not playing a child: `TriggerIgnored`. On any other cue they act as `nothing` (validation warns `SecondTriggerNeedsPlaylist`; the value is kept, so a group-mode change makes it apply) |

- **Broken**: a cue broken at run time or started broken is not affected by its option: `CueBroken` (a paused one resumes), as before.
- **Paused** (QLab check S1, M2.28: QLab resumes a paused cue whose option is Hard stop): a trigger on a paused cue resumes it, whatever its option; no option applies and nothing is warned. Only a release (below) applies the option to a paused cue.
- **Fading out in a panic** (a workspace Panic or the cue's own): a trigger hard-stops it and starts it afresh whatever its option (see [Panic](#panic-pb-03)). Matches QLab 5 (docs/todo/open-qlab-questions.md P3: the old sound cuts at once).
- **Groups**: the option of the cue that was triggered applies. A group's option acts on the group as a whole; a child's applies when the child itself is triggered (by any source, including its group starting it: a timeline group starting a child that is already busy applies the child's option; matches QLab 5, open-qlab-questions.md S6).
- **On release**: `Input::TriggerReleased { cue }` (the binary sends it on hotkey or MIDI key-up, M4; QLab offers it for hotkey, MIDI and cart triggers). It is a second trigger only if the cue has `second_trigger_on_release`, is active (not broken, not fading out in a panic) and its option is not `nothing`: then the option applies as above, on `now`, also to a **paused** cue (stop stops it, restart restarts it, panic stops it at once, devamp is held for the resume, `play_next`/`play_previous` move the playlist on and resume it). Otherwise it does nothing and says nothing (a release never starts or resumes a cue). With `panic` or `stop` this gives sampler behaviour: press to start, release to fade or stop, press again to start afresh. QLab check S5 (M2.28): start, pause, then press the hotkey: the press resumes the cue (S1) and the release, with `stop`, stops it. An unknown cue warns `UnknownCue`.
- Stop, panic and devamp start nothing and cost no chain budget; restart and play next/previous are charged for what they start.

## Preview (CUE-05, PB-09)

`Input::Preview { cue }` plays an audio cue, or the audio cues of a group, **to listen to them**, outside the show; `Input::StopPreview { cue }` ends it (`None`: every preview). In v0.0.1 only the operation exists engine-side: the audition output itself (PB-09, untagged) needs a setting the show file does not have yet, so until then the binary plays previews on the cue's own patch (M4.2; see the progress archive).

- **What plays**: the cue's audio from the start of its action, now (`Action::PreviewStart { cue, run, at }`, `at = now`): no pre-wait, no post-wait, no continue mode, no load-to-time. Loops and slices play as the cue says; an infinite loop plays until stopped. Unknown cues warn `UnknownCue`; a cue with static problems warns `CueBroken` and plays nothing.
- **Groups** (QLab check V1, M2.28: QLab previews a group): a group's preview starts, at once, a preview of every armed audio cue inside it (any depth, whatever the group's mode; children of a disarmed group inside it are left out, as the show would leave them), each its own preview with its own `PreviewStart` and `PreviewChanged`, then `PreviewChanged { cue: group, active: true }`. An audio cue inside it with static problems is skipped with `CueBroken`; one already being previewed on its own is left as its own preview. A preview is named by its cue id, so with duplicate ids (an invalid workspace: loading refuses it, no command makes one) an audio cue whose id names another cue first is skipped (M2.32). With none to play: `PreviewIgnored { reason: nothing_to_preview }`. The group is previewing while any audio cue its preview started still is; when the last one ends (by itself, stopped, failed, deleted) the group reports `PreviewChanged { active: false }` too. `StopPreview { cue: group }` stops the audio cues its preview plays; stopping one of them stops only that one. A group that is deleted (or is no longer a group) stops its preview. QLab previews video cues too; Video is v0.0.2. QLab's behaviour for a playlist, random or "start first" group is not measured: openLab plays all its audio cues at once (open question).
- **Disarmed** (QLab check V2, M2.28: QLab does not play it): a disarmed cue or group cannot be previewed: `PreviewIgnored { reason: disarmed }`. Other kinds are `PreviewIgnored { reason: not_audio }` and do nothing.
- **Fade-in**: the preview plays the cue's own fade-in (its levels and fades as the model has them), as QLab's preview does (check Q8, M2.20: QLab-confirmed).
- **Invisible to the show**: a preview has no `CueState` (the cue keeps whatever show state it has), moves no playhead, does not touch double-GO protection, never triggers a continue, auto-follow or "start next cue", does not make a group run, uses none of the call's chain budget, and does not use the show's `RunId`s: previews are numbered from `PREVIEW_RUN_BASE` (2^63), so the show's ids are the same whether or not anything was previewed, and a preview id can still be the mixer's voice id. The same cue can play in the show and in a preview at once; each ignores the other's stop, reset and end reports (feedback is matched on cue **and** run).
- **Reported**: `Action::PreviewChanged { cue, active, at }` on start and on every end; `is_previewing(cue)`, `previewing()` (groups included), `preview_run(cue)` (audio cues only).
- **Second preview** of a cue or group that is being previewed: ignored (`PreviewIgnored { reason: already_previewing }`), as a second trigger is; a UI that toggles sends `StopPreview` while `is_previewing`.
- **End**: the voice ends by itself (`ActionEnded` with the preview's `run`: `PreviewChanged { active: false }`), `StopPreview` (the preview is over as of now: `PreviewStop { cue, run, at: max(now, start), fade }` with a linear `PREVIEW_STOP_FADE_SECONDS` (50 ms) fade-out, so a stop does not click in the operator's headphones; a paused preview is silent and stops with no fade; the fade is the mixer's, the engine does not wait for it and a late end report is stale), a failure (`ActionFailed` with its `run`: `PreviewStop` hard, `PreviewChanged`, `PreviewFailed` warning; the cue is **not** broken in the show), the cue being deleted or no longer an audio cue (hard stop, at the next signalled call).
- **Pause All / Resume All** (QLab check V4, M2.28: QLab pauses previews) pause and resume every preview too, after the show's cues: `PauseVoice { cue, run, at: max(now, start), offset }` (where the preview has got to in the cue's action), and on Resume All `ResumeVoice { cue, run: fresh, paused, at, offset }` with a fresh preview id, as for a show cue, so the paused segment's late reports are stale. While paused the preview is still a preview (`is_previewing`); an end report dated after the pause is ignored (it comes from carrying out the pause), and one dated on the pause sample ends the preview, as one before it (M2.34: see `ActionEnded`). Pause, Resume, Stop, Reset, Load and Start on the cue itself concern the show only.
- **Panic** (QLab checks V4 and V6, M2.28): a playing preview fades out with the show, ending on the panic's end `E` (`PreviewStop { at, fade: { frames: E − at, curve: PANIC_CURVE } }`), and is over as of the Panic (`PreviewChanged { active: false }`); a paused preview stops at once (no fade). A **second Panic** before `E`, or `panic_duration` 0, stops every preview at once, and also cuts the voices still fading out from the first Panic (a hard `PreviewStop` for each, with no further `PreviewChanged`). So does Stop All. Those voices are forgotten when their end report comes or the panic window ends.

## Control cues (CT-11..CT-19)

A control cue is a cue like any other (pre-wait, post-wait, continue mode, operations, second-trigger rule). At its **action start** `A` (after its own pre-wait) it acts on its target **as if the operator had done the operation** at that moment, and its own action then completes at once (so auto-follow fires at `A`). Its own continue mode applies as for any cue. Behaviour follows QLab 5.

- The operation is dated on `A`: an operation in the lookahead window acts on its own sample (`StopVoice { at: A }`, not `now`); a late one (`A < now`) acts at `now`, except a start, which is dated `A` like any trigger so later timing keeps its schedule (the late rule then applies to voices).
- The cue is still in its action while it acts, so a trigger from its target back to it is ignored (`TriggerIgnored`).
- **Targets**: a cue with no target, a missing target, itself as target or a target of the wrong kind has static problems (see [Broken cues](#broken-cues-cue-06-nfr-07)): it is `broken` and its action never runs. The run-time checks (`NoTarget`, `TargetMissing`, `TargetWrongKind`: the cue does nothing, its timing and continue apply) remain for static problems that are out of date (a model change the binary did not signal inside a cue or group).
- Targets that are groups use the group operations ([Operations on a group](#operations-on-a-group)): Stop/Pause/Load/Reset reach every descendant, Start starts the group in its mode; a target inside a group starts on its own, its groups do not run (see [A child started on its own](#a-child-started-on-its-own)).

| Cue | Action at `A` |
|---|---|
| Start (CT-11) | the Start operation on the target, dated `A`: idle/loaded → starts; paused → resumes (whatever its option, QLab check S1); otherwise active → its [second-trigger option](#second-trigger-m214) (default: `TriggerIgnored`); broken → `CueBroken`. A disarmed target is skipped as on GO. |
| Stop (CT-12) | Stop with the cue's fade (`fade_out`, duration 0 = hard stop). |
| Pause (CT-13) | Pause (a paused or idle target is left as it is). |
| Load (CT-14) | Load to `load_to_time` (an active target: `LoadIgnored`; broken: `CueBroken`). |
| Reset (CT-15) | Reset (clears broken). It does not undo Arm/Disarm changes. |
| Devamp (CT-16) | see [Devamp](#devamp-ct-16) |
| GoTo (CT-17) | see [GoTo](#goto-ct-17) |
| Arm / Disarm (CT-19) | see [Arm and Disarm](#arm-and-disarm-ct-19) |
| Wait (CT-20) | nothing; its action lasts its duration |
| Memo (CT-21) | nothing; its action completes at once |

### GoTo (CT-17)

- Moves the playhead of the **target's** cue list (any list of the workspace, not only the GoTo cue's own) to the target, at any depth (the playhead may stand on any cue, see [Playhead](#playhead-pb-05-cl-06)).
- With "and GO" it then GOes on that list, dated `A`: the target starts and the playhead moves past its continue chain (or into an armed "start first and enter" group), exactly as an operator GO. As in QLab, this is not an operator GO: double-GO protection does not block it and it does not restart the double-GO interval.

### Arm and Disarm (CT-19)

- The engine cannot change the `&Workspace`. An Arm/Disarm cue emits `SetArmed { cue, armed }` and records the change as an **override** that the engine honours for the rest of that call: a Disarm followed by a trigger of the target in the same chain sees the target disarmed (its action is skipped, a Load sends no `LoadVoice`, GO does not enter a disarmed "start first and enter" group).
- Only the target itself changes (a group's children keep theirs). A running target keeps running; the change applies to its next action. Arming an already armed cue (as the engine sees it) does nothing and emits nothing.
- The binary applies every `SetArmed` to the model before the next `handle` call (M4.2 contract), so each call starts by dropping all overrides: from then on the model rules, including an operator edit of `armed` made right after.

### Devamp (CT-16)

- **"Start next cue" is the Devamp cue's continue** (QLab: with it, the Devamp cue acts as if it auto-continued when the slice ends). On an armed Devamp cue it replaces the cue's own continue mode: the next cue starts once, when the loop is left, never also at the Devamp cue's action start, and the Devamp cue's post-wait is not used. For the playhead (M2.24, QLab check D5): GO on it moves the playhead **onto** the cue it will start, which stands by until the loop is left and stays under the playhead when it starts (a chain reaching the Devamp cue stops there too). Without "start next cue" (or on a disarmed or broken Devamp cue) its own continue mode applies as usual, also for the playhead.
- **Modes** (QLab 5's two Devamp settings, check D7, M2.28; show file `devamp_mode`, since version 3): `current_slice` ("Devamp currently looping slice") leaves whatever loop the audio target is playing and goes on to the next slice, the behaviour below; `looping_cue` ("Devamp looping cue") leaves the **cue's own** loop. openLab has no play count for the whole cue (QLab has one besides the slices'): a cue without slice markers loops as a whole through `last_slice_play_count`, and that is the cue's loop, which both modes leave; on a cue **with** slice markers every loop is a slice's, so `looping_cue` does nothing there but warn `DevampIgnored { cue: target }` (nothing is sent or left pending, so its "start next cue" never fires and a later Devamp is free to act), as QLab does when it is fired while a slice loops. QLab's other measured case ("devamp currently looping slice" on a cue whose whole range also loops: slice 2 plays, then the cue plays again and slice 1 loops again) needs the whole-cue play count, which openLab does not have yet (#144). Shows from version 2 get `current_slice`, which is exactly what their Devamp cues did. The mode concerns audio targets only: a looping playlist is devamped the same way in both modes, and the second trigger `devamp` acts as `current_slice`.
- **Audio target** that is playing (in its action with a started voice; not paused, stopping or broken; for a paused one see **Pause** below): emits `DevampVoice { cue: target, run, at: max(A, now, voice start), stop }` (`stop` = "stop target when slice ends"). The audio side answers:
  - `DevampScheduled { at: L }`: the voice leaves its loop on `L`. With "start next cue", the cue **after the Devamp cue** (QLab: the Devamp cue then acts as if it auto-continued when the slice ends; looked up as for any continue when it fires) starts on exactly `L` — a deadline, so it lands on `L` inside the lookahead window, and late at `now` (with `L` as its timing) otherwise. The target plays on into its next slice (or ends there with `stop`) and completes on its end report as usual. If the target's end report comes before that deadline was carried out (the voice ended at `T ≤ L`), the next cue starts on `min(L, T)`, so it never waits past the end of the cue it follows. **Pause**: a pending devamp survives a pause of its target (QLab). On resume it is sent again for the resumed segment (`DevampVoice` with the fresh run id, dated on the resume), and any `L` already known is forgotten: the next cue starts on the `L` the new answer gives. Answers for the paused segment's id are stale and ignored. **A Devamp fired at a paused target** (paused in its action) is kept, neither ignored nor taken for a resume (user decision 2026-10-25): the cue stays paused, nothing is sent to the paused segment, and the devamp is pending exactly like one sent before the pause, so the resume sends it (`DevampVoice` for the fresh run, dated on the resume, right after the `ResumeVoice`): the cue finishes the loop pass it was paused in and then leaves the loop, with "start next cue" on the answer's `L` as usual. One `DevampVoice`, after the resume, so no command for the voice is dated before an earlier one. A second Devamp meanwhile is `DevampIgnored` (one at a time); a stop or reset of the paused target drops it.
  - `DevampIgnored`: nothing to leave (no slice table, as for a cue that is not looping); `DevampIgnored { cue: target }` warning, no next cue.
  - A stopped, reset, deleted or broken target cancels a pending devamp (and its next cue).
- One devamp at a time per voice: a second Devamp while one is pending sends nothing and warns `DevampIgnored` (the audio side would ignore it, and its answer could not be told apart).
- **Looping playlist group** (M2.15) that is running (not stopping): it finishes its current child and then **completes** instead of moving on or wrapping; its continue applies (auto-follow fires unless a child broke at run time), and with "start next cue" the cue after the Devamp cue starts on the same sample. A paused playlist completes when its child completes after the resume. "Stop target when slice ends" makes no difference for a playlist.
- A group that is not a looping playlist (or already devamped): `DevampIgnored`, nothing changes. A target that is not running (idle, loaded, pre-waiting or paused in its pre-wait, stopping, broken): `TargetNotRunning`. Any other kind: `TargetWrongKind`.

## Fade cues (CT-10)

Audio levels only in v0.0.1 (§21). A Fade of an audio cue is **absolute** (QLab): over its duration, with its curve, it moves the target's levels from their current values to the Fade's values. A Fade of a **group** is **relative** (QLab check F2, M2.28: children at 0 and −20 dB faded by a group Fade at −10 dB end at −10 and −30 dB): each level of each audio cue in it moves **by** the Fade's value, i.e. to its current value plus the Fade's dB (its gain times the Fade's gain), never above `MAX_DB` (+12 dB). Shows saved before format version 3 meant group Fades absolutely: loading one warns `GroupFadeNowRelative` on each such Fade cue (file-format.md §2).

- **What it fades**: at its action start `A`, every **playing** audio cue it targets: the target itself, or for a Group target every audio cue inside it (any depth) that is playing then (relative: each moves by the Fade's values from where it is on the ramp's first sample `S`, including where an earlier Fade has put or is moving it; a level that is silent then, such as an unlisted crosspoint, stays silent and gets no ramp). Playing = in its action with a started voice (running, fading, paused or stopping), not broken. Cues that start later are not faded.
- **Which levels**: the Fade's `master_db`, each set `output_db[o]` and each listed crosspoint, per target. Indices beyond that target's outputs (`output_db` past `outputs.len()`, a crosspoint output past it, a crosspoint input of 64 or more) are ignored; crosspoint inputs beyond the file's channels are ignored by the mixer. A muted output or crosspoint of the target is not faded (a fade never changes mutes, so its gain stays 0). An unlisted crosspoint of the target is silent and fades up from silence.
- **Ramps**: per target and level, `Ramp { cue, run, at: S, param, gain, frames: E − S, curve }` with `S = max(A, now, voice start, the voice's last committed command)` and `E = A + duration` (minus a load-to-time offset). So a ramp never names a voice before the mixer has it, a late fade starts late but still ends on `E`, and `gain` is linear (`db_to_gain`, the mixer's conversion). Duration 0 sets the levels on `S`.
- **Current levels**: the mixer starts every ramp from the value the gain has on its first sample (docs/audio.md, Ramp definition), so a fade interrupted by another fade (or a second fade after a first) continues without a jump. The engine tracks the same thing: each running audio cue keeps the gains Fade cues have set or are moving, as `from → to over frames from start`, evaluated with the mixer's formula (`ramp_gain`, `curve_shape`, `db_to_gain`; `tests/level_maths.rs` checks that they match `openlab_audio::ramp_value`, `Curve::shape` and the dB conversion bit for bit). The mixer itself evaluates fade curves within `openlab_audio::RAMP_TOLERANCE` (1e-6 relative, in practice up to one f32 step) of `ramp_value`, not bit for bit, so a held or resumed fade continues from the engine's level to within that tolerance, which is inaudible. Untouched levels are the model's, and an edit of a playing cue's levels reaches its voice (see "Level edits on a playing cue" below), so the model's level is the heard one. `fade_level(cue, param, at)` reads one level (`None` = untouched); `fade_ramps(cue, at)` lists every faded level with its value, target, end sample and curve. A ramp of 0 frames (a Fade of duration 0) is tracked the way the mixer hears it: a linear ramp over the de-zipper time (5 ms, at least one sample; docs/audio.md, De-zipper), except on the voice's own start sample, where it is immediate (its first start: a resume keeps the same mixer voice, so a 0-frame ramp on a resume sample is de-zippered too). The `Ramp` action still carries `frames: 0`; `fade_ramps` reports the de-zipper as the moving ramp it is (linear, ending 5 ms later). A hold (a paused Fade) is a ramp from the current value to itself, so it changes nothing. These levels belong to the cue's run: a stopped and restarted cue starts from the model's levels again (Reset restores its saved levels, CT-15).
- **Ownership**: each level is moved by the Fade that last ramped it. A later Fade takes it over; the earlier Fade then no longer touches it (pausing or stopping it sends nothing for that level).
- **Completion**: the Fade's action completes on `E` (auto-follow fires then); its targets have reached its values. An edit of a running Fade's duration moves `E` (see [Model edits](#model-edits)); an edit of a level it is moving completes it at once, without stopping its target (see [Level edits on a playing cue](#level-edits-on-a-playing-cue-aud-06-aud-08-m59b)). With **stop target when done** the target (a group: with everything in it) is hard-stopped on `E` — exactly on the sample the ramp ends — before the auto-follow fires. It stops the target whatever it is doing then.
- **Pause** of the Fade cue holds its ramps where they are on the pause sample `P` (`Ramp { at: max(P, ramp start), gain: current value, frames: 0 }`, the mixer's value on that sample, so nothing moves); **resume** at `R` ramps each held level from there to the Fade's value, ending on the Fade's shifted end (`E + R − P`), with the same curve over the remaining frames (continuous; the remaining path is a fresh curve from the held value, not the tail of the original one). **Stop** (or Reset, or deleting it) holds the ramps where they are and never stops the target. A held level whose ramp had already ended sends nothing.
- **State**: the Fade cue reports `running` during its fade. Each audio cue it is moving reports `fading` (CUE-04) while it is in its action and a running, unpaused Fade with a non-zero ramp on it exists; it returns to `running` when that Fade completes, pauses or stops. Paused, stopping and broken take precedence. A group target reports its own state (`running`); its faded children report `fading`. Second triggers on a fading cue follow its second-trigger option like on any active cue.
- **Not playing**: if nothing it targets is playing at `A`, the Fade warns `TargetNotRunning` and does nothing, but still runs its duration (its timing and continue apply, as in QLab; "stop target when done" then stops the target on `E` if it is running by then). A target of another kind: `TargetWrongKind`; none or missing: `NoTarget`/`TargetMissing`.
- Feedback never breaks a Fade cue (it owns no voice).

## Level edits on a playing cue (AUD-06, AUD-08, M5.9b)

An edit of an Audio cue's levels (master, cue output levels and mutes, crosspoints and their mutes; `SetCueProperty KindFields` from the Levels tab, an undo or redo of one) is heard on its playing voice at once, as QLab 5 does (5.3 change log, manual pp. 34-36). No restart, no new voice, no state change: the cue keeps running.

- **Which cues**: an audio cue with a started voice (running, fading, paused, stopping), not broken. An idle, loaded or pre-waiting cue has no voice: the edit is in the model, and the voice starts with it. Previews are not followed (they keep the levels they started with).
- **What is sent**: each run keeps what its voice has been given, per parameter (`Run::given`: the model's levels at the voice's start, and each edit sent since). When the engine follows edits (`model_changed` / `model_changed_cues`, M4.2 contract), after the deadlines due in that call are carried out (so a fade ending in the call has already let go of its levels), each such run compares the model's levels with that (`level::level_edits`) and emits one `Ramp { cue, run, at, param, gain, frames, curve: linear }` per parameter whose gain or mute differs: an unlisted or removed crosspoint and an output beyond the list are silent, a mute is gain 0 (its level is kept, so unmuting restores it), ganging alone changes nothing. `at = max(now, voice start, the voice's last committed command)`. Several edits between two calls are one ramp to the last; work per call is one comparison per started audio voice plus the changed gains (at most 1 + 64 outputs + their crosspoints, whatever the edit rate). A fader drag (many coalesced edits per second) is therefore one short ramp per edit, each retargeted by the next from wherever the gain is.
- **Patch**: a change of the cue's patch is not a level edit and core sends nothing for it; the binary moves the playing voice to the new patch's outputs with a short crossfade (docs/control.md "Patch slots", #293; QLab's behaviour is not documented: open question 24).
- **Ramp length**: `frames` = 10 ms (`EDIT_RAMP_SECONDS`, at least one frame), linear; 0 on the voice's own start sample (nothing heard yet, applied at once). Twice the mixer's 5 ms de-zipper (docs/audio.md, De-zipper) because an edit can be a full-scale step (a mute, a typed level), and still short enough to feel immediate. The mixer starts every ramp from the gain's current value, so an edit during an edit ramp, a fade or a resume never jumps.
- **Paused cues**: the ramp is sent to the paused voice. The mixer advances no gain while a voice is paused, so the edit is heard over its ramp from the resume (under the resume's declick), and the resumed voice plays at the edited level.
- **Fades**: **the edit always wins** (QLab 5.5.3, `docs/todo/open-qlab-questions.md` row 23: focusing the master during a fade snaps the sound to the field's value and the Fade cue completes at once). The edited level is sent as above and taken from any Fade that set or moves it (`Level::owner`); the model's level rules it again. An edit (or mute) of a level a **running, unpaused** Fade cue is moving **completes that Fade at once**, on the call's `now`: its auto-follow fires, but its "stop target when done" does **not** apply. The edit is the operator deliberately taking the level over, so the target (a group target with everything in it) keeps playing at the edited level; nudging a fader during a fade-out-and-stop must never cut the sound. A shortened duration (Model edits) is not a take-over and still stops the target on the new end. The other levels it was moving, on this cue or on other cues it fades (a group Fade), are **held where they are** (`Ramp { gain: current value, frames: 0 }`, as when a Fade is shortened to now; no jump to the Fade's values), and it lets go of them; a later edit of one replaces it. An edit of a level the Fade does not move changes nothing for the Fade. A **paused** Fade starts nothing: the edited level leaves it, the Fade stays paused, and its resume moves only the levels it still has. A level a finished or stopped fade set (no owner) follows the next edit of it the same way. Since an edited level is the model's, a later Fade starts from it (absolute: ramps from the heard value; relative group fade: moves the edited level by its dB).

## Network cues (CT-30)

A Network cue sends one OSC message (`address` and typed `args`: int, float, string, bool) to its network patch (`host`, `port`, UDP or TCP). Its action has no duration: when the action starts it emits `Action::SendOsc { cue, at, destination, address, args }` and completes at once, so pre-wait, post-wait and continue modes behave as for a Memo. Core sends nothing: the binary encodes and delivers the message off the control thread and the audio thread (docs/control.md, Network output). `at` is the sample the action started on; OSC is not sample accurate, the binary sends when `at` enters its lookahead window or at once if it is late.

Only a cue that is armed and has no problems emits `SendOsc`. A disarmed cue skips the action like any disarmed cue; a broken one is skipped for its problems (see below). Whether delivery succeeds is not the cue's business, as in QLab: the cue is complete when it has been handed over, and a failed send is a warning from the binary. The OSC output override (PB-10) is the binary's too: with network output disabled `SendOsc` is received and dropped, the cue still runs, completes and continues.

Whether a destination's host name resolves, or anyone listens, is never a problem (QLab 5 flags only a missing patch, an incomplete patch and an invalid message); the binary resolves names off the control thread and a failed send is a warning.

## Broken cues (CUE-06, NFR-07)

Problems that keep a cue from running are found **before it is triggered** (NFR-07), so the operator sees them in the list, the inspector and the pre-show check. Core does no I/O: the binary reports what it learns about media and devices as inputs; target and reference problems come from the model. A cue can have several problems (`CueProblem`, in this order: target, nothing to fade, media, patch/device):

| Problem | Cue kinds | From |
|---|---|---|
| `no_target` | targeting cues (Fade, Start, Stop, Pause, Load, Reset, Devamp, GoTo, Arm, Disarm) | the model: target not set |
| `target_missing { target }` | targeting cues | the model: target not in the workspace |
| `target_self` | targeting cues | the model: the cue targets itself |
| `target_wrong_kind { target }` | Fade (needs Audio or Group), Devamp (needs Audio or a playlist group) | the model (the same rule as load-time validation) |
| `nothing_to_fade` | Fade | the model: the fade sets no level (`master_db` unset, every `output_db` entry unset, no crosspoints); QLab: "No parameters set to fade" (M2.26, check F4) |
| `no_media` | Audio | the model: no file assigned |
| `media_missing { media }`, `media_unsupported { media, reason }` | Audio | `Input::MediaStatus` for the cue's media reference |
| `patch_missing { patch }` | Audio | the model: patch not in the workspace |
| `device_unavailable { patch, resolution }` | Audio | `Input::PatchStatus`: any resolution but `mapped` (unmapped, device missing, channels missing, output count mismatch) |
| `network_patch_missing { patch }` | Network | the model: destination not in the workspace |
| `network_host_invalid { patch, reason }` | Network | the model: the destination's host is empty, is not an IP address or a valid host name, or its port is 0 (`check_endpoint`) |
| `network_message_invalid { reason }` | Network | the model: the address is not a valid OSC address (`/`, printable ASCII, no spaces, at most 512 bytes), too many arguments (32), a string over 4096 bytes or with a NUL, a non-finite float, or the encoded message over 8192 bytes (`check_message`) |
| `started_broken` | any | shown alone while a cue that was triggered with problems, fixed since, still has that run pending (it reports `broken` until the run ends; see Triggering) |

- **Not problems**: damaged media that plays (M3 probe warnings: the binary reports it `available` and shows its warnings itself); a trigger cycle (load-time validation warns; the engine bounds it at run time, see [Chains](#chains-and-the-chain-bound), since a timed loop of Start cues is legitimate); a disarmed cue (it is still broken if it has problems). A **group** has no problems of its own because of its children, but as in QLab 5 it **shows as broken** while any descendant (any depth) is shown with problems (`started_broken` included; M2.24, QLab check G6): with no run of its own it reports the state `broken` (`StateChanged`, dated `now`, on every change; `cue_states()` lists it), `has_broken_descendant(group)` is true (false for a cue that is not a group), and `Action::GroupWarningChanged { group, warning }` reports every change (also `false` once for a deleted group that had one) as the reason. It is still not refused: GO, Start or a continue starts it as usual, its broken children are skipped and the others play (while it runs it reports its run's state). It is not in `broken_cues()`, which lists the cues with problems. It follows the incremental scheme below: a status input or a run's end updates only the groups around the cues whose problems changed (a parent index built with the model's part); the rebuild after `model_changed()` recounts them. Run-time breaks (`broken_reason`) do not count. The pre-show list is unchanged: it lists the broken cues themselves.
- **Inputs**: `MediaStatus { media, status }` with `status` `available`, `missing`, `unsupported { reason }` or `unknown` (forgets the report: assumed playable), keyed by the cue's `MediaRef` exactly as stored, so every Audio cue on that reference shares it. `PatchStatus { patch, resolution }` with `resolve_patch`'s `PatchResolution`. `Availability { media: [(media, status)], patches: [(patch, resolution)] }` carries many of both in one call (workspace open, a rescan, a drive that went away). Nothing reported yet = no problem: the engine cannot know a file is missing until the binary says so.
- **Incremental** (a show can have thousands of cues and files): the model's part (targets, patches, media references, with indexes from media reference and patch to their cues) is brought up to date only on the first call after `model_changed()` or `model_changed_cues(footprint)` — the binary calls one of them after every model change (M4.2 contract) — so model edits count from that call (a deleted target breaks its control cues, a retarget fixes them). `model_changed()` rebuilds everything: the reference, and what a change with no footprint (a newly opened workspace, a relink) needs. `model_changed_cues` is for a command, undo or redo and costs what the edit touched (M4.12a, NFR-24): it recomputes the cues in the footprint, the cues the edit added (a group's descendants included) and every cue whose problems depend on one of them. **The dependency rule**: a cue's problems come from its own content, from the existence and kind of its target (`can_target` reads the kind, and a group's mode, of the cue a fade, devamp, stop, ... names) and from the patch and network patch id sets, so a touched, added or removed cue refreshes the cues that target it (the engine keeps the reverse index `by_target`); group warnings (`has_broken_descendant`) are recounted for the groups a cue was added to, removed from or moved between, and around every cue that started or stopped showing problems, from what each group's cues hold. Where the engine cannot follow from the footprint (a patch or cue list id set differs from the one the facts were computed against, a duplicate cue id, a cue the index cannot place) it rebuilds everything; a footprint that misses a changed cue is the same contract break as a missed `model_changed` (counted by the edit cross-check and when a refused cue is rechecked). The engine keeps its own `CueIndex` (core `cue_index.rs`: each cue's container and the order of each container's cues, followed from the footprint, found by walking recorded ancestors and checking each step, so a stale record never gives a wrong cue). An added subtree is new as a whole: a cue in it that the index already had (an id removed and added again in one edit, as a transaction or its undo does, alone or inside another group, as a group or not) is reported gone and fresh, with every old and new descendant, including descendants that kept their ids; the footprint's `added` set is passed to `CueIndex::reconcile` for this. When anything was added, `reconcile` walks every added, removed or moved cue as an added top, because a cue moved out of an added subtree later in the same transaction, or by another edit before the next call, is no longer under the added top yet carries the new content (the media catalog's `sync_cues` gets the same rule). `verify_problem_cache(ws)` compares the whole bookkeeping with a from-scratch rebuild; the property test `commands_prop::incremental_problems_equal_a_full_rebuild` holds an engine told footprints to one told `model_changed()` over random commands, undo, redo, runtime inputs and media and patch reports: same actions on every call, same broken cues and group warnings. A status input recomputes only the cues on that media reference or patch, and an unchanged report nothing. A call with nothing new costs nothing; `problem_checks()` counts the cues computed (tested: O(affected)). Every build trusts the signal, except that a cue about to be refused for its problems (Start, GO, a continue, Load, its action start) first has its problems recomputed from the current workspace: if they no longer match, the problems are rebuilt and the mismatch counted in `unsignalled_model_changes()`, so a cue fixed by an unsignalled edit is never refused for its old problem. Healthy cues pay nothing for this. Each cue whose problems changed gets `ProblemsChanged { cue, problems }` (the full new list; empty = fixed) and, if its reported state changed, `StateChanged` (`idle` ↔ `broken`) dated `now`. The first call reports every broken cue. A deleted broken cue reports `idle` once.
- **State**: a cue with problems and no runtime reports `broken`. A cue with a runtime keeps reporting its runtime state (a playing cue whose file is reported missing plays on; whatever the audio side then does arrives as feedback) and reports `broken` when its runtime ends. A **loaded** cue that gets problems is unloaded (`UnloadVoice`) and reports `broken`. A cue that gets problems during its pre-wait skips its action when the pre-wait ends (as below) and reports `broken` from then.
- **Triggering** (Start, GO, a continue, a Start/GoTo cue): a cue with problems does not start (`CueBroken` warning) but keeps its timing exactly like a disarmed cue (user decision, M2.13): pre-wait, then its action is skipped, then its post-wait. Its continue fires on schedule, an auto-follow at its (skipped) action start as for a disarmed cue (M2.24, QLab check P5); it reports `broken` throughout (no `pre-waiting`). GO moves the playhead past its continue chain as usual: GO on a broken auto-follow cue starts the cue it follows into and moves the playhead past that one too. A broken Devamp cue sends no devamp, so its "start next cue" never fires and, as for a disarmed one, its own continue mode applies (also for the playhead). Stop or Reset cancels its pending continue. A group with such a child runs the child's timing and still auto-follows (QLab check G2). Fixing the problems while that run is pending does not start the skipped action; the run ends as it was, and meanwhile the cue shows `started_broken` (so a broken cue always has a reason to show), then `[]` when the run ends. Load warns `CueBroken` and loads nothing. Reset does not clear static problems.
- **Pre-show** (NFR-07, M4.8): `broken_cues()` lists every cue shown with problems and its problems, in workspace order (lists in order, cues depth-first). Breaks at run time are not static and are in `broken_reason(cue)` / `cue_states()`.
- `CueProblem` implements `Display` with an English sentence for logs; the UI localises from the variant (CUE-06 "human-readable").

## Display name (M2.29c, QLab check R2)

`display_name(cue)` (core, `Cue::display_name`) is the name a UI shows: the stored `name` if it is not empty; otherwise, for an Audio cue with media, the file name **with its extension** (the last `/`-separated component of the stored `MediaRef`, as stored: no case or Unicode-form change; a backslash is a file-name character); otherwise empty. Assigning or relinking a file never writes `name`, so a cue the user named keeps its name when the file is renamed, and an unnamed cue follows the file (see [persistence.md](persistence.md) "Media watch and follow"). OSC `/cue/{n}/name` still returns the stored name. Shared fixture `engine/fixtures/display_name.json` (Rust test `display_name.rs`; the Swift test comes with the app part of M2.29c).

## Panic (PB-03)

`Input::Panic` stops everything, as QLab's Panic: every cue of every list, at every depth.

- **Fade**: every playing voice (an audio cue in its action, not paused) gets `StopVoice { at, fade: { frames: E − at, curve: PANIC_CURVE } }`, with `E = now + panic_duration` and `at` as for any stop (no earlier than `now`, the voice's start or a committed command), so every voice reaches silence and **stops on the same sample `E`**; the cue reports `stopping` and goes `idle` on `E` without waiting for feedback. `PANIC_CURVE` is linear in gain (the setting has only a duration), as QLab's (check Q6, M2.18: QLab's panic fade sounds steady with its tail dropping faster than its head, which is a gain-linear fade). The stop gain multiplies the voice's other gains, so the fade starts from wherever the voice is.
- **Takeover**: a Fade cue moving levels is stopped, which holds its ramps where they are (see [Fade cues](#fade-cues-ct-10)); the panic then fades the voice out from there. A cue already fading out with a stop that would end after `E` gets the panic's `StopVoice` (the mixer restarts the stop gain's ramp from its current value, so it ends on `E`); one that ends on or before `E` keeps its stop.
- **Everything else stops at once**: pre-waiting, post-waiting, paused (a paused voice is silent: hard stop), loaded (`UnloadVoice`) and silent cues (Wait, Memo, control, Fade). So nothing pending fires: pre-waits, post-wait auto-continues, auto-follows, a Devamp cue's "start next cue" (also when the voice would leave its loop during the panic fade), playlists moving on, "stop target when done". A group in its action with a child still fading reports `stopping` and goes idle when its last child stops (on `E`). A cue broken at run time with a pending auto-continue stays broken; the continue is cancelled.
- **Feedback during the fade** starts nothing either: a voice that ends early is stopped (`idle`), and a voice that **fails** while it fades out (`ActionFailed`/`StartFailed`, any reason) shows `broken` (a `device_lost` one is `idle` at once if its patch is reported `mapped`) but ends as a stopped cue: its group hears a stop (a group with no other busy child stops, it does not complete), and no continue, playlist step (also not the follow-through of a playlist that is not running) or halt follows from it. The same holds for a cue's own panic (`PanicCue`, its `panic` second trigger) and for a cue being stopped with a fade with no panic: the failure only ends a stop that was under way (M2.31).
- **A lost device** (`ActionFailed`/`StartFailed` with `device_lost`, panic or not) ends the run the same way, as a stop (M2.31): no auto-follow, no auto-continue (its pre-wait and post-wait are cancelled), no playlist step (running or follow-through), no halt, and its group hears a stop. The binary sends these failures one input before `Input::DeviceLost` stops everything; in between, a playlist moving on would run a control cue (a Disarm is saved with the show) even though its audio children are already refused.
- **Second press**: a Panic before `E` (while `panic_end()` is `Some(E)` and `now < E`) hard-stops everything at once, including cues started since. `panic_duration` 0 is always that hard stop. A Panic on or after `E` is a new panic with its own fade; so is one after the clock went back to before the panic (a device restart ends the panic window).
- **Previews** fade out with the show; a paused one stops at once; a second Panic cuts them (see [Preview](#preview-cue-05-pb-09)).
- **After it**: nothing is active, loaded or pending (`next_deadline()` is `None`, `cue_states()` holds only broken cues, `panic_end()` is `None` from the first call on or after `E`). Fade levels go with their runs. Playheads do not move. Arm/Disarm overrides only last for the call that made them anyway.
- **GO during the panic fade** is accepted and starts cues normally (QLab does not lock the workspace during a panic); the panic's end does not touch them, a second Panic does. A cue still **fading out in the panic** is not active for the second-trigger rule (operator intent: recovering from a panic): Start, GO or a continue on it hard-stops its fading voice and starts it afresh (a new run and `RunId`; the mixer cuts a hard stop on its sample without de-click, so the cut of a partly faded voice can click: progress archive M2.18); on a group, it hard-stops everything in the group and starts the group again. A child started on its own while its group fades out in the panic (and every group around it doing so) ends that group's run at once (`idle`, or `broken`) instead of leaving it `stopping` until the new child ends: a child started on its own does not make its group run, and the group's other children finish their panic fades on their own. A cue whose own stop fade the panic kept (it ends sooner) counts as fading out in the panic too. A cue fading out because of an ordinary stop with fade, with no panic, keeps the second-trigger rule (its option; default `TriggerIgnored`). A cue's own `panic` second trigger fades it out "in a panic" in this sense too. Panic does not touch double-GO protection: a GO within `min_go_interval` of the last accepted GO is still ignored.

`Input::GoFrom { list, cue }` (protocol `go_from`, OSC `/go "3"`): moves the list's playhead to `cue` and GOes as one input; if `cue` is not a playhead position of the list it warns `NotInList` and does nothing (no GO). A GO that double-GO protection would refuse (`min_go_interval`) leaves the playhead where it was (`GoIgnored`); QLab's behaviour for `/go "3"` under double-GO protection is not measured.

### Stop All and a cue's own panic

`Input::StopAll` (OSC `/stop` and `/hardStop`): every cue of every list, at every depth, and every preview stops at once, children before their groups, exactly as `Stop` with no fade does for one cue (pending pre-waits, continues and devamp next cues fire nothing). It ends any panic window (`panic_end()` is `None` after it), so a Panic right after is a new panic with its fade, not a second press. `Input::PanicCue { cue }` (OSC `/cue/{n}/panic`) is the cue's own panic of its `panic` second trigger (see `panic_tree`): the cue and what is in it fade out over `panic_duration` (0: at once); other cues and the workspace panic are untouched. **Second press** (QLab check Q7, M4.1d): `PanicCue` on a cue that, or whose descendant, is already fading out in a panic (its own or a workspace Panic) stops it and what is in it at once (`StopVoice` with no fade); other cues keep playing. The `panic` second-trigger option does not do this (a trigger on a cue fading out in a panic restarts it, see Second trigger). Both ignore an unknown cue or nothing running (`PanicCue` warns `UnknownCue` for an id not in the workspace).

## Reset All

`Input::ResetAll` (protocol `reset_all`, the app's sidebar Reset all) follows QLab's sidebar reset (manual pp. 97-98: hard stop of everything, temporary changes reset, every playhead to its list's first cue, the workspace as just opened). As one input, in this order:

- **Stop All** (see above): every cue of every list at every depth and every preview stops at once, a panic fade under way included; no panic window is left, so a Panic right after is a first one with its fade.
- **Reset** of every cue that still has a runtime, children before their groups: a cue broken at run time is cleared (its pending auto-continue cancelled), a loaded cue unloads (`UnloadVoice`). A cue with static problems stays broken, as Reset leaves it.
- **Random groups** forget their round-robin cycle (as a new engine: the workspace opened again).
- **Playheads**: each list's playhead moves to its first cue (none for an empty list); the binary primes the cues from there as after any playhead move ([Actions for the binary](#actions-for-the-binary-m42-contract)). QLab also loads that first cue; openLab's priming takes the place of that load.
- **Kept**: Arm/Disarm changes and level edits (they are edits of the model, saved with the show; QLab check A1), double-GO protection's timer.

## Pause All and Resume All (PB-04)

- `Input::PauseAll` pauses every active cue of every list at every depth, groups before their children, with the Pause operation (so every pause rule holds: timers, voices `PauseVoice`, Fade cues holding their ramps, devamps kept). Stopping, loaded, idle and broken cues are left as they are (as Pause leaves them). Then every playing preview pauses (QLab check V4, see [Preview](#preview-cue-05-pb-09)).
- `Input::ResumeAll` resumes **every** paused cue, however it was paused (Pause All, a Pause cue, the operator), as QLab's Resume All does; groups first, so a group resumes with its paused children (the group rules for resume apply, incl. a playlist moving on). Every resume gives the run a fresh `RunId` and re-sends a pending devamp, as Resume does. Then every paused preview resumes. With nothing paused it does nothing.
- **A failure while paused** (M2.31): a paused show starts nothing. A paused cue that fails (`ActionFailed` or `StartFailed`, not `device_lost`) loses its voice at once (silenced and freed) but stays paused (`is_paused`) when what its end would start must wait for the resume: a skipped cue's auto-follow (`StartFailed`), or the next child of a **playlist** it is a child of, running or not. The end is then carried out on the resume sample (Resume, Resume All, or a trigger that resumes it), and the playlist hears of the failure there: a running playlist halts for a child that broke while playing (its action ending on the child's nominal end, moved on by the pause) or moves on past one skipped before it played; one with no run starts its next child. A **playlist child** shows `paused` until that resume and `broken` from it (QLab 5.5.3, `docs/todo/open-qlab-questions.md` row 2: the failed child and its paused playlist keep the paused icon until Resume), whether it was paused by Pause All, by a Pause of its playlist or on its own; any other held cue shows `broken` at once. Stop, Reset, Panic and Stop All cancel the hold (a stopped one shows `broken`). An `ActionEnded` dated before the pause and arriving after it is held the same way (M2.33, see [Feedback](#feedback)). Other feedback starts nothing while paused: a group whose last child leaves while it is paused ends on the resume, a running playlist moves on at the resume, a `DevampScheduled` for a paused voice is replaced by the devamp the resume sends again, and `ActionLength`/`CueLengths` only set lengths.

## Actions for the binary (M4.2 contract)

Besides the voice actions above:

- `Ramp { cue, run, at, param, gain, frames, curve }` → mixer `Ramp { voice: run, target: param (Master / CueOutput(o) / Crosspoint{input, output}), gain, fade: Fade { frames, curve } }` (curves map one to one). The binary must not apply gangs to it (the Fade's values are already per output).
- **Known lengths** (`Input::ActionLength { cue, run, frames }`, M4.2a fix round): when the binary starts a show voice whose action is finite, it sends the action's length in samples, counted from the action's start (a load-to-time offset included; a start held up after its deadline adds the delay), so the engine owns the end as a **deadline** on that exact sample. Auto-follow, a playlist moving on and a group completing then come on the end sample itself, committed in the lookahead window like any deadline, instead of one or two blocks late when the mixer's report arrives. After a `DevampScheduled { at }` it sends the new length (where the voice leaves the loop plus the rest of the table; the leave sample alone for a devamp stop), and nothing while what follows still loops for ever. Previews do not send it.
- **Nominal lengths** (`Input::CueLengths { lengths }`, M2.27): the binary tells the engine each Audio cue's nominal action length (its plan from the top at the device rate, `None` when it is not known or loops forever), and again whenever it changes (an edit of trims or slices, a probe answer, a newly opened workspace; `None` for a cue that is gone or whose file is not playable). The control loop takes them from the plans it builds for `bad_plan` (`PlanChecks::take_changes`, docs/control.md). Only a halted playlist uses them (see "Halted playlist" under [Modes](#modes)); a cue never told is "not known".
- `DevampVoice { cue, run, at, stop }` → mixer `Devamp { voice: run, stop }` at `at`; its `DevampScheduled`/`DevampIgnored` events go back as `Input::DevampScheduled { cue, run, at }` / `Input::DevampIgnored { cue, run }` for that voice. After a `ResumeVoice` the engine re-sends a pending devamp for the fresh run: a binary that pauses by stop and restart sends it to the restarted voice; one with a native pause that kept the first devamp answers it with the `DevampScheduled` it has (tagged with the fresh run), not with `DevampIgnored`.
- `SetArmed { cue, armed }` → set the cue's `armed` in the model as a runtime change (not an undo step) **before the next `handle` call**: the engine honours it only for the rest of the call that made it. (A later save then stores it; see progress archive M2.17.)
- **Model changes** (M2-D): call `engine.model_changed()` (everything) or, for a command, undo, redo or an applied `SetArmed`, `engine.model_changed_cues(&footprint)` (the cues the edit named, M4.12a) after every change to the workspace (a command, undo, redo, relink, an applied `SetArmed`, a newly opened workspace) before the next `handle` call. The openLab binary does this by construction: a doc's workspace is writable only through a guard that signals when it ends (docs/control.md, Model changes). A change not signalled inside a cue or group leaves the static problems, the playheads and the chain limit out of date until the next signal, in every build (see [Model edits](#model-edits) for the guards); log any increase of `unsignalled_model_changes()`, it means an edit path misses the signal.
- **Availability inputs** (M2.8): send `Input::MediaStatus { media, status }` for each media reference the workspace uses once the probe (M3, off the control thread) has an answer: on workspace open, when a cue gets a new file, on relink, and when a file disappears or comes back (file-system watching, or a failed stream); damaged-but-playable files are `available`. Send many at once as one `Input::Availability` (open, rescan, a drive unplugged). Send `Input::PatchStatus { patch, resolution }` with `resolve_patch` for each patch on open, when the device list changes (hot-plug, device loss) and when the operator edits a patch mapping (WS-07). A binary that plays an unmapped patch on a default device sends the `mapped` resolution it uses. Show `ProblemsChanged` in the list and inspector (CUE-06), show a group that reports `broken` with no problems of its own as broken because of a descendant (`GroupWarningChanged`, and `has_broken_descendant` for a fresh client, give that reason; QLab check G6), and use `broken_cues()` for the pre-show check (M4.8). A device lost while voices play reports `ActionFailed { reason: device_lost }` for those runs at once (a hard stop, auto-follow does not fire); report the patches `device_missing` first and `mapped` once the device is back, which makes those cues playable again (the binary's outage policy: docs/control.md, Devices).
- `SendOsc { cue, at, destination, address, args }` (M4.6, CT-30) → encode the OSC message and deliver it to the network patch `destination` on a worker (never the control thread's own I/O, never the audio thread); a failure is a warning, not feedback (the cue has completed). Look names up off the control thread to fill the sender's address cache; the outcome is never reported to the cue engine. Never probe the destination itself.
- **Preview** (CUE-05): `Input::Preview` / `StopPreview` for the cue's preview key and protocol commands. `PreviewStart { cue, run, at }` → open the cue's stream and start a voice with id `run` at `at`, from the start of the cue's action, on the **audition output** (PB-09; until the audition patch exists, the cue's own patch), with the cue's levels as the model has them; `PreviewStop { cue, run, at, fade }` → stop that voice on `at` with the fade (the mixer's `StopVoice`); map the voice's `VoiceFinished` / failure to `Input::ActionEnded` / `ActionFailed` with `cue` and `run` as for show voices (a preview's `run` is recognised by the engine). `PreviewChanged` drives the preview button's state (a group's too: its preview is its audio cues' previews). Pause All and Resume All send `PauseVoice` / `ResumeVoice` for a preview's run, carried out as for a show voice (a preview's run is a voice id like any other). Fade Ramps and Devamp do not apply to previews.
- **Hotkeys** (M2.24, QLab check K1; for M4/M5, the binary has no hotkey handling yet): a hotkey press is to send `Input::Start` for every cue `Workspace::cues_with_hotkey(&hotkey)` returns (same key and modifiers, in workspace order): cues may share a hotkey, and both start, with no warning (validation does not warn either). A cue hotkey that is also a workspace key (`settings.hotkeys`, a transport or, since v5, a selected-cue key, e.g. Space = GO, `L` = Load Selected; `TransportHotkeys::action_of`) never starts the cue: the workspace action wins and `cues_with_hotkey` returns nothing for that key (the app matches hotkeys itself, M5.7, and drops transport keys there: that is where the rule is enforced today; M5.7a); validation warns `HotkeyUsedByWorkspace { action }` for the cue, and editing a cue's hotkey to such a key is allowed (QLab check K1b, M2.28: QLab shows "Hotkey used by workspace" with a warning icon on the cue; the app shows it, M5). A press on a paused cue resumes it (S1); the release follows the cue's on-release option (S5).
- **Second trigger on release** (M2.14): send `Input::TriggerReleased { cue }` when a hotkey or MIDI key (note-off) that triggered `cue` is released (cart triggers too, when carts exist); the engine decides whether it acts.
- **Panic** (PB-03): `Input::Panic` for the Panic transport key and the protocol `panic` action; `Input::StopAll` (protocol `stop_all` / `hard_stop_all`, OSC `/stop`, `/hardStop`) stops every cue and preview at once with no fade and leaves no panic window, and `Input::PanicCue { cue }` (protocol `panic_cue`, OSC `/cue/{n}/panic`) is a cue's own panic as its `panic` second trigger; it carries out its own `StopVoice` fades (no separate mixer panic is needed). `Input::PauseAll` / `Input::ResumeAll` for the Pause All / Resume All keys.
- A voice that the binary pauses by stopping and restarting (M3.18) must restart with the Fade levels and ramps the engine reports with `fade_ramps(cue, at)` on the resume sample: start with each `value`, then send `Ramp { gain: to, frames: end − at, curve }` for each one still moving (`end > at`; a fresh curve from there, like a resumed Fade). Fade ramps on a paused voice must apply as on a playing one.

## Feedback

- `ActionEnded { cue, run, at }` (from `VoiceFinished`), `ActionFailed { cue, run, reason }` and `StartFailed { cue, run, reason }` are matched on **cue and run**. `StartFailed` is `ActionFailed` for a voice that had not produced any audio yet: the cue breaks the same way (owns no voice, reports `broken` with `reason`), but it was only skipped, so its auto-follow fires on the failure sample and its group still auto-follows (rule 2). A cue that is paused when it fails this way starts nothing while paused: its auto-follow is held and fires on the resume sample (Resume, Resume All, or a trigger that resumes it); Stop, Reset or Panic cancel it. The binary sends it when the stream cannot be opened or primed for a start (file gone, read error before the first block), or the mixer refuses a voice's first start (not a resume); any later failure is `ActionFailed` (wired in M4.14: docs/control.md, Mixer events). `ActionLength { cue, run, frames }` too: it is honoured for a run playing its voice in its action and not stopping or broken (else ignored). The end is counted from where the voice (re)started (`end = voice start + frames − position then`), so a pause moves it by exactly the pause and a length sent while paused counts from the resume. It is cancelled by a stop (the stop's own fade end applies), a hard stop, a failure or a reset, and replaced by a later length. A voice's `ActionEnded` before the deadline is an earlier end and still completes the action at its `at`; after the deadline (`ActionEnded` on or after the planned end) it is stale: the deadline has completed the run and released its voice. The mixer does not skip what a starved voice missed (docs/audio.md, Voices: an underrun delays the rest), so after an underrun the real end is later than planned: the engine keeps the planned end (the successor starts on time; the late tail overlaps it), and the binary reports the underrun as a warning. Feedback for an idle cue, an unknown cue, or an old run (the cue has been stopped, reset, resumed or started again since) is ignored without any action.
- `ActionEnded` completes an audio action at `at` (clamped to no earlier than its start), or ends a fade-out stop. While the cue is paused, an `ActionEnded` dated after the pause sample is ignored: a paused voice cannot end by itself, so such a report comes from carrying out the pause. An end dated before the pause or on the pause sample (the voice ended just before the pause applied, its report arriving after it) still completes the action, on its `at`. The tie goes to the end (M2.34): the mixer dates an end on the first sample after the voice's last, so a voice ending on the pause sample had nothing left to play when the pause applied, and an end the engine knows ahead (`ActionLength`) on that sample is carried out before the pause in the same call; read as the pause, its report would leave the cue (or preview) paused with no voice, and a binary that had already forgotten the voice would never report it again. A binary that carries out a pause as stop and restart must therefore not report that stop as an `ActionEnded`. But a paused show starts nothing (M2.33), so if that end would start a cue (its auto-follow, its Devamp cue's next cue once the voice has left the loop, or the next child of a playlist with no run that it was started in on its own), the end is held instead: the cue stays paused (its voice is gone, so the resume sends no `ResumeVoice` for it) and the end is carried out on the resume sample (Resume, Resume All, or a trigger that resumes it), where what it starts starts, looked up in the workspace as it is then. Stop, Reset, Panic and Stop All cancel it. While held, an `ActionFailed`/`StartFailed` or `DevampIgnored` for the ended voice is ignored. The same holds for a cue paused on its own (Pause, a Pause cue), as for a failure while paused. Once the cue has resumed, reports for the paused segment carry its old id and are ignored like any stale id, so a pause's late end report can never complete the resumed cue. A genuine end of the resumed voice carries the fresh id and completes the cue as usual (a binary that resumes a voice which had already ended reports that end with the fresh id). A hard stop forgets the run immediately, so the voice's `Stopped` report that follows is stale and ignored.
- `DevampScheduled { cue, run, at }` and `DevampIgnored { cue, run }` answer a `DevampVoice` (see [Devamp](#devamp-ct-16)); they too are matched on cue and run and ignored when stale. `LoopReached`/`SliceEnded` are not inputs: the engine does not need them.
- Feedback never concerns a Group or a running Fade cue (neither owns a voice); any naming one is ignored.

## Model edits

Each call compares the workspace with what the engine knows. **Only the first call after `model_changed()` does** (M2.12; the binary signals every change by construction, docs/control.md Model changes): stopping deleted cues, moving playheads, recounting the chain limit and rebuilding the static problems are whole-workspace passes that a Tick on a big show must not pay (`model_syncs()` counts them). Every build trusts the signal, but compares the workspace's outline on every call (`shape.rs`: the cue list ids, each list's top-level cue count, the patch and network patch counts; one comparison per list, no allocation): if it differs from the last followed call, the change is counted in `unsignalled_model_changes()` (so the binary logs it at `error`) and the call follows the edits as if signalled. An edit inside a cue or a group escapes the outline, so the engine also guards wherever a missed signal could refuse or drop a cue or a GO, so the worst a missed signal costs is a late edit, never a lost start: a cue about to be refused for its problems is rechecked; a spent chain budget is recounted once (cues added unsignalled raised the real limit) and raised if the recount is higher; a GO whose playhead cue is gone resyncs that list's playhead instead of being ignored. A deleted cue that is still running when nobody signalled keeps its runtime until the next signalled call.

**Debug and release act alike.** The **edit cross-check** (`set_edit_cross_check`; on by default in debug builds, off in release) only counts: after each call it compares the workspace with the one the last call saw (`==`, then the debug text so a NaN equals itself) and the problem cache with a full rebuild (`verify_problem_cache`), and counts in `unsignalled_model_changes()` a workspace change nobody signalled and a cache that newly differs (a footprint that missed a cue), unless the call counted it already (the outline check, a refused cue's recheck). It follows and repairs nothing, so an engine with it gives the same actions on every call as one without (tested: `an_unsignalled_edit_inside_a_group_is_followed_alike_with_or_without_the_cross_check`); it costs a whole-workspace comparison and rebuild per call, which is why release builds leave it off.

**Incremental (M4.12c)**: the engine's `CueIndex` also keeps each cue's place, so these passes cost what the edit touched. After a signalled edit the chain limit comes from the index's cue count (not a walk of the lists), the cues present are read from the index, and a playhead is placed from the footprint: the index notes, before it follows the edit, what the edit touched around each playhead, and `sync_playheads` places the playhead from that (with nothing added, removed or moved it reads nothing). `whole_show_passes()` counts the passes that still walk everything (a full rebuild, duplicate ids, a new list); the property tests hold the result equal to `model_changed()`'s. **An unsignalled edit that moves cues** is the caller's breach (every build trusts the signal; the edit cross-check counts it): the playhead then catches up at the next signalled structural edit (add, remove or move) or at the next GO, and not at any call in between. Both land alike, as a full rebuild does: a deleted playhead cue gives way to the next position that still exists. A signalled structural edit that finds its playhead cue gone from the workspace without being in the footprint keeps the list's old order and compares it with the list as it stands (tested: `an_unsignalled_edit_that_moves_cues_is_caught_up_at_the_next_structural_edit_or_go`).

The passes compare the workspace with what the engine knows:

- A cue with a runtime that is no longer in the workspace is hard-stopped and forgotten.
- Changed times apply to **timers not yet started**: the pre-wait is fixed when the cue starts; the post-wait and the continue mode (auto-follow) are fixed when the action starts. The next cue is looked up when the trigger fires. The exception is a running Wait or Fade's duration (below).
- Playheads follow edits as described above; double-GO reads `min_go_interval` at each GO.
- **Running groups**: a deleted child is stopped like any deleted cue (if it was the group's last busy child, the group stops). A deleted group stops with all its descendants. A child added to a running timeline is not started (children start only when the action starts); a playlist plays it when it comes up (unshuffled) or from the next pass (shuffled). Reordering applies to children started later (see Playlist). A group waits on the runs that started in it (as its children, or as children started on its own while in it), wherever those cues are moved while they run. A busy cue **moved into** a running group neither keeps it running nor, if it breaks, cancels its auto-follow, and its end starts nothing there. A busy child **moved out** keeps running and the group goes on waiting for it: a drag is not a completion, so nothing starts on the drag. When the moved child ends, its group carries on as if it were still inside: a running playlist moves on to the child that took its place, and a group with no other busy run completes and auto-follows (if the moved child broke while playing, the group does not follow, rule 2). A stop or panic on the group reaches only its own tree: the group lets go of children dragged out of it (they play on, and the group does not wait for them nor hear of their end), and so do the start and the end of the group's run, so a run of the group never waits on a cue moved out before it started. A moved child's end carries on an idle playlist (follow-through) only while it is still that playlist's child (assumed, `docs/todo/open-qlab-questions.md` #45). A deleted busy child counts as stopped: a group left with no busy run by it stops. A group's mode is read when its action starts and again whenever it acts (a playlist changed to another mode stops moving on and completes with its current child; loop and shuffle are read when it moves on or starts a pass; a child's continue is checked against the mode when it fires). A cue whose kind changes to or from Group while it runs is stopped.
- **Control and Fade cues** read their target and settings when their action starts (a Fade's levels, curve and "stop target when done" are fixed then; a Load cue's `load_to_time` is read then).
- **A running Wait or Fade takes an edited duration** (QLab 5.5.3, `docs/todo/open-qlab-questions.md` row 30): followed in the first call after the edit is signalled (`follow_duration_edits`), its action now ends at the new duration from its start (load-to-time offset and pauses counted as for the original end), or on that call's `now` when it has already run longer; a paused one stays frozen and, if it is past the new length, ends on the resume sample. Its auto-follow fires and a Fade's "stop target when done" stops the target on that new end. A Fade **keeps its rate**: the ramps the mixer has go on unchanged, and at the new end each level still on its way is held where the original curve has got to (`Ramp { gain: that value, frames: 0 }`) and the Fade lets go of it; a lengthened Fade's levels arrive when they would have and the Fade completes later, its targets reporting `fading` until then. A Fade paused when its duration is edited, or edited and then paused, resumes to where its original curve is at the new length (`FadeRamp::gain_at`), and each resumed ramp ends at the earlier of the new end and the ramp's own planned end moved on by the pause, so a lengthened Fade keeps its rate across a pause too. A broken, disarmed or stopping Wait or Fade is not re-timed; an edit during the pre-wait applies as before, since the action has not started.
- **Arm/Disarm** changes the engine made (`SetArmed`) are honoured for the rest of the call; each call starts from the model (which the binary has updated).

## Warnings

`Action::Warning(EngineWarning)` never stops anything: `UnknownList`, `UnknownCue`, `NotInList`, `NumberNotFound`, `CueBroken` (a start or load of a broken cue), `TriggerIgnored`, `LoadIgnored`, `LateStart`, `ChainLimit`, `CueRemoved`, `NoTarget`, `TargetMissing`, `TargetWrongKind`, `TargetNotRunning`, `DevampIgnored`, `PreviewIgnored`, `PreviewFailed`. They are structured so the UI can localise them.

## Not yet

- **Groups**: playlist crossfades and per-group options beyond loop/shuffle.
- **Open QLab questions on halted playlists** (M2.27, from QLab check Q2; decided here as the most defensible reading, not measured): a remaining child whose length is not known or endless (a looping or unprobed audio cue, a nested looping playlist, a nested random or "start first" group) cancels the group's auto-follow, as the group could never say when it would have ended; a looping playlist that halts never follows; the group shows `post-waiting` while its follow is pending (QLab shows it finished); a nested group that ends with a child broken at run time still counts as a broken child of the playlist around it (that playlist moves on and does not follow), it does not halt it; a broken child that was paused on its own when it failed has its nominal end counted from its frozen deadline. QLab showed the measured case only (a plain list of 10 s audio cues).
- **Fade with nothing to fade** (M2.26, QLab check F4): a Fade that sets no level has the static problem `nothing_to_fade` (QLab: "No parameters set to fade"), so it is broken like any cue with problems: GO and Start skip it (`CueBroken`) and its "stop target when done" does not stop the target; its timing and continue run as for any broken cue. The target need not be playing or even set for the problem to show (a Fade with no target has `no_target` as well, listed first). Setting any one level (master, one output, one crosspoint) fixes it, incrementally like other model problems.
- **Target** cues (CT-18) are not in v0.0.1; video fades (CT-10 video part) are v0.0.2.
- **Network cues** send OSC only. Raw UDP/TCP string messages and OSC parameter fades are later (REQUIREMENTS §21).
- **Priming**: `Loaded` means "loaded by an operation"; keeping cues near the playhead primed (ARCHITECTURE §3.5) is the binary's job (M4.2).
