# openLab UI protocol (engine <-> UI)

Types: `openlab-core::protocol` (`engine/crates/core/src/protocol/`). They are the source of truth; this page is the spec the Swift types follow. One golden JSON file per message is in `engine/fixtures/protocol/{client,server}/` (the Swift tests decode every one). Architecture: ARCHITECTURE section 6. Model edits are core's `Command` ([commands.md](commands.md)); cue states and warnings are the cue engine's ([cue-engine.md](cue-engine.md)).

## 1. Conventions

- **Transport**: WebSocket on `127.0.0.1`, random port; one JSON object per text frame, UTF-8. The server is not part of the types crate: see [network.md](network.md) (limits, ordering per connection, slow clients).
- **Auth**: the engine writes `{port, token, pid}` to `<app-support>/openLab/engine.json` (mode 0600). The client's first frame must be `hello` with the token.
- **Envelope**: `{"type": "<snake_case name>", ...fields}`. Nested variants (transport actions, requests, commands, runtime changes, upserts, problems, warnings, result data) are also internally tagged with `"type"`.
- **Units**: times are **seconds** (f64), as in the show file, never samples. Levels in the model are dB (as the show file). Meter peaks are **linear amplitude** (f32): 0.0 is silence, 1.0 full scale, above 1.0 a clip. Ids are the model's UUID strings. `RequestId` is a non-negative integer (u64) the client chooses, unique on its connection; `u64::MAX` is reserved for the server's own requests (`bad_request` if a client uses it). `revision` and `seq` are u64.
- **Numbers**: JSON has no NaN or infinity. For **client** input the codec refuses negative or out-of-range values where they are meaningless (a load time, a fade duration) and empty paths: `decode_client` returns `ProtocolError`, never panics, whatever the input (non-JSON, wrong types, missing fields, huge numbers, deep nesting). Numeric payloads inside a `command` are not checked by the codec: `Workspace::apply` validates every time and level (finite, in range; [commands.md](commands.md) "Valid") and refuses with `command_refused`. For **engine** output the encoder sanitises `progress` and `meters` instead of failing: a time or peak that is negative, NaN or infinite is sent as 0 (an overrun of a loop end must not cost the UI a whole tick).
- **Frame limits** (checked on the byte length before any parsing): the first frame of a connection, `hello`, at most `MAX_HELLO_FRAME_BYTES` (4 KiB; the server reads it with `decode_hello`, before the token is checked); later client frames at most `MAX_CLIENT_FRAME_BYTES` (1 MiB); engine frames at most `MAX_SERVER_FRAME_BYTES` (32 MiB, for snapshots). Over the limit: `ProtocolError::TooLarge`.
- **Errors**: an envelope whose `type` is missing is `MissingType`, one that is not a message type of the direction is `UnknownType`; everything else wrong (bad JSON, wrong field types, missing fields, an unknown variant *inside* a known message such as a transport action or request kind) is `Malformed`. All are rejections; the engine answers `error` with `bad_request` or `unknown_message`.
- **Compatibility**: unknown **fields** are ignored (no `deny_unknown_fields`), so a newer peer can add optional fields without a version bump; the receiver must treat absent optional fields as documented. Unknown message **types** and unknown variants of nested enums are errors. Removing, renaming or re-typing a field, or changing its meaning, bumps `PROTOCOL_VERSION` (now **2**: M4.15f, several workspaces; section 2). Any change to a message updates the fixtures, the Swift `Codable` types and this page in the same commit.
- **Fixtures**: `UPDATE_PROTOCOL_FIXTURES=1 cargo test -p openlab-core --test protocol` rewrites them (pretty-printed, keys in declaration order, trailing newline); without it the test compares byte for byte and fails on drift. Files are named after the message type (`client/transport.json`); further variants add `_<variant>` (`client/transport_stop.json`, `server/result_error.json`). Every variant of the nested enums the client must decode has its own file (the pre-show report is `server/result_preshow_check` with every status and shape, and `result_preshow_check_ok`): `server/warnings_<warning>`, `server/runtime_problem_<problem>`, `server/runtime_problem_device_unavailable_<resolution>`, `server/runtime_state_<state>`, `server/runtime_state_broken_<reason>`, `server/error_<code>`, `server/log_<level>`; tests fail if a variant has no sample.

## 2. Connection

The engine holds up to 8 open workspaces ("docs", ARCHITECTURE section 6). A doc is named by its `doc` id, a non-negative integer (`DocId`, u64) handed out in open order from 0 and never reused while the engine runs (a new engine run starts again from 0, with a new token). A connection is either **bound** to one doc or the **app connection**:

1. Client connects and sends `hello { protocol_version, token, client_name, workspace? }`. `workspace` is a `doc` id: the connection is bound to that doc. Without it the connection is an app connection.
2. The engine answers `welcome`, or sends `error` and closes: `protocol_version_mismatch` (the version differs from the engine's; `error.protocol_version` says what the engine speaks), `bad_token` (wrong token, or any other message came first), `no_workspace` (`workspace` names no open doc: closed, or never opened in this run; the client must not retry). `hello` decodes for any `protocol_version`, so a client from another version can be told why.
   - Bound: `welcome { protocol_version, doc, snapshot }`, the doc's snapshot. Everything the connection sends acts on that doc and it receives that doc's broadcasts only (plus the engine's own `log`, `log_entry`, `status`). `revision` and `runtime_seq` are counted per doc: a new doc's snapshot starts at revision 1.
   - App connection: `welcome { protocol_version, workspaces }`, the open docs (`WorkspaceInfo` below). A `workspaces` message follows every change of the list: a doc opened or closed, or one's name, path or unsaved state changed. It receives no doc's broadcasts. A workspace message on it (`command`, `undo`, `redo`, a `transport` other than `panic`, `save`, `save_as`, `relink`, `preshow_check`, `close` without `doc`) answers `no_workspace`. Its `request: snapshot` answers a `workspaces` message, then `result`.
3. After `welcome` the client may send everything below. Every `command`, `transport`, `undo`, `redo`, `request`, `close`, `panic` and `hotkey` gets exactly one `result` with its `id` (a frame the engine cannot read gets an `error` with `bad_request` or `unknown_message`; the connection stays open).
4. **App-scope messages** work on any connection, bound or not, and act on the engine or every doc: `new`, `open`, `open_recovery` (open another doc), `scan_recovery`, `list_devices`, `log_tail`, `set_output_overrides` (PB-10, engine-wide), `close { doc }`, `panic` (Esc: every doc panics, as a `panic` transport in each would; twice within the fade is a hard stop), `hotkey` (every doc's cues with that hotkey start, or get their release). On the app connection `transport { action: panic }` is the app-scope panic too. Pause All, GO and the other transport actions act on the bound doc only (the front window's: the UI's notion, the engine has no front doc).
5. **Closing a doc** (`close`, on its own connection or `close { doc }` on any): refused with `unsaved_changes` while it has unsaved edits unless `discard_changes` (then its autosave is removed). Its cues stop at once (Panic twice), the requester gets its `result`, then every connection bound to it gets `closed { doc }` and the engine closes them; the app connections get the `workspaces` list without it. A client must not reconnect to a closed doc (its `hello` answers `no_workspace`).
6. `goodbye { shutdown }` ends the session. `shutdown: true` also asks the engine to quit; the default leaves it running for a reconnect.

A client that sees a gap in `revision` or in `seq` (section 4) sends `request: snapshot` and replaces its state.

`PROTOCOL_VERSION` is **2** since M4.15f: `welcome` has two shapes, `new`/`open`/`open_recovery` open another doc instead of replacing the one open and lose `discard_changes`, and `revert` is gone (QLab 5 has none). An engine refuses a client of protocol 1 at `hello`.

## 3. Client -> engine

| `type` | Fields | Notes |
|---|---|---|
| `hello` | `protocol_version: u32`, `token`, `client_name`, `workspace?` (a `doc` id) | first frame; `workspace` binds the connection (section 2) |
| `command` | `id`, `command`, `coalesce?` | `command` is core's `Command` ([commands.md](commands.md)): one undo step. The engine replies `model_changed`, then `result { ok: { revision } }`; a refused command changes nothing and replies `error.code = command_refused`, with one exception: if a transaction's rollback itself failed (core's `RollbackFailed`, only a wrong inverse can cause it) the workspace is partly changed, so the engine logs an error (`engine`), bumps the revision (the document is dirty), clears undo and redo, sends `document` and a whole `snapshot` instead of a `model_changed`, and then replies `command_refused` with a message saying the workspace is partly changed (undo and redo likewise). A command that changes nothing (a value set to what it already is) replies `ok` with the current revision, sends no `model_changed` and is no undo step. `coalesce`: a string of at most 128 bytes (longer: `bad_request`, nothing applied); consecutive commands with the same key are one undo step, each still sent as its own `model_changed` ([commands.md](commands.md) "Coalescing"). Absent = no coalescing |

| `undo`, `redo` | `id` | like a command; `ok.revision` after, `ok` without a revision if there was nothing to undo or redo |
| `request` | `id`, `request` | see below |
| `close` | `id`, `doc?`, `discard_changes?` (default false) | close `doc`, or the bound doc when absent (section 2); `result { ok }`, then `closed`; errors `unsaved_changes`, `no_workspace` (no such doc open, or no `doc` on the app connection). Fixtures `client/close.json`, `client/close_doc.json` |
| `panic` | `id` | app-scope Panic (Esc): every open doc; `result { ok }` |
| `hotkey` | `id`, `key` (1 to 64 bytes, the cue hotkey's key name), `modifiers?` (`{shift, control, alt, command}`, default all false), `phase?` (`down` (default) or `up`) | app-scope (QLab 5 fires a hotkey in every open workspace, in front or not): `down` starts every cue of every doc whose `triggers.hotkey` is exactly this key and these modifiers (a doc whose transport keys use the key starts none: the workspace action wins, M2.28; that action is the front window's, the UI sends it as a `transport`), `up` sends each of those cues its release (`trigger_released`); `result { ok }`. The `result` of a transport action means "accepted and handed to the cue engine"; what happened shows in `runtime` (states, playhead, warnings such as `go_ignored` or `trigger_ignored`).

### Requests

| `request.type` | Fields | Effect and reply |
|---|---|---|
| `new` | - | app-scope: another doc opens, a new empty workspace (one cue list, one stereo patch); `result { ok: { data: { type: "opened", doc } } }` (fixture `server/result_ok_opened.json`). Bind a connection to `doc` for its snapshot. Errors `command_refused` (8 docs open, or another document request is being handled) |
| `open` | `path`, `recovery?` | app-scope: another doc opens with a show file; `opened { doc }` as for `new`; errors `already_open` (that file is open: the app finds its doc by path in `workspaces`), `not_found` (no such file), `io` (unreadable, not a regular file, or the read stalled past the engine's timeout), `bad_show_file`, `command_refused`. When an autosave is newer than the show file and `recovery` is absent, nothing is opened and the `result` carries `recovery_offer` (below). | `open_recovery` | `workspace_id`, `path_hash?`, `modified_ms?` | app-scope: another doc opens with an autosave found by `scan_recovery`, as an **untitled, unsaved** workspace (`document.path` null, dirty); `opened { doc }`. `path_hash` / `modified_ms` pick one of several autosaves of the same workspace id (the listed entry's values); absent: the newest. Errors `not_found`, `io`, `bad_show_file`, `command_refused` |
| `scan_recovery` | - | app-scope: | list **every** recovery file in the engine's recovery folder, including the autosave of a never-saved workspace and files moved aside as stale (`stale: true`; they may hold the newest work): the launch offer after an unclean exit (NFR-05), and what to show when a show cannot be opened: `result { ok: { data: { type: "recovery_entries", entries: [{workspace_id, path_hash?, show_name?, modified_ms?, stale}] } } }`, newest first; `modified_ms` is milliseconds since the Unix epoch (wall clock, UTC); errors `command_refused` |
| `save` | - | save to the current path; `document` update, `result`; `no_workspace` if never saved (use `save_as`); `io` if the write failed |
| `save_as` | `path` | save to `path` and make it the workspace's path; `document` update, `result`; `io` if it could not be written; `already_open` (nothing written) if `path` is the show file of another open doc, one another doc's save is writing, or one an `open` is reading (also under another spelling of the same file: a symlink, `/var` for `/private/var`; the writer compares the files before it writes); `bad_request` (on decode) if `path` is not absolute |
| `relink` | `folder` (absolute, at most 4096 bytes; else `bad_request`) | relink the bound doc's missing media (WS-03, NFR-04, M1.17). The folder is walked on the document worker, on a copy of the workspace, never on the control thread, within core's scan limits (16 levels, 50 000 folders, 200 000 files, 20 s; symlinked folders are not entered). Missing files are matched by normalised file name; the matches are applied as **one undo step** (`model_changed`, then the result); nothing is guessed between duplicates (`ambiguous`). A match is skipped if the cue was edited to another file while the folder was walked. `result { ok: { revision, data: { type: "relink", relinked, ambiguous: [{cue, candidates}], unmatched, truncated, skipped } } }`: `relinked` is the number of cues changed, `unmatched` the cues still missing, `truncated` is true when a depth, folder, file or time limit ended the walk early (so `unmatched` may name a cue whose file lies beyond it: the UI says so), `skipped` the unreadable folders and non-UTF-8 names. Errors: `not_found` (no such folder), `bad_request` (not a folder), `io`, `command_refused` (another document request is being handled, or the walk did not return in time: a volume that stopped answering), `no_workspace` (the doc closed during the walk). The walk shares the document worker with `open` and `scan_recovery` (one at a time) |
| `list_devices` | - | app-scope: `result { ok: { data: { type: "devices", devices: [{name, output_channels}] } } }` |
| `preshow_check` | - | the pre-show check (SM-06, NFR-07): one report of every broken cue, missing or unsupported media file, patch with no device, network destination and system problem: `result { ok: { data: { type: "preshow_check", ok, summary, broken_cues, media, patches, network, system } } }`; shape below. Answered at once from the engine's current state |
| `log_tail` | `max?` | app-scope: the newest show-log entries the engine holds in memory (at most 1000), oldest first, for a log window opened after the fact (DX-02): `result { ok: { data: { type: "log_tail", entries: [entry], dropped, seq } } }`; `max` absent: all. `dropped` counts records the disk writer lost (they are still in `entries` while in memory); `seq` is the number of the newest record, to join the live `log_entry` pushes (M4.7c). Entry fields below |
| `set_output_overrides` | `network_disabled` | app-scope (works on the app connection with no doc open), PB-10: with `true`, Network cues still run, complete and continue but send nothing (the OSC/network output override). Engine-wide (every open workspace) and in memory only: not in a show file or any setting, and off again after the engine restarts, as QLab's Overrides. `result { ok }`. The state is `network_output_disabled` in `status` (below) |
| `set_show_mode` | `on` | the connection's workspace enters Show Mode (`true`) or goes back to Edit Mode (SM-01; M4.9). Kept by the engine per open workspace, in memory only (not in the show file; off when the workspace is opened again or the engine restarts), so a UI that restarts gets it back in `document.show_mode`. While any open workspace is in Show Mode, or any cue runs, the engine keeps the system, the display and the screen saver from idling (SM-07; macOS). `document` update when it changes, then `result { ok }`. Editing is not locked by the engine: the UI does that. Workspace-bound (`no_workspace` on the app connection) |
| `set_patch_mapping` | `patch`, `mapping?` | WS-07 (M4.4g): sets (`mapping: {device, channels}`) or clears (`mapping` null or absent) where the connection's workspace's `patch` plays **on this machine**; kept in the engine's machine settings under the workspace id and patch id, not in the show file. `device` must be a name `list_devices` gives; `channels` has one 0-based device channel per output of the patch, each below the device's `output_channels`. Refused with nothing changed: `not_found` (no such patch, or no such device), `bad_request` (wrong channel count, channel out of range). Answers `ok` with no data; the patches resolve again at once, so `runtime` problems and `preshow_check` `patches` show the new `resolution` (`unmapped`, `output_count_mismatch`, ...) and a running cue's slot follows in place. A clear is stored explicitly (the default mapping does not map the patch again). Workspace-bound |
| `snapshot` | - | `snapshot`, then `result`; on the app connection `workspaces`, then `result` |

Paths are never empty, and the paths of `open` and `save_as` must be absolute (`bad_request` on decode): a relative one would resolve against the engine's own working directory.

#### Opening and closing workspaces (M4.4, M4.15f)

- **Another doc opens; the others play on.** `new`, `open` and `open_recovery` add a doc (at most 8; QLab 5 opens a workspace beside the ones open). Nothing that is running stops. The `result` carries `opened { doc }` and nothing else: the requester gets no snapshot (on a bound connection it is another doc's connection), and nothing is broadcast as a snapshot. The app connections get a `workspaces` list with the new doc; a connection bound to it (`hello { workspace: doc }`) gets its snapshot and its `warnings` (load repairs, recovery notices) in the snapshot.
- **The engine never prompts.** Opening needs no `discard_changes` (nothing is replaced). `close` over unsaved edits is refused with `unsaved_changes` unless it says `discard_changes: true`; discarding also removes the autosave of the dropped edits (ordered after any autosave write in flight, so it is not offered again). The UI asks the operator, then repeats the `close` with the flag.
- **`recovery`** (`open` only): `restore` opens the autosave (dirty until saved, bound to the show path); `ignore` opens the show file as saved and leaves the autosave in place (it is offered again next time until a save, or the next autosave, replaces it). A `recovery_offer` result (`{ type: "recovery_offer", path, workspace_name, modified_ms }`; `path` is the `path` of the `open` it answers, `modified_ms` is milliseconds since the Unix epoch, wall clock UTC) means the autosave is newer than the show file and nothing was opened; the UI asks and repeats the `open` with a choice.
- **A show that cannot be opened** is `bad_show_file` (or `io` when the file cannot be read). The UI then sends `scan_recovery` and may offer `open_recovery` for an entry.
- **One show file, one doc.** `open` of a show file that is open answers `already_open` (paths compared as media paths are: case, Unicode form and `.`/`..` ignored; and, on the document worker before the read, by the file itself, so a symlinked folder or `/var` for `/private/var` is caught), and so does `open` of a file another doc's `save_as` is still writing. A `save_as` onto another doc's show file is `already_open` too (above). Two docs never own one file, so neither's save can overwrite the other's. A copy of an open show (another file with the same workspace id) opens with a fresh workspace id and dirty (docs/todo/open-qlab-questions.md row 10: whether QLab persists the new id).
- **Numbering is per doc.** Each doc's `revision` starts at 1 and `runtime_seq` at 0 when it opens; a connection only ever sees one doc's, so there is nothing to mix up. Closing a doc ends its connections.
- Only one document request that reads a file (`open`, `open_recovery`, `scan_recovery`) or builds a doc (`new`) is handled at a time, engine-wide (the file is read and the doc built off the control thread); another arriving meanwhile is refused with `command_refused`. A read that has not finished after 20 s (a stalled network volume) answers `io` and later requests are served normally.

Saving: `save` and `save_as` write on a separate thread. The `result` comes when the file is durably written; the new `document` (path, `dirty` false when no edit happened meanwhile) is broadcast before it. A failed write is `io`, the workspace stays dirty and the autosave keeps running. The engine autosaves a dirty workspace every `settings.autosave_interval` seconds to the recovery folder (docs/persistence.md); that is not visible on the protocol.

`recovery` is absent unless chosen and not written then; `new` is a bare object (`{"type":"new"}`; a `discard_changes` an older client sends is an unknown field, ignored). The Swift client (M5) must implement the `close` / `unsaved_changes` and recovery flows (docs/handoff/m5-protocol-requests.md).

### Progress

`progress` goes to the connections bound to the doc whose cues it reports (section 2), at most 30 Hz in sample time, and only while something in the doc counts: nothing is sent while every cue is idle or loaded, and no wake is added for it (it rides on the control loop's usual wakes).

- `items`: actions in progress. An audio cue's from its voice (`elapsed` its position in the file's action, offset included); a cue without a voice (Wait, Fade, Group, ...; M4.2e) from its run: `elapsed` since its action start (plus a load-to-time offset). `remaining` is null when there is no end (an infinite loop, a cue waiting for feedback, a group with a busy child). A broken run skips its action and has no item.
- `waits` (M4.2e; absent when empty, so a client that predates it reads none): `wait` is `pre_wait` or `post_wait` (an auto-continue's post-wait, counted from the action start, or a halted playlist's wait for its auto-follow); `remaining` is never null. A cue can be in both lists at once (an action with its post-wait). The countdowns keep their schedule for a cue that is broken or skipped (docs/cue-engine.md, rule 2).
- A paused cue's entries keep coming with the values it froze at (as for a paused voice). Stop, Reset and Panic end them with the run.
- Times are sanitised (section 1); the full rules are in docs/cue-engine.md, "Timer progress".

### Pre-show check (M4.8)

`result.ok.data` of `preshow_check` (`type: "preshow_check"`):

- `ok`: true when nothing is a problem: `summary.total` is 0 and no cause below is listed as a problem. Not problems: `not_checked` destinations, patches no cue uses, the `preload_over_budget` warning.
- `summary`: `broken_cues`; `media` (files missing or unsupported); `patches` (patches that cues use and that have no device; unused ones are not counted); `network` (destinations with status `missing` only); `network_unchecked`; `system` (entries that are problems, so not `preload_over_budget`); and `total` = `broken_cues + system`, the problem rows a list shows. Media, patches and destinations are the causes of broken cues and are not added again.
- `broken_cues`: `[{cue, list, number?, name, problems}]` in workspace order (lists in order, cues depth-first). `problems` are the same `problem` objects as in `runtime` and `snapshot`. A disarmed cue is listed only if it has problems of its own; a group is not listed for a broken child. `name` is the name the cue list shows.
- `media`: `[{path, status, reason?, cues}]` by path; `status` is `missing` or `unsupported` (`reason` is the probe's message); `cues` use the file.
- `patches`: output patches with no device to play on: `[{patch, name?, device?, mapped, resolution?, cues}]`, workspace order, then patches cues name that the workspace lacks (`name` and `resolution` absent). `resolution` is the `resolution` object of `device_unavailable` (`unmapped`, `device_missing`, `channels_missing`, `output_count_mismatch`); `mapped` says whether this machine has a mapping for the patch (WS-07); `device` is the mapped device when it is missing; `cues` are the audio cues on the patch (empty for a patch no cue uses: listed all the same, as it cannot play on this machine, but not counted and not a failure).
- `network`: destinations Network cues use: `[{patch, name?, host?, port?, protocol?, status, cues}]`, workspace order, then missing ones by id. `status` is `missing` (the workspace has no such destination: a problem) or `not_checked` (it exists; **reachability is not probed in v0.0.1**, M4.6: this is neither a problem nor a pass, and does not make `ok` false).
- `system`: the `warnings` list (device lost or stalled, damaged media, preload problems, cues whose slices cannot play, ...), sorted by `code`, cue, message. Any entry makes `ok` false except `preload_over_budget` (the file is streamed and plays; listed, not counted).

Media status is what the media probes and the media watch last reported (docs/control.md, Pre-show check); the request does no file access.

### Show log entries and status (M4.7)

A show-log entry (`LogEntry`; in `log_tail` and `log_entry`): `time_ms` (wall clock, milliseconds since the Unix epoch, UTC), `show_time?` (seconds of audio rendered; absent for engine records that have none), `level`, `kind`, `message` (English, for people), `cue?`, `source?`. `kind` is `go` (a GO, with the cue it starts), `transport` (any other transport action, with the cue it names), `trigger` (a transport action arrived: `source` is `ui` or `osc <ip>`; rate-limited per source, with an `N more input(s) not logged` record), `cue_start`, `cue_stop`, `cue_fail` (a cue broke at run time; the message carries the reason), `device`, `document` (opened, saved, save failed) and `engine` (everything else: warnings, errors, health). The same records, one JSON object per line, are written to the log file ([logging.md](logging.md)); a client may parse them with the same types.

`log_entry` (M4.7c) pushes each record as it is made: `seq` numbers every record the engine makes, from 1, pushed or not, and the `log_tail` result carries `seq` too, the number of the newest record when it was answered (0: none yet). A live view reads `log_tail` once, then appends each `log_entry` whose `seq` is above the last it has; an entry at or below it is already in the view; a jump (`seq` more than one above the last) means records were not pushed, and the view reads `log_tail` again. Pushes are lossy like `meters` (dropped while the client's queue is half full, never marking it lagged) and rate-limited on the same 10 s wall-clock window as trigger records: at most 200 per window; the newest record the engine could not hand over (over the budget, or its outbound queue half full) is pushed as soon as the budget and the queue allow (held back by the budget: when the window ends). A push the network hub drops for one slow client is not offered again: that client learns of the gap from `status.log_seq` (about once a second), which is above the last `seq` it received, and reads `log_tail` then. The show log is the engine's, not a workspace's: `log_entry` is not tagged with a doc. A `log` notice is also a record, so a client that shows both sees it twice; a log window should use `log_entry` and `log_tail` only.

`status`: `cpu_percent` (the engine process's CPU since the previous status, in percent of one core; `null` without a figure), `engine_load` (audio callback time over block time, worst case since the previous status, as a fraction: 1.0 means a callback took as long as its block lasts, above 1 is a dropout; `null` when no callback ran since the previous status, e.g. the device is lost, and for offline rendering), `xruns` (since start), `disk {streams, underrun_frames, healthy}` (`healthy`: no underrun for ten seconds), `device {name?, state, sample_rate, block_frames?, channels, latency_ms?}` (`state`: `ok`, `lost` while the engine tries to reopen it, `failed` when only a restart helps, `absent` for offline rendering) `log_dropped` (show-log records the disk writer lost), `log_seq` (the `seq` of the newest show-log record, 0: none yet; absent from an older engine: read as 0) and `network_output_disabled` (PB-10, M4.6: the network output override is on, so Network cues send nothing; the UI must show this plainly while it is true; absent: false). A client that connects gets its first `status` with the next periodic one (within a second). Non-finite numbers are sent as 0.

These are additions: `PROTOCOL_VERSION` stays 1 (no released client). The Swift client (M5) must decode `status`, `log_entry` and the `log_tail` result (`log_tail.seq` and `status.log_seq` are new in M4.7c; a message without them reads as 0).

M2.28 additions (also optional for the client, `PROTOCOL_VERSION` stays 1): a Devamp cue's kind carries `devamp_mode` (`current_slice` | `looping_cue`, show file version 3; set with the `kind` cue property, fixture `client/command_set_devamp_kind.json`); `preview_ignored` has the reasons `disarmed` and `nothing_to_preview`; `previewing` and `preview` changes name groups too (a group's preview is its audio cues' previews).

### Snapshot

`revision` (the model revision it is at), `runtime_seq` (the last `runtime` `seq` folded in), `document`, `workspace` (the show-file workspace object, [file-format.md](file-format.md) section 4), `cue_states` (cues not idle: `{cue, state, reason?}`), `problems` (`{cue, problems}` for cues with static problems), `group_warnings` (group ids with a broken descendant; such a group with no run of its own is in `cue_states` as `broken`, with no `reason` and no `problems` entry), `playheads` (`{list, cue}`), `previewing` (cue ids; a group being previewed is listed with its audio cues), `warnings`.

### Model changes

`model_changed.revision` rises by exactly 1 per message, starting from `snapshot.revision`; any other step is a gap. Apply `deletes` first, then `upserts` in order. A `delete` of an id the client does not hold is ignored; an `upsert` of a cue the client already holds replaces it wherever it is.

| Upsert `type` | Fields | Meaning |
|---|---|---|
| `cue` | `list`, `parent` (null: top level), `index`, `cue` | put the cue (new, changed or moved) at `index` among the cues of `parent`. A group's upsert carries its whole subtree and replaces it; its children are not upserted separately |
| `cue_list` | `id`, `name`, `index` | name and place among the lists; its cues come as `cue` upserts |
| `patch`, `network_patch` | `index`, `patch` | place among the patches |
| `settings` | `name`, `settings` | the workspace name (set by the undoable `rename_workspace` command, fixture `client/command_rename_workspace.json`; names and hosts are bounded, docs/commands.md "Names") and settings; since show file v4 the settings carry `osc_access` (`{no_passcode: {view, edit, control}, passcodes: [{passcode, rights: {view, edit, control}}]}`) where they carried `osc_passcode` (M4.5c). The passcodes are visible to every client that holds a token, as the old one was. New commands `add_osc_passcode`, `remove_osc_passcode`, `set_osc_rights` (docs/commands.md); the `osc_passcode` setting command is gone. Swift treats settings and commands as opaque JSON, so no Swift type changes; M5.13a builds the UI |

Deletes: `cue {id}` (with its children), `cue_list {id}`, `patch {id}`, `network_patch {id}`. Deleting a cue list deletes its cues with it; the engine only removes empty lists, so the cues were deleted or moved out in the same or an earlier message.

Edits to settings, patches and cue lists: one `settings` upsert (name and all settings), a `patch` / `network_patch` / `cue_list` upsert per item added or changed and a delete per item removed, and for a move (or an undo of one), or when two or more items of a collection changed in one message, an upsert of every item in that collection at its final index, ascending. A `cue_list` upsert for a list the client holds keeps its cues. They come before the cue upserts of the same message.

What the engine sends for a cue edit: a `delete` for each cue removed or moved, then an `upsert` for each cue added, moved or changed (its final place; in tree order, parents first, ascending index within a parent), so a move is a delete and an upsert in the same message and several moves in one undo step cannot collide. A cue inside a group that is also upserted is not sent separately. Only the cues the edit names are sent (an undo or redo names what the step changed), and exactly one `model_changed` goes out per edit, undo, redo or runtime model change (`SetArmed`); a client that sees a revision gap requests `snapshot`. Edits to a group itself send its whole subtree. See [control.md](control.md) "Model changes".

The `model_changed` for revision N is always sent before the `result` that reports `ok.revision = N`, so a client that has seen the result has the change.

### Runtime changes

`runtime.seq` rises by 1 per message (gap: request a snapshot). `changes[].type`:

| Type | Fields | Source |
|---|---|---|
| `cue_state` | `cue`, `state`, `reason?` | `Action::StateChanged`. `state`: `idle`, `loaded`, `pre_waiting`, `running`, `paused`, `post_waiting`, `fading`, `stopping`, `broken`. `reason` (`voice_rejected`, `stream_failed`, `device_lost`) is set when it broke while running. A `broken` state with no `reason` is a cue with static problems (listed in `problems`) or, with neither, a group with a broken descendant (`group_warning: true` is the reason; it has no problems of its own and still starts) |
| `problems` | `cue`, `problems` | `ProblemsChanged`: the full list of static problems, empty when none |
| `group_warning` | `group`, `warning` | `GroupWarningChanged`: the group has a descendant shown with problems, which is why it shows as broken (its `cue_state` is `broken` while it has no run) |
| `playhead` | `list`, `cue` | `PlayheadChanged` |
| `preview` | `cue`, `active` | `PreviewChanged` |
| `warning` | `warning` | `Warning`, and `GoIgnored` as a `go_ignored` warning |

`RuntimeChange::from_action(action, &engine)` does this mapping (the mixer-side actions map to nothing); it reads the engine after `handle` to fill `reason` for a `broken` state, which is absent for a cue broken only by static problems. Problems: `no_target`, `target_missing {target}`, `target_self`, `target_wrong_kind {target}`, `nothing_to_fade` (M2.26: a Fade that sets no level), `no_media`, `media_missing {media}`, `media_unsupported {media, reason}`, `patch_missing {patch}`, `device_unavailable {patch, resolution}`, `network_patch_missing {patch}`, `network_host_invalid {patch, reason}` (an unusable host or port), `network_host_unresolved {patch, reason}` (a host name that does not resolve), `network_message_invalid {reason}` (a malformed or oversized OSC message; `reason` is English, for the log), `started_broken`; `resolution` is `mapped`, `unmapped`, `device_missing`, `channels_missing`, `output_count_mismatch`. Warnings mirror the engine's (`unknown_list`, `unknown_cue`, `not_in_list`, `number_not_found`, `cue_broken`, `trigger_ignored`, `load_ignored`, `late_start {late_ms}`, `chain_limit`, `cue_removed`, `no_target`, `target_missing`, `target_wrong_kind`, `target_not_running`, `preview_ignored {reason}` (`not_audio`, `already_previewing`, `disarmed`, `nothing_to_preview`), `preview_failed`, `devamp_ignored`) plus `go_ignored {list, reason}` and `notice {code, message, cue?}` for what only the binary knows. The UI localises from the variant or `code`; `message` is English.
