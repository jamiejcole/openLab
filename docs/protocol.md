# openLab UI protocol (engine <-> UI)

Types: `openlab-core::protocol` (`engine/crates/core/src/protocol/`) are the source of truth for fields; this page states behaviour, ordering and limits the types cannot. One golden JSON file per message variant is in `engine/fixtures/protocol/{client,server}/`; the Swift tests (`ProtocolFixtureTests`) decode every one. Model edits are core's `Command` (skill `edit-commands`); cue states and warnings are the cue engine's (skill `cue-engine`). Server mechanics (limits, ordering per connection, slow clients): skill `engine-ws-server`.

## 1. Conventions

- **Transport**: WebSocket on `127.0.0.1`, random port; one JSON object per UTF-8 text frame.
- **Auth**: the engine writes `{port, token, pid}` to `<app-support>/openLab/engine.json` (mode 0600). The client's first frame must be `hello` with the token.
- **Envelope**: `{"type": "<snake_case name>", ...fields}`. Nested variants (transport actions, requests, commands, runtime changes, upserts, problems, warnings, result data) are internally tagged with `"type"` too.
- **Units**: times are **seconds** (f64), never samples. Model levels are dB. Meter peaks are **linear amplitude** (f32; 1.0 full scale, above is a clip). Ids are UUID strings. `RequestId` is a client-chosen u64, unique per connection; `u64::MAX` is reserved for the server's own requests (`bad_request` if a client uses it). `revision` and `seq` are u64.
- **Numbers**: JSON has no NaN or infinity.
  - Client input: the codec refuses negative or out-of-range values where meaningless (a load time, a seek position, a fade duration) and empty paths. `decode_client` returns `ProtocolError` and never panics, whatever the input.
  - Numeric payloads inside a `command` are not checked by the codec: `Workspace::apply` validates every time and level and refuses with `command_refused`.
  - Engine output: the encoder sanitises `progress` and `meters`: a negative, NaN or infinite time or peak is sent as 0 (a loop-end overrun must not cost the UI a tick). Other non-finite numbers in `status` are also sent as 0.
- **Frame limits** are checked on byte length before parsing (`MAX_HELLO_FRAME_BYTES`, decoded before the token is checked; `MAX_CLIENT_FRAME_BYTES`; `MAX_SERVER_FRAME_BYTES`; all in `protocol/mod.rs`). Over: `ProtocolError::TooLarge`.
- **Errors**: a missing `type` is `MissingType`; a `type` that is not a message of the direction is `UnknownType`; everything else wrong (bad JSON, wrong field types, an unknown variant inside a known message) is `Malformed`. All are rejections: the engine answers `bad_request` or `unknown_message`, as a `result` under the frame's id when it can be read (section 3), else as `error`. After `welcome` the connection stays open, except for a frame over the size limit, which ends it. A bad `hello` (malformed, or over `MAX_HELLO_FRAME_BYTES`) answers `bad_request` and ends the connection.
- **Compatibility**: unknown **fields** are ignored, so a newer peer may add optional fields without a version bump; receivers treat absent optional fields as documented. Unknown message **types** and unknown nested variants are errors. Removing, renaming or re-typing a field, or changing its meaning, bumps `PROTOCOL_VERSION` (now **4**: section 2). A client ignores a runtime change `type` it does not know. Any change updates the fixtures, the Swift `Codable` types and this page in the same commit.
- **Fixtures**: see skill `wire-protocol`. The test compares byte for byte and fails if a variant has no sample.

## 2. Connection

The engine holds several open workspaces ("docs"; limit in REQUIREMENTS §21). A doc is named by its `doc` id (`DocId`, u64), handed out in open order from 0 and never reused while the engine runs; a new engine run restarts from 0 with a new token. A connection is **bound** to one doc or is the **app connection**.

1. The client sends `hello { protocol_version, token, client_name, workspace?, pid? }`. `workspace` is a `doc` id and binds the connection; without it the connection is an app connection. `pid` is the client's process id: when an app connection ends without `goodbye`, the engine does not relaunch the app while that process runs, and waits for it to reconnect.
2. The engine answers `welcome`, or sends `error` and closes: `protocol_version_mismatch` (`error.protocol_version` says what the engine speaks), `bad_token` (wrong token, or any other message came first), `no_workspace` (`workspace` names no open doc; the client must not retry). `hello` decodes for any `protocol_version`, so another version can be told why.
   - Bound: `welcome { protocol_version, doc, snapshot }`. Everything the connection sends acts on that doc, and it receives only that doc's broadcasts plus the engine's own `log`, `log_entry`, `status`. `revision` and `runtime_seq` count per doc (a new doc's snapshot is revision 1).
   - App connection: `welcome { protocol_version, workspaces }`. A `workspaces` message follows every change to the list (a doc opened or closed, a name, path or unsaved state changed). It receives no doc's broadcasts. Doc-scoped messages on it (`command`, `undo`, `redo`, `transport` other than `panic`, `save`, `save_as`, `relink`, `preshow_check`, `close` without `doc`) answer `no_workspace`. Its `request: snapshot` answers a `workspaces` message, then `result`.
3. After `welcome` the client may send anything below. Every `command`, `transport`, `undo`, `redo`, `request`, `close`, `panic` and `hotkey` gets exactly one `result` with its `id`. A frame the engine cannot read gets `error` (`bad_request` or `unknown_message`). If the frame is a JSON object with a string `type` and a `u64` `id` (other than the reserved one), the engine answers it as a refused request: one `result` with that `id` and `error { code: bad_request | unknown_message }`, so the waiting call fails. Otherwise (no readable id) it sends the id-less `error`, which belongs to no request: a client publishes it and fails no request because of it (it cannot tell which one the engine meant); its requests end by their own deadline or when the connection drops. Both kinds count toward `MAX_BAD_FRAMES`.
4. **App-scope messages** work on any connection and act on the engine or every doc: `new`, `open`, `open_recovery`, `scan_recovery`, `discard_recovery`, `list_devices`, `set_output_device`, `set_buffer_size`, `log_tail`, `set_output_overrides`, `close { doc }`, `panic`, `hotkey`, `set_stand_back`.
   - `panic` (Esc) panics every doc; twice within the fade is a hard stop. On the app connection `transport { action: panic }` is this app-scope panic.
   - `hotkey`: see section 3.
   - Pause All, GO and other transport actions act on the bound doc only (the front window's: the UI's notion; the engine has no front doc).
5. **Closing a doc**: see "Opening and closing workspaces". `goodbye { shutdown }` ends the session; `shutdown: true` also asks the engine to quit. The engine closes the connection once it has read the goodbye; the client waits for that close (bounded) before closing its own side. A socket closed while engine messages are still arriving is reset, and the reset can discard the goodbye before the engine reads it: the engine then treats the end as a crash and plays on.

A client that sees a gap in `revision` or `seq` (section 4) sends `request: snapshot` and replaces its state.

`PROTOCOL_VERSION` is **4**. An engine refuses any other version at `hello`.

## 3. Client -> engine

Fields: `ClientMessage` in `protocol/client.rs`. Behaviour notes:

- **`command`** (`id`, `command`, `coalesce?`): `command` is core's `Command`, one undo step.
  - Reply order: `model_changed`, then `result { ok: { revision } }`. A refused command changes nothing and replies `command_refused`.
  - Exception: if a transaction's rollback itself fails (`RollbackFailed`, only a wrong inverse can cause it) the workspace is partly changed. The engine logs an error, bumps the revision (dirty), clears undo and redo, sends `document` and a whole `snapshot` instead of `model_changed`, then replies `command_refused` saying the workspace is partly changed.
  - A command that changes nothing replies `ok` with the current revision, sends no `model_changed`, and is no undo step.
  - `remove_stage` (alone or in a transaction), and an `undo` or `redo` whose step removes a stage, is refused with `command_refused` while a Video cue on that stage is loaded, pre-waiting, playing, paused or stopping, or a cue's picture is still up on it; the message is `stage "<name>" cannot be removed while cue "<number or name>" uses it` (the app reads the cue from it). The step stays on the undo or redo stack.
  - A Video cue (`kind.type` `video`: `media`, `stage`, `duration`, `docs/file-format.md` §5.3) is edited by `media` (as an Audio cue's), `stage { value }` (a stage id or `null` for "none"; a stage the workspace lacks is accepted and the cue shows `stage_missing`) and `kind_fields` with `duration` (a still's seconds, 0 to 24 h, or `null`: until stopped) or its geometry fields (`fill_stage`, `fill_style`, `translation`, `scale`, `scale_locked`, `rotation`, `crop`, `anchor`, `opacity`, `layer`, `smooth`; ranges in `docs/file-format.md` §5 `video`). `translation`, `scale` and `anchor` (`{x, y}`) and `crop` (`{top, bottom, left, right}`) may give only the parts that change; the others keep their values, and an unknown part is refused. Out of range or of the wrong type is `command_refused`.
  - A cue's triggers are edited whole by `set_cue_property` `triggers { value }` (`hotkey`, `hotkey_enabled`, `wall_clock`, docs/file-format.md §5.1 `triggers`). A `wall_clock` time past 23:59:59 or with no day is refused (`command_refused`); a `wall_clock` left out is a new cue's (off, 00:00:00, every day), and the engine leaves it out of a cue it sends while it is that. Each cue whose wall-clock time the computer's local clock reaches starts as a `start` transport would (no playhead move), with a `trigger` log record whose `source` is `wall clock`. A cue whose time the clock passed over (the computer asleep, the engine held up, the clock set, a time daylight saving skipped) is not started late: a `notice` warning with code `wall_clock_missed` and the cue goes to its workspace's clients; while the computer's local time cannot be read no trigger fires and a workspace with one on gets a `wall_clock_unknown` notice.
  - A Fade cue's picture values for a Video target (`kind.geometry`, docs/file-format.md §5 `fade`) are edited by `kind_fields` with `geometry`, which may give only the parts that change (a tick, a value, one part of `translation` or `scale`); an unknown part is refused. Out of range or of the wrong type is `command_refused`.
  - `coalesce` is at most `MAX_COALESCE_KEY` bytes (longer: `bad_request`, nothing applied). Consecutive commands with the same key are one undo step, each still sent as its own `model_changed`.
- **`undo`, `redo`**: `ok.revision` after; `ok` without a revision when there was nothing to undo. A step that removes an active or previewed cue stops the cue as a delete does, with a `cue_removed` warning.
- **`hotkey`** (`id`, `key` 1 to 64 bytes, `modifiers?`, `phase?` `down` default or `up`): app-scope. `down` starts every cue of every doc whose `triggers.hotkey` is exactly this key and these modifiers; `up` sends each of those cues its release (`trigger_released`). A doc whose workspace key map (`settings.hotkeys`, the current edited map) uses the key starts none: the workspace action wins, and that action is the front window's, sent by the UI as a `transport`. The cue-editing keys of the map (`edit_number` ... `toggle_flag`) count too: the engine starts no cue on them and does nothing else with them; the app edits the selected cues. A key outside the bounds is `bad_request`.

### Transport actions

Each action becomes one cue-engine input (mapping in `control/transport.rs`; semantics in skill `cue-engine`). Notes the types do not carry:

- `go_from { list, cue }`: the playhead moves to `cue`, then GO, in one step; nothing starts if `cue` is not a playhead position of `list` (`not_in_list` warning).
- `stop_all` and `hard_stop_all` both map to `StopAll`: every cue and preview stops at once, no fade, nothing pending fires, no panic window. They stay distinct so a client can say which it means (OSC `/stop`, `/hardStop`).
- `stop { cue, fade_out? }` fades out over `fade_out` (`{duration, curve}`) when given; `hard_stop { cue }` never fades.
- `panic_cue { cue }`: the cue's own panic; it and what is in it fade out over `panic_duration` (0: at once). Other cues and the workspace panic are untouched.
- `reset_all`: every cue and preview stops at once (a panic fade included), every cue is reset (run-time break cleared, loaded cue unloaded), random groups start a fresh cycle, each list's playhead returns to its first cue: the doc as just opened.
- `load { cue, at }`: loads the cue (a group: its children) to `at` seconds into its pre-wait and action together, and carries the time on through its sequence: each cue its auto-continue or auto-follow chain would start is loaded at the time left once it would have started (one the time does not reach is loaded at its top, and kept as it is if it already stands there; a disarmed or broken one is not loaded but the time carries past it; a later cue that is already running ends what the load reaches). A negative `at` counts back from the end of the whole sequence (to the start when that end is unknown or `at` goes past the start; `sequence_span` gives it); not finite is `bad_request`. OSC's `/load` still takes 0 or more. A Load cue loads its target the same way.
- `set_playhead { list, cue }`: null cue means past the end.
- `preview { cue }`: an audio cue, or every armed audio cue in a group. For a Network cue it sends its message once now (no `preview` change follows). `stop_preview { cue? }`: absent or null stops every preview.
- `seek { cue, position }`: an Audio or Video cue's playback moves to `position` seconds into its media file (a click in its timeline); negative or not finite is `bad_request`. The engine keeps the point inside the trims (before the in point: the in point; at or past the out point: the end of a pass of the last slice, so its next pass follows if it has one, a slice looping until devamped looping on from its start, and otherwise nothing is left, so a playing cue's action ends there) and plans the slices from it, so the rest of a looping slice still loops and a point past a loop is reached. A point inside a skipped slice (play count `"skip"`) moves to the start of the next slice that plays, or, with none after it, to the end of the last slice that does (handled as a point at the out point is). Idle or loaded: loaded there (`loaded`), and a start plays from there with no pre-wait. Pre-waiting: the action starts there now. Playing: the sound jumps there and plays on: no state change, no pre-wait, the post-wait and its continue keep their time, an auto-follow fires at the moved sound's end; the voice it leaves crossfades into the new point (10 ms) once the new point's stream is ready (at most 0.25 s later), and progress shows the new point at once. Paused: moved, still paused; a resume plays from there. A preview of the cue jumps too. A Video cue's seek is the same in every state (a preview excepted: Video cues have none): the engine places `position` in the cue's plan at its first play, so a point before the start trim goes to the trim, one inside a repeated slice to its first play, one in a gap to the next slice, at or past the end trim to the end of the last slice's first play as for an Audio cue (its other plays follow; played once, the action ends there), and past a loop that never ends to the end of one play of it (the loop plays on from its start); its sound, if it has any, goes on from the same point of the same plan as its picture (a cue holding its last frame plays both from the point again), and a late start before the seek is not counted against the point; a still, or a movie not probed yet, is ignored. A stopping cue ignores it without a warning (its stop ends it where it is); a post-waiting cue whose sound has ended and a cue that is not Audio or Video get a `load_ignored` warning; a broken cue (or one its lost device left paused while the device is away) gets `cue_broken` and nothing loads or sounds. Bursts are cheap: each cue prepares at most one stream per 50 ms and has at most two voices sounding, the rest of a burst replacing the seek still waiting.
- `batch { actions }`: 1 to `MAX_BATCH_ACTIONS` per-cue actions (`start`, `stop`, `hard_stop`, `panic_cue`, `pause`, `resume`, `load`, `seek`, `reset`, `preview`, `stop_preview`), no cue twice.
  - All items run in order at one scheduling time before anything else is handled, so cues started together start on the same sample and cues stopped together end on the same sample (NFR-21).
  - An empty or longer list, another action (a nested `batch` included) or a repeated cue makes the frame `bad_request`, nothing done. A cue not in the workspace gets `unknown_cue` and the other items still run. One `result` for the batch.
  - `panic_cue` items are one press: a cue fading only because an earlier item panicked its group or children is not pressed again.

The `result` of a transport action means accepted and handed to the cue engine. What happened shows in `runtime` (states, playhead, warnings such as `go_ignored`, `trigger_ignored`).

### Requests

Fields and reply shapes: `Request` and `ResultData` (`client.rs`, `server.rs`). Behaviour:

- **`new`, `open`, `open_recovery`, `scan_recovery`, `discard_recovery`**: "Opening and closing workspaces".
- **`save`**: `document` update, then `result`. `no_workspace` if never saved (use `save_as`); `io` if the write failed.
- **`save_as { path }`** (absolute): saves and makes `path` the doc's path. `io` on write failure. `already_open` (nothing written) if `path` is another open doc's show file or one another save or `open` is touching, including under another spelling (symlink, `/var` for `/private/var`; the writer compares by file).
- **`relink { folder }`** (absolute, at most `MAX_FOLDER_BYTES`): relinks the bound doc's missing media (WS-03, NFR-04).
  - Walked on its own thread, on a copy of the workspace, never on the control thread, within core's scan limits; symlinked folders are not entered. Missing files match by normalised file name; matches apply as **one undo step**; duplicates are `ambiguous`, never guessed; a match is skipped if the cue was edited to another file meanwhile.
  - `truncated` is true when a limit ended the walk early, so `unmatched` may name a cue whose file lies beyond it (the UI says so).
  - `preview: true` walks the same way, with the same limits and errors, and changes nothing: no edit, no `model_changed`, no `revision`. The result lists each single match in `matches` (the file in the form the show file would store it), beside `ambiguous` and `unmatched`; a match whose cue was edited during the walk is left out. The client applies the ones the operator accepts as one ordinary `command` (a `transaction` of media edits), which the engine checks and stores like any file edit: one undo step, in the same path form an applied `relink` stores.
  - `matches` and `ambiguous` together list at most `MAX_RELINK_LIST_BYTES` of paths, whole cues only; `capped` is true when cues were left out of both lists (and so are in none). They are still missing, so the next search finds them.
  - Errors: `not_found`, `bad_request` (not a folder), `io` (also a walk that did not return in time), `command_refused` (another relink is walking), `no_workspace` (doc closed meanwhile). `open` and `scan_recovery` are not held up by it.
- **`copy_media`** (WS-04, QLab 5's on-demand copy): copies every file the bound doc's Audio and Video cues target that is not inside its show folder into the folder's `audio` or `video` folder, a file the folder already holds with the same content (size, then every byte) used instead of a new copy, a taken name numbered (`kick 2.wav`), each copy written under a temp name and renamed into place only when whole. Answers `ok` as it starts; `command_refused` for a show never saved, in Show Mode, or while this doc's `copy_media` runs or waits. The files are copied on a thread of their own, one copy at a time engine-wide (copies made as files are added, by the workspace's `copy_media_on_add`, queue the same way), paced so streams keep their disk; `media_copy_progress` reports it and `media_copied` ends it. Only then are the cues whose file is in place pointed at their copies, a few dozen a control wake so no wake is long, all one undo step (an undo or edit in those wakes splits it); `media_copied` follows the last `model_changed`; a cue whose file was changed meanwhile keeps the change; a cue playing plays its old file to its end. Files that fail (missing, unreadable, a full disk, a read-only folder, a volume not responding) leave their cues as they were. Show Mode, or closing the doc, stops a copy whose files are still being copied: nothing is retargeted (one already pointing cues at its copies finishes, unless the doc closed). A copy whose thread makes no progress for the document timeout (20 s) is given up: reported stopped, nothing retargeted.
- **`list_devices`**: each device's `name`, `output_channels`, `is_default` and `buffer_frames` (what it is asked for on this machine); `state` when the engine has opened an output on it since start, for the primary or for a patch (as in `status.outputs`, `closed` included; absent: never), and `primary` on the engine's primary device. `selected` is the device chosen with `set_output_device` (absent: none). A device that left the list (lost) is only in `status.outputs`.
- **`set_buffer_size { device, frames }`** (AUD-21): the frames per callback asked of `device` on this machine, 16 to 1024 (512 when none is set); kept in machine settings. A device the engine plays on reopens at once at that size, its cues playing on after the gap; the other devices are untouched. A size the device cannot do falls back to the nearest it can, with a `warn` log; a reopen that fails is a device loss. `bad_request` (out of range), `not_found` (not a `list_devices` name) or `io` change nothing.
- **`backup_keep`** and **`set_backup_keep { count }`** (app-scope): answer `backup_keep { count }`, how many backups of each workspace this machine keeps (0: none are made). `set_backup_keep` (0 to 1000) is kept in the machine settings and used by the next save; above the maximum is `bad_request`, settings that cannot be kept `io`; nothing changes on a refusal.
- **`set_stand_back { on }`** (app-scope): while `on`, the stage window on the display with the menu bar stands back under every app's windows (over the desktop), so a question the app asks there (an alert, a sheet, a panel) can be seen; nothing it draws changes, no cue stops or fades. The app sets it while such a question is up. It is told to every stage host started while on, and reset when the last app connection ends. Answers `ok`.
- **`osc_state`** and **`set_osc_port { port }`** (app-scope): answer `osc { port, open, error? }`: the port OSC listens on (UDP and TCP; the one in use while `open`, else the one asked for), whether its sockets are open, and why the last start or change failed. `set_osc_port` (1 to 65535, kept in the machine settings for later starts) opens the new port first and closes the old one only then: a port that cannot be opened (in use) is `io` with the reason, the old port goes on listening and `osc_state` carries `error`; port 0 is `bad_request`; settings that cannot be kept are `io` and nothing changes. `unsupported` when OSC is not running in this engine.
- **`set_output_device { device? }`**: the primary device (whose clock is the show's) the engine opens at its **next start** (it never switches live; the app restarts it). Must be a `list_devices` name; null means system default. Kept in machine settings. `not_found` or `io` change nothing. At start an unlisted chosen device falls back to the default with a `warn` log, so the show still starts.
- **`preshow_check`**: "Pre-show check"; answered at once from current state, no file access.
- **`log_tail { max? }`**: the newest in-memory show-log entries, oldest first, with `dropped` and `seq`.
- **`set_output_overrides { network_disabled }`** (works with no doc open): with `true`, Network cues still run, complete and continue but send nothing. Engine-wide, in memory only, off after an engine restart; shown as `network_output_disabled` in `status`.
- **`set_show_mode { on }`** (SM-01): kept per open doc and saved with it (`show_mode`, file-format §4.1); a file without one starts in Edit Mode. Changing it does not mark the doc unsaved. It survives a UI restart (`document.show_mode`); a `snapshot`'s `workspace` never carries it. While any doc is in Show Mode or any cue runs, the engine prevents idle sleep (SM-07). The UI, not the engine, locks editing. `no_workspace` on the app connection.
- **`list_patch_mappings`** (WS-07): where each of the doc's patches plays on this machine, workspace order; `mapping` (as `set_patch_mapping` takes it, `system` included) absent for a patch never mapped or cleared. `resolution` is where it resolves now: the device and channels it plays on, or why not (`unmapped`, also while it waits for a free mixer slot; `device_missing` while its device is absent, away or not open yet, with `reason` when the device is listed but cannot be used: it cannot run at the clock device's rate, its first open failed, or too many devices are open; `channels_missing`; `output_count_mismatch`).
- **`set_patch_mapping { patch, mapping? }`**: sets (`{device, channels, system?}`) or clears (null or absent) where the doc's `patch` plays **on this machine**; kept in machine settings under workspace id and patch id, not in the show file.
  - `device` must be a name `list_devices` gives; `channels` has a 0-based device channel for each of the patch's first outputs (1 to its count; later outputs have none of their own), each below `output_channels`. Refused with nothing changed: `not_found` (patch or device), `bad_request` (count, range). Patches resolve again at once, so `runtime` problems and `preshow_check` show the new `resolution`. A device the engine does not play on yet opens for the patch (AUD-02), which is `device_missing` until it plays.
  - `system: true` (absent: false) puts the patch on the **system output**: the device `list_devices` marks `is_default` at any moment, followed when the operating system's default output changes; `device` is then `""`. Its channels are checked against the default device; `not_found` when no device is the default, `bad_request` with a `device` name. Its `resolution` names the device it plays on now (`device_missing` with device `system output` while there is none). A patch naming a device never follows the default.
  - A cue playing through the patch follows a new device at once: the sound moves there in step (a crossfade about 0.1 s later), paused, fading and looping cues included; one whose new device is not connected or cannot be used stops as on a lost device (`cue_state` `paused`, reason `device_lost`) with a `device_lost` notice naming that device. A new mapping on the same device moves it in place.
  - A clear pauses the cues playing through the patch; a later mapping does not resume them. A clear is stored explicitly.
- **`list_displays`** (VID-01, app-scope): the displays the stage host lists (`displays: [{id, name, width, height, fps}]`, ids stable across restarts, sizes in pixels, `fps` the display's fastest refresh rate in frames a second, 0 when unknown, at most 1000) and `video` (false: this machine's openLab has no video output; absent: the stage host has not started). The stage host starts with the engine; until it has listed them (a moment after start) the list is empty, so ask again. An engine without a stage host (none installed beside it) answers an empty list with no `video`.
- **`list_stage_mappings`** (VID-01): each of the doc's stages, workspace order: `mapping` (the display chosen on this machine: `{display, name, width, height}` as it was when chosen; absent: none) and `state` (where it is now, the stage host's `stage_status` state, section 5; absent until the stage host has said). A stage with no display or a missing one is not an error: its state says so and the show log warns. `panicked: true` (absent: false) marks a stage keeping black whose black is down: a panic took it down (QLab 5 manual p. 227), or no picture has played on it since its workspace opened; it is hidden between cues until a cue plays on it, and the engine tells the stage host it does not keep black until then. `monitor: true` (absent: false): the stage's monitor window is open (`set_stage_monitor`).
- **`set_stage_mapping { stage, display? }`** (VID-01): shows the doc's `stage` on `display` (an id `list_displays` gives) **on this machine**, or on none (null or absent); kept in machine settings under workspace id and stage id, not in the show file, and handed to the stage host at once. Refused with nothing changed: `not_found` (stage or display), `bad_request` (a display id empty, over 512 bytes or with control characters), `io` (settings cannot be saved).
- **`set_stage_monitor { stage, open }`** (VID-01): opens or closes the doc's `stage`'s monitor window, a live copy of the stage in a resizable window of the stage host's own, the stage fitted with black bars where the shapes differ, drawn whether or not the stage is shown on a display. Opening one already open brings it to the front. The engine keeps which are open (not in the show file or the settings) and reports it as `monitor` in `list_stage_mappings` and `video_outputs`; a monitor closes when the operator closes its window, its stage is removed, its workspace closes, or the last app connection (bound to no workspace) ends, by a quit or a crash. Show Mode leaves monitors as they are. Opening or closing one never touches what the stage's display shows. Refused with nothing changed: `not_found` (stage).
- **`snapshot`**: a `snapshot` (on the app connection `workspaces`), then `result`.
- **`sequence_span { cue }`**: how long the sequence that starts at `cue` lasts, seconds (`sequence_span { span? }`): pre-waits and actions through its auto-continue and auto-follow chain as a run times them, what a negative `load` time counts back from. `span` is absent when the end is unknown (audio not probed yet, a loop or group with no end) or the cue is unknown.
- **`waveform { cue, start, end, buckets }`** (AUD-14): peaks of an Audio cue's file (or, for a Video cue whose movie has sound, of the audio track it plays over the movie's length; a movie without sound or a still is `unsupported`) over `start..end` (finite, `0 <= start < end`) in `buckets` (1 to 8192) parts. `end` is clamped to the file length; fewer buckets may come back (few frames, or a size cap).
  - The file is read whole once by the waveform reader (never a probe worker; one file at a time engine-wide) and cached per workspace under a byte cap, so later answers at any zoom are instant; a re-probe reads again.
  - Refused: `bad_request` (range or count out of bounds; not an Audio cue), `not_found` (no cue or no file), `unsupported` (missing, unplayable, not probed yet, or too long; ask again once `media_duration` is known), `command_refused` (too many waiting), `io` (disk stopped answering past `waveform_timeout`; repeated timeouts stop further reads until restart).

Paths are never empty, and `open` and `save_as` paths must be absolute (`bad_request` on decode): a relative one would resolve against the engine's own working directory.

#### Test support (test-only; not in a release engine)

An engine built with `test-support` and started with `--virtual-device stepped|realtime` plays on virtual outputs (skill `devices`). Five more app-scope requests drive it: `advance { frames }` (stepped only), `lose_device { device? }`, `restore_device { device? }`, `set_default_device { device }`, `drop_out { device?, count }`. A release engine refuses them like any unknown request (`bad_request`) and refuses `--virtual-device` (exit 2; `mac/scripts/verify-bundle.sh` checks the bundled engine). The Swift cases are Debug only.

- `advance` waits for background work, then renders `frames` at 48 kHz block by block with a control tick and the same wait after each, so states, meters, log times and status are as a device would have made them. `frames: 0` only waits. Errors: `unsupported` (no virtual device, or realtime), `bad_request` (another `advance` under way), `internal`.
- Two virtual devices: `openlab:virtual` ("openLab Virtual Output", listed from the start and the system's output) and `openlab:virtual-2` ("openLab Virtual Output 2", listed only once `restore_device` names it). Both have 2 outputs at 48 kHz. `device` is the id; absent, the first.
- `lose_device` removes a virtual device as an unplugged interface would (cues playing or waiting on it show `paused` with reason `device_lost`, the others routed to it `broken`); `restore_device` lists it (again) and the engine opens it at the next device-list read. `set_default_device` makes the list mark that device as the system's output from the next list read (patches on the system output follow it); one that is not listed leaves the list with no default. `drop_out` makes the device's stream report `count` dropouts (1 to 10000, else `bad_request` at decode) as a host reports xruns, at its next block (stepped: the next `advance`). `unsupported` without a virtual device, `not_found` for another id.
- On a stepped engine nothing moves between requests (device time, the epoch clock behind log `time_ms`, autosave, `status`), and worker answers are taken in at the next `advance`, so a script gets the same messages every run. Send `advance { frames: 0 }` after `open` before binding a connection so the welcome snapshot has every media duration.

- An engine on the virtual device runs a stage host only when started with `--virtual-displays ID:WxH,...` (test-support builds): drawn offscreen on those displays, never a window on the machine's own.
- `stage_test_card { stage, frame }` and `stage_probe { stage, points }` (workspace-bound, any engine built with test-support and a stage host): the stage host draws its test card on the stage (`ok` once sent), and reads the stage's picture back at 1 to 64 `points` (fractions of the stage from the top left), answered by `stage_probe { frame?, colours }` once the stage host has drawn it; app-scope `display_probe { display, points }` reads what a display shows (every stage on it, stacked, as its window draws them) and is answered the same way (`frame`: the test card's barcode, absent when the stage shows none; `colours`: RGBA per point). `not_found` for an unknown stage, `unsupported` while the stage host is not running, `internal` if it stops before answering. Workspace-bound `monitor_probe { stage, width, height, points }` reads what the stage's monitor window shows at a content size of `width` x `height` pixels (1 to 16384), answered the same way, with no `colours` when the stage host has no monitor window open for the stage.

#### Opening and closing workspaces

- **Another doc opens; the others play on.** `new`, `open` and `open_recovery` add a doc (limit in REQUIREMENTS §21). Nothing running stops. The `result` carries `opened { doc }` and nothing else; app connections get a `workspaces` list with the new doc; a connection bound to it (`hello { workspace: doc }`) gets its snapshot, including load-repair and recovery warnings.
- **The engine never prompts.** Opening needs no `discard_changes`. `close` over unsaved edits is refused `unsaved_changes` unless `discard_changes: true`; discarding also removes the autosave this doc wrote of the dropped edits, ordered after any autosave write in flight so it is not offered again. The UI asks the operator, then repeats `close` with the flag.
- **`open_recovery`** opens an autosave from `scan_recovery`, dirty. It binds to its show file (`document.path` set, as `open` with `restore`) when it is the current autosave of that file, newer than the file, and the file still holds this workspace, unused by another doc. Otherwise it is untitled (`document.path` null), with a `recovery_untitled` notice when it named a file that could not be used.
- **Closing**: the doc's cues stop at once (Panic twice), the requester gets its `result`, then every connection bound to it gets `closed { doc }` and is closed; app connections get `workspaces` without it. A client must not reconnect to a closed doc (`hello` answers `no_workspace`). `close` errors: `unsaved_changes`, `no_workspace` (no such doc, or no `doc` on the app connection).
- **`recovery`** (`open` only): `restore` opens the autosave (dirty, bound to the show path); `ignore` opens the show as saved and leaves the autosave (offered again until a save or later autosave replaces it). Absent, with an autosave newer than the show file: nothing opens and the `result` carries `recovery_offer { path, workspace_name, modified_ms }`; the UI asks and repeats `open` with a choice. `modified_ms`: wall-clock ms since the Unix epoch.
- **`open_recovery { workspace_id, path_hash?, modified_ms? }`** opens an autosave from `scan_recovery` as an **untitled, unsaved** doc. The optional fields pick one of several autosaves of one workspace id; absent: the newest.
- **`scan_recovery`** lists every recovery file, including a never-saved doc's autosave and files moved aside as stale (`stale: true`; they may hold the newest work), newest first. It serves the launch offer after an unclean exit (NFR-05) and what to show when a show cannot be opened (`bad_show_file`, or `io`).
- **One show file, one doc.** `open` of an open show, or of a file another doc's `save_as` is writing, answers `already_open`. Paths compare as media paths do (case, Unicode form, `.`/`..`) and, on the document worker before the read, by the file itself. So neither doc's save can overwrite the other's. A copy of an open show (another file, same workspace id) opens with a fresh workspace id and dirty.
- **`discard_recovery { workspace_id, path_hash?, modified_ms? }`** deletes the one autosave file `open_recovery` would open for that selector (it cannot be undone), and nothing else; the `result` is plain `ok`. `not_found` when no listed autosave matches; `command_refused` for the current autosave of an open workspace; `io` when the file cannot be removed. A save of a doc restored from a set-aside autosave (`open_recovery`) removes that file once the save is done: the operator has taken its contents. Any other save leaves set-aside files.
- **One document read at a time** engine-wide (`open`, `open_recovery`, `scan_recovery`, `discard_recovery`, `new`); another arriving meanwhile is `command_refused`. A read unfinished after the engine's timeout (a stalled network volume) answers `io`, and later requests are served normally.
- **Saving**: `save` and `save_as` write on a separate thread. `result` comes once the file is durably written; the new `document` (path, `dirty` false when no edit happened meanwhile) is broadcast before it. A failed write is `io`; the doc stays dirty and autosave keeps running. Autosave is not visible on the protocol (skill `persistence`).

## 4. Engine -> client

Fields: `ServerMessage` in `protocol/server.rs`. Behaviour:

- **`welcome`**: section 2. **`snapshot`**: the whole state again (after `request: snapshot`, a resync, or a save-as to another folder that re-spelled media references); the client replaces everything.
- **`document { path, dirty, can_undo, can_redo, show_mode? }`**: `show_mode` absent means false.
- **`runtime { seq, changes }`**: event-driven, applied in order.
- **`progress`**, **`meters`**: at most 30 Hz, only while something runs; meters are linear peaks per channel since the previous message: a cue's has one peak per output of its patch (1 to 128), a patch's `peaks` one per mapped cue output (the patch's first outputs, as many as this machine's mapping lists, which may be fewer than its cue outputs), each read at the device output it is mapped to, and its `cue_outputs` one per cue output, that cue output itself after its level and mute in the patch and before the crosspoints and device outputs (what the patch editor's rows meter; absent from an engine that predates it). A cue whose voices a lost device stopped has no entry from the loss on, until it plays again, and no meter shows what that device played before its loss once it is back.
- **`log`**: untimed engine notices; lossy like `meters` (a client whose queue is half full misses some). **`log_entry`**: each show-log record; lossy and rate-limited. A `log` notice is also a record, so a log window uses `log_entry` and `log_tail` only.
- **`status`**: about once a second, and early (not faster than every 250 ms) when `xruns`, the disk's health, the device's state, an output device's opening or state, or `network_output_disabled` change; droppable like `meters`. A new client gets its first with the next periodic one.
- **`workspaces`** (app connections only): the open docs in open order; **replaces** the previous list. `path` is null for a never-saved doc. `name` is the shown name: a saved doc's file name without its extension, else the name stored in the show (the name OSC addresses it by). `path_hash` names the doc's autosave (matches its `recovery_entries` entry): a copy of a show shares its `workspace_id`, so the app tells the open doc's autosave from another copy's by this hash. Sent when a doc opens or closes and when a name, path or unsaved state changes (checked once per control-loop wake).
- **`closed { doc }`**: to connections bound to `doc`; the engine closes the connection next.
- **`warnings`** (DX-01): workspace-level notices in force (load repairs, damaged media, device problems); **replaces** the previous list; empty clears. Two say the sound is going wrong while it plays (NFR-27): `audio_dropouts` (with `device` and `count`, the dropouts so far) on each output device a patch of the workspace plays on, from its first dropout until ten seconds without one, its `count` brought up to date at most every ten seconds; and `disk_behind` (no `device`) while a voice underran less than ten seconds ago, the same condition as `status.disk.healthy` false. Both are also show-log records. Broken cues are not here: their rows, with the cue id, come from `problems` in the snapshot and `runtime`.
- **`video_outputs { displays, video?, stages }`** (VID-01): to connections bound to a workspace, whenever the display list, a stage set, a stage's display choice or a stage's state changes (a display unplugged, the stage host started or stopped); **replaces** the previous one. The same data as `list_displays` and `list_stage_mappings` for that workspace (`stages` in workspace order). Sent as state (never dropped for a slow client; resent if the queue was full), and at most once per 100 ms, so a stage host reporting in a burst cannot flood clients. Also pushed to the workspace's connections after every `snapshot` request on one of them (so after `welcome`: the engine's own snapshot on bind), even when nothing changed and within the 100 ms: a client needs no request to have it. It is sent as soon as the snapshot is answered (at the engine's next tick if its outbound queue was full), so it comes before the broadcasts of anything the engine handles after that snapshot. It is a broadcast, not a reply, so it never overtakes a newer push; a connection waiting for its snapshot gets it after the snapshot's `result`.
- **`media_copy_progress { cues, files_done, files_total, bytes_done, bytes_total, on_demand }`** (WS-04): to connections bound to the doc whose media is being copied into its show folder, when the copy starts and at most every 250 ms while it runs; lossy like `progress`. `cues` are the cues whose files are being copied (the copying state); `bytes_total` is 0 until the copy has looked at the files.
- **`media_copied { report }`** (WS-04): the copy ended: `copied` (new files), `reused` (files the folder held with the same content), `in_folder` (files already inside, left alone), `failed` (cue, file as the cue holds it, `reason` `missing`/`unreadable`/`disk_full`/`read_only`/`not_responding`/`bad_name`/`other`, and the engine's words; at most 200, `failed_count` counts all) and `cancelled` (stopped: nothing retargeted). Sent as state; the copying state ends with it.
- **`result { id, ok { revision?, data? } | error { code, message } }`**: exactly one of `ok`/`error`. **`error`**: not tied to a request (section 2).

### Progress

Sent to connections bound to the doc whose cues it reports while something in the doc counts, and once more whenever the set of loaded cues standing at a time or a point of their media file changes (and after a snapshot request); otherwise nothing while every cue is idle or loaded, and no wake is added for it. A loaded cue standing inside its action (loaded to a time past its pre-wait: `load`, a Load cue) or, for Audio and Video, at a point of its media file (a seek) has an item with `elapsed` the seconds into its action it stands at (0 for a seek) and, for Audio and Video, `position` (no `remaining`), in every message sent while it stands there, so a cue standing loaded costs nothing more. A cue loaded inside its pre-wait has none. A previewed Audio cue (no show voice of its own sounding) has an item as a playing one's, from its preview voice (`elapsed`, `remaining`, `position`), in every message while it previews, in place of its loaded item if it is loaded, and one more message without it follows the stop. A message carrying a changed loaded set that the engine's outbound queue drops (more than half full) is made again on the next report pass. Full rules: skill `cue-engine` ("Timer progress").

- `items`: an audio cue's from its voice (`position`, when present: seconds into the media file the voice is at, with its slices, loop passes and devamps applied, so it stays inside a looping slice and moves on after a devamp; absent for a cue without a voice, past a finite plan's end, and for a voice a devamp stop has ended); a Video cue's from its picture (`elapsed` on the engine clock from its start plus any load-to-time offset, held while paused; `remaining` from the video's length or the still's duration, null for a still shown until stopped; `position` the seconds into a video's file, absent for a still); a cue without a voice (Wait, Fade, Group, ...) from its run, `elapsed` since its action start plus any load-to-time offset. `remaining` is null when there is no end (infinite loop, waiting for feedback, group with a busy child). A broken run has no item.
- `waits` (absent when empty): `wait` is `pre_wait` or `post_wait`; `remaining` is never null. A cue can be in both lists. Countdowns keep their schedule for a cue that is broken or skipped.
- A paused cue's entries keep coming at the values it froze at. Stop, Reset and Panic end them.

### Pre-show check

`result.ok.data` of `preshow_check` (SM-06, NFR-07). Media status is what probes and the media watch last reported (skill `media-files`).

- `ok` is true when nothing is a problem: `summary.total` is 0. Not problems: `not_checked` destinations, patches no cue uses, the `preload_over_budget` warning.
- `summary.total` = `broken_cues + system`. Media, patches and destinations are causes of broken cues and are not added again; `patches` counts only used patches with no device and `network` only `missing` destinations.
- `broken_cues` in workspace order, with the same `problem` objects as `runtime`. A disarmed cue is listed only for problems of its own; a group is not listed for a broken child.
- `media`: by path, `missing` or `unsupported`, with the cues using it.
- `patches`: patches with no device to play on, then patches cues name that the workspace lacks. A patch no cue uses is listed but not counted and not a failure. A Video cue whose file is known to have no sound (a still, a silent movie) is not a user of the patch it names.
- `network`: destinations Network cues use: `missing` (a problem) or `not_checked` (exists; **reachability is not probed**: neither problem nor pass, `ok` stays true).
- `system`: the `warnings` list (device lost or stalled, damaged media, preload problems, unplayable slices, `audio_track_missing`: a Video cue's stored audio track is not in its movie and the first plays), sorted by `code`, cue, message, leaving out notices whose `patch` no cue uses and a device's own notices (`device_lost`, `device_stalled`, `device_unrecoverable`, `outputs_dropped` with no `patch`, `audio_dropouts`) while no cue's patch is on that device; the clock device's (the primary output) `device_lost`, `device_stalled` and `device_unrecoverable` count whenever the workspace has any cue, as every timed cue runs on its clock (the `warnings` list keeps them). A cue's patch is on the device its mapping names, for the system output the system's output device now; while some cue's patch has no device to name, every device's notices count. Any entry makes `ok` false except `preload_over_budget` (streamed and plays).

### Show log entries and status

A `LogEntry`: `time_ms` (wall-clock ms, UTC), `show_time?`, `level`, `kind`, `message` (English), `cue?`, `source?`. `trigger` records (a transport action arrived; `source` `ui` or `osc <ip>`) are rate-limited per source with an `N more input(s) not logged` record. The same records go to the log file (skill `engine-lifecycle`).

**Live log resync.** `seq` numbers every record the engine makes from 1, pushed or not; `log_tail` carries the `seq` of the newest record when answered (0: none).
- A live view reads `log_tail` once, then appends each `log_entry` whose `seq` is above the last it has. An entry at or below it is already in the view.
- A jump of more than one means records were not pushed: read `log_tail` again.
- Pushes are lossy (dropped while the client's queue is half full) and rate-limited on the trigger records' 10 s wall-clock window. A push the hub drops for a slow client is not offered again: that client sees `status.log_seq` (about once a second) above the last `seq` it got, and reads `log_tail`.
- The log is the engine's, not a doc's: `log_entry` carries no doc.

**`status`**: `cpu_percent` (engine process, percent of one core; null without a figure), `engine_load` (worst callback time over block time since the previous status; 1.0 means a callback took as long as its block, above 1 is a dropout; null when no callback ran, e.g. device lost, and for offline rendering), `xruns`, `disk { streams, underrun_frames, healthy }` (healthy: no underrun for ten seconds), `device { name?, state, sample_rate, block_frames?, channels, latency_ms? }` (the primary device; `state`: `ok`, `lost` while the engine tries to reopen, `failed` when only a restart helps, `absent` for offline rendering), `outputs` (AUD-02: every output device the engine has opened since start, the primary and each device a patch was mapped to, `closed` ones included; the primary first (`primary: true`), then the others in the order they opened, each `{ name, state, primary?, sample_rate, channels, block_frames?, latency_ms? }`; `channels` is 0 and `block_frames` absent until a device's first open answers; `state`: `up`, `opening` (for a patch mapped to it, until it plays), `lost` (reopening), `reconfiguring` (reopening at once at another buffer size), `closed` (no patch maps to it), `failed` (only a restart helps); `sample_rate` is the device's own: the primary's when it can run at it, else one of its own; absent reads as empty), `log_dropped`, `log_seq` (absent reads as 0), and `network_output_disabled` (absent: false). **The UI must show `network_output_disabled` plainly while true.**

### Media durations

What an Audio or Video cue's file gives it to play, for the Duration column (CL-02): derived from the probe plus trims and slices, never saved. Seconds, rounded down to the millisecond.
- `file`: whole file. `trimmed`: start trim to end trim, every slice that plays once (a skipped slice is not counted). `duration`: the cue's action (`trimmed` with every slice's play count); absent when a slice loops until devamped (QLab 5 excludes pre-wait: manual pp. 94-95 and 124). `channels`: 1 to 64 (AUD-06).
- An Audio cue's `audio_file` is its file's format as the probe read it: `{ codec, channels, sample_rate }`, `codec` a short name (`pcm`, `pcm_float`, `flac`, `alac`, `aac`, `mp1`, `mp2`, `mp3`, `vorbis`, `opus`, `other`). Absent for a Video cue, with the lengths, and when the probe did not read the codec.
- A Video cue's: `file` is a video's length (absent for a still), `trimmed` and `duration` a video's as an Audio cue's (its trims, slices and play counts on the file's length; `duration` absent while it loops for ever, and with hold at end still the played length), a still's `duration` its typed one (absent for a still shown until stopped, no `trimmed`), and `picture` its file's format as the probe read it (`{"type":"video","codec","width","height","fps","duration"}` or `{"type":"still","format","width","height"}`, the shapes of the probe line in section 5).
  - A movie with sound (VID-06) adds `audio_tracks: [{ codec, channels, sample_rate }]`, its audio tracks in file order (`codec` is the sample format's four-character code: `mp4a` AAC, `lpcm`/`sowt`/`twos`/`in24`/`fl32` PCM, `alac`), `audio_track` (which of them the cue plays, from 0: its stored `audio_track`, or 0 when the file has no such track) and `channels` (that track's: the rows of the cue's levels). A movie without sound and a still have none of the three: the cue has no sound, no levels to show, and no patch problem.
  - A Video cue's sound is edited by `kind_fields` with `patch` (a patch id or `null`), `levels` (the whole object, as an Audio cue's, limited to the workspace's volume limits the same way) and `audio_track`; a playing cue's level edits reach its voice at once, as an Audio cue's.
- A field is absent when unknown: all while the file is unprobed, missing or unplayable; `trimmed` and `duration` when trims and slices cannot play (`slices_unplayable`) or every slice is skipped (`nothing_plays`).
- A change with only `cue` means "not known now": the client drops what it held, so a missing file, relink or removed cue never leaves a stale length.
- They ride the runtime channel, not `cue` upserts: a probe answer is not an edit and would move the revision and unsaved state. A change is sent when the probe answered again, the file went missing, trims, slices, counts or file were edited (after that edit's `model_changed`), or the cue was removed; one `runtime` message per tick.

### Snapshot

Fields: `Snapshot` in `server.rs`. `workspace` never carries `show_mode`. `cue_states` lists cues not idle. `played` (absent: none) lists the cues started since they were last reset, whose rows show their `second_color`. `playlist_next` (absent: none) gives each Playlist group with a child it plays next, which the cue list marks on the group's box. `group_warnings` lists groups with a broken descendant; one with no run of its own is `broken` in `cue_states` with no `reason` and no `problems` entry. A previewed group is listed in `previewing` with its audio cues.

### Model changes

`model_changed.revision` rises by exactly 1 per message from `snapshot.revision`; any other step is a gap (request `snapshot`). Apply `deletes` first, then `upserts` in order. A `delete` of an unknown id is ignored; an `upsert` of a cue the client holds replaces it wherever it is.

- `cue { list, parent, index, cue }` puts the cue (new, changed or moved) at `index` among the cues of `parent` (null: top level). A group's upsert carries its whole subtree and replaces it; children are not upserted separately.
- `cue_list { id, name, index }`; its cues come as `cue` upserts, and an upsert for a held list keeps its cues. `patch`, `network_patch`, `stage`: `index`, item. `settings { name, settings }`: the name and all settings (OSC passcodes inside are visible to every client holding a token).
- Deletes: `cue` (with children), `cue_list`, `patch`, `network_patch`, `stage`. The engine only removes empty cue lists, so their cues were deleted or moved out in the same or an earlier message.
- Collections: a `patch`/`network_patch`/`stage`/`cue_list` upsert per item added or changed and a delete per item removed; for a move (or its undo), or when two or more items of a collection changed, an upsert of every item of that collection at its final index, ascending. These come before the message's cue upserts.
- Cue edits: a `delete` for each cue removed or moved, then an `upsert` for each cue added, moved or changed, in tree order (parents first, ascending index), so several moves in one undo step cannot collide. A cue inside an also-upserted group is not sent separately. One `model_changed` per edit, undo, redo or runtime model change (`SetArmed`).
- **`model_changed` for revision N is always sent before the `result` reporting `ok.revision = N`.**

### Runtime changes

`runtime.seq` rises by 1 per message (a gap means request a snapshot). Change types, from `RuntimeChange` (`protocol/wire.rs`): `cue_state`, `problems`, `group_warning`, `playhead`, `preview`, `played`, `playlist_next`, `go_protection`, `warning`, `media_duration`.

- `cue_state { cue, state, reason? }`: `reason` (`voice_rejected`, `stream_failed`, `device_lost`, `decode_failed`: a Video cue's picture could not be decoded or drawn) is set when the cue broke while running. With `paused`, `reason` `device_lost` marks a cue its output device's loss stopped while it played or waited (as QLab 5 shows it): it owns nothing, its time (a `progress` item with the values its voice had, `position` included, or its pre-wait or post-wait countdown in `waits`) stands still, `resume` clears it to idle (broken while the device is still away) and a start plays it from its beginning; a waiting one is idle again by itself when the device returns. A running group whose playing children it left so is marked the same way (a start clears a group's mark at once). A `paused` state without `reason` is an ordinary pause. The same holds for `cue_states` in the snapshot. A `broken` state with no `reason` is a cue with static problems (listed in `problems`) or, with neither, a group with a broken descendant (it has no problems of its own and still starts).
- `playlist_next { group, cue }`: the child the Playlist group plays next changed; `cue` `null`: none. Not running: its first child that a start plays: one with a run of its own (also broken, paused or fading out in a panic), unless it is playing or waiting and its second trigger ends that run (stop, hard stop, or a panic that stops it at once rather than fading it out: a `panic_duration` of 0, or a run with no voice playing in its action, such as one in its pre-wait, a Wait or a group with no child left fading out; hard stop and restart counts as a new run); else the first that is not skipped, has no static problems, is not broken at run time with its run ended, and is not left paused by a lost device that is still away; a looping one goes round again after every pass that plays none but started a run (one that ends at once), the children whose runs it ended counting as new runs; none while shuffled (its order is drawn at the start), disarmed, or loaded to a time at or past its span (its start plays no child; also once a media length that arrives later puts it there). Playing: the one after its current child as the group stands now (wrapping when it loops, and round again as a start does; a shuffled pass's next, none between passes); none while it stops, is devamped or halted, and after its last child. Also sent with `null` once for a group that had a child and was deleted or left Playlist mode.
- `go_protection { active }`: double-GO protection began with an accepted GO (`true`) or its time passed (`false`); while it is in force a GO is ignored with a `go_ignored` warning of reason `double_go`. Not in the snapshot: a client that connects inside the time shows none.
- `played { cue, played }`: the cue was started for the first time since it was last reset (`true`), or a reset (of the cue, a group around it, Reset All) made it unplayed (`false`). A played cue with a `second_color` shows that colour. Runtime only: a newly opened show has none played.
- `problems`: the full list of static problems, empty when none. An Audio or Video cue whose file plays has `slices_unplayable { reason }` when its trims, markers and play counts do not fit the file (a looping slice under 50 ms, a start trim past the end), and `nothing_plays` (no fields) when every slice inside its trims has the play count `"skip"`, so no part of the file plays (QLab 5 manual pp. 184-185); GO passes over the cue as over any broken cue, and one slice that plays clears it. A Video cue adds `no_stage` (its stage is "none") and `stage_missing { stage }` to the media problems it shares with Audio cues (`no_media`, `media_missing`, `media_unsupported`: also a movie with an audio track that cannot be decoded or has too many channels, the reason naming the track). One whose file has sound also has an Audio cue's patch problems (`patch_missing`, `device_unavailable`) and `no_patch` (its output patch is "none"); a file without sound never has them. A Target cue (QLab 5 manual p. 686) has its target problems (`no_target`, `target_missing`, `target_self`, `target_wrong_kind`: a Fade or a cue that acts on no cue) and one of `no_new_target`, `new_target_missing { target }`, `new_target_unnumbered { target }` or `new_target_wrong_kind { target }` (its target cannot act on that cue, or it is the target itself); the temporary target it gives when it runs is runtime only and not sent. `group_warning { group, warning }`: why a group shows broken (its `cue_state` is `broken` while it has no run).
- `warning` mirrors the engine's warnings, plus `go_ignored {list, reason}` and `notice {code, message, cue?, device?, patch?, count?}` for what only the binary knows. `count` is how often a repeating notice happened: `audio_dropouts`' dropouts so far; on the runtime `underrun` notice (a cue's voice ran out of audio from the disk and plays late from there; `cue` names it) the underruns of that cue since its previous `underrun` notice, which goes out at once and then at most once per ten seconds per cue, so a client adds the counts up. `device` is the audio device a device notice is about (`device_lost`, `device_unrecoverable`, `device_stalled`, `audio_dropouts`, `outputs_dropped`, `patch_device_missing`, `patch_device_unusable`, `patch_routing_beyond_device`), by its system name, so a client can show one entry per device; `patch` names the output patch a patch notice is about (`patch_device_missing`, `patch_device_unusable`, `patch_no_system_output`, `patch_no_device`, a patch's `outputs_dropped`, `patch_routing_beyond_device`, `mixer_patches_exhausted`), so a client can show one entry per device and patch; the runtime `device_lost` notice (one per loss, with the doc's count of cues stopped) and the `warnings` one (in force while the device is away) name it the same.
- `media_duration` does not come from the cue engine: it comes from the control loop's plan checks (above).
- The UI localises from the variant or `code`; `message` is English.

### Ordering and gaps

- Match a `result` to its request by `id`: results may leave in a different order than the requests were sent.
- The server may hold a `result` with `ok.revision = N` until `model_changed` N has been written (at most `revision_wait`, 2 s). If a `result` is ahead of the client's model, request a `snapshot`.
- Never pipeline `snapshot` requests: while one is outstanding, broadcasts are withheld until its `result`.
- On one connection, broadcasts are ordered before replies, and a `snapshot` is never followed by older broadcasts (those at or below its revision or `seq` are filtered). `document` and `warnings` may arrive after the `snapshot`; they are still current.
- Revision and `seq` gaps are forwarded unchanged; the client recovers with `request: snapshot`. A lagged client gets a fresh unsolicited `snapshot` and is not closed; a `result` without a revision may overtake it.
- `closed { doc }` arrives after the requester's `result`. A resync for a closed doc answers `no_workspace`, then `closed`.
- `u64::MAX` is a reserved request id (`bad_request`). A second `hello` and binary frames are `bad_request`; 32 consecutive bad frames close the connection (`MAX_BAD_FRAMES`).
- `meters`, `progress`, `status`, `log_entry` and `log` are dropped for a slow client without lagging it.

### Error codes

`ErrorCode` in `server.rs`; the client acts on the code, never the message:
- `protocol_version_mismatch`, `bad_token`: connection ends at `hello`; do not retry blindly.
- `bad_request`, `unknown_message`: the frame was rejected; after `welcome` the connection stays open unless the frame was over the limit. A bad `hello` or an over-limit frame ends it.
- `command_refused`: the engine refused a valid message (validation, limit, busy). Nothing changed.
- `not_found`, `already_open`, `unsaved_changes`, `io`, `bad_show_file`, `unsupported`, `internal`.
- `no_workspace`: no doc to act on (none open, a closed doc, an app connection, or a save with no path yet).

## 5. Stage host link (engine <-> `openlab-stage`)

Not seen by clients. The engine spawns the stage host (the process that owns the video output windows; skill `video`) and speaks to it over the child's stdin (engine to stage host) and stdout (stage host to engine): one JSON object per line, UTF-8, `\n`-terminated. Types: `openlab-core::stage_link` (`engine/crates/core/src/stage_link.rs`); seed lines in `engine/fuzz/stage-link-seeds/`.

- **Version.** The engine's first line is `hello { version }`; the stage host answers `hello { version, pid, video }` and quits when the versions differ (`LINK_VERSION`, 6: version 2 added picture geometry, version 3 a picture's plan, action time and fades on `play` and its action time on `pause`, version 4 `ramp`, version 5 monitor windows, version 6 `app`). `video: false`: this build has no video output (every stage `failed`).
- **Engine to stage host:** `stages { stages: [{id, width, height, display?, keep_black, stack}] }` is every stage of every open workspace and replaces the previous set; `stack` ranks every stage (0 at the bottom; the engine orders by layer, then name, file-format §4.7), and the stages on one display are drawn in one window, bottom first; `display` is a display id from `displays` (absent: no display on this machine); `monitor` (a title, absent: none) asks for the stage's monitor window: a resizable window of its own showing the stage fitted, black bars where the shapes differ, drawn after the displays and never holding them up, whether or not the stage is shown on a display; `raise_monitor { stage }` brings it to the front, opening it again if the operator closed it. `stand_back { on }`: while on, the window on the display with the menu bar is under every app's windows instead of over them (a stage host that hears nothing from the engine for 4 s stands it back by itself until the engine speaks). `app { connected, pid }`: whether the operator's app is connected to the engine, and its process id when it gave one (`null` otherwise); sent when an app connects or the last one goes, and to every stage host that starts, before its `stages`. While `connected` is false every output window is down (each stage that would be shown is `hidden`; pictures play on unseen, monitors are not drawn), so no stage outlives the app; a stage host not told keeps them up. A click on a stage stays with it (no app behind sees it) and brings the app with `pid` forward with the keys; the stage host never keeps the keys (whenever it is the active app it hands them to that app, or lets them go when it knows none). `ping { seq }` is answered by `pong { seq }`. `quit` closes every window and ends the process.
- **Stage host to engine:** `displays { displays: [{id, name, width, height, fps}] }` after `hello` and after every display change (ids are stable across restarts: on macOS the display UUID; sizes in pixels). `stage_status { stage, state }` when a stage's state changes: `{"state":"shown","display"}`, `hidden` (keep-black off, or its black down: taken down by a panic or nothing played since its workspace opened, and nothing plays; or no app is connected, `app`), `no_display`, `{"state":"display_missing","display"}`, `{"state":"failed","reason"}`. `log { level: info|warn|error, message }` goes to the show log. `monitor_closed { stage }`: the operator closed the stage's monitor window (or it could not be drawn); it stays closed, whatever `stages` sets the engine sent before it heard, until a `raise_monitor` or a set without that monitor.
- **Limits** (checked by both ends after parsing; a line breaking one is refused as a whole): a line at most 1 MiB (a full stage set with the longest display ids and monitor titles fits); at most 32 displays and 512 stages; ids, names and messages at most 512 bytes without control characters (a message may hold newlines), ids and names not empty; sizes 1 to 16384; a display's `fps` 0 to 1000 (absent: 0). A refused line is a `warn` log and is otherwise ignored; the reader never holds more than one line.
- **Pictures** (Video cues; engine to stage host): `clock { sample, rate }` is the engine's sample clock (rate 1 to 384000), sent at least every 10 ms of samples while a picture is up and before every `play` (a routine one may be dropped while the stage host is behind reading; the next replaces it); the stage host moves it on by its own clock between messages when it draws on real displays, at most 30 ms past the last one (a clock that stops freezes the picture), and offscreen draws exactly at the last one. `load { picture, stage, file, still, offset, geometry }` opens a file (a path, 1 to 4096 bytes, no control characters) for a picture id of the engine's on a stage, held at `offset` seconds (0 to 24 h) and not drawn until it plays, drawn with `geometry` (the Video cue's geometry fields, docs/file-format.md §5 `video`, each in its range or the line is refused); `geometry { picture, geometry }` replaces a picture's geometry (an edit while it is up), drawn so from the next frame, its run untouched; `ramp { picture, param, ramp: { from, to, at, frames, curve } }` moves one value a Fade cue fades (`param` `opacity`, `translation_x`, `translation_y`, `scale_x`, `scale_y` or `rotation`; `from` and `to` in that value's range, docs/file-format.md §5 `video`, or the line is refused) from `from` on sample `at` to `to` on `at + frames` along `curve` (a falling move traces the rising curve backwards, as a level's fade), then holds `to`, drawn over the picture's own value until the picture goes; 0 frames is `to` from `at` on; a later `ramp` of the same value takes over from its own sample (before it, the one in force still applies); `play { picture, at, offset, action, plan, into, fades }` plays it from sample `at`, `offset` seconds into the file and `action` seconds into its cue's action then; `plan` (a movie's trims, slices and loops from the top of its action, at most 256 passes `{from, length, plays}` in seconds, `plays` 0 looping until devamped, each time 0 to 24 h and every length above 0), `into` seconds into it on `at` (0 to 24 h), gives its position: pass by pass, a loop's next pass from its start (a new pass is a seam, read again from its start however near), held just before the end of the last pass once the plan is over; a play with an empty plan holds at `offset` (a still ignores both; a movie never runs on past its range); `fades { fade_in, fade_out, end }` (fade specs and the action's end in seconds, `null` while it loops for ever) scale its opacity by its action time, rising from the action's start and falling to `end`; a `play` dated before the clock replaces the run from its own sample (a devamp sends its plan again from the same `at` with the loop cut); `pause { picture, at, offset, action }` holds the frame at `offset`, its fades held at `action`, from sample `at`; `stop { picture, at, fade, cut? }` fades it out over `fade` samples from `at` (0: gone on `at`), then it goes; with `cut` (a sample) it goes on that sample if the fade is not over by then (its cue's action ends mid-fade: the end of its range or of the pass a devamp stops it at); `unload { picture }` takes it away now. At most 256 pictures at once. A picture's frame at a position is the last whose time is at or before it; pictures on one stage are drawn lowest layer first, and on one layer earliest-started first (the later-started on top), each placed by its geometry, clipped to the stage, at its opacity (premultiplied: a transparent pixel of the file stays transparent), sampled smooth or nearest-neighbour. A `load` never holds up the stage host: the file is opened (a movie's frame at `offset` decoded) on a thread of the picture's own. Stage host to engine: `picture_opened { picture }` once that is done; `picture_failed { picture, reason }` when a picture cannot be opened, decoded or drawn, its open takes over 10 s or its decoder reads no frame for 5 s while one is wanted, or it is larger than 67108864 pixels (it is gone; other pictures are not affected). A stage host that starts is sent every picture that is up again (its `load`, the last `ramp` of each value, first `play`, then last `play` or `pause`, then its `stop` if it is stopping), except after a crash (a fault signal or failing exit, never a kill): a picture that was opening or decoding at two crashes within 60 s (engine clock) breaks its cue if it was the only one; several are held back and sent again one at a time, and the one the stage host then crashes on breaks its cue, so a file that crashes the stage host ends up alone.
- **Probe.** `openlab-stage --probe <file>` is a separate, throwaway process the engine starts on a probe worker for each Video cue's file: it reads the file, prints one line and exits. Types: `openlab-core::video_probe`. `{"type":"video","codec":"h264"|"hevc"|"prores"|"hap"|"hap_alpha"|"hap_q","width","height","fps","duration"}` (HAP's other flavours, such as HAP Q Alpha, are reported `unsupported`) (sizes 1 to 16384 a side and at most 67108864 pixels in all, a quarter of the largest stage, `fps` above 0 to 1000, `duration` seconds above 0 to 24 h), `{"type":"still","format":"png"|"jpeg"|"tiff","width","height"}` (the same size limits; a still is decoded whole, so a damaged or cut-short one is `unsupported`), `{"type":"missing"}` or `{"type":"unsupported","reason"}` (1 to 512 bytes, no control characters). A line at most 4096 bytes; anything else, a crash, or no line within 20 s (the process is then killed) makes the file unsupported with a reason. Where the build has no video output the probe answers `unsupported`.
- **Lifetime.** The stage host exits when its stdin ends, so it never outlives the engine. The engine's supervision (watchdog, relaunch, quit) is in skill `video`.
- **Test support** (test-support builds of both ends only): `test_card { stage, frame }` draws the test card (skill `video`), `probe { stage, points: [[x, y]] }` (1 to 64 points, fractions of the stage from the top left) is answered by `probed { stage, frame?, colours: [[r, g, b, a]] }` (a probe first draws as a frame would now, so any state that changes, a stage left with nothing to show, is reported ahead of its answer), `hang` makes the stage host stop answering, `probe_display { display, points }` reads what a display shows (every stage on it, stacked), answered by `display_probed { display, frame?, colours }`, `set_displays { displays }` replaces a stage host's virtual displays (as if displays were plugged in or unplugged), `probe_monitor { stage, width, height, points }` reads what the stage's monitor window shows at that content size, answered by `monitor_probed { stage, frame?, colours }` (no colours when it has no monitor window open), and `close_monitor_window { stage }` closes it as the operator's click on its close button does. `openlab-stage --virtual-displays <list>` takes, in any order, `--media-limits <open_ms>,<frame_ms>` (the picture limits of the files named next), `--good-media-limits <open_ms>,<frame_ms>` (every other file's; each value at most 3600000, a limit not given stays the shipped one) and `--media-clock-by-hand`; a picture file whose name contains `openlab-test-hang-open`, `openlab-test-hang-decode`, `openlab-test-crash-open` or `openlab-test-crash-decode` makes its decoder hang or crash there; `openlab-test-slow-decode` makes each frame it reads move the media clock on 400 ms. With `--media-clock-by-hand`, the limits are measured on a media clock that only `advance_media_clock { ms }` (0 to 86400000) and slow frames move. `openlab-stage --test-decoder <file>` prints `hardware` or `software`: the decoder VideoToolbox picks for a movie. `openlab-stage --make-test-media <h264|hevc|prores|prores4444|hap|hap-alpha|hap-q> <file> <frames> <fps>` (`prores4444` and `hap-alpha`: the card's right half below the barcode at half alpha, straight; HAP frames are made by openLab's own test writer, and a HAP kind followed by `@<n>` has every frame from `n` on damaged) or `<png|jpeg|tiff> <file>` writes a movie whose every frame is the test card for its own frame number (288 x 160), or frame 0's card as a still; `huge-png <file>` a black still of 16384 x 8192 (too many pixels to play); `wide-png`, `tall-png`, `alpha-png`, `tiny-png <file>` the geometry tests' stills (skill `video`).
