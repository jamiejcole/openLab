# Video (stages and the stage host)

QLab 5 model: manual pp. 207-212 (Video cues), 225-230 (stages), 241-243 (Fade cues).

Design decided by the user on 2026-11-13: decode and drawing live in a third process, the stage host; macOS decodes with AVFoundation/VideoToolbox (HAP in-house) and draws with Metal; video follows the audio clock; no video on Windows in v0.0.2.

Built so far: stages, their per-machine display, the stage host with black output windows, its supervision by the engine, the test card read back in tests, and the Video cue's model, file format, commands and problems (`CueKind::Video { media, stage, duration }`; skills `cue-engine` (its kinds reference) and `edit-commands`).

Probing Video cues' files and playing their pictures on stages in step with the engine's clock are built (below). Not built: audio from video files (#645), HAP, opacity/geometry/effects, Fade cues on pictures.

## Must not break
- A stage with keep-black on and its display connected shows black whenever nothing plays on it, never a frozen frame (VID-12), while the stage host runs. The desktop does show: from the engine's death until a relaunched engine's stage host is up; between a stage host crash and its relaunch (about 150 ms); and for the whole pause after repeated crashes (`retry_after`). The app-side black backstop that covers these is issue #667.
- The engine links no GUI framework and no video decoder. Everything that touches windows, displays, the GPU or (later) media is in `openlab-stage`, so a crash or hang there never stops sound.
- Every line crossing the link is validated on both ends (`stage_link::decode_*`): a bad line is a warning, never a panic, a hang or unbounded memory.
- The stage host exits when its stdin ends, so it never outlives the engine.
- The stage host never activates or takes key focus: the operator's keys stay with the app.

## Stages (`openlab-core` `video.rs`, `model.rs`)
- `Workspace.stages: Vec<Stage>`: `id` (`StageId`), `name`, `width`/`height` in pixels (1 to `MAX_STAGE_PIXELS` 16384, p. 208), `keep_black` (QLab's "keep rendering between cues", p. 227; default off, so a stage on the operator's display never covers it between cues). At most `MAX_STAGES` (64). File format §4.7.
- `layer` 0-1000 (default 1): of stages on the same display, a higher layer is drawn on top; on one layer the name sorting first is on top (p. 227; `stack_order`). Edits: `AddStage`, `RemoveStage`, `MoveStage`, `SetStageProperty` (skill `edit-commands`).
- Load: a size of 0 or above 16384 is clamped (`StageSize` warning), a layer from 1001 to 65535 too (`StageLayer`); a negative, fractional or out-of-type number refuses the file as a wrong type; stages past 64 are dropped (`TooManyStages`), two with one id refuse the file (`DuplicateStageId`), odd names warn (`stages.name`).
- Which display shows a stage is per machine: `settings.json` `workspaces.<id>.stages.<stage id>` = `StageMapping { display, name, width, height }` (the display's id plus what it was when chosen). `MachineSettings::stage_mapping` / `set_stage_mapping` (refuses empty or over-long text, control characters, sizes out of range). A damaged entry in the file drops only itself with a warning.

## The link (`openlab-core` `stage_link.rs`; contract `docs/protocol.md` "Stage host link")
- One JSON object per line; `LINK_VERSION` 1; lines at most `MAX_LINE_BYTES` (512 KiB: a full `MAX_LINK_STAGES` set with the longest display ids fits; tested).
- Engine to stage host (`ToStage`): `hello`, `stages` (the full set, replacing the last: id, size, display id or none, keep_black), `ping`, `quit`; test support `test_card`, `probe`, `hang`, `set_displays` (virtual displays plugged or unplugged).
- Stage host to engine (`FromStage`): `hello` (version, pid, `video`: false where the build has no video output), `displays` (after hello and on every change), `stage_status` (`shown`, `hidden`, `no_display`, `display_missing`, `failed`), `pong`, `log`; test support `probed`.
- Limits checked after parsing: at most `MAX_DISPLAYS` (32) displays and `MAX_LINK_STAGES` stages, text 1 to `MAX_TEXT_BYTES` (512) bytes without control characters, sizes 1 to 16384, probe points 1 to 64 inside the stage.

## The stage host (`engine/crates/video`, binary `openlab-stage`)
- `host.rs` is the same on every platform: `Host<P: Platform>` keeps the stages, the displays and each stage's state. A stage is shown only with its display connected and (while black) keep-black on; otherwise hidden with the reason. `serve` reads lines with `read_line` (never holds more than one line's limit; an over-long line is skipped and reported) and ends at end of input or a failed write.
- The stages shown on one display are drawn in one window (per display, not per stage), bottom first by `stack`; a stage keeping black is a black quad over what is below it. Test support `probe_display` reads a display's composite.
- After a `stages` message the host reports every stage's state (so the engine knows each was dealt with); after a display change only the states that changed.
- macOS (`platform/mac`): an accessory app (no Dock icon or menu bar) whose windows come up with `orderFrontRegardless`, borderless, never key, ignoring the mouse, at screen-saver level over the display's whole frame (covering its menu bar and Dock), on every Space, out of Mission Control and window cycling. Never system full-screen.
- AppKit and Metal live on the main thread; a reader thread decodes lines and queues them on the main queue.
- The main thread never opens or decodes a picture's file (below), so it always answers `ping` and keeps every other stage drawn. Offscreen (test support) the host loop runs on the main thread with a reader thread feeding it (`host::serve`), polling pictures every 16 ms between messages. At the end of input (or a failed write) the process ends with `_exit` from whichever thread sees it: no exit handlers or stdio flush, so a hung main thread cannot keep it alive.
- Displays: CoreGraphics' active list, named by ColorSync's display UUID (stable across restarts and reconnection), pixel size from the display mode, name from AppKit's screen (else "Built-in Display" / "Display N"). A reconfiguration callback re-reads them and moves every stage, and reads them once more `SECOND_DISPLAY_READ` (500 ms) later, in case AppKit's screen list had not caught up (a re-plugged display would otherwise stay missing until the next display event).
- Drawing (`gpu.rs`): Metal clears the stage to black and draws each picture as a quad (nearest-neighbour sampling). A stage of another shape than its display is fitted, shape kept, black bars elsewhere (assumed; see skill `qlab-behaviour`).
- Other platforms (`platform/none.rs`): `video: false`, no displays, every stage `failed` with the reason.

## Probing Video cues' files (`openlab-engine` `stage_probe.rs`; stage host `platform/mac/probe.rs`; core `video_probe.rs`)
- The engine never opens a video file or still: a probe worker (never the control thread) runs `openlab-stage --probe <file>` as a throwaway process, kills it after `PROBE_PROCESS_LIMIT` (20 s), and validates its one line (`decode_probe_report`). A decoder that crashes or hangs on a hostile file takes only that process; the stage host drawing the show never opens an unprobed file. No stage host configured: every picture probe is `unsupported` ("no video output").
- Why not in the drawing stage host: a crash there would black out every stage mid-show; why not in the engine: the engine links no decoder.
- Picture size: at most 16384 a side and `MAX_PICTURE_PIXELS` (67,108,864: a quarter of the largest stage, so 8192 x 8192 or a 16384 x 4096 panorama, 256 MiB as BGRA) in all, for stills and movie frames (`picture_size_plays`, checked by the probe, the probe line's decoder and the stage host before it allocates).
- macOS probe, stills: ImageIO (PNG, JPEG, TIFF). ImageIO decodes lazily, so the probe copies the image's data, which decodes every pixel: a PNG or TIFF damaged past its header gives none and is `unsupported` ("damaged"). A cut-short JPEG decodes to grey without an error, so a JPEG must also have its end-of-image marker after its last scan. Damage inside a JPEG's scan data that leaves its structure whole is not detected (it shows as noise).
- macOS probe, movies: AVFoundation reads the first video track's four-character code (`avc1`/`avc3` H.264, `hvc1`/`hev1` HEVC, `apco`..`ap4x` ProRes), natural size, nominal frame rate and the asset's length, and decodes the first frame. HAP (`Hap1`, `Hap5`, `HapY`, ...) is reported unsupported: no decoder for it is built yet (no HAP encoder here to test one with).
- Anything else is `unsupported` with a reason naming the codec or format.
- The media catalog tracks a Video cue's file like an Audio cue's (`media_use` gives its kind; `Entry::picture`; `Probe::Picture`; `ProbeAnswer::Pictured`), so missing-file marks, the media watch, the stalled-volume gate and relink all apply unchanged. A file used by an Audio and a Video cue is probed as the kind that asked first (the other cue cannot play it; audio from video files is issue #645).
- Tests: `tests/video_cues.rs` makes media with the test-support `--make-test-media` (AVFoundation encoders, ImageIO; frames are the test card for their own number).
  - It probes every codec and still format, damaged and seeded-mutated files (bounded by the probe limit), and Video cues on the real engine (probe problems, the media watch).
  - The probe line is fuzzed with the link (`fuzz/src/stage_link_input.rs`, seeds `fuzz/stage-link-seeds/probe_reports.jsonl`).
  - HAP files cannot be made here (no encoder), so HAP is unsupported for now.

## Playing pictures (`openlab-engine` `control/pictures.rs`; stage host `host.rs`, `platform/mac/media.rs`, `gpu.rs`)
- The cue engine runs a Video cue's picture as a voice. `DocCx::execute` sends a Video cue run's voice actions to `picture_action` (not the mixer's voices): load, play, pause, stop (with its fade), unload on the stage host, each picture an id of the engine's (`Pictures`). Ramps and ducks have nothing to act on; a devamp is answered `DevampIgnored`.
- The run's length (a video's from the probe, a still's typed duration; none for a still without one) is told at its start as `ActionLength`, so the cue ends on its last frame's sample. A stop's end (its fade) is a deferred `ActionEnded`. A cue whose action is over (`StateChanged` to idle, post-wait or broken) has its picture stopped on that sample (`end_pictures`).
- The clock: `clock { sample, rate }` at least every 10 ms of samples while a picture is up (`picture_clock`, each tick), before every play and before a test probe.
- A routine clock (not one before a play or probe) goes as `Order::Clock`: dropped while the stage host's write queue is half full, so a burst (an offline test running ahead of real time, a stage host busy for a moment) never fills it and gets the stage host stopped as not reading.
- Offscreen the stage host draws at the last clock exactly; on real displays it moves the clock on by its own clock, at most `CLOCK_HOLD` (30 ms, three clock periods) past the last `clock` (a clock that stops, as when no output device runs, freezes the picture), and redraws about 60 times a second (`frames` thread queueing one redraw at a time on the main thread).
- Stage host: a picture is drawn from its first play's sample; its position follows the clock from its play (or holds while paused; a change dated ahead of the clock keeps the run before it until then); a stop fades its opacity to 0 over the fade, then it goes. Pictures on one stage are drawn earliest-started first, so the later-started is on top, each fitted to its stage (shape kept) over the stage's black. Opacity uses Metal blending (`Quad.tint.a`).
- Decode (`media.rs`): each picture has a decode thread of its own (`openlab-stage-decode`) that owns its file: `load` starts it and returns at once. A still is decoded once through ImageIO; a movie is read in order with AVFoundation's asset reader, its open including the frame at the load's offset.
- The stage host says `picture_opened` when that is done. The main thread posts the position it wants (the newest only) and takes the newest decoded frame from a one-slot mailbox (a newer frame replaces one not taken: dropped, never queued), uploads it and draws.
- On real displays the main thread asks for the frame due at the next refresh (`FRAME_AHEAD`, 1/60 s) and draws what is ready, never waiting; an offscreen probe waits for the frame at the clock exactly (within the limits below), so tests are exact.
- The frame shown is the last whose time is at or before the position. A position more than one frame behind the frame held, or more than `SKIP_AHEAD` 2 s past it, starts reading there; a smaller step back (the clock corrected by a few milliseconds) holds the frame and never restarts the reader (`BACK_HOLD_FRAMES`).
- Limits (`media::LIMITS`): an open over 10 s or a frame asked for and not decoded within 5 s fails that picture alone ("took longer than"); tests shorten them with the test-support `--media-limits OPEN_MS,FRAME_MS` after `--virtual-displays`. A decode thread stuck in the platform's code cannot be stopped: it is let go (it ends by itself if the call ever returns), and at most `MAX_DECODERS` (512) decode threads may be alive, past which a load fails ("too many pictures are still being read").
- Memory per picture: a still holds its pixels once while decoding, then one texture; a movie at most five frames of its size (two textures, the mailbox, the frame in hand on the decode thread and the one read past it) besides the platform decoder's own buffers; a picture is at most `MAX_PICTURE_PIXELS`, checked before anything of its size is allocated (a 1080p movie: about 40 MB; the largest picture: 1.25 GiB).
- Each picture has two textures: a new frame goes into the one not drawn last, and only once the command buffer that last drew from it is done, so a frame never changes under the GPU (no tearing); until then the frame waits in the mailbox.
- A reader failure, or frames that run out more than two frames before the movie's length, is a failure: `picture_failed`, reported when the main thread next polls (every frame-loop tick, or 16 ms offscreen), the picture dropped; the engine breaks only that cue (`decode_failed`, notice `video_decode_failed`). A file that cannot be played at GO is `StartFailed` (`video_unplayable` notice).
- A load or GO whose file's probe has not answered (just after the show opened, or the file was set, relinked, changed or came back: the catalog's `probing`) waits as an Audio cue's does (`Pictures::held`): nothing goes to the stage host, `probe_wait` once for a start.
  - On the answer (`release_pictures`, from `flush_media`) it loads, and a start plays at `max(start, now)` from its head with `cold_start`, the delay counted into its `ActionLength`.
  - A pause holds it (the answer then loads without playing), a stop or unload drops it. A failed answer breaks it (`video_unplayable`); a start held past `PROBE_HOLD_LIMIT` (sample time) is `StartFailed { decode_failed }` with `probe_timeout`, broken until reset like an Audio cue's.
- A picture whose stage is removed while it plays is reported failed too (its cue would otherwise run on unseen).
- Progress: a Video cue's run is not a mixer voice and has no action timer, so `reports` adds `picture_progress`: elapsed from its play's sample plus its offset (load to time), held at the pause's offset while paused, `remaining` from its length (none for a still without a duration), `position` the seconds into a video's file.
- Why a stage host stopped: `StageEvent::Stopped { crashed }` is true only when it ended by itself with a fault signal (SIGILL, SIGTRAP, SIGABRT, SIGFPE, SIGSEGV, SIGBUS, SIGSYS) or a failing exit status (a panic). A kill by the supervisor (not answering, not reading, flooding) or from outside (SIGKILL, SIGTERM) is not a crash. The supervisor waits up to `EXIT_WAIT` (200 ms) after its output closes for its exit status.
- Only a crash can be a picture's doing, and only a picture with a decoder running (`pictures_host_stopped`): one not yet open, or a movie playing (inferred from the engine's last messages: a still once open, and a movie paused or not yet played, have none). Those are suspects; other stops change nothing and every picture comes back.
  - A suspect at a second crash within `SUSPECT_WINDOW_S` (60 s of the engine clock) that is the only one is the culprit: its cue breaks.
  - Several such suspects are held back (kept off the stage host, cues running unseen) and tried again alone, one at a time, the latest suspected first (`try_held_back_pictures`, each tick). A crash within `PROBATION_S` (5 s) of a trial breaks that picture's cue; a trial that passes clears it.
- A stage host that starts (after a crash too) is sent the clock and every picture's load, first play and last play/pause/stop again (`resend_pictures`), so a picture comes back where the clock is (a paused one on its held frame, in its place in the stacking) while its cue keeps running. Picture messages are written only to a stage host that has answered `hello` and has its stages.
- Tests (`tests/video_cues.rs`, real engine, offline driver, virtual display; `ControlConfig::picture_probe`, test support, wraps the real probe to hold an answer back):
  - a GO waiting for its probe (played late, paused, stopped, failed, timed out), relink of a Video cue's file, a still until stopped and for its duration, a movie in step from its first frame to its last and its end, pause holding the frame and resume, load to time, two cues stacked, panic fading, a cut-short movie breaking only its cue, a killed stage host (a paused picture comes back on its frame);
  - an open or a frame decode that hangs (test-support fault switches in the decoder, by file name: `openlab-test-hang-open`, `-hang-decode`, `-crash-open`, `-crash-decode`; never in a shipped stage host) failing only its cue while the stage host answers and its keep-black stage stays black, a decoder crash on open and later, a still too large to hold.
  - `media.rs` unit tests: a failed open reported when polled, a small step back holding the frame.
  - Not yet measured on the 2014 Mac mini target (two 1080p cues).

## The engine side (`openlab-engine` `stage.rs`, `control/stages.rs`)
- `stage::StageHost` is the supervisor: thread `openlab-stage-link` spawns the stage host (own process group, stdin/stdout/stderr piped), with a writer thread (bounded queue of `WRITE_QUEUE` lines; full means the child stopped reading: killed), a reader thread (`read_line` + `decode_from_stage`; bad lines become warnings, at most `MAX_BAD_LINES_LOGGED` per child) and a stderr thread (first `MAX_STDERR_LINES` lines to the log).
- A `stage_status` for a stage the stage host was not given is dropped (supervisor), and the control thread keeps states only for stages it sent, so child input cannot grow engine memory.
- Report log lines (stage states, displays, the stage host's `log`) go through `Engine::report_line`: at most `MAX_REPORT_LINES_PER_SECOND` (20) a second by the control loop's clock, the rest counted and said as one warning on the first tick after that second (`flush_report_lines`), quiet or not; the supervisor also caps `log` messages at `MAX_LOGS_PER_SECOND`. A `displays` list equal to the last is not logged again. A message that fails to encode is logged as an error.
- Health: `hello` must be answered within `hello_within` (20 s: a cold start on a loaded machine or a slow disk is not a hang) and every `ping` (each `ping_every`, 1 s) within `answer_within` (5 s); a child that does not, sends more than `MAX_LINES_PER_SECOND`, or closes its output is killed (reaped on a thread of its own) and replaced at once with the last stage set.
- Starts older than `restart_window` are forgotten before a crash is counted (`forget_old_starts`), so a crash after a long healthy run is relaunched at once. More than `max_restarts` (5) starts in `restart_window` (60 s) pauses video output for `retry_after` (30 s), logged as an error. A stage host of another link version is never started again.
- `StageHost`'s drop sends `quit`; the stage host gets 1 s, then is killed. Its stdin closing also ends it, so it never outlives the engine however the engine ends.
- The control thread: `sync_stages` (every tick) builds every open doc's stages with this machine's display ids and hands the set to the supervisor when it changed. An idle tick compares only each doc's stages and a count of display-choice changes (`Stages::synced`, `mappings`) and does no more. The stage host starts with the control loop (`Control::empty`), so its displays are known when a new workspace is made. A changed stage's state is forgotten until the stage host reports it again.
- `StageEvent`s arrive through the inbox (`Inbox::Stage`): states and displays are kept for `list_stage_mappings`/`list_displays`; a state a stage cannot be seen in (`no_display`, `display_missing`, `failed`) is a `warn` log line, `shown`/`hidden` `info`; a stop is `warn` (restarting) or `error` (paused).
- An engine on the virtual device (`--virtual-device`) runs a stage host only with `--virtual-displays ID:WxH,...` (test-support builds), passed on to it: test engines never open windows on the machine's displays, and their scripts stay deterministic.
- Where the stage host is: `Contents/Helpers/openLab Stage.app/Contents/MacOS/openlab-stage` beside the engine's `Contents/MacOS`, else `openlab-stage` beside the engine (development). Missing: video output off, one `info` log line at start (a build or development engine without it is not a show fault). Tests set `ControlConfig::stage_host`.
- A new workspace gets one stage per listed display (QLab 5 manual p. 226): "Stage 1", "Stage 2"... in display order, sized as the display, keep-black off, each shown on its display on this machine (`Engine::add_display_stages`, from `fresh_workspace`).
- Push: `push_video_outputs` (every tick) sends each workspace's connections `video_outputs { displays, video?, stages }` when a report, a stage set or a display choice changed, as a state message, at most once per `PUSH_EVERY_MS` (100 ms) by the control clock.
- A doc connection's `snapshot` request (the bind's too) has `video_outputs` pushed at once, right after the snapshot's reply and whatever the gap (`Control::push_doc_video_outputs`; at the next tick only if the outbound channel was full), so a connection that binds after the last push has it.
- That push goes out before anything handled after the snapshot, so a message taken in the same wake (a client's first GO) cannot put its broadcasts ahead of it; the order would otherwise depend on how fast the client spoke. A broadcast, never a reply: a connection writes broadcasts ahead of replies, and a reply could land after a newer push. The app keeps it in `WorkspaceStore.videoOutputs` and draws it on the workspace settings Video page (skill `mac-app`).
- Requests (`docs/protocol.md`): `list_displays` (app-scope), `list_stage_mappings`, `set_stage_mapping { stage, display? }` (the display must be listed now; stored in `settings.json`, refused `io` when settings cannot be saved).

## Tests
- Test support only (never in a shipped stage host: `scripts/rust-checks.sh` checks): `--virtual-displays ID:WxH,...` runs offscreen with those displays and no windows.
- `test_card` draws the test card (`card.rs`: a white guard cell, the frame number's 16 bits, a white guard cell across the top tenth; red, green, blue, yellow quadrants); `probe` draws the stage offscreen (at most 1024 px a side, the stage's shape) and reads colours back; `probed` carries the barcode's frame (or none) and the asked points' RGBA.
- Tests assert what a stage shows by reading the barcode and a few point colours: never a stored image, never a hash.
- `tests/output_window.rs` (its own `main`, on the main thread) builds the shipped output window for the main screen's frame without ordering it front and checks level, collection behaviour, never key or main, mouse ignored, no shadow, borderless, frame equal to the screen's, not visible. Without a screen it reports a skip (a failure on CI).
- `gpu.rs` tests draw on the machine's GPU (they fail, not skip, without Metal); `displays.rs` tests read the real display list and open no window. No test opens a window.
- Real-engine tests: `engine/crates/video/tests/stages.rs` (macOS) runs the control loop on the offline driver (the engine's `tests/show` helpers) with the real test-support stage host (`CARGO_BIN_EXE_openlab-stage`, `--virtual-displays`) and reads stages back with `stage_probe`.
- Covered there: black, the test card, display choice, no display, keep-black off, a display unplugged and back mid-cue, a killed and a hung stage host replaced while a cue's sound plays on, the stage host gone after shutdown.
- Also covered there: the windowed stage host exiting when its input closes, a SIGKILLed test engine leaving no stage host, a crash after a long healthy run relaunched at once (injected `StageClock`), a reporting burst bounded in log lines and memory, and `/bin/sh` stand-ins for a flooding, a log-bursting and a silent stage host. `OfflineShow::settle_stages`, `wait_for` and `send_until` wait on the stage host (hang guards).
- The link codec is fuzzed: `fuzz/fuzz_targets/stage_link.rs`, body `fuzz/src/stage_link_input.rs`, run on stable by core's `tests/fuzz_stage_link.rs` over `fuzz/stage-link-seeds`.
