# Video (stages and the stage host)

QLab 5 model: manual pp. 207-212 (Video cues), 225-230 (stages), 241-243 (Fade cues).

Design decided by the user on 2026-11-13: decode and drawing live in a third process, the stage host; macOS decodes with AVFoundation/VideoToolbox (HAP in-house) and draws with Metal; video follows the audio clock; no video on Windows in v0.0.2.

Built so far: stages, their per-machine display, the stage host with black output windows, its supervision by the engine, the test card read back in tests, and the Video cue's model, file format, commands and problems (`CueKind::Video { media, stage, duration, geometry, timing, sound }`; skills `cue-engine` (its kinds reference) and `edit-commands`).

Probing Video cues' files and playing their pictures on stages in step with the engine's clock are built (below), and the app's Video cue (toolbar, drops, I/O tab; skill `mac-app`). Geometry is built (below), time and loops (below) and the sound of a movie's audio track through the mixer (below; the app's Levels tab, sound-format line, track and patch pop-ups: skill `mac-app`). Fade cues on pictures are built (below).
HAP, HAP Alpha and HAP Q movies play (below). Monitor windows are built (below). Not built: HAP's other flavours (HAP Q Alpha and the rest), effects and blend modes, a Fade's 2D path, 3D rotation and fading the rate.

## Must not break
- A stage with keep-black on, its display connected and its black up (below) shows black whenever nothing plays on it, never a frozen frame (VID-12). The stage host draws that black while it runs; in its gaps (the engine's death until a relaunched engine's stage host is up, a stage host crash or kill until its relaunch, about 150 ms, the whole `retry_after` pause after repeated crashes) the app's black backstop shows instead (below).
- The engine links no GUI framework and no video decoder. Everything that touches windows, displays, the GPU or (later) media is in `openlab-stage`, so a crash or hang there never stops sound.
- Every line crossing the link is validated on both ends (`stage_link::decode_*`): a bad line is a warning, never a panic, a hang or unbounded memory.
- The stage host exits when its stdin ends, so it never outlives the engine.
- The stage host never activates or takes key focus: the operator's keys stay with the app.

## Stages (`openlab-core` `video.rs`, `model.rs`)
- `Workspace.stages: Vec<Stage>`: `id` (`StageId`), `name`, `width`/`height` in pixels (1 to `MAX_STAGE_PIXELS` 16384, p. 208), `keep_black` (QLab's "keep rendering between cues", p. 227; default on, and for a file without the key: user 2026-11-19, skill `qlab-behaviour` Q286). At most `MAX_STAGES` (64). File format §4.7.
- A stage's black is up only once a picture has played on it since its workspace opened (or it was added), and until a panic (p. 227: kept until quit or panic): the engine's `Stages::armed` (`arm_stage` at a picture's first play or a test card; `release_stages` at a panic, with nothing playing too). Otherwise it is sent as `keep_black` false: hidden once its pictures have faded, and no display covered before the first picture (#708).
  - Clients see `panicked` in `video_outputs` and `list_stage_mappings`; the app's backstop leaves such a stage's display.
  - `Control::new` (tests and the offline driver: a show already running) arms its starting workspace's stages; `open_doc` (the app's New, Open and reattach) starts every stage disarmed. An engine relaunched after a crash therefore comes back with its stages' black down until their next picture.
- Removing a stage a Video cue is loaded, pre-waiting, playing, paused or stopping on is refused (`DocCx::stage_removal_refused`, `CommandError::StageInUse` naming stage and cue): a command, a transaction, an undo or a redo step. A live picture counts by its load's stage (`Engine::cue_with_picture_on`): a cue aimed elsewhere mid-run keeps its picture there (Q572). With its cues idle it goes (Q300).
- `layer` 0-1000 (default 1): of stages on the same display, a higher layer is drawn on top; on one layer the name sorting first is on top (p. 227; `stack_order`). Edits: `AddStage`, `RemoveStage`, `MoveStage`, `SetStageProperty` (skill `edit-commands`).
- Load: a size of 0 or above 16384 is clamped (`StageSize` warning), a layer from 1001 to 65535 too (`StageLayer`); a negative, fractional or out-of-type number refuses the file as a wrong type; stages past 64 are dropped (`TooManyStages`), two with one id refuse the file (`DuplicateStageId`), odd names warn (`stages.name`).
- Which display shows a stage is per machine: `settings.json` `workspaces.<id>.stages.<stage id>` = `StageMapping { display, name, width, height }` (the display's id plus what it was when chosen). `MachineSettings::stage_mapping` / `set_stage_mapping` (refuses empty or over-long text, control characters, sizes out of range). A damaged entry in the file drops only itself with a warning.

## The link (`openlab-core` `stage_link.rs`; contract `docs/protocol.md` "Stage host link")
- One JSON object per line; `LINK_VERSION` 5 (2 added picture geometry, 3 a picture's plan, action time and fades, 4 `ramp`, 5 monitor windows); lines at most `MAX_LINE_BYTES` (1 MiB: a full `MAX_LINK_STAGES` set with the longest display ids and monitor titles fits; tested).
- `read_line` (both ends) reads again after a read a signal interrupted (`ErrorKind::Interrupted`): only the end of input or a real error ends the link.
- Engine to stage host (`ToStage`): `hello`, `stages` (the full set, replacing the last: id, size, display id or none, keep_black, monitor title or none), `ping`, `quit`, `raise_monitor`, the picture messages (`load` with its `geometry`, `geometry` for an edit while it is up, `ramp` for a value a Fade cue moves); test support `test_card`, `probe`, `hang`, `set_displays` (virtual displays plugged or unplugged), `probe_monitor`, `close_monitor_window`.
- Stage host to engine (`FromStage`): `hello` (version, pid, `video`: false where the build has no video output), `displays` (after hello and on every change), `stage_status` (`shown`, `hidden`, `no_display`, `display_missing`, `failed`), `pong`, `log`, `monitor_closed`; test support `probed`, `display_probed`, `monitor_probed`.
- Limits checked after parsing: at most `MAX_DISPLAYS` (32) displays and `MAX_LINK_STAGES` stages, text 1 to `MAX_TEXT_BYTES` (512) bytes without control characters, sizes 1 to 16384, probe points 1 to 64 inside the stage.

## The stage host (`engine/crates/video`, binary `openlab-stage`)
- `host.rs` is the same on every platform: `Host<P: Platform>` keeps the stages, the displays and each stage's state. A stage is shown only with its display connected and (while black) keep-black on; otherwise hidden with the reason. `serve` reads lines with `read_line` (never holds more than one line's limit; an over-long line is skipped and reported) and ends at end of input or a failed write.
- The stages shown on one display are drawn in one window (per display, not per stage), bottom first by `stack`; a stage keeping black is a black quad over what is below it. Test support `probe_display` reads a display's composite.
- `Platform::present` answers `Presented::Drawn`, `Presented::Skipped` (window up, no drawable for this frame: the mac layer's `nextDrawable` timed out under GPU load) or an error.
  - A skip keeps the window and its last frame, marks nothing failed, warns once per stretch (`Host::skipping`, reset by a drawn frame or the window closing) and sets `redraw_due`, so the next poll draws again though nothing plays. A stretch past `SKIP_LIMIT` (3 s), or an error, fails the display's stages and closes its window. A monitor window skips the same way, silently.
- After a `stages` message the host reports every stage's state (so the engine knows each was dealt with); after a display change only the states that changed.
- macOS (`platform/mac`): an accessory app (no Dock icon or menu bar) whose windows come up with `orderFrontRegardless`, borderless, never key, ignoring the mouse, over the display's whole frame, on every Space, out of Mission Control and window cycling. Never system full-screen.
- Output window level: screen-saver on every display, the one with the menu bar (a laptop's only one) included: a stage covers its whole display over every app's windows, the menu bar and the Dock (user 2026-11-19, Q298). The window is never key, so the app keeps the keys: Esc (panic, which takes the black down) and the transport keys act while its windows cannot be seen.
- Stand back (#708): the window on the display with the menu bar (`Platform::menu_bar_display`) drops under every app's windows (normal - 1, over the desktop), drawing what it drew, nothing stopping, while the app has a question up (`set_stand_back`, `ToStage::StandBack`; resent to a relaunched stage host, reset when the last app connection ends) or the stage host has heard nothing from the engine for `ENGINE_SILENCE` (4 s, four missed pings; `Host::check_silence` from every poll; one warn log).
  - Any word from the engine, or the question answered, covers again. Other displays never stand back.
  - Pings go only when the control thread has said it runs since the last (`StageHost::alive`, from each tick at most every 250 ms), so a hung control thread silences the stage host though the supervisor thread runs on. Test support: `--menu-bar-display ID` (or `*` after a display in the `--virtual-displays` list) and `--engine-silence-ms MS`; `OfflineShow::handle_next_within` takes reports without ticking. The stand-back level is not read back offscreen (a log line says each change).
  - While no alive mark has come, the next ping is no deadline (`stage::ping_deadline`): the supervisor sleeps until an order, a line or a ping's answer time, and the next `Alive` sends the overdue ping at once. A ping already out keeps its answer time.
- The app's own window levels are never raised to get over a stage: its menus, pop-ups and sheets would end up under it.
- AppKit and Metal live on the main thread; a reader thread decodes lines and queues them on the main queue.
- The main thread never opens or decodes a picture's file (below), so it always answers `ping` and keeps every other stage drawn. Offscreen (test support) the host loop runs on the main thread with a reader thread feeding it (`host::serve`), polling pictures every 16 ms between messages. At the end of input (or a failed write) the process ends with `_exit` from whichever thread sees it: no exit handlers or stdio flush, so a hung main thread cannot keep it alive.
- Displays: CoreGraphics' active list, named by ColorSync's display UUID (stable across restarts and reconnection), pixel size from the display mode, name from AppKit's screen (else "Built-in Display" / "Display N"). A reconfiguration callback re-reads them and moves every stage, and reads them once more `SECOND_DISPLAY_READ` (500 ms) later, in case AppKit's screen list had not caught up (a re-plugged display would otherwise stay missing until the next display event).
- Drawing (`gpu.rs`): Metal clears the stage to black and draws each picture as a quad placed by core's `quad` (its geometry), clipped to its stage by a scissor rect, smooth or nearest-neighbour by its `smooth`, its premultiplied colour scaled by opacity (fade times geometry) and blended over, so a transparent pixel of the file stays transparent. A stage of another shape than its display is fitted, shape kept, black bars elsewhere (assumed; see skill `qlab-behaviour`).
- Alpha: stills decode premultiplied; a movie frame whose `kCVImageBufferAlphaChannelModeKey` says straight (AVFoundation does for ProRes 4444) is premultiplied on its decode thread (`media::premultiply`); one that says nothing is taken as opaque or premultiplied.
- HAP textures are drawn as they are, each quad told how its texture holds colour (`gpu::Colour`, the shader's `mode`): HAP's DXT1 (BC1) opaque (an RGB format: a three-colour-mode block's transparent texel draws black), HAP Alpha's DXT5 (BC3) straight alpha multiplied in by the shader, HAP Q's scaled YCoCg in DXT5 turned into opaque RGB by the shader (the format's published conversion), so opacity and blending work as for every other picture.
- Other platforms (`platform/none.rs`): `video: false`, no displays, every stage `failed` with the reason.

## Probing Video cues' files (`openlab-engine` `stage_probe.rs`; stage host `platform/mac/probe.rs`; core `video_probe.rs`)
- The engine never opens a video file or still: a probe worker (never the control thread) runs `openlab-stage --probe <file>` as a throwaway process, kills it after `PROBE_PROCESS_LIMIT` (20 s; test support: `ControlConfig::picture_probe_limit`), and validates its one line (`decode_probe_report`).
- A decoder that crashes or hangs on a hostile file takes only that process; the stage host drawing the show never opens an unprobed file. No stage host configured: every picture probe is `unsupported` ("no video output").
- Why not in the drawing stage host: a crash there would black out every stage mid-show; why not in the engine: the engine links no decoder.
- The answer is the probe's first line, believed as soon as it is read: the engine never waits for the probe's output to end (a process holding that pipe open would keep a good answer back until the limit, and the cue would be broken as "could not be read in time").
- Every process the engine starts (stage host, probe, the app's relaunch) goes through `platform::spawn::spawn`, one at a time: on macOS a pipe is made and marked close-on-exec in two steps, so a child started in between by another thread inherits it. A stage host that inherited a probe's output pipe held it open for its whole life; one that inherited another's input pipe would not see its engine end.
- Picture size: at most 16384 a side and `MAX_PICTURE_PIXELS` (67,108,864: a quarter of the largest stage, so 8192 x 8192 or a 16384 x 4096 panorama, 256 MiB as BGRA) in all, for stills and movie frames (`picture_size_plays`, checked by the probe, the probe line's decoder and the stage host before it allocates).
- macOS probe, stills: ImageIO (PNG, JPEG, TIFF). ImageIO decodes lazily, so the probe copies the image's data, which decodes every pixel: a PNG or TIFF damaged past its header gives none and is `unsupported` ("damaged"). A cut-short JPEG decodes to grey without an error, so a JPEG must also have its end-of-image marker after its last scan. Damage inside a JPEG's scan data that leaves its structure whole is not detected (it shows as noise).
- macOS probe, movies: AVFoundation reads the first video track's four-character code (`avc1`/`avc3` H.264, `hvc1`/`hev1` HEVC, `apco`..`ap4x` ProRes, `Hap1` HAP, `Hap5` HAP Alpha, `HapY` HAP Q), natural size, nominal frame rate and the asset's length, and decodes the first frame (a HAP movie's is read and unwrapped as the stage host reads it, `media::hap_first_frame`: no platform decoder reads HAP).
  - A movie cut short in its picture data whose index survives therefore probes playable (its frames run out on stage and the cue breaks then); only damage to the index, or a first frame that does not decode, is caught here. Which a given cut is depends on the encoder's output sizes, so tests cut inside the index for "unsupported" and accept either answer for a cut further in.
  - HAP's other flavours (`HapM` HAP Q Alpha, `HapA`, `Hap7`, `HapH`) are reported unsupported by name (QLab 5 lists HAP, HAP Alpha and HAP Q, manual pp. 209-211); a HAP movie whose first frame is damaged is unsupported with the reason.
- Anything else is `unsupported` with a reason naming the codec or format.
- The media catalog tracks a Video cue's file like an Audio cue's (`media_use` gives its kind; `Entry::picture`; `Probe::Picture`; `ProbeAnswer::Pictured`), so missing-file marks, the media watch, the stalled-volume gate and relink all apply unchanged. A file used by an Audio and a Video cue is probed as the kind that asked first (the other cue cannot play it).
- Tests: `tests/video_cues.rs` makes media with the test-support `--make-test-media` (AVFoundation's software encoders, hardware encode off; ImageIO; frames are the test card for their own number). HAP movies (`hap`, `hap-alpha`, `hap-q`; `@<n>`: frames from `n` damaged) are made by openLab's own HAP frame writer (`hap::write`, test support) and passed through AVFoundation's writer as they are.
  - `~still:<n>` after a codec holds the last frame `n` frame periods (a screen recording's still tail), `~sound:<n>` runs the sound tracks `n` periods past it (#770).
  - Each kind of file is made once per test process (`fixture`, one at a time) and copied into each test's folder: a CI virtual machine's paravirtual video hardware failed encodes and decodes intermittently while several tests ran.
  - `--make-test-media` and `--test-decoder` run with a bounded wait (`spin::output_within`, 120 s): a stalled framework fails that test, naming the command, instead of holding the run.
  - Tests that play a movie take it through `movie!`: in a codec that decodes reliably here (`decodes_reliably`: software, as the test-support `openlab-stage --test-decoder <file>` reports VideoToolbox picks, or hardware outside a virtual machine), H.264 first. With none, or the codec a test names not reliable, the test records a skip in the file `OPENLAB_TEST_SKIPS` names and ends; without that variable it fails.
  - `scripts/rust-checks.sh test` (and its release modes) sets it and, after the run, passing or not, prints each codec's decoder (hardware or software, in a virtual machine or not) and a `SKIPPED n test(s)` list. Movies are only played by these tests: if every codec is hardware in a VM, no movie plays on that machine.
  - Why: on a CI virtual machine the paravirtual decoder failed ("Cannot Decode") and stalled good movies past the 5 s frame limit. The limits stay on the real clock there: a stalled decoder is what they catch.
  - Every limit a slow but working media framework can trip is six times the shipped one in these tests (test-support settings; CI virtual machines stalled a good file's open past 10 s, a probe past 20 s, a frame past 5 s): the stage host's good-file limits (`--good-media-limits`), the probe process (`picture_probe_limit`, 120 s) and the pool's watchdog past it (`probe_timeout`, 150 s).
  - Also there: `hello_within` and `answer_within` 120 s, and the offline driver's waits 180 s (`OfflineShow::set_settle_timeout`), past a stage probe at the open and frame limits (90 s). `tests/stages.rs` lengthens `hello_within` and the waits too.
  - The tests that prove a limit fires use fault-switch files with short limits of their own (`--media-limits`, below); damaged and mutated files are probed within the shipped limit (any answer passes there).
  - Failures of `on_stage` and `expect_state` print what the engine saw (`seen`: pictures up and open, given-up waits, the show log's tail).
  - It probes every codec and still format, damaged and seeded-mutated files (bounded by the probe limit), and Video cues on the real engine (probe problems, the media watch).
  - The probe line is fuzzed with the link (`fuzz/src/stage_link_input.rs`, seeds `fuzz/stage-link-seeds/probe_reports.jsonl`).
  - HAP movies decode the same on every machine (no platform decoder): their tests do not go through `movie!`. A Mac whose GPU cannot sample BC textures fails a HAP picture ("cannot draw HAP movies"); the HAP tests then fail, not skip.

## Playing pictures (`openlab-engine` `control/pictures.rs`; stage host `host.rs`, `platform/mac/media.rs`, `gpu.rs`)
- The cue engine runs a Video cue's picture as a voice. `DocCx::execute` sends a Video cue run's voice actions to `picture_action` (not the mixer's voices): load, play, pause, stop (with its fade), unload on the stage host, each picture an id of the engine's (`Pictures`). Each is passed on to the run's sound, if its movie has any (Sound, below); a devamp is carried out on the picture's plan (time and loops, below).
- The run's length (a video's from the probe, a still's typed duration; none for a still without one) is told at its start as `ActionLength`, so the cue ends on its last frame's sample. A cue whose action is over (`StateChanged` to idle, post-wait or broken) has its picture stopped on that sample (`end_pictures`).
- A stop's end (its fade) is a deferred `ActionEnded`. A stop fading past the end of a playing movie's action (its end trim, or a pending devamp's stop at the end of its pass; not hold at end) fades picture and sound together until that end, where the `stop` carries a `cut` (`stop_picture`): picture, sound and the cue's state end on that sample (skill `qlab-behaviour`).
- A devamp of a movie's loop sends the plan again with the pass under way the loop's last; with "stop target" nothing follows it and the cue is told that end, and that end takes the picture (`end_pictures`).
  - No stop is dated ahead for it: a pause before the pass ends keeps the picture on its frame however long it lasts, and the resume (which asks for the devamp again) moves the end by the time paused, for picture and sound alike.
  - A stop whose fade would end after the pass fades the picture with its sound until the pass's end, and ends both and the cue there.
- The clock: `clock { sample, rate }` at least every 10 ms of samples while a picture is up (`picture_clock`, each tick), before every play and before a test probe.
- A routine clock (not one before a play or probe) goes as `Order::Clock`: dropped while the stage host's write queue is half full, so a burst (an offline test running ahead of real time, a stage host busy for a moment) never fills it and gets the stage host stopped as not reading.
- Offscreen the host's poll between messages also redraws (as the windowed frame loop does), so a stopped picture goes and its stage is hidden or kept black; a test probe redraws first, so states it changes are reported ahead of its answer.
- Offscreen the stage host draws at the last clock exactly; on real displays it moves the clock on by its own clock, at most `CLOCK_HOLD` (30 ms, three clock periods) past the last `clock` (a clock that stops, as when no output device runs, freezes the picture), and redraws about 60 times a second (`frames` thread queueing one redraw at a time on the main thread).
- Stage host: a picture is drawn from its first play's sample; its position follows the clock from its play (or holds while paused; a change dated ahead of the clock keeps the run before it until then); a stop fades its opacity to 0 over the fade, then it goes (on its `cut` sample if that comes first). Pictures on one stage are drawn lowest layer first, then earliest-started first (the later-started on top), each placed by its geometry over the stage's black.
- Decode (`media.rs`): each picture has a decode thread of its own (`openlab-stage-decode`) that owns its file: `load` starts it and returns at once. A still is decoded once through ImageIO; a movie is read in order with AVFoundation's asset reader, its open including the frame at the load's offset. A reader is opened a frame before where it is wanted (`open_reader`): AVFoundation starts at the first frame dated at or after a range's start, which would skip the frame on show there.
- HAP (`hap.rs`, platform-free): the reader passes the samples through as stored; each frame (bounded by `max_frame_len` before it is copied) is unwrapped on the decode thread: its section header, Snappy (`snap`) whole or in chunks, every length checked against the texture a frame of its size must be before that is allocated. The texture goes up as BC1 or BC3 (rows of 4 x 4 blocks).
  - A frame that does not unwrap is a reader failure (reopened once, then the cue breaks, the reason saying "HAP frame is damaged").
  - Memory: a HAP movie's frames are its textures (an eighth of BGRA for HAP, a quarter for HAP Alpha and HAP Q), plus one frame as stored while it is unwrapped.
- A reader's first read passes over any frame before the one on show at its place without copying it (`read_from`), so a primed seam or a jump copies no more frames than a reader opened at the place would.
- The stage host says `picture_opened` when that is done. The main thread posts the position it wants (the newest only) and takes the newest decoded frame from a one-slot mailbox (a newer frame replaces one not taken: dropped, never queued), uploads it and draws.
- On real displays the main thread asks for the frame due at the next refresh (`FRAME_AHEAD`, 1/60 s) and draws what is ready, never waiting; an offscreen probe waits for the frame at the clock exactly (within the limits below), so tests are exact.
- A picture standing still (paused, without a plan, or its plan over: `CuePicture::held`) is asked for its own frame, not one a refresh ahead, so a pause within a refresh of the end trim never shows the frame past it. A pause keeps the plan's pass it paused in, so its decoder sees no loop seam and never reads again for it.
- The frame shown is the last whose time is at or before the position. A position more than one frame behind the frame held, or more than `SKIP_AHEAD` (0.5 s) past it, starts reading there (a jump, or a decoder that fell behind skips to the clock instead of showing every late frame); a smaller step back (the clock corrected by a few milliseconds) holds the frame and never restarts the reader (`BACK_HOLD_FRAMES`).
- Limits (`media::LIMITS`): an open over 10 s, or a frame asked for with no frame read for 5 s (the limit runs from the decode thread's last frame read, so a slow decoder that keeps going is waited for and only a stalled one fails), fails that picture alone ("took longer than"). An open past its limit names what it was doing (reading the image, reading the movie's tracks, decoding its first frame), so a stall on a show machine or a CI runner says where it stopped.
- The decode thread also fails a frame it reads past the frame limit since the last one (what the main thread would have found polling in between).
- Tests set the limits after `--virtual-displays` (test support; options in any order, each at most an hour, shipped unless given): `--media-limits OPEN_MS,FRAME_MS` (shorter) for the files a fault switch names, `--good-media-limits OPEN_MS,FRAME_MS` (longer) for every other file.
- With `--media-clock-by-hand` the limits run on a media clock only the test moves (`advance_media_clock`, `Control::advance_stage_media_clock`; each slow-decode frame moves it 400 ms), so the hang and slow-decode tests never depend on the machine's speed.
- An offscreen probe does not wait for a file whose fault is a hang, and waits at most `PROBE_GUARD` (60 s) of real time for any picture, or its open and frame limits together if longer (test support). A decode thread stuck in the platform's code cannot be stopped: it is let go (it ends by itself if the call ever returns), and at most `MAX_DECODERS` (512) decode threads may be alive, past which a load fails ("too many pictures are still being read").
- Memory per picture: a still holds its pixels once while decoding, then one texture; a movie at most six frames of its size (two textures, the mailbox, the frame in hand on the decode thread, the one read past it, and a looping movie's next pass's first frame) besides the platform decoder's own buffers; a picture is at most `MAX_PICTURE_PIXELS`, checked before anything of its size is allocated (a 1080p movie: about 40 MB; the largest picture: 1.25 GiB).
- Each picture has two textures: a new frame goes into the one not drawn last, and only once the command buffer that last drew from it is done, so a frame never changes under the GPU (no tearing); until then the frame waits in the mailbox.
- A reader that ends cleanly holds its last frame to the cue's end, however far before the movie's length (a still tail, a longer sound track; #770): no read again past it, and a reader opened past it (load to time, re-open, a seam, a restarted stage host) reads back for that frame (`Movie::last_frame_before`). A file cut short or damaged under the reader makes the reader fail; that is never taken for an end.
- A movie's reader that fails after its open (an error from the reader) first gets the movie opened again (`media::reopen`), on its decode thread: a fresh asset and reader at the newest position asked, that position answered from it. A brief decoder fault or a media-services reset then costs a held frame, not the cue.
  - Once per failure: the movie opened again may be opened again at a later failure only after it has read `REOPEN_SETTLE` (10 s) of frames. A damaged file fails again at once and is reported; a failure at the open is never retried. Bounded in time by the frame limit of the position waiting (the main thread fails it past that).
  - One `warn` `log` line per re-open (file name, position, the reader's error); the cue is not told. A stage host that restarts loads the picture afresh, allowance and all.
  - Same decoder: AVFoundation's asset reader has no supported switch to software decode (VideoToolbox takes one only for a session of its own), so the system picks the decoder again.
- A reader failure the re-open did not cover (not allowed, or it failed too: the reason says both) is a failure: `picture_failed`, reported when the main thread next polls (every frame-loop tick, or 16 ms offscreen), the picture dropped and its display drawn again at once without it (`Host::redraw_due`), never its last frame left up; the engine breaks only that cue (`decode_failed`, notice `video_decode_failed`). A file that cannot be played at GO is `StartFailed` (`video_unplayable` notice).
- A load or GO whose file's probe has not answered (just after the show opened, or the file was set, relinked, changed or came back: the catalog's `probing`) waits as an Audio cue's does (`Pictures::held`): nothing goes to the stage host, `probe_wait` once for a start.
  - On the answer (`release_pictures`, from `flush_media`) it loads, and a start plays at `max(start, now)` from its head with `cold_start`, the delay counted into its `ActionLength`.
  - A pause holds it (the answer then loads without playing), a stop or unload drops it. A failed answer breaks it (`video_unplayable`); a start held past `PROBE_HOLD_LIMIT` (sample time) is `StartFailed { decode_failed }` with `probe_timeout`, broken until reset like an Audio cue's.
- A picture whose stage goes while it plays (removal is refused then, above; this is the backstop) is reported failed too (its cue would otherwise run on unseen).
- When pictures end (`prune_pictures`) the engine sends the clock once more: with none left up no clocks follow, and a stage host held short of a stop's end would keep its frame drawn.
- A start whose picture is not open yet (a GO on a cue neither loaded nor standing by, or one its probe held) waits for `picture_opened`, its first frame decoded (`Live::wait`): nothing is drawn or heard, its sound is loaded meanwhile (unless primed from the top). On the tick after the open, picture and sound start together at `max(start, now)` from the start point, the wait counted into `ActionLength`, `cold_start` notice (`start_waiting_pictures`). So the opening frames are never skipped.
  - Only a stage host that is up with video holds a start: one down (crashed, paused) or a picture held back after crashes plays at once, unseen, as before. A picture failing while it waits is `StartFailed` (`video_decode_failed`; nothing was seen or heard, so its auto-follow fires). `OPEN_WAIT_LIMIT_S` (15 s, sample time; past the 10 s open limit) breaks one the stage host never answers.
  - Meanwhile a pause holds it (nothing sent), a resume waits again from the action's place (sound loaded under the new run), a seek loads the picture afresh at the point and waits there, a devamp is kept until it plays, a stop or panic ends it with nothing shown.
  - One GO's sequence (`pictures/sequence.rs`): the starts of one cue-engine call that starts a picture (a GO and its auto-continues at once, a fire-all group's children) wait together until every picture among them is open; Audio cues' starts are held too, as starts the voices keep waiting (`Voices::apply_gated`): a stop or panic ends one unheard, a pause keeps it until its resume, a level change is queued for its start.
  - Then each starts as long after its dated sample as the earliest was held (spacing kept, by the date the sequence gave it, a sound resumed meanwhile too; `ActionLength` counting the hold; `Voices::open_gate`). A cue the sequence reaches in a later call starts on its own time (skill `qlab-behaviour` Q561).
- Standing by (`pictures/primes.rs`): each doc's first `MAX_PICTURE_PRIMES` (4) Video cues of its prime set (the playhead window, targets, armed hotkeys; any armed idle Video cue with a file and a stage) are loaded on the stage host from their start, never drawn, after each priming pass (skill `engine-control`).
  - One open ahead is asked of the stage host at a time across every doc, most urgent first (a slow disk serves the cue standing by first); when it answers, or the stage host stops or starts, every doc primes again (`Control::reprime`). A prime let go before its open answered still counts until it answers (the stage host's open limit answers a stuck one), then is unloaded.
  - `load_picture` takes a prime the stage host has that opens the same file, stage and point (its geometry sent again if edited); one of the cue from elsewhere is let go.
  - Not opened ahead: a file on a volume the stalled-volume gate holds back (`MediaCatalog::volume_stalled`, skill `media-files`), a file whose open ahead failed, and one that crashed the stage host twice while opening ahead with no other suspect (at most 256 files).
  - A prime opening at a crash is a suspect with the running pictures (`pictures_host_stopped`), counted by file within `SUSPECT_WINDOW_S`; a run's picture of that file takes the count over, and an open without a crash clears it. As the only repeat suspect its file is barred, keeping its count, so its GO breaks at its next crash (three crashes in all). With others, those are tried alone and nothing is opened ahead until the trials end.
  - Primes are sent again to the next stage host one at a time.
- Seek (a click in the Time & Loops timeline): `transport_one` maps the file's time through the cue's plan (`video_seek_point`, `action_at`: first play, nearest trim, a loop that never ends left after one play, past the end trim the end of the last slice's first play so its passes left follow, as Audio's Q401) and feeds core `Input::Seek` with seconds into the action.
  - Core loads an idle or loaded cue there past its pre-wait (as a load to time), starts a pre-waiting one there, and for a started run emits `SeekVoice` with samples into the action, counted from then as the picture's own time (`seek_picture` sets the plan's `late` to 0). `seek_picture` plays the picture on from there (paused: holds the frame there).
  - Its sound (a movie with sound, `sound_info`) moves by the picture's plan, never a file frame: `Voices::seek` with `SeekTo::Plan`, the rest of the picture's table from the point (`rest_of_table`; paused: the table the resume will play). A run whose voice has ended (hold at end) gets one; one held paused waits for the resume; past the plan's end it has nothing and the old voice fades out.
  - A moved sound that swaps in late (its stream slow to fill, at most `SEEK_PRIME_WAIT`) reports it as `Effects::late`: the picture is put back by as much (`picture_late`). Tests: core `video.rs`, `video_cues.rs` (`a_seek_*`).
- Loaded progress: a loaded Video cue (picture loaded, not played) reports its load frame as `position` (`loaded_pictures`), an Audio cue its prepared stream's first frame (`Voices::loaded_at`), beside `elapsed` (time into the action, any loaded cue); `reports` sends those items only with another progress message or when the set changed.
- Progress: a Video cue's run is not a mixer voice and has no action timer, so `reports` adds `picture_progress`: elapsed from its play's sample plus its offset (load to time), held at the pause's offset while paused, `remaining` from its length (none for a still without a duration, a loop, or hold at end), `position` the seconds into a video's file where its plan is (`plan_point`: inside a loop, the loop's pass).
- Why a stage host stopped: `StageEvent::Stopped { crashed }` is true only when it ended by itself with a fault signal (SIGILL, SIGTRAP, SIGABRT, SIGFPE, SIGSEGV, SIGBUS, SIGSYS) or a failing exit status (a panic). A kill by the supervisor (not answering, not reading, flooding) or from outside (SIGKILL, SIGTERM) is not a crash. The supervisor waits up to `EXIT_WAIT` (200 ms) after its output closes for its exit status.
- Only a crash can be a picture's doing, and only a picture with a decoder running (`pictures_host_stopped`): one not yet open, or a movie playing (inferred from the engine's last messages: a still once open, and a movie paused or not yet played, have none). Those are suspects; other stops change nothing and every picture comes back.
  - A suspect at a second crash within `SUSPECT_WINDOW_S` (60 s of the engine clock) that is the only one is the culprit: its cue breaks.
  - Several such suspects are held back (kept off the stage host, cues running unseen) and tried again alone, one at a time, the latest suspected first (`try_held_back_pictures`, each tick). A crash within `PROBATION_S` (5 s) of a trial breaks that picture's cue if nothing else was opening or decoding then (a GO meanwhile, a picture opened ahead), else it is counted with the other suspects; a trial that passes clears it.
- A stage host that starts (after a crash too) is sent the clock and every picture's load, first play, last play or pause, then its stop if it is stopping (`resend_pictures`; a held-back picture's trial sends the same).
  - So a picture comes back where the clock is (a paused one on its held frame, a stopping one where its pauses put it, fading on to its stop's end, in its place in the stacking) while its cue keeps running. Picture messages are written only to a stage host that has answered `hello` and has its stages.
- Tests (`tests/video_cues.rs`, real engine, offline driver, virtual display; `ControlConfig::picture_probe`, test support, wraps the real probe to hold an answer back):
  - a GO waiting for its probe (played late, paused, stopped, failed, timed out), relink of a Video cue's file, a still until stopped and for its duration, a movie in step from its first frame to its last and its end, pause holding the frame and resume, load to time, two cues stacked, panic fading, a cut-short movie breaking only its cue, a killed stage host (a paused picture comes back on its frame);
  - an open or a frame decode that hangs, failing only its cue while the stage host answers and its keep-black stage stays black; a decoder crash on open and later; a still too large to hold.
  - The decoder's test-support fault switches, by file name (never in a shipped stage host): `openlab-test-hang-open`, `-slow-open` (the open takes 300 ms of the hand-moved media clock), `-hang-first-frame` (tracks read, first frame not decoded), `-hang-decode`, `-crash-open`, `-crash-decode`, `-slow-decode` (400 ms of media clock a frame), `-fail-decode-once` / `-again` / `-often` (below).
  - A crash switch aborts (SIGABRT) only once no decode thread is inside an AVFoundation call (a movie's open, frame read, prime or letting go; each is made under `media_call`) and lets none start meanwhile: a client killed mid-call may leave the system's media services stuck for the later tests' probes and opens (seen on the hosted arm64 VM in release).
  - The reader fault switches fail a movie's reader mid-stream: once, again after the re-open, or every 11 s of frames.
  - `media.rs` unit tests: a failed open reported when polled (never opened again), a small step back holding the frame, a reader failure opening the movie again once, a second failure failing it, the allowance back after a stretch of good frames.
  - HAP: `hap.rs` units (every flavour and packing, lying chunk tables, seeded random, cut and mutated frames), `gpu.rs` `hap_textures_draw_their_colours`, and in `video_cues.rs` each flavour probed and played in step, damaged files (first frame, later frames) and seeded-mutated movies probed and played without a stage host crash.
  - A movie opened again mid-play (`video_cues.rs`, named after the flows): the picture back at the clock with one log line, a second failure breaking only that cue, a damaged file (open or every read) breaking with no loop, a movie with sound heard on unbroken and in step after.
  - Offline, each block first waits until no start waits for its picture's open (`OfflineShow::wait_for_pictures`, on by default), so a start plays on the sample it was dated; a test of a slow or hung open turns it off and moves the media clock by hand (`a_video_cue_never_loaded_*`, `the_same_cue_loaded_first_*`, `an_unloaded_cue_whose_file_cannot_be_opened_*`).
  - Not yet measured on the 2014 Mac mini target (two 1080p cues).

## Time and loops (VID-07; `openlab-core` `video_timing.rs`, engine `control/pictures.rs`)
- `VideoTiming`, fields of the Video kind (`#[serde(flatten)]`, boxed, each defaulted when absent): `start_time`, `end_time`, `fade_in`, `fade_out`, `slices`, `last_slice_play_count` (the Audio cue's names and checks, `validate.rs` `media_timing`), and `hold_at_end` (default off, as QLab's).
  - QLab 5 manual p. 214: Time & Loops as an Audio cue's, plus hold at end. Slices are the Audio cue's too: the same plan gives them, so they cost nothing more. Decisions: skill `qlab-behaviour` Q470-Q475.
- A movie is planned as an Audio cue is: `control::plan::cue_slices` on `picture_info(file length, engine rate)`, the slice table in engine samples (loop floor and table limits included).
  - `checks.rs` builds it for the cue engine's lengths (`CueLengths`, `CuePassLengths`), the slice problems (`SliceProblems`: a plan that cannot play breaks the cue, `slices_unplayable`; every slice skipped, `nothing_plays`; a skipped slice has no pass in the plan sent to the stage host, which jumps from the pass before it to the one after as at any seam) and the clients' `media_duration` (`trimmed`, `duration`: the Duration column). A still ignores them.
- `play_picture` sends `play` with the plan from the top as `PlanPass`es (seconds), `into` it the picture's own time at the play, and `PictureFades` (the fades and the action's end, none while it loops for ever). A play with no plan holds at its offset on the stage host, so a movie never runs on past its range from any path (a hold at end after a resume or a load past the end).
  - A fresh start plans from the model; a resume plays on with the plan the run started with, cut by every devamp carried out since (`RunPlan.top`, `RunPlan::settled`), as a paused Audio voice keeps its plan whatever was edited since, its end time aside; a late start (`late`, held by its probe) is in the action's time, not the picture's.
  - A start whose loaded picture is of a file changed since is loaded afresh; one whose file is being probed again waits for the answer as a held start does (`probe_wait`, then plays or breaks); `play_picture` never returns silently.
  - `ActionLength` is the plan's length; none while it loops for ever or with hold at end (the cue stays active on its last frame until stopped). A load opens on the frame the plan is at there; a pause holds where the plan is.
- The stage host and the engine's progress read a plan with the same `plan_point` (position, time left in the pass, the next jump, ended, the pass's number) and `fade_factor` (opacity: rising from the action's start, falling to its end, multiplied; held at its value once the plan is over).
- An end time edited while it plays (`follow_picture_end`, as an Audio voice's, skill `engine-control`): `top` and `table` are cut at the new end (`new_end` on the time and loops the plan was made from, `RunPlan.planned`) and the plan sent again from the same `play` sample, so nothing before the new end changes.
  - The cue is told its length (no earlier than where it is: past the end it ends at once and its end takes the picture). Its sound gets the same cut. A paused picture keeps the cut plan for its resume, which tells the length; a stopping one is left to its stop.
- Devamp (`devamp_picture`, `devamped`): the pass under way at the devamp's sample is the loop's last (a loop split by a start part way in drops its later entry), the slices after it follow (none with `stop`, which also stops the picture there).
  - The plan is sent again from the same `play` sample, so nothing before the seam changes; `DevampScheduled` and the new `ActionLength` go to the cue engine.
  - While a devamp is pending (the picture has not reached its leave sample) the same devamp again is answered with the same sample and a different one is `DevampIgnored`; so is one on a still, a paused picture or a plan already over.
  - At its leave sample a devamp is carried out, as an Audio voice takes its own at the boundary: the cut table becomes the run's plan (`top`) and the next devamp is worked out afresh on the loop under way then (two vamps in one cue).
  - A resume keeps a devamp carried out before the pause (the picture plays on in the slice after the loop, to the length the cue engine was told) and drops one still pending, which the cue engine sends again for the fresh run.
- The seam: near a pass's end (`PRIME_AHEAD`, 1 s) the drawn picture passes the next jump with the position it asks for (`CuePicture::upcoming`).
  - The decode thread, when no frame is asked, opens a second reader there and reads its first frame (`Movie::prime`); at the jump `restart` takes it instead of opening one.
  - Until the next pass's first frame is ready the frame shown stays up: a seam is never a black frame, at worst a held frame. A frame shown a refresh ahead is in the next pass (`position_after`, `pass_after`); in the plan's last pass (`PlanPoint::last`) it is never past where the plan holds at its end, in the same pass, so the frame after the end trim is neither flashed at the end nor held with hold at end.
  - The decoder is told the pass with each position: a position behind the frame shown in a new pass is a seam and reads again from there however small the step (a loop of a frame or two), where a step back within a pass of a frame or less is held. A failed prime is not retried for the same place (`prime_failed`).
- Tests: core `video_timing` units, `commands_video.rs` (edits and refusals), `validation.rs` (load), cue engine `video.rs` (Devamp target, slice problems), link round trip and refusal, `host.rs` (plan, fades, hold, the refresh ahead at a seam and at the plan's end), `media.rs` (the primed reader at a seam; frames asked a refresh ahead through the plan's end, the path a real display draws by), engine `pictures.rs` (`devamped`).
  - `video_cues.rs`: one test per Time & Loops flow plus trims past the end, a devamp across a stage host relaunch, a second devamp in one run, and a pause and resume before and after a devamp's leave sample.
  - The app's `VideoCueTests` per flow.

## Sound (VID-06; `openlab-core` `video_sound.rs`; engine `control/picture_sound.rs`, `control/media/`; audio `decode.rs`, `mp4_priming.rs`)
- Model: `CueKind::Video`'s `sound: VideoSound { patch: Option<PatchId>, levels: CueLevels, audio_track }`, stored as fields of the kind (file format §5). `CueKind::levels()` / `levels_mut()` / `sound_patch()` are what level edits, Fade cues, volume limits, paste repair and patch removal read for both Audio and Video cues: nothing treats "has levels" as "is an Audio cue".
- Probe: the picture probe's worker also reads the movie's sound with the audio decoder (`openlab_audio::probe_movie`: every sound track, at most `MAX_MOVIE_SOUND_TRACKS`, each probed as an audio file is, so damage is known at cue load).
  - The engine never links a video decoder for it: symphonia reads the MP4/QuickTime container's audio tracks (PCM, AAC, ALAC), found by a bounded scan of the `hdlr`/`stsd` boxes (`mp4_priming.rs`), so a sound track in a codec it cannot decode is seen as a track that fails, never as "no sound".
- A movie with any track that cannot be played (unknown codec, damaged at its start, over 64 channels) fails its probe as a whole (`media_unsupported`, the reason naming the track): it never plays its picture silently. A file without a sound track has no sound: no voice, and its cue never has a patch problem.
- Each track is fitted to the movie's length (`Media::Track` with a `Fit`: silence after a shorter track's end, a longer one cut), and the picture's plan is built on the fitted probe of the track the cue plays (`sound_info`), so picture and sound follow one slice table to the sample through every loop.
- Problems (core `broken.rs`): the binary tells which movies have sound (`Input::MediaSound`, with each probe answer); only then the cue needs its patch: `no_patch` (none set), `patch_missing`, `device_unavailable`, as an Audio cue's. A lost device's mark clears as an Audio cue's does.
- The voice: the picture's code passes each voice action on (`sound_action`) from where it carries it out, dated as the picture is: load, start (on the picture's own start sample, a start held by its probe included), pause, resume, stop with its fade, unload, a devamp the picture carried out, ramps and ducks. The voice is made by the same `Voices` code as an Audio cue's (stream, levels, integrated fades from the cue's time and loops, patch following, moves between devices).
- Of what the voice reports back only failures reach the cue engine: its length, end and devamp answers are the picture's to give, once, so hold at end keeps the cue active after the sound has ended.
  - The picture's own answers go in `Effects::pictured`, apart from the voices' `feedback` and `deferred`; `DocCx::after`, which every `Effects` passes through, drops the voices' length, end and devamp reports of a Video cue or of a cue with a picture up (`pictures_report`). No call site filters, so a report made on any path (a mixer event, a lost event made up for by the meter reconciliation, a parked device) is dropped the same way.
  - A voice failure (stream error, mixer refusal, device lost) breaks or stops the cue and its picture leaves on that sample; a picture failure cuts the voice (`end_sounds`).
- A Video cue known to have nothing to hear (`known_silent`: probed, a still or a movie with no sound track) has no use for the patch it names: clearing the patch's device does not pause it (`pause_cues_on` asks `cue_patch`), the pre-show check does not list it on the patch, and it is not primed.
- A cue its sound's device left (shown paused, owning nothing) loses its picture too (`end_pictures`); nothing resumes when the device returns.
- The sound is the clock: the mixer reports the end of an underrun with what the voice missed (`Event::UnderrunEnded`), and the picture's plan is put back by as much from that sample and the run's end moved (`picture_late`).
  - A devamp's stop already sent to the stage host moves with it, so the pass under way plays whole; a paused picture (the pause came before the report was read) is held that much earlier and its plan counts the lateness, so the resume plays both on together and tells the later end.
  - A picture stopping for another reason (a stop or panic fade) is left alone: it ends with its sound on the stop's sample whatever the plan. A picture loaded and not started has no voice playing, so no such report.
  - What a voice on a device at another rate missed is told in master frames (`Outputs::poll_events`).
  - A voice on a second device plays at its device's rate, dated on the master clock, so it runs ahead (or behind) as far as that device's clock drifts from the master's. `Outputs::drift` tells how far, per voice, from that device's smoothed counter readings (skill `devices`, Clock); a pause holds it.
  - Each tick `follow_sound_clocks` moves a playing picture by the drift it has not followed once that reaches `DRIFT_STEP_US` (0.5 ms), through `picture_late` with a signed lateness (`RunPlan::late` negative: the picture leads its action; `followed` is the drift in it). 0.5 ms is the threshold, not a step size: clock drift moves it about that much at a time, while a picture whose sound moved to another device gives back all it followed of the first in one move.
- A patch moved to another device while the cue plays (`Action::RelocateVoice`): the voice moves as an Audio cue's does, at its new device's rate (`rate_for` reads `CueKind::sound_patch`), and the run's new id is given to its picture (`relocate_picture`), which plays on untouched and tells the cue its length again. Without that a pause, stop or devamp after the move would not find the picture.
- Clients: `media_durations` carries `audio_tracks`, `audio_track` (the one played) and `channels`; a stored track the file lacks plays the first and lists an `audio_track_missing` warning. Progress of a Video cue is its picture's (the voice's is left out).
- A Video cue's sound is primed like an Audio cue's (skill `engine-control`, Priming): a cue near the playhead or with a hotkey has its stream ready, so a GO does not start cold; a cold start (a `StartVoice` with no prime) is an underrun at the start that the picture then follows. The `waveform` request answers for a Video cue with the audio track it plays.
- Not built: preload and preview of a Video cue's sound.
- Tests (`tests/video_cues.rs`; test movies with sound tracks from `--make-test-media <codec>+pcm:2:48000`, whose channels say where in the file they are): probe formats, in step from GO to the end, pause/resume, load to time, each loop seam on and off a frame boundary, devamp, hold at end, a start held by its probe, stop and panic, level edits, integrated fades, a Fade cue, no sound and no patch.
  - Devices: device loss; a patch moved to a device at another rate (then paused, resumed and started again there).
  - The sync measure (frame on the stage against the sound rendered) runs ten minutes of movie at 24, 25, 30 and 60 fps and of a track at 160/147 of the device's rate in the normal suite, and thirty seconds of a 48 kHz track on a 44.1 kHz device (ten minutes of that take minutes in a debug build). The test media writer redraws only the barcode band per frame, so ten-minute movies are made in seconds.
  - A second device whose clock runs 100 ppm fast (`Fake::set_drift`; the stand-in waits for the extra frames it plays, so no underrun): ten minutes on the stand-in devices, the stage probed each minute against the sound that device rendered; a device back from a loss; a cue moved to the primary after following a fast device.
  - Ganged, default and pasted levels on a Video cue: core `tests/commands_video.rs`.

## Fade cues on pictures (VID-05; core `video_geometry.rs` `FadeGeometry`, `PictureParam`, `PictureRamp`; engine `control/pictures.rs`; stage host `host.rs`)
- QLab 5 manual pp. 241-247. A Fade cue's `geometry` ticks opacity, position, scale and rotation (no crop, as QLab's); the cue engine moves each ticked value of its Video target as a level of the run (skill `cue-engine`, its fade-levels reference, "Picture values"), so takeover, pause, panic, stop target when done and completion are the levels' code. Decisions: skill `qlab-behaviour` Q520-Q528.
- The cue engine's `Ramp` of a `LevelParam::Picture` goes to `ramp_picture`, never the mixer (`target` in `voices` has no gain for it): from where the run's last ramp of that value is on its sample (the cue's own value if none), as the mixer starts a gain's, it sends `ramp { picture, param, ramp }` with `from` and `to` put within the value's range.
  - The last ramp of each value is kept on the picture (`Live::ramps`) and sent again, after the `load`, to a stage host that starts, so a relaunch mid-fade draws the picture where the fade has it and carries on.
- A run whose picture is not up yet (held by its probe, or loaded again on a changed file) gets no ramp; when it loads it is given each value the cue engine tracks (`fade_ramps`), still moving to where it goes by its end (`seed_picture_ramps`).
- Stage host: per value a short list of ramps by start sample (at most `MAX_RAMPS`, 8), the one the clock has reached in force, so a takeover dated ahead inside the lookahead never jumps the picture early; `geometry_at(clock)` draws them over the picture's own geometry (`ToStage::Geometry` edits change the values no ramp holds). Opacity multiplies with the integrated fades and a stop's fade as before, so a panic fades the picture from where a held Fade left it.
- A Fade of a cue that is not running is `target_not_running`, logged at `info` (the app lists no warning for it).
- Tests: core `cue_engine/video.rs` (ticks, curve, relative, takeover, pause, panic, not running, edit takeover, limits, groups), `commands_video.rs` (parts, every path refuses), `validation.rs` (load clamps), link round trip and refusal, `host.rs` (curve over geometry, a ramp dated ahead), `video_cues.rs` one per flow of the app's Fade-on-video checklist plus a stage host relaunched mid-fade, an edit taking a value over and a start held by its probe.

## The engine side (`openlab-engine` `stage.rs`, `control/stages.rs`)
- `stage::StageHost` is the supervisor: thread `openlab-stage-link` spawns the stage host (through `platform::spawn::spawn`; own process group, stdin/stdout/stderr piped), with a writer thread (bounded queue of `WRITE_QUEUE` lines; full means the child stopped reading: killed), a reader thread (`read_line` + `decode_from_stage`; bad lines become warnings, at most `MAX_BAD_LINES_LOGGED` per child) and a stderr thread (first `MAX_STDERR_LINES` lines to the log).
- A `stage_status` for a stage the stage host was not given is dropped (supervisor), and the control thread keeps states only for stages it sent, so child input cannot grow engine memory.
- Report log lines (stage states, displays, the stage host's `log`) go through `Engine::report_line`: at most `MAX_REPORT_LINES_PER_SECOND` (20) a second by the control loop's clock, the rest counted and said as one warning on the first tick after that second (`flush_report_lines`), quiet or not; the supervisor also caps `log` messages at `MAX_LOGS_PER_SECOND`. A `displays` list equal to the last is not logged again. A message that fails to encode is logged as an error.
- Health: `hello` must be answered within `hello_within` (20 s: a cold start on a loaded machine or a slow disk is not a hang) and every `ping` (each `ping_every`, 1 s) within `answer_within` (5 s); a child that does not, sends more than `MAX_LINES_PER_SECOND`, or closes its output is killed (reaped on a thread of its own) and replaced at once with the last stage set.
- Starts older than `restart_window` are forgotten before a crash is counted (`forget_old_starts`), so a crash after a long healthy run is relaunched at once. More than `max_restarts` (5) starts in `restart_window` (60 s) pauses video output for `retry_after` (30 s), logged as an error. A stage host of another link version is never started again.
- `StageHost`'s drop sends `quit`; the stage host gets 1 s, then is killed. Its stdin closing also ends it, so it never outlives the engine however the engine ends.
- The control thread: `sync_stages` (every tick) builds every open doc's stages with this machine's display ids and hands the set to the supervisor when it changed. An idle tick compares only each doc's stages and a count of display-choice changes (`Stages::synced`, `mappings`) and does no more. The stage host starts with the control loop (`Control::empty`), so its displays are known when a new workspace is made. A changed stage's state is forgotten until the stage host reports it again.
- `StageEvent`s arrive through the inbox (`Inbox::Stage`): states and displays are kept for `list_stage_mappings`/`list_displays`; a state a stage cannot be seen in (`no_display`, `display_missing`, `failed`) is a `warn` log line, `shown`/`hidden` `info`; a stop is `warn` (restarting) or `error` (paused).
- An engine on the virtual device (`--virtual-device`) runs a stage host only with `--virtual-displays ID:WxH,...` (test-support builds), passed on to it: test engines never open windows on the machine's displays, and their scripts stay deterministic.
- Where the stage host is: `Contents/Helpers/openLab Stage.app/Contents/MacOS/openlab-stage` beside the engine's `Contents/MacOS`, else `openlab-stage` beside the engine (development). Missing: video output off, one `info` log line at start (a build or development engine without it is not a show fault). Tests set `ControlConfig::stage_host`.
- A new workspace gets one stage per listed display (QLab 5 manual p. 226): "Stage 1", "Stage 2"... in display order, sized as the display, keep-black on (its black down until its first picture), each shown on its display on this machine (`Engine::add_display_stages`, from `fresh_workspace`).
- Push: `push_video_outputs` (every tick) sends each workspace's connections `video_outputs { displays, video?, stages }` when a report, a stage set or a display choice changed, as a state message, at most once per `PUSH_EVERY_MS` (100 ms) by the control clock.
- A doc connection's `snapshot` request (the bind's too) has `video_outputs` pushed at once, right after the snapshot's reply and whatever the gap (`Control::push_doc_video_outputs`; at the next tick only if the outbound channel was full), so a connection that binds after the last push has it.
- That push goes out before anything handled after the snapshot, so a message taken in the same wake (a client's first GO) cannot put its broadcasts ahead of it; the order would otherwise depend on how fast the client spoke. A broadcast, never a reply: a connection writes broadcasts ahead of replies, and a reply could land after a newer push. The app keeps it in `WorkspaceStore.videoOutputs` and draws it on the workspace settings Video page (skill `mac-app`).
- Requests (`docs/protocol.md`): `list_displays` (app-scope), `list_stage_mappings`, `set_stage_mapping { stage, display? }` (the display must be listed now; stored in `settings.json`, refused `io` when settings cannot be saved).

## Monitor windows (VID-01 windowed mode; `openlab-video` `host.rs`, `platform/mac/monitor.rs`; engine `control/stages.rs`)
- QLab 5 manual p. 157: a stage's monitor window is a live copy of what goes to that stage, opened from the stage's row on the settings Video page or a Video cue's I/O tab (the app's buttons: skill `mac-app`). Decisions: skill `qlab-behaviour` Q586-Q588.
- Design (decided for #648): the stage host draws the monitor in a window of its own, from the same layer (stage, picture, cues) a display draws. The app only asks the engine (`set_stage_monitor`); no frames leave the stage host, so no new machinery, no copies and no dependency. Shipping frames to the app was rejected: a new transport for megabytes a second, and an app stall could back up into the stage host.
- The engine keeps the open monitors (`Stages::monitors`, never saved) and sends each as its stage's `monitor` title (the stage's name made link-safe, `stage_link::link_text`) in the stage set, so a relaunched stage host opens them again. Opening one already open sends `raise_monitor`.
- A monitor goes with its stage, its workspace, a `monitor_closed` from the stage host, or `Inbox::AppsGone` (the WebSocket server's last app connection ended: a quit or a crash; the stages play on). Show Mode does not touch them. `video_outputs` and `list_stage_mappings` report `monitor`.
- A monitor opened or closed is not a change of where its stage is: the stage's state is kept (the engine compares stage outputs without the monitor).
- Stage host (`Host::monitors`): a monitor draws its stage's layer whether the stage is shown, hidden between cues or has no display or a missing one (so a show can be built on a laptop alone), after every display in `apply` so it never delays an output.
  - The operator's close (`take_closed_monitors`, a window no longer visible and not minimized) is reported once as `monitor_closed` and kept closed against stage sets sent before the engine heard; `raise_monitor` opens it again. A monitor that cannot be drawn closes with a `warn` log and `monitor_closed`.
- macOS window (`monitor.rs`): an `NSPanel`, titled, closable, resizable, minimizable, non-activating and key only if a view needs typing (none does), so clicking, moving or resizing it never activates the stage host or takes the operator's keys; not hidden on deactivation; normal level. It opens at the stage's shape (longer side 640 points, neither under 90), cascaded from the main screen's centre.
- The stage is fitted to the window, black bars elsewhere (`gpu.draw`'s fit), drawn at the window's backing pixels (at most 4096 a side). Each picture's frame is the one the displays show at the next refresh (`FRAME_AHEAD`); drawing a picture's texture twice in a tick is safe as both command buffers are on one queue, so the monitor's completion implies the display's.
- Never stalls an output: a monitor skips a frame while its window is not visible (`occlusionState`) or its last command buffer is not done, so `nextDrawable` never waits on the window server for it; its layer has display sync off; a missing drawable skips the frame. Its draw is one more render pass of the same quads into a smaller target.
- Not built (QLab has them; v0.0.3): the float option and the clone button.
- Tests: `host.rs` (shown or not, title, set changes, operator's close, raise, a failing monitor), `output_window.rs` (the panel as built), `stages.rs` and `video_cues.rs` one test per #648 flow (the monitor read back with `monitor_probe` at a given window size beside the display's and the stage's own probe), `net/ws.rs` (the last app connection ending sends `AppsGone`).

## The app's black backstop (VID-12; `mac/openLab/BlackBackstop.swift`)
- The app (`AppController.backstop`) holds a borderless black window on each display that a keep-black stage of an open workspace is shown on (`BackstopPlan.covers`), so the gaps above show black, not the desktop. It reads the workspaces' models and the display choices of their last `video_outputs`, never the stages' states, so it is up whether or not a stage host runs.
- A stage whose black was up when its engine went away is carried (`BlackBackstop.carried`, from the stores waiting to be reattached): the relaunched engine reopens the workspace with every black down, and the app holds it black until Esc or a picture played on the stage there (Q670).
- Why the app: it outlives both the engine and the stage host. Workspaces waiting to be reattached after an engine restart keep their model and display choices, so the backstop stays through the whole relaunch.
- On every display a stage keeping black (black up) is shown on, the one with the menu bar too, as the stage covers it (Q531). Esc takes it down at once in the app (`BlackBackstop.dismiss`, from `panicAll`), whether or not an engine answers; a stage stays dismissed until its engine says its black is down (`panicked`), then follows the engine again. Displays are matched to the stage host's ids by ColorSync UUID (`systemDisplays`).
  - On the display with the menu bar it stands back (normal - 2, under the stage standing back) while the app has a question up (`BlackBackstop.asking`) or the engine has not answered the app's watch (`engineSilent`: an ask each second while it covers that display, `AppController+StandBack`).
- Level: screen-saver minus one, so under the stage host's output windows and over everything else on that display. Never key or main, mouse ignored, on every Space, out of cycling and the Window menu, not hidden with the app.
- It goes when its stage goes, keep-black is turned off, the stage moves to another display, the display goes, or the workspace closes. Displays are read on AppKit's display change and again `secondReadDelay` (0.5 s) later, which puts back a window the system moved off a display that went away, or takes it down.
- Tests: `BlackBackstopTests` (the plan, and on the real engine with virtual displays given places off every screen: a killed stage host, the goes-when cases, two workspaces, display changes) and `EngineCrashFlowTests` (the engine killed and relaunched by the app).

## Tests
- Test support only (never in a shipped stage host: `scripts/rust-checks.sh` checks): `--virtual-displays ID:WxH,...` runs offscreen with those displays and no windows.
- `test_card` draws the test card (`card.rs`: a white guard cell, the frame number's 16 bits, a white guard cell across the top tenth; red, green, blue, yellow quadrants); `probe` draws the stage offscreen (at most 1024 px a side, the stage's shape) and reads colours back; `probed` carries the barcode's frame (or none) and the asked points' RGBA.
- A probe that cannot be drawn (`warn`), or reads no frame while pictures are loaded on the stage (`info`: how many loaded, how many due at the clock, and the barcode cells' colours: all black when no frame was drawn, other colours when a frame drawn is not a whole test card), also sends a `log` line.
- A picture that failed as the probe drew it (its decoder failed while the probe waited) is reported before the `probed` answer, so the engine has the failure (the cue's problem, the log) when the test reads the answer, and `video_cues.rs`'s `on_stage` puts the pictures up and open, given-up waits and the show log's tail in its failure, so a picture missing on a CI run says why.
- Tests assert what a stage shows by reading the barcode and a few point colours: never a stored image, never a hash.
- `tests/output_window.rs` (its own `main`, on the main thread) builds the shipped output window for the main screen's frame without ordering it front and checks its level (screen-saver), collection behaviour, never key or main, mouse ignored, no shadow, borderless, frame equal to the screen's, not visible. Without a screen it reports a skip (a failure on CI).
- It also presents a stage on the menu bar's display through the shipped `present`: the window is at screen-saver level when it is ordered front. Test support records that level and never really orders it front.
- `gpu.rs` tests draw on the machine's GPU (they fail, not skip, without Metal); `displays.rs` tests read the real display list and open no window. No test opens a window.
- Real-engine tests: `engine/crates/video/tests/stages.rs` (macOS) runs the control loop on the offline driver (the engine's `tests/show` helpers) with the real test-support stage host (`CARGO_BIN_EXE_openlab-stage`, `--virtual-displays`) and reads stages back with `stage_probe`.
- Covered there: black, the test card, display choice, no display, keep-black off, a display unplugged and back mid-cue, a killed and a hung stage host replaced while a cue's sound plays on, the stage host gone after shutdown.
- A real engine process whose app connections drop mid-cue (a force-quit) keeps the picture up and ends the cue on time (`stages.rs`, a blocking WebSocket client).
- Also covered there: the windowed stage host exiting when its input closes, a SIGKILLed test engine leaving no stage host, a crash after a long healthy run relaunched at once (injected `StageClock`), a reporting burst bounded in log lines and memory, and `/bin/sh` stand-ins for a flooding, a log-bursting and a silent stage host. `OfflineShow::settle_stages`, `wait_for` and `send_until` wait on the stage host (hang guards, lengthened as above).
